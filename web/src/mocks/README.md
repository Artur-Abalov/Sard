# Моки API (MSW)

Обработчики из этого каталога отвечают на запросы `src/api/client.ts` без
запущенного sard-server:

- в dev-сервере: `VITE_API_MOCKS=1 npm run dev` запускает service worker
  (`browser.ts`) до первого рендера;
- в Vitest: `vitest.setup.ts` поднимает `msw/node` (`node.ts`) для каждого
  тестового файла с `onUnhandledRequest: 'error'`, поэтому запрос без обработчика
  роняет тест, а не уходит в сеть.

Обработчики общие — `handlers.ts`, по ресурсам — `api/*.ts`.

## Данные и сессия

- Фикстуры — `fixtures.ts`: агенты онлайн (`db1`), офлайн (`web2`), отозванный
  (`old3`), с зафиксированным дубликатом (`clone4`) и ни разу не подключавшийся
  (`new5`, без Register); у `db1` репозиторий без `repositoryId` (`offsite`) и плагины
  `files` (схема агента, равна `agent/plugins/files/schema.json`), `postgres` (секрет,
  число, выбор), `custom` (вложенный объект — редактор JSON) и `hooks` (без `backup`);
  запуски — в очереди у офлайн-агента, идущий (350 строк лога), упавший, упавший со
  снимком (`partial: true`, строка `[REDACTED]`), потерянный с поздним выводом
  (`partial: false`), отклонённый, с превышением времени (лог усечён, последняя строка
  без времени), успешный и успешный запуск удалённого источника; токены во всех четырёх
  состояниях, у использованного — агент `db1`.
- Моки помнят изменения между запросами (`state.ts`): вход, созданные токены и
  источники, отзыв, новые запуски. Ограничение D6 соблюдается: второй запуск
  источника с активным — 409 с `activeRunId`. Удаление источника мягкое (запуски и
  снимки остаются, карточка — 404), отзыв агента необратим и идемпотентен, источник
  отозванного агента не создаётся (422 `agent_revoked`) и не запускается (409); отзыв
  агента переводит его активные шаги в `lost` (`agent revoked`), а запуски — в `failed`, как на сервере;
  `GET /overview` считает по правилам `docs/specs/server/rest-api-w2.feature`; `sourceName` и
  `sourceDeleted` запусков берутся из источников на момент ответа;
  проверка конфига по схеме плагина остаётся на сервере и в моках не воспроизводится (К13).
- Установка агента (U1b): `GET /agent-install` и `GET /agents/{id}/upgrade` отвечают
  заготовленными командами релиза `v1.4.0` (restic `0.19.1`, подписанный); настоящие
  команды, адреса и правила — на сервере (`docs/specs/server/agent-install.feature`).
  Агент `web2` отмечен `outdated`, остальные — нет.
- Сессия: пароль `admin` (`MOCK_PASSWORD`); без сессии все эндпоинты, кроме
  `/status` и входа, отвечают 401. После 5 неверных паролей за 15 минут вход
  блокируется на 15 минут от пятой неудачи (`lockedAt` в `state.ts`); попытки
  во время блокировки её не продлевают. `Retry-After` отсчитывает оставшееся
  время в секундах, округляя вверх (900 сразу после пятой неудачи, меньше —
  позже), как на сервере (`LoginAttemptTracker`); неудачи старше 15 минут не
  считаются (К4, приведено к серверу). И воркер в dev, и Vitest стартуют без
  сессии — страница входа открывается первой. Изменяющий запрос (`POST`,
  `PUT`, `PATCH`, `DELETE` под `/api/v1`) с заголовком `Origin`, отличным от
  адреса страницы, отвечает 403 `origin_rejected` (`origin.ts`).
- Постраничная выдача (`paging.ts`) и проверки источника и срока токена
  (`validation.ts`) — чистые функции со своими тестами. Курсор мока — смещение,
  клиент считает его непрозрачным. В production-сборку не попадает ни то, ни
  другое: ветка в `main.tsx` там статически ложна, а скрипт воркера отдаёт из
  `node_modules/msw` плагин Vite, который работает только в dev-сервере (в
  `public/` воркера нет).

## Как добавить обработчик, когда схема OpenAPI расширится

1. Перегенерировать типы клиента: `make openapi` (или `npm run gen:api` после
   изменения `src/api/openapi.json`). Новый путь появится в `src/api/schema.d.ts`.
2. Положить пример данных в `fixtures.ts` с типом из схемы
   (`components['schemas'][...]`), чтобы тесты сравнивали с тем же объектом.
3. Добавить обработчик в `handlers.ts` через типизированный `http` из `http.ts`
   и помощник `response(status).json(body)`:

   ```ts
   http.get('/api/v1/agents/{id}', ({ params, response }) =>
     response(200).json({ ...agent, id: params.id }),
   )
   ```

   Путь, параметр, статус или тело, которых нет в схеме, — ошибка `tsc`.
   `contract.typecheck.ts` проверяет, что это по-прежнему так.

4. Если тесту нужен другой ответ, он переопределяет обработчик только для себя:
   `server.use(http.get(...))`. `vitest.setup.ts` сбрасывает обработчики после
   каждого теста.

Обработчики пишутся только для эндпоинтов, которые уже есть в схеме.

## Расписания (F3b)

- `GET /schedule-preview` отвечает значениями, записанными из ответа сервера при часах
  `T0 = 2026-10-09T12:00:00Z` в поясе Europe/Berlin (`schedulePreviews` в `fixtures.ts`), для
  `0 2 * * *`, `0 * * * *`, `30 2 * * 1-5`, `0 3 * * 0`, `*/5 * * * *` и `0 21 * * *`.
  Отличия от сервера, названные в `docs/qa/schedules.md`: cron вне фикстур описан как «Особое
  расписание: …» с тремя срабатываниями через сутки от текущего времени, а не вычислен; пояс
  на даты не влияет (одни и те же моменты в любом поясе); пояс по умолчанию — UTC
  (`SERVER_TIMEZONE`).
- Проверки cron и пояса общие у предпросмотра и сохранения (`validation.ts`): пять полей,
  нормализованный cron не длиннее 200 символов («cron is longer than 200 characters»,
  значение не повторяется), пояс IANA; предпросмотр дополнительно проверяет `lang` (ru или en).
- Сохранение расписания хранит `notifyOnSuccess` (по умолчанию `false`) и не трогает
  `lastRun`; изменение источника расписание не меняет.
- Фикстуры: у источника `db1 /etc` включённое расписание с последним запуском `failed`,
  двумя пропусками подряд и назначенным догоняющим запуском; журнал — все пять исходов,
  строка с `alert` и две строки простоя, одна с обрезанным счётом; у `web2 /srv` расписание
  выключено, `notifyOnSuccess` включён; у `web2 /home` расписания нет. Запуски с триггером
  `manual`, `schedule` и `catch_up` (у последнего — `catchUp`).
