# Плагин `postgresql`

Плагин `postgresql` сохраняет одну базу PostgreSQL логическим дампом (`pg_dump`, формат
custom) потоком в репозиторий restic: на диске хоста дамп не появляется. Роли и другие
глобальные объекты кластера (`pg_dumpall --globals-only`) он сохраняет вторым снимком,
связанным с первым. Спецификация — `docs/specs/agent/postgresql-plugin.feature`, ручная
проверка — `docs/qa/postgresql-plugin.md`, решения — `docs/adr/0051-postgresql-plugin.md`.

Не входит в плагин: проверка восстановления в песочнице (этап 2), кластеры и реплики,
WAL, `pg_basebackup`, PITR, автоматическое восстановление (пока его делают руками, см.
ниже).

## Что нужно на хосте

Плагин не содержит драйвера PostgreSQL: подключение, версию сервера и права он проверяет
программой `psql`, а дамп делает `pg_dump` — оба с хоста агента.

| Что | Где взять |
|---|---|
| `pg_dump`, `psql`, `pg_dumpall` | пакет `postgresql-client` (Debian, Ubuntu, Alpine) или `postgresql` (RHEL, Fedora); официальный образ `postgres` их содержит |

Пакеты deb и rpm агента только *предлагают* клиент (`Suggests`): агент без баз данных его
не требует.

- **`pg_dump` ищется** в `pg_dump_path`, а если поле не задано — в `PATH` агента. `psql` и
  `pg_dumpall` берутся из того же каталога. Не найден — шаг FAILED до начала дампа с
  подсказкой, какой пакет поставить.
- **Версия `pg_dump` не должна быть старше сервера.** Сравнивается старший номер
  (`pg_dump` 16.2 подходит серверу 16.4, `pg_dump` 16 не подходит серверу 18). Если старше —
  шаг FAILED, сообщение называет обе версии. Для нескольких серверов разных версий ставят
  `pg_dump` новейшей из них (пакеты PGDG) и указывают его в `pg_dump_path`.
- **Минимальная версия сервера — PostgreSQL 14.** Сервер 13 и старше — FAILED.

## Роль для бэкапа

Агент входит под обычной ролью, не под суперпользователем. Ей нужны `LOGIN` и право
читать все таблицы — встроенная роль `pg_read_all_data` (PostgreSQL 14 и новее):

```sql
CREATE ROLE backup LOGIN PASSWORD '...';
GRANT pg_read_all_data TO backup;
```

Если в базе включена защита строк (row level security) и политики не пускают роль к
части строк, добавьте атрибут `BYPASSRLS`: без него `pg_dump` либо откажет, либо сохранит
не все строки.

```sql
ALTER ROLE backup BYPASSRLS;
```

`pg_read_all_data` не покрывает большие объекты (large objects): чтение объекта проверяет
его собственные права, и `pg_dump` базы с большим объектом чужого владельца падает с
`could not open large object …: permission denied for large object …`. Если в базе есть
большие объекты, выдайте роли чтение каждого из них:

```sql
GRANT SELECT ON LARGE OBJECT 4242 TO backup;
```

Для всех существующих объектов сразу (от суперпользователя или владельца объектов, в
нужной базе):

```sql
SELECT format('GRANT SELECT ON LARGE OBJECT %s TO backup', oid) FROM pg_largeobject_metadata \gexec
```

Помните: новые большие объекты требуют новых `GRANT`, поэтому повторяйте запрос, например по расписанию.

Запасной путь, если выдавать права по одному неудобно:

```sql
ALTER ROLE backup SET lo_compat_privileges = on;
```

Это отключает для роли **все** проверки прав на большие объекты,
включая запись и удаление: роль сможет изменять и удалять любые большие объекты. Выбирайте его
осознанно и только для роли, под которой не работает ничто, кроме бэкапа.

Права на отдельные таблицы проверяет сам `pg_dump`: он берёт `ACCESS SHARE` на каждую
выгружаемую таблицу до выгрузки данных. Таблица без права `SELECT` — шаг FAILED, снимка
нет, сообщение называет причину `pg_dump` и таблицу. Такую таблицу можно исключить
(`exclude_tables`). Если роль не суперпользователь и не член `pg_read_all_data`, в лог шага
попадает одна строка WARN с именем роли.

Роль должна быть допущена в `pg_hba.conf` к этой базе с паролем (`scram-sha-256` или
`md5`).

## Секрет с паролем

Пароль в конфиге источника не пишется: конфиг называет только имя секрета, а значение
лежит в файле на хосте агента (ADR 0008). Пока нет `sard-agent secret set` (A8), секрет
создаётся вручную: файл `0600` владельца агента (пользователя `sard-agent`), имя — в `secrets:` файла `agent.yaml`.

```bash
sudo install -d -m 0750 -o sard-agent -g sard-agent /etc/sard/secrets
printf '%s\n' 'пароль роли backup' | sudo -u sard-agent tee /etc/sard/secrets/pg-app >/dev/null
sudo chmod 0600 /etc/sard/secrets/pg-app      # файл 0600 владельца агента
```

```yaml
# /etc/sard/agent.yaml
secrets:
  pg-app: /etc/sard/secrets/pg-app
```

После правки `agent.yaml` нужен перезапуск агента: `sudo systemctl restart sard-agent`.
Агент сообщает серверу имена секретов, консоль предлагает их в поле «пароль» источника, а
сервер при сохранении источника проверяет, что секрет есть у агента.

Значением пароля считается содержимое файла без завершающих `\r` и `\n`. Пустое значение
и значение с байтом NUL — ошибка шага.

Пароль передаётся `psql`, `pg_dump` и `pg_dumpall` только переменной окружения
`PGPASSWORD` их процесса: не аргументом командной строки (его видно всем в списке
процессов) и не файлом `.pgpass`. Окружение процесса видит только его владелец и root —
те же, кто читает файл секрета. Переменные `PG*` и `LC_ALL` из окружения самого агента
дочерним процессам не передаются. Пароль не попадает в лог шага, сообщение шага и журнал
агента (ADR 0033).

## Конфиг

| Поле | Тип | Описание |
|---|---|---|
| `host` | строка, обязательно | Имя хоста, IPv4, IPv6 (без скобок) или абсолютный путь **каталога** сокета, например `/var/run/postgresql`. До 255 байт; без запятой, `@` и пробела. |
| `port` | целое 1…65535, по умолчанию 5432 | Для сокета — номер в имени файла `.s.PGSQL.<port>`. |
| `database` | строка, обязательно | Имя базы, до 63 байт. Одна база на источник: несколько баз — несколько источников. |
| `user` | строка, обязательно | Роль, до 63 байт. |
| `password_ref` | строка, обязательно | **Имя** секрета агента с паролем. |
| `tls_mode` | `disable`, `require`, `verify-full` | По умолчанию `require` для TCP; для сокета допустим только `disable`, он же умолчание. |
| `tls_root_cert` | абсолютный путь | Файл CA на хосте агента. Только с `verify-full`; без него libpq ищет `~/.postgresql/root.crt` пользователя агента. |
| `exclude_schemas`, `exclude_tables` | массивы строк | Шаблоны `pg_dump` (`--exclude-schema`, `--exclude-table`), до 256, каждый до 1024 байт, без повторов. Шаблон, которому ничего не соответствует, не ошибка. |
| `pg_dump_path` | абсолютный путь | Исполняемый файл `pg_dump`; `psql` и `pg_dumpall` — из того же каталога. |
| `include_globals` | boolean, по умолчанию `true` | Сохранять глобальные объекты кластера вторым снимком. `false` — один снимок, `pg_dumpall` не нужен. |
| `globals_role_passwords` | boolean, по умолчанию `false` | Положить в снимок хэши паролей ролей. Нужен суперпользователь. |

```json
{"host": "db1.example.com", "database": "billing", "user": "backup",
 "password_ref": "pg-billing", "tls_mode": "verify-full", "tls_root_cert": "/etc/sard/pg-ca.pem",
 "exclude_tables": ["public.log_*"]}
```

Синтаксис шаблонов исключения описывает документация PostgreSQL:
<https://www.postgresql.org/docs/current/app-pgdump.html> (параметры `--exclude-schema` и
`--exclude-table`, шаблоны как в `psql`). Поле `password` и строка подключения в схеме
запрещены (`additionalProperties: false`).

Параметры подключения агент передаёт строкой `--dbname=` с каждым значением в кавычках:
имя базы вида `app' host=evil` остаётся именем базы. В строку входят таймауты, чтобы
недоступный хост не держал шаг до таймаута TCP: `connect_timeout=30`,
`keepalives_idle=60`, `keepalives_interval=10`, `keepalives_count=6`, а также
`application_name=sard-agent` — по нему сессии агента видны в `pg_stat_activity`.

## Что делает шаг

1. **PREPARING.** Проверяется секрет, ищутся `pg_dump`, `psql` и (при `include_globals`)
   `pg_dumpall`, читаются их версии. `psql` входит в базу и спрашивает версию сервера и
   роль. Ошибка входа — FAILED с причиной от PostgreSQL (пароль в ней маскируется).
   Проверяются версии и роль (см. выше). Если `globals_role_passwords` включён, а роль
   не суперпользователь, шаг FAILED сразу: содержимое снимка не зависит от прав роли, тихого
   отката нет.
2. **DUMPING.** При `include_globals`: `pg_dumpall --globals-only` в память (до 64 МиБ);
   вывод не попадает ни в лог, ни на диск. Сбой — FAILED, ни одного снимка нет.
3. **UPLOADING.** `pg_dump --format=custom --compress=0 --no-password
   --lock-wait-timeout=300000` и `restic backup --stdin` одновременно. Сжатие выключено:
   сжатый дамп restic почти не дедуплицирует, а сжимает сам. Ожидание блокировок таблиц —
   не больше 5 минут. Затем второй снимок — глобальные объекты.

Шаг успешен только если `pg_dump` завершился с кодом 0, весь его вывод передан restic, он
не пуст и начинается с сигнатуры `PGDMP`. Иначе restic останавливается до конца потока, и
снимка нет: неполный дамп не становится снимком, который выглядит успешным.

Отмена и таймаут шага останавливают `psql`, `pg_dump`, `pg_dumpall` (SIGTERM, через 10 секунд
SIGKILL) и restic; после шага не остаётся процессов и сессий `sard-agent` на сервере.

### Результат

`snapshot_id` и `repository_id` — снимка базы; `total_bytes` и `added_bytes` — суммы по
обоим снимкам. Если снимок базы сохранён, а сохранить глобальные объекты не удалось, шаг
FAILED, а результат содержит снимок базы: он полон, а неполнота набора видна — у него нет
связанного снимка глобальных объектов. Отмена или таймаут во время сохранения глобальных
объектов оставляют основной снимок.

### Имена файлов и метки

Имя файла в снимке — `<база>.dump`, глобальные объекты — `<база>.globals.sql`. Байты имени
базы вне `[A-Za-z0-9_-]` записываются как `%XX` (UTF-8, заглавные hex), так что имя
никогда не равно `.` или `..` и не содержит `/` и запятой: `app` → `app.dump`, `my db` →
`my%20db.dump` и `my%20db.globals.sql`, `a.b` → `a%2Eb.dump`.

Метки снимка базы: метки шага (`sard.source`, `sard.run`, …) и
`postgresql.server_version`, `postgresql.pg_dump_version`, `postgresql.database` (имя в
том же кодировании), `postgresql.format=custom`, `postgresql.part=database`.
Метки снимка глобальных объектов — те же, но `postgresql.format=plain`,
`postgresql.part=globals`, `postgresql.pg_dump_version` — версия `pg_dumpall`, а также
`postgresql.role_passwords=true|false` и `postgresql.main_snapshot=<id снимка базы>`.

Сервер знает только снимок базы. Будущее удержание (forget/prune) обязано удалять пару
снимков вместе; пока `restic forget` с группировкой по путям удерживает снимки
`/<база>.dump` и `/<база>.globals.sql` по одной политике раздельно.

## Глобальные объекты и пароли ролей

Дамп одной базы (`<база>.dump`) не содержит ролей и глобальных объектов: ни ролей, ни их
атрибутов и членства, ни табличных пространств. Они лежат во втором снимке
(`<база>.globals.sql`), если `include_globals` не выключен.

По умолчанию `pg_dumpall` получает `--no-role-passwords`: он работает под любой ролью, а
хэшей паролей в снимке нет, поэтому роли восстанавливаются **без паролей** (см. ниже).

**`globals_role_passwords: true` кладёт в репозиторий хэши паролей ролей (SCRAM).** Они
лежат внутри зашифрованного репозитория, сервер Sard их не видит, но хэш позволяет
перебирать пароль офлайн тому, кто прочитает репозиторий вместе с ключом. Включайте это
осознанно. Роль должна быть суперпользователем, иначе шаг FAILED до всех снимков. При
`include_globals: false` поле ничего не меняет и роль не проверяется.

## Восстановление руками

Автоматического восстановления пока нет: действие `restore` плагина объявлено, но шаг
завершается FAILED с сообщением, что восстановление для плагина postgresql ещё не
реализовано, и ничего не запускает. Из снимков базу восстанавливают стандартными
средствами PostgreSQL. После A8 команда `sard-agent repo restore` заменит `restic`
ниже. `pg_restore` и `psql` должны быть **не старше** версии из метки
`postgresql.pg_dump_version`; новый кластер — не старше исходного.

В примерах `restic` настроен переменными `RESTIC_REPOSITORY` и `RESTIC_PASSWORD_FILE`
репозитория источника, `$SN` — `snapshot_id` шага (снимок базы).

1. **Найти снимок глобальных объектов** по метке `postgresql.main_snapshot`:

   ```bash
   GS=$(restic snapshots --json --tag postgresql.main_snapshot=$SN | jq -r '.[0].id')
   ```

2. **Восстановить глобальные объекты** суперпользователем нового кластера, **до** базы:

   ```bash
   restic dump $GS /app.globals.sql | psql -X -d postgres
   ```

   Ошибки «role … already exists» ожидаемы для ролей, которые в новом кластере уже есть
   (начальный суперпользователь).

3. **Восстановить базу**: `restic dump` (или `restic restore`), `createdb`, `pg_restore`
   в новую базу:

   ```bash
   restic dump $SN /app.dump > app.dump
   createdb restored
   pg_restore -d restored app.dump
   ```

   Роли из шага 2 нужны уже здесь: владельцы объектов в дампе — эти роли.

4. **Пароли ролей.** Без `globals_role_passwords` роли восстановлены без паролей — войти
   по паролю они не могут. Задайте пароли:

   ```sql
   ALTER ROLE app_rw PASSWORD '...';
   ```

   С `globals_role_passwords: true` восстановленная роль входит прежним паролем.

**Без снимка глобальных объектов** (`include_globals: false`) создайте роли заранее
(`CREATE ROLE ...` с теми же именами) либо восстановите без владельцев и прав:

```bash
pg_restore --no-owner --no-acl -d restored app.dump
```

Имя файла с символами вне `[A-Za-z0-9_-]` записано как `%XX`: база `my db` лежит в
`/my%20db.dump`, её глобальные объекты — в `/my%20db.globals.sql`.

## Сообщения об ошибках

Сообщение шага — одна строка на английском; ошибку libpq или `pg_dump` оно цитирует
(последняя строка с `error:` или `FATAL:`). Полный stderr `psql` и `pg_dump` идёт в лог шага
строками: WARN для строк с `error:`, `FATAL:`, `warning:`, остальные — INFO.

| Причина | Что делать |
|---|---|
| `pg_dump not found …` | Поставьте клиент PostgreSQL или задайте `pg_dump_path`. |
| `pg_dump 16.4 is older than the PostgreSQL server 18.0` | Поставьте `pg_dump` 18 или новее, задайте `pg_dump_path`. |
| `password authentication failed for user …` | Неверный пароль в секрете или нет такой роли. |
| `no pg_hba.conf entry …` | Разрешите роли вход с хоста агента в `pg_hba.conf`. |
| `server does not support SSL` | Сервер без TLS: `tls_mode: disable` или включите TLS на сервере. |
| `permission denied for table …` | Роли нужно `pg_read_all_data` или `SELECT` на таблицу; либо `exclude_tables`. |
| `pg_dump failed: empty output`, `not a custom-format archive` | `pg_dump` завершился, не создав архив: смотрите лог шага. |
