# Плагин `postgresql`

Плагин `postgresql` сохраняет одну базу PostgreSQL логическим дампом (`pg_dump`, формат
custom) потоком в репозиторий restic: на диске хоста дамп не появляется. Роли и другие
глобальные объекты кластера (`pg_dumpall --globals-only`) он сохраняет вторым снимком,
связанным с первым. Спецификация — `docs/specs/agent/postgresql-plugin.feature`, ручная
проверка — `docs/qa/postgresql-plugin.md`, решения — `docs/adr/0051-postgresql-plugin.md`.

Не входит в плагин: проверка восстановления в песочнице (этап 2), кластеры и реплики,
WAL, `pg_basebackup`, PITR. Восстановление в новую базу делает консоль (см. «Восстановление
из консоли»); поверх существующей базы — руками (см. «Восстановление руками»).

## Что нужно на хосте

Плагин не содержит драйвера PostgreSQL: подключение, версию сервера и права он проверяет
программой `psql`, а дамп делает `pg_dump` — оба с хоста агента.

| Что | Где взять |
|---|---|
| `pg_dump`, `psql`, `pg_dumpall` | пакет `postgresql-client` (Debian, Ubuntu, Alpine) или `postgresql` (RHEL, Fedora); официальный образ `postgres` их содержит |

Пакеты deb и rpm агента только *предлагают* клиент (`Suggests`): агент без баз данных его
не требует.

- **`pg_dump` ищется** в `pg_dump_path`, а если поле не задано — в `PATH` агента. `psql` и
  `pg_dumpall` берутся из того же каталога. Не найден — шаг FAILED до начала дампа с
  подсказкой, какой пакет поставить.
- **Версия `pg_dump` не должна быть старше сервера.** Сравнивается старший номер
  (`pg_dump` 16.2 подходит серверу 16.4, `pg_dump` 16 не подходит серверу 18). Если старше —
  шаг FAILED, сообщение называет обе версии. Для нескольких серверов разных версий ставят
  `pg_dump` новейшей из них (пакеты PGDG) и указывают его в `pg_dump_path`.
- **Минимальная версия сервера — PostgreSQL 14.** Сервер 13 и старше — FAILED.

## Роль для бэкапа

Агент входит под обычной ролью, не под суперпользователем. Ей нужны `LOGIN` и право
читать все таблицы — встроенная роль `pg_read_all_data` (PostgreSQL 14 и новее):

```sql
CREATE ROLE backup LOGIN PASSWORD '...';
GRANT pg_read_all_data TO backup;
```

Если в базе включена защита строк (row level security) и политики не пускают роль к
части строк, добавьте атрибут `BYPASSRLS`: без него `pg_dump` либо откажет, либо сохранит
не все строки.

```sql
ALTER ROLE backup BYPASSRLS;
```

`pg_read_all_data` не покрывает большие объекты (large objects): чтение объекта проверяет
его собственные права, и `pg_dump` базы с большим объектом чужого владельца падает с
`could not open large object …: permission denied for large object …`. Если в базе есть
большие объекты, выдайте роли чтение каждого из них:

```sql
GRANT SELECT ON LARGE OBJECT 4242 TO backup;
```

Для всех существующих объектов сразу (от суперпользователя или владельца объектов, в
нужной базе):

```sql
SELECT format('GRANT SELECT ON LARGE OBJECT %s TO backup', oid) FROM pg_largeobject_metadata \gexec
```

Помните: новые большие объекты требуют новых `GRANT`, поэтому повторяйте запрос, например по расписанию.

Запасной путь, если выдавать права по одному неудобно:

```sql
ALTER ROLE backup SET lo_compat_privileges = on;
```

Это отключает для роли **все** проверки прав на большие объекты,
включая запись и удаление: роль сможет изменять и удалять любые большие объекты. Выбирайте его
осознанно и только для роли, под которой не работает ничто, кроме бэкапа.

Права на отдельные таблицы проверяет сам `pg_dump`: он берёт `ACCESS SHARE` на каждую
выгружаемую таблицу до выгрузки данных. Таблица без права `SELECT` — шаг FAILED, снимка
нет, сообщение называет причину `pg_dump` и таблицу. Такую таблицу можно исключить
(`exclude_tables`). Если роль не суперпользователь и не член `pg_read_all_data`, в лог шага
попадает одна строка WARN с именем роли.

Роль должна быть допущена в `pg_hba.conf` к этой базе с паролем `scram-sha-256`
(`password_encryption = 'scram-sha-256'`, умолчание с PostgreSQL 14). Метод `md5` и
`password` агент по TCP отвергает, пока привязка секрета не разрешит их явно
(«Привязка секрета»).

## Секрет с паролем

Пароль в конфиге источника не пишется: конфиг называет только имя секрета, а значение
лежит в файле на хосте агента (ADR 0008). Секрет создаёт `sard-agent secret set`: файл
`/etc/sard/secrets/pg-app` с правами `0600` владельца агента, имя — в `secrets:` фрагмента
`/etc/sard/agent.d/secret-pg-app.yaml` (основной `agent.yaml` не меняется) и перезапуск
службы ([настройка хоста агента](../operations/agent-host-setup.md)).

```bash
printf '%s' 'пароль роли backup' | sudo sard-agent secret set pg-app \
  --plugin postgresql --target db1.example.com:5432/app --stdin
```

Агент сообщает серверу имена секретов и их привязки. Консоль предлагает секреты в поле
«пароль» источника, сервер при сохранении проверяет, что секрет есть у агента. Если
привязка не разрешает цель источника, страница источника предупреждает об этом и
показывает команду для хоста.

## Привязка секрета

Куда уйдёт пароль, решает оператор хоста агента, а не сервер (S11, дополнение ADR 0008).
`secret set` требует `--plugin` и хотя бы один `--target`. Агент отдаёт пароль только этому
плагину и только этим целям, что бы ни прислал сервер. При чужой цели шаг падает до
подключения: ни одна программа не запускается, файл секрета не читается. Сообщение шага
называет секрет и цель и даёт команду, которая её разрешает:

```
secret "pg-app" is not allowed for postgresql at evil.example:5432/app; if that is intended,
run on the agent host: sudo sard-agent secret set pg-app --plugin postgresql --target evil.example:5432/app
```

Цель — `хост[:порт][/база]`:

| Цель | Что разрешает |
|---|---|
| `db1.example.com:5432/app` | Ровно этот хост, порт и базу. |
| `db1.example.com:5432/*`, `db1.example.com:5432` | Любую базу этого сервера (нужно для восстановления из консоли: оно создаёт новую базу). |
| `db1.example.com` | Любой порт и любую базу. |
| `[2001:db8::5]:5432/app` | Адрес IPv6 — в скобках. |
| `/var/run/postgresql:5432/app` | Каталог сокета; база — только после порта. |

Групповых символов в хосте нет. Имя хоста сравнивается без учёта регистра, адрес — по
значению. Имя и адрес — разные цели: источник с `host: 10.0.0.5` не попадает в привязку
`db1.example.com`. `--target` можно повторять.

Что привязка разрешает сверх правил плагина:

| Флаг | По умолчанию | Что разрешает |
|---|---|---|
| `--auth scram-sha-256,md5` | TCP: только `scram-sha-256`; сокет: любой метод | Точный список методов, которые может запросить сервер: `scram-sha-256`, `md5`, `password`, `none`. На сокете задаёт ограничение, которого иначе нет. |
| `--allow-tls require` или `--allow-tls disable` | к серверу в сети — только `verify-full` | Более слабый `tls_mode` источника. |
| `--ca-file /etc/sard/pg-ca.pem` | `tls_root_cert` источника, иначе системные CA | CA, которым проверяется сертификат сервера; важнее `tls_root_cert` из конфига. |
| `--allow-no-channel-binding` | channel binding обязателен при TLS и SCRAM | SCRAM по TLS без channel binding (например, через пулер). |

Привязка лежит в `/etc/sard/secret-bindings/<имя>.yaml` рядом с главным конфигом. Файл
принадлежит root (группа службы, `0640`), это не часть конфига: агент предыдущей версии
запускается с ним. Повторный `secret set` заменяет привязку целиком: перечислите все цели.
Файл, который могут менять группа или прочие, или с другим владельцем, агент не
использует. `sard-agent secret list` показывает привязки (колонка `BOUND_TO`),
`sard-agent check` — строку `secret.bound`. Секрет, объявленный в `agent.yaml` вручную,
получает привязку тоже вручную, тем же файлом:

```yaml
plugin: postgresql
targets:
  - db1.example.com:5432/app
allow_tls: require    # необязательно
```

## Аутентификация и TLS

Строку подключения для `psql`, `pg_dump`, `pg_dumpall` и `pg_restore` собирает одна
функция плагина, одинаково для бэкапа, отпечатка, восстановления и отката:

- **TCP** (сеть и `localhost`): `require_auth=scram-sha-256`, если привязка не задаёт
  `--auth`. Сервер, который просит `md5` или пароль открытым текстом, пароль не получает:
  libpq обрывает вход до отправки. `require_auth` идёт в строке подключения, а не в
  `PGREQUIREAUTH`: клиент старше PostgreSQL 16 отвергает неизвестный параметр строки до
  подключения, а неизвестную переменную пропустил бы молча.
- **TLS со SCRAM**: `channel_binding=require` — обмен SCRAM привязан к сертификату
  сервера, и посредник, пересылающий его к настоящему серверу, будет замечен.
- **Сервер в сети** (не сокет, не `localhost`, не 127.0.0.0/8, не `::1`): `tls_mode`
  `disable` и `require` отклоняются до запуска программ, если привязка не разрешает их
  `--allow-tls`. Без `tls_mode` используется `verify-full`: проверяются сертификат и имя
  хоста, CA — из `--ca-file` привязки, `tls_root_cert` источника или системный
  (`sslrootcert=system`).
- **Сервер на этом хосте по TCP**: `tls_mode` любой, по умолчанию `require`; SCRAM
  обязателен — порт `localhost` может занять любой пользователь хоста, пока PostgreSQL
  не запущен.
- **Сокет**: TLS нет (`disable`); метод входа — какой выберет сервер (`peer`, `trust`,
  `scram-sha-256`), если привязка не задаёт `--auth`.

Клиенту PostgreSQL на хосте нужна libpq 16 или новее (параметр `require_auth`). Версия
`psql` и версия libpq могут различаться: пакеты PGDG ставят libpq новее клиента. На сокете
старый клиент работает.

Значением пароля считается содержимое файла без завершающих `\r` и `\n`. Пустое значение
и значение с байтом NUL — ошибка шага.

Пароль передаётся `psql`, `pg_dump` и `pg_dumpall` только переменной окружения
`PGPASSWORD` их процесса: не аргументом командной строки (его видно всем в списке
процессов) и не файлом `.pgpass`. Окружение процесса видит только его владелец и root —
те же, кто читает файл секрета. Переменные `PG*` и `LC_ALL` из окружения самого агента
дочерним процессам не передаются. Пароль не попадает в лог шага, сообщение шага и журнал
агента (ADR 0033).

## Конфиг

| Поле | Тип | Описание |
|---|---|---|
| `host` | строка, обязательно | Имя хоста, IPv4, IPv6 (без скобок) или абсолютный путь **каталога** сокета, например `/var/run/postgresql`. До 255 байт; без запятой, `@` и пробела. |
| `port` | целое 1…65535, по умолчанию 5432 | Для сокета — номер в имени файла `.s.PGSQL.<port>`. |
| `database` | строка, обязательно | Имя базы, до 63 байт. Одна база на источник: несколько баз — несколько источников. |
| `user` | строка, обязательно | Роль, до 63 байт. |
| `password_ref` | строка, обязательно | **Имя** секрета агента с паролем; секрет должен быть привязан к `postgresql` и этой цели. |
| `tls_mode` | `disable`, `require`, `verify-full` | По умолчанию `verify-full` для сервера в сети, `require` для сервера на этом хосте; для сокета допустим только `disable`, он же умолчание. К серверу в сети `disable` и `require` — только по `--allow-tls` привязки. |
| `tls_root_cert` | абсолютный путь | Файл CA на хосте агента. Только с `verify-full`; `--ca-file` привязки важнее; без обоих — системные CA. |
| `exclude_schemas`, `exclude_tables` | массивы строк | Шаблоны `pg_dump` (`--exclude-schema`, `--exclude-table`), до 256, каждый до 1024 байт, без повторов. Шаблон, которому ничего не соответствует, не ошибка. |
| `key_tables` | массив строк `схема.таблица` | Таблицы, строки которых отпечаток считает точно (имена как есть, не шаблоны), до 64. Не заданы — 10 самых больших по `pg_total_relation_size`. См. «Отпечаток базы». |
| `pg_dump_path` | абсолютный путь | Исполняемый файл `pg_dump`; `psql` и `pg_dumpall` — из того же каталога. |
| `include_globals` | boolean, по умолчанию `true` | Сохранять глобальные объекты кластера вторым снимком. `false` — один снимок, `pg_dumpall` не нужен. |
| `globals_role_passwords` | boolean, по умолчанию `false` | Положить в снимок хэши паролей ролей. Нужен суперпользователь. |

```json
{"host": "db1.example.com", "database": "billing", "user": "backup",
 "password_ref": "pg-billing", "tls_mode": "verify-full", "tls_root_cert": "/etc/sard/pg-ca.pem",
 "exclude_tables": ["public.log_*"]}
```

Синтаксис шаблонов исключения описывает документация PostgreSQL:
<https://www.postgresql.org/docs/current/app-pgdump.html> (параметры `--exclude-schema` и
`--exclude-table`, шаблоны как в `psql`). Поле `password` и строка подключения в схеме
запрещены (`additionalProperties: false`).

Параметры подключения агент передаёт строкой `--dbname=` с каждым значением в кавычках:
имя базы вида `app' host=evil` остаётся именем базы. В строку входят таймауты, чтобы
недоступный хост не держал шаг до таймаута TCP: `connect_timeout=30`,
`keepalives_idle=60`, `keepalives_interval=10`, `keepalives_count=6`, а также
`application_name=sard-agent` — по нему сессии агента видны в `pg_stat_activity`.

## Что делает шаг

1. **PREPARING.** Проверяется секрет, ищутся `pg_dump`, `psql` и (при `include_globals`)
   `pg_dumpall`, читаются их версии. `psql` входит в базу и спрашивает версию сервера и
   роль. Ошибка входа — FAILED с причиной от PostgreSQL (пароль в ней маскируется).
   Проверяются версии и роль (см. выше). Если `globals_role_passwords` включён, а роль
   не суперпользователь, шаг FAILED сразу: содержимое снимка не зависит от прав роли, тихого
   отката нет.
2. **DUMPING.** При `include_globals`: `pg_dumpall --globals-only` в память (до 64 МиБ);
   вывод не попадает ни в лог, ни на диск. Сбой — FAILED, ни одного снимка нет.
   Затем открывается транзакция отпечатка (см. «Отпечаток базы»): `psql` начинает
   `REPEATABLE READ READ ONLY`, экспортирует её снимок (`pg_export_snapshot()`) и снимает в
   нём отпечаток. Сбой — FAILED, бэкап без отпечатка не делается.
3. **UPLOADING.** `pg_dump --format=custom --compress=0 --no-password
   --lock-wait-timeout=300000 --snapshot=<снимок транзакции отпечатка>` и
   `restic backup --stdin` одновременно; транзакция отпечатка открыта, пока работает
   `pg_dump`. Сжатие выключено:
   сжатый дамп restic почти не дедуплицирует, а сжимает сам. Ожидание блокировок таблиц —
   не больше 5 минут. Затем второй снимок — глобальные объекты.

Шаг успешен только если `pg_dump` завершился с кодом 0, весь его вывод передан restic, он
не пуст и начинается с сигнатуры `PGDMP`. Иначе restic останавливается до конца потока, и
снимка нет: неполный дамп не становится снимком, который выглядит успешным.

Отмена и таймаут шага останавливают `psql`, `pg_dump`, `pg_dumpall` (SIGTERM, через 10 секунд
SIGKILL) и restic; после шага не остаётся процессов и сессий `sard-agent` на сервере.

### Результат

`snapshot_id` и `repository_id` — снимка базы; `total_bytes` и `added_bytes` — суммы по
обоим снимкам. Если снимок базы сохранён, а сохранить глобальные объекты не удалось, шаг
FAILED, а результат содержит снимок базы: он полон, а неполнота набора видна — у него нет
связанного снимка глобальных объектов. Отмена или таймаут во время сохранения глобальных
объектов оставляют основной снимок.

### Имена файлов и метки

Имя файла в снимке — `<база>.dump`, глобальные объекты — `<база>.globals.sql`. Байты имени
базы вне `[A-Za-z0-9_-]` записываются как `%XX` (UTF-8, заглавные hex), так что имя
никогда не равно `.` или `..` и не содержит `/` и запятой: `app` → `app.dump`, `my db` →
`my%20db.dump` и `my%20db.globals.sql`, `a.b` → `a%2Eb.dump`.

Метки снимка базы: метки шага (`sard.source`, `sard.run`, …) и
`postgresql.server_version`, `postgresql.pg_dump_version`, `postgresql.database` (имя в
том же кодировании), `postgresql.format=custom`, `postgresql.part=database` и, если
сервер его отдал, `postgresql.system_identifier` (идентификатор кластера, см. «Восстановление
из консоли»).
К ним агент добавляет `sard.fp=<SHA-256 отпечатка>` при создании снимка: снимок не
переписывается после бэкапа.
Метки снимка глобальных объектов — те же (без `sard.fp`), но `postgresql.format=plain`,
`postgresql.part=globals`, `postgresql.pg_dump_version` — версия `pg_dumpall`, а также
`postgresql.role_passwords=true|false` и `postgresql.main_snapshot=<id снимка базы>`.

Сервер знает только снимок базы. Будущее удержание (forget/prune) обязано удалять пару
снимков вместе; пока `restic forget` с группировкой по путям удерживает снимки
`/<база>.dump` и `/<база>.globals.sql` по одной политике раздельно.

## Отпечаток базы

Каждый бэкап несёт отпечаток базы — то, с чем проверка восстановления (V5) сравнит
восстановленную копию: «пустой дамп тоже восстанавливается успешно». Отпечаток снимает
тот же код плагина, что потом снимет его с копии; сравнивает агент, не плагин
(ADR «Отпечаток источника и интерфейс проверки плагина»).

Что входит:

| Факт | Правило | Что это |
|---|---|---|
| `major_version` | точно | Старший номер версии сервера. |
| `server_version` | для сведения | Полная версия. |
| `extension:<имя>` | точно | Установленное расширение. |
| `extension_version:<имя>` | для сведения | Его версия. |
| `tables` | точно | Число таблиц, которые выгрузит `pg_dump`: пользовательские (`r`, `p`), не временные, не члены расширений, не исключённые шаблонами. |
| `database_size` | для сведения | `pg_database_size`: у копии он другой (нет мёртвых строк). |
| `rows:<схема>.<таблица>` | точно | `count(*)` ключевой таблицы; ключевой таблицы нет в дампе — значение `missing`. |
| `key_tables` | для сведения | Как выбраны ключевые таблицы: `configured` или `the N largest`. |

Отпечаток и дамп видят одно состояние: транзакция `REPEATABLE READ` экспортирует снимок,
отпечаток снимается в ней, `pg_dump --snapshot` выгружает тот же снимок, транзакция
открыта до конца `pg_dump`. Запись в базу во время бэкапа не попадает ни в дамп, ни в
отпечаток, поэтому допуск расхождения нулевой. Если сессия `psql` транзакции оборвалась
раньше, чем закончился `pg_dump`, бэкап FAILED. Шаблоны `exclude_schemas` и `exclude_tables`
отпечаток переводит в регулярные выражения так же, как `psql` и `pg_dump`
(`processSQLNamePattern`), а сопоставляет их сам PostgreSQL — набор таблиц совпадает с тем,
что выгрузит `pg_dump`.

Глобальные объекты (`pg_dumpall`) отпечатка не имеют.

**Цена на источнике.** Отпечаток только читает. Его транзакция начинается до `pg_dump`
(хеш нужен в метке снимка, а метка ставится при создании снимка) и потому удлиняет бэкап на
время запросов: каталоги, `pg_database_size` и `count(*)` ключевых таблиц — полное
чтение каждой. Каждый подсчёт ограничен минутой (`statement_timeout`), все вместе — десятью;
подсчёт сверх лимита записывается как `not counted: …` для сведения, бэкап продолжается, но
эту таблицу проверка уже не сравнит. Пока открыта транзакция, VACUUM не убирает строки,
удалённые после её начала, — как и при обычном `pg_dump`. Замер на 876 МБ (данные в
памяти, PostgreSQL 16): отпечаток 0,43 с, `pg_dump` той же базы 4,3 с; на данных с диска
`count(*)` больших таблиц дороже — если он упирается в лимит, задайте `key_tables` из
небольших, но значимых таблиц.

## Глобальные объекты и пароли ролей

Дамп одной базы (`<база>.dump`) не содержит ролей и глобальных объектов: ни ролей, ни их
атрибутов и членства, ни табличных пространств. Они лежат во втором снимке
(`<база>.globals.sql`), если `include_globals` не выключен.

По умолчанию `pg_dumpall` получает `--no-role-passwords`: он работает под любой ролью, а
хэшей паролей в снимке нет, поэтому роли восстанавливаются **без паролей** (см. ниже).

**`globals_role_passwords: true` кладёт в репозиторий хэши паролей ролей (SCRAM).** Они
лежат внутри зашифрованного репозитория, сервер Sard их не видит, но хэш позволяет
перебирать пароль офлайн тому, кто прочитает репозиторий вместе с ключом. Включайте это
осознанно. Роль должна быть суперпользователем, иначе шаг FAILED до всех снимков. При
`include_globals: false` поле ничего не меняет и роль не проверяется.

## Восстановление из консоли

Консоль восстанавливает снимок базы **в новую базу** на выбранном целевом агенте (по
умолчанию с теми же параметрами подключения, что у источника, и именем
`<база>_restored_<ГГГГММДД>`). Поверх существующей базы восстановление не пишет никогда:
база с таким именем уже есть — отказ `DATABASE_EXISTS` до любых изменений. Спецификация —
`docs/specs/agent/console-restore.feature` (R2b), решения — `docs/adr/0060-console-restore.md`
и `docs/adr/0065-console-restore-postgresql.md`.

**Что нужно на целевом хосте и сервере**

- Нужен клиент PostgreSQL не старше версии `pg_dump` снимка (метка `postgresql.pg_dump_version`,
  сравнивается старший номер): `pg_restore` и рядом с ним `psql`, из `pg_restore_path` или
  `PATH` агента. Нет — `PG_CLIENT_MISSING` (шаг предлагает запустить
  `sudo sard-agent check`); старше — `PG_CLIENT_TOO_OLD`.
- Целевой сервер — не ниже 14 и не старше сервера источника по старшему номеру (метка
  `postgresql.server_version`; без метки проверяется только минимум 14 и в лог идёт WARN):
  иначе `PG_SERVER_TOO_OLD`.
- Роль для восстановления — суперпользователь или с `CREATEDB` (`CREATEDB_REQUIRED`).
  Если выбрано `restore_globals` (глобальные объекты — роли кластера), роль должна быть
  **суперпользователем** (`SUPERUSER_REQUIRED`). Пароль берётся из секрета хоста
  (`password_ref`) и передаётся только переменной `PGPASSWORD`.

**Порядок шага.** Проверки (стадия `check`, первая сработавшая определяет причину): снимок,
клиент и его версия, вход в служебную базу `postgres`, версии и права, глобальные объекты,
отсутствие базы. Затем: глобальные объекты (если выбраны) одной транзакцией
`psql --single-transaction -v ON_ERROR_STOP=1`; `CREATE DATABASE … TEMPLATE template0`;
`restic dump` потоком в `pg_restore --exit-on-error` (дамп не пишется на диск). Без
`restore_globals` `pg_restore` получает ещё `--no-owner --no-acl --no-tablespaces`: ролей и
табличных пространств источника на целевом сервере может не быть, владельцы и права не
восстанавливаются (консоль предупреждает об этом).

**Глобальные объекты** (`restore_globals`) меняют кластер целиком. Отказ до изменений:
`GLOBALS_SNAPSHOT_MISSING` (у снимка нет снимка глобальных объектов), `GLOBALS_TABLESPACES`
(в файле есть `CREATE TABLESPACE`: его нельзя выполнить в транзакции, а каталог — каталог
хоста источника; восстановите без глобальных объектов или создайте табличные пространства
вручную), `ROLES_EXIST` (роль уже есть на целевом сервере: изменение существующей роли
откатить нельзя). Операторы `CREATE ROLE` и `ALTER ROLE` начального суперпользователя
целевого кластера (роль с OID 10) пропускаются, в лог идёт строка INFO. Строка файла с
командой `psql` (`\!` и подобные; допустимы только `\restrict` и `\unrestrict`, которые
пишет `pg_dumpall` 2025 года и позже) — отказ. Роли восстанавливаются без паролей, если
`globals_role_passwords` при бэкапе был выключен.

**Всё или ничего.** При любом сбое после начала изменений (ошибка `pg_restore`, потеря
хранилища, отмена, таймаут шага) созданная шагом база и созданные шагом роли удаляются
(`DROP DATABASE … WITH (FORCE)`, затем `DROP ROLE`) **по OID, записанным при создании**: имя,
которое теперь ведёт к другому объекту, не трогается. Не удалось удалить — шаг FAILED с
`CLEANUP_FAILED (rollback)`, сообщение и результат называют оставшееся (`database …`,
`role …`): удалите это вручную. Сообщение любого отказа имеет вид
`<ПРИЧИНА> (<стадия>): …; nothing was restored`, стадии — `check`, `globals`,
`create-database`, `restore`, `rollback`.

**Журнал отката** — запись плагина в журнале восстановления агента,
`executor.state_dir/restore-journal/<command_id>.json` (`0600`, конверт
`{plugin, command_id, entry}`; `entry` — запись плагина в base64): целевое подключение и **имя**
секрета (не пароль), имена и OID созданных объектов; каждое состояние (намерение, создано,
завершено) сохраняется с `fsync` до действия, которое оно объявляет. Запись удаляет агент после
того, как записал результат шага; запись, в которой остался объект с OID, который не удалось
убрать, он оставляет до следующего старта. Журнал агента выпуска R2b,
`executor.state_dir/pg-restore/<command_id>.json`, агент читает как записи плагина postgresql ещё
один выпуск (и удаляет вместе с результатом команды), но сам в него не пишет. Если
агент убит посреди восстановления, при следующем старте, до приёма шагов, он откатывает
по журналу: «создано» — удаляет по OID, «завершено» — шаг SUCCEEDED с припиской
`agent restarted after the restore completed`, объект, у которого записано только
намерение (OID не успел записаться), **не удаляется по имени**, а называется оставшимся
(`CLEANUP_FAILED`). Недоступный при старте сервер — тоже `CLEANUP_FAILED` с перечнем
оставшегося; запись остаётся до следующего старта, и откат повторяется.

**Режим `pg_restore` и таблица блокировок.** Таблица блокировок PostgreSQL общая на кластер:
одна транзакция `pg_restore` с большим числом объектов может исчерпать её и сорвать
транзакции других приложений. Поэтому перед `CREATE DATABASE` агент читает оглавление
дампа (начало потока `restic dump` идёт в `pg_restore -l`, затем поток останавливается) и
сравнивает число записей N с ёмкостью `C = max_locks_per_transaction × (max_connections +
max_prepared_transactions)` целевого сервера. Если `N < restore.postgresql_lock_share × C`,
`pg_restore` идёт **одной транзакцией** (`--single-transaction`), иначе отдельными. Долю
хозяин хоста задаёт в `agent.yaml` или `agent.d`: `restore.postgresql_lock_share`, число от 0
до 1 включительно, по умолчанию 0.5; 0 — никогда одной транзакцией; другое значение
останавливает старт агента. Выбор виден в логе шага:
`pg_restore mode: single transaction | separate transactions (N objects, lock capacity C,
share S)`. Сервер на настройку не влияет. Всё или ничего держится в обоих режимах — на
удалении базы, а не на транзакции. Не удалось прочитать оглавление — `PG_RESTORE_FAILED
(check)` до создания чего-либо.

**Восстановление в кластер источника.** Опасно по умолчанию: в одной базе кластера вы
получаете копию, но нагрузку и блокировки делите с живыми базами. Консоль и агент
предупреждают, но не запрещают. Надёжный признак — идентификатор кластера
`system_identifier`: при бэкапе плагин читает его запросом
`select system_identifier from pg_control_system()` и пишет снимку базы метку
`postgresql.system_identifier=<число>`; при восстановлении агент сравнивает метку с
идентификатором целевого сервера и при совпадении пишет в лог шага WARN
`the target is the cluster the snapshot was taken from (system identifier …)`; совпадение —
это тот же кластер. Метки нет (старый снимок) или идентификатор не прочитать — сравнение
пропускается, строка INFO, отказа нет (консоль тогда сравнивает только адрес сервера).
**Какое право нужно для метки:** на PostgreSQL 14, 16 и 18 (проверено на кластерах этих
версий) `EXECUTE` на `pg_control_system()` выдано `PUBLIC`, поэтому его имеет любая роль с
`LOGIN`: отдельный `GRANT` не нужен, роль для бэкапа остаётся прежней. Если администратор
отозвал это право (`REVOKE EXECUTE ON FUNCTION pg_control_system() FROM PUBLIC`), бэкап
идёт как обычно, но без метки, а в лог шага пишется INFO «the system identifier of the
cluster is not recorded».

Файл настроек: в `agent.yaml` или `agent.d/*.yaml` —

```yaml
restore:
  postgresql_lock_share: 0.5
```

| Причина | Что делать |
|---|---|
| `PG_CLIENT_MISSING (check)` | Поставьте клиент PostgreSQL на целевом хосте или задайте `pg_restore_path`; `sudo sard-agent check`. |
| `PG_CLIENT_TOO_OLD`, `PG_SERVER_TOO_OLD` | Нужен клиент не старше `pg_dump` снимка и сервер не ниже 14 и не старше сервера источника. |
| `PG_CONNECT (check)` | Цитата ошибки libpq: пароль, `pg_hba.conf`, TLS, адрес. |
| `CREATEDB_REQUIRED`, `SUPERUSER_REQUIRED` | `ALTER ROLE … CREATEDB`; для `restore_globals` — суперпользователь. |
| `DATABASE_EXISTS` | Выберите новое имя базы. |
| `ROLES_EXIST`, `GLOBALS_TABLESPACES`, `GLOBALS_SNAPSHOT_MISSING` | Восстановите без глобальных объектов или подготовьте кластер. |
| `PG_GLOBALS_FAILED (globals)`, `PG_CREATE_DATABASE`, `PG_RESTORE_FAILED` | Цитата ошибки `psql` или `pg_restore`; созданное шагом удалено. |
| `CLEANUP_FAILED (rollback)` | Удалите вручную то, что названо в «left behind». |

## Восстановление руками

Восстановление **поверх существующей базы** и в кластер с особыми требованиями делают
стандартными средствами PostgreSQL. Из снимков базу восстанавливают так; снимки находит и выкладывает на диск команда
`sard-agent repo snapshots` и `sard-agent repo restore` (без сервера Sard и без
регистрации агента, `docs/operations/agent-host-setup.md`). `pg_restore` и `psql`
должны быть **не старше** версии из метки `postgresql.pg_dump_version`; новый
кластер — не старше исходного.

Команда `repo restore` выкладывает снимок PostgreSQL файлами (`<цель>/<база>.dump` и
`<цель>/<база>.globals.sql`, оба `root:root`, `0600`) и **печатает** команды `psql`,
`createdb` и `pg_restore`; она их не запускает. Какие файлы выкладывать и какие команды печатать,
решает плагин `postgresql` (необязательный интерфейс SDK `Extractor`), сама команда базу не знает;
строку `plugin.programs` команды `sard-agent check` тоже даёт плагин (`ProgramChecker`). В примерах `<имя>` — репозиторий
источника, `$SP` — идентификатор источника, `$T` — каталог для файлов (новый или пустой).

1. **Найти снимок**: `sudo sard-agent repo snapshots <имя> --source $SP` — снимки базы и
   глобальных объектов видны рядом, с одним `RUN`.

2. **Выложить файлы** и отдать их пользователю `postgres` (дамп содержит все данные базы,
   глобальные объекты при `globals_role_passwords` — хеши паролей ролей, поэтому файлы
   закрыты для всех, кроме root):

   ```bash
   sudo sard-agent repo restore <имя> latest --source $SP --target $T
   sudo chown -R postgres $T
   ```

   Одна команда выкладывает дамп и, если есть, файл глобальных объектов из самого нового
   снимка с меткой `postgresql.main_snapshot=<id снимка базы>`; id снимка базы вместо
   `latest` восстанавливает именно его. Итог команды печатает следующие шаги с готовыми
   путями. Цель создана для root с правами `0700`, поэтому `chown -R` отдаёт `postgres`
   и каталог.

3. **Восстановить глобальные объекты** суперпользователем нового кластера, **до** базы:

   ```bash
   # allow-sudo-u: psql от суперпользователя нового кластера PostgreSQL, не sard-agent
   sudo -u postgres psql -X -d postgres -f $T/app.globals.sql
   ```

   Ошибки «role … already exists» ожидаемы для ролей, которые в новом кластере уже есть
   (начальный суперпользователь).

4. **Восстановить базу**: `createdb`, `pg_restore` в новую базу:

   ```bash
   # allow-sudo-u: createdb от суперпользователя нового кластера PostgreSQL, не sard-agent
   sudo -u postgres createdb restored
   # allow-sudo-u: то же, pg_restore от суперпользователя PostgreSQL
   sudo -u postgres pg_restore -d restored $T/app.dump
   ```

   Роли из шага 3 нужны уже здесь: владельцы объектов в дампе — эти роли.

5. **Пароли ролей.** Без `globals_role_passwords` роли восстановлены без паролей — войти
   по паролю они не могут. Задайте пароли:

   ```sql
   ALTER ROLE app_rw PASSWORD '...';
   ```

   С `globals_role_passwords: true` восстановленная роль входит прежним паролем.

**Без снимка глобальных объектов** (`include_globals: false`) создайте роли заранее
(`CREATE ROLE ...` с теми же именами) либо восстановите без владельцев и прав:

```bash
pg_restore --no-owner --no-acl -d restored app.dump
```

Имя файла с символами вне `[A-Za-z0-9_-]` записано как `%XX`: база `my db` лежит в
`/my%20db.dump`, её глобальные объекты — в `/my%20db.globals.sql`.

## Сообщения об ошибках

Сообщение шага — одна строка на английском; ошибку libpq или `pg_dump` оно цитирует
(последняя строка с `error:` или `FATAL:`). Полный stderr `psql` и `pg_dump` идёт в лог шага
строками: WARN для строк с `error:`, `FATAL:`, `warning:`, остальные — INFO.

| Причина | Что делать |
|---|---|
| `pg_dump not found …` | Поставьте клиент PostgreSQL или задайте `pg_dump_path`. |
| `pg_dump 16.4 is older than the PostgreSQL server 18.0` | Поставьте `pg_dump` 18 или новее, задайте `pg_dump_path`. |
| `password authentication failed for user …` | Неверный пароль в секрете или нет такой роли. |
| `no pg_hba.conf entry …` | Разрешите роли вход с хоста агента в `pg_hba.conf`. |
| `server does not support SSL` | Сервер без TLS: включите TLS на сервере или задайте `tls_mode: disable` и разрешите его в привязке (`--allow-tls disable`). |
| `secret "…" is not allowed for postgresql at …` | Цель источника вне привязки секрета: выполните на хосте агента команду из сообщения или исправьте источник. |
| `secret "…" has no binding on this host …` | Секрет без привязки: `sudo sard-agent secret set <имя> --plugin postgresql --target …`. |
| `tls_mode disable would send the password …` | `tls_mode` слабее, чем разрешает привязка: включите TLS (`verify-full`) или разрешите `--allow-tls`. |
| `authentication method requirement "scram-sha-256" failed: server requested a hashed password` | Роль входит по `md5`: задайте `password_encryption = 'scram-sha-256'` и пароль роли заново, или разрешите `--auth scram-sha-256,md5`. Пароль не отправлен. |
| `channel binding is required, but server did not offer …` | Между агентом и сервером пулер или роль без пароля SCRAM: исправьте сервер или разрешите `--allow-no-channel-binding`. |
| `invalid connection option "require_auth"` | libpq на хосте старше 16: поставьте клиент PostgreSQL 16 или новее (образ агента `-pg18` его содержит) или укажите `pg_dump_path`. |
| `root certificate file … does not exist` | Нет CA для `verify-full`: `--ca-file` в привязке или `tls_root_cert` источника. |
| `permission denied for table …` | Роли нужно `pg_read_all_data` или `SELECT` на таблицу; либо `exclude_tables`. |
| `pg_dump failed: empty output`, `not a custom-format archive` | `pg_dump` завершился, не создав архив: смотрите лог шага. |
