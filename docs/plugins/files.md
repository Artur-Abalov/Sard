# Плагин `files`

Плагин `files` сохраняет каталоги и файлы хоста в репозиторий restic. Спецификация —
`docs/specs/agent/files-plugin.feature`, ручная проверка — `docs/qa/files-plugin.md`.

## Конфиг

| Поле | Тип | Описание |
|---|---|---|
| `paths` | массив строк, обязательное | Абсолютные пути (начинаются с `/`), от 1 до 64, каждый до 4096 байт. Без повторов и без вложенных друг в друга путей: `/etc` и `/etc/ssh` вместе — ошибка конфига. |
| `exclude` | массив строк | Шаблоны исключения restic, до 256 штук, каждый до 1024 байт. |
| `one_file_system` | boolean, по умолчанию `false` | `true` — restic не заходит в каталоги других файловых систем (`--one-file-system`). |
| `control_paths` | массив строк | Контрольные пути: файлы и каталоги внутри `paths`, которые при каждом бэкапе обязаны существовать и быть непустыми, до 64. См. «Отпечаток». |
| `sample_files` | целое 0…1000, по умолчанию 100 | Сколько случайных файлов хешировать (SHA-256) перед бэкапом; 0 — выборки нет. |
| `sample_max_file_bytes` | целое, по умолчанию 67108864 (64 МиБ) | Файлы больше этого в выборку не попадают. |

```json
{"paths": ["/etc", "/var/www"], "exclude": ["*.log", "/var/www/cache"], "one_file_system": true}
```

Синтаксис шаблонов `exclude` описывает документация restic:
<https://restic.readthedocs.io/en/stable/040_backup.html#excluding-files>.
Агент шаблоны не разбирает: если restic шаблон не принял, шаг завершается ошибкой
с причиной от restic и снимка нет.

Существование путей проверяется при запуске шага, а не при сохранении конфига.

## Что делает шаг

1. **PREPARING.** Агент проверяет каждый указанный путь (не обходя дерево): он
   существует, каталог открывается и читается его список, файл открывается на
   чтение. Путь, который сам является символической ссылкой, отклоняется: restic
   сохранил бы саму ссылку без данных. Любая неудача — шаг FAILED до запуска restic;
   сообщение называет пути и причины (не больше десяти и общее число).
   Затем каждый контрольный путь: нет или пуст (каталог без записей, файл в 0 байт) — шаг
   FAILED до restic, причина `control path: no such file or directory` или
   `control path: empty`. Так ловится отмонтированный диск, который иначе сохранился бы
   «успешно» пустым каталогом.
2. **DUMPING.** Черновик отпечатка: состояние контрольных путей и выборка хешей (см.
   «Отпечаток»).
3. **UPLOADING.** `restic backup` с метками шага, шаблонами `exclude`, а при
   `one_file_system` — с `--one-file-system`. Если репозиторий заблокирован другим
   процессом, restic ждёт до 5 минут (`--retry-lock 5m`; срок пока не настраивается),
   затем шаг завершается ошибкой с именем репозитория. Таймаут шага действует и во
   время ожидания.
4. Отпечаток дополняется итогами restic и сохраняется отдельным снимком (см. «Отпечаток»).
5. Результат: `snapshot_id`, общий и добавленный объём, `repository_id`, число файлов,
   отпечаток и его хеш.

Симлинки внутри дерева сохраняются как ссылки, а не содержимым цели. Пустой каталог —
успешный бэкап.

### Отпечаток

Отпечаток — то, с чем проверка восстановления (V5) сравнит копию. Его снимает тот же код
плагина, что потом снимет его с копии; сравнивает агент.

| Факт | Правило | Что это |
|---|---|---|
| `control:<путь>` | точно | `nonempty` — путь есть и не пуст. |
| `sha256:<путь>` | точно | SHA-256 файла выборки, снятый до бэкапа. Если размер или время изменения файла после бэкапа другие (restic мог прочитать другое содержимое) — для сведения, `changed during the backup`. |
| `stat:<путь>` | для сведения | Размер и время изменения файла выборки при хешировании. |
| `files`, `bytes` | точно | Итоги restic: число файлов и их объём (`total_files_processed`, `total_bytes_processed`). У копии — обход каталога: обычные файлы и их размеры; ссылки и каталоги не считаются ни там, ни там. |
| `sample` | для сведения | «N of M files hashed» и что прервало выборку. |

Выборка — равномерная (резервуар) по всем обычным файлам `paths`, которые restic
сохранит: шаблоны `exclude` применяются по правилам restic, отрицания (`!…`) не
учитываются — выборка может пропустить файл, который restic сохранит, но не возьмёт
исключённый. Ограничения: файл не больше `sample_max_file_bytes`, обход не дольше 10 минут,
чтение не больше 1 ГиБ; что не успелось, отмечено в `sample`, бэкап продолжается.

Где лежит. Выборку можно дополнить только после бэкапа, а restic не умеет добавить метку к
снимку, не создав новый. Поэтому окончательный отпечаток сохраняется **отдельным снимком**
`sard-fingerprint.json` с метками шага, `files.part=fingerprint`,
`files.main_snapshot=<id снимка файлов>` и `sard.fp=<SHA-256 отпечатка>`; снимок файлов не
переписывается. Сервер получает тот же отпечаток в результате шага; хеши файлов выборки и
их пути он консоли не показывает.

**Цена на источнике.** Полный обход дерева до бэкапа (restic потом обходит его ещё раз) и
чтение файлов выборки — до 100 файлов, до 1 ГиБ. Источник только читается.

### Файлы, которые не удалось прочитать

Если внутри дерева есть нечитаемые файлы, restic всё равно создаёт снимок (без них), а
шаг завершается **FAILED**: молча неполный бэкап хуже упавшего. Сообщение содержит
число различных путей и первые десять из них; снимок остаётся в репозитории и
передаётся в результате шага.

**Что значит «неполный».** Снимок существует, но в нём нет перечисленных файлов. Шаг и
запуск завершаются FAILED; свежесть источника и «последний успех» не обновляются: такой
бэкап за успешный не считается. Консоль помечает снимок как «неполный» и не восстанавливает
его; восстановить его можно только на хосте командой `sard-agent repo restore`. Проверка
восстановления (verify) неполный снимок пропускает.

**Что делать.** Обычная причина — права чтения у пользователя `sard-agent` (см.
[«От чьего имени читаются файлы»](#от-чьего-имени-читаются-файлы)). Выдайте права на
перечисленные пути и запустите бэкап снова. В журнале агента строка «step finished»
содержит `message` (то же сообщение) и `snapshot_id` (неполный снимок).

**Что показывает сервер.** При нечитаемых файлах сервер показывает их число, до десяти первых путей и
подсказку о правах со ссылкой на раздел
[«От чьего имени читаются файлы»](#от-чьего-имени-читаются-файлы).

**Пометка полноты на хосте.** Команда `sard-agent repo snapshots` показывает в колонке COMPLETE, подтвердил ли бэкап, что прочитал каждый файл: `confirmed` — к снимку привязан
снимок отпечатка (он пишется, только если основной снимок полный); `unconfirmed` —
привязанного снимка отпечатка нет; `-` — не применимо (снимок не Sard, снимки PostgreSQL
и сам снимок отпечатка). `unconfirmed` ошибается только в сторону осторожности: его
получают неполные снимки, полные снимки, у которых снимок отпечатка не создан (сбой после
основного снимка), и снимки, сделанные до появления отпечатков (до V2), а также снимки
сторонних плагинов без собственных меток. Если есть хотя бы один `unconfirmed`, команда
печатает в stderr одну строку-пояснение; в JSON это поле `completeness`.

`sard-agent repo restore` снимка с `unconfirmed` восстанавливает как обычно, но до запуска
restic пишет в stderr предупреждение «completeness of snapshot … is not confirmed», а в
итоге добавляет строку `completeness: not confirmed`. Флага нет; `latest` выбирает снимок
как раньше и только предупреждает. Что делать: проверьте права `sard-agent` (раздел
выше) и запустите бэкап снова.

### Восстановление

Действие `restore` для `files` объявлено, но настоящего восстановления пока нет: шаг
завершается FAILED с сообщением, что восстановление для плагина files ещё не
реализовано, restic не запускается и на диске ничего не меняется. `verify` и `run`
плагином не поддерживаются.

## От чьего имени читаются файлы

Агент работает от непривилегированного пользователя `sard-agent`, а не root
(`deploy/agent/sard-agent.service`). Он видит только то, что этому пользователю
разрешено читать: сообщение шага «permission denied» значит, что права не выданы.
Выдайте чтение одним из способов ниже, от самого узкого к самому широкому.

### Через группу

Добавьте пользователя в группу, которая владеет данными:

```bash
sudo usermod -aG www-data sard-agent
sudo systemctl restart sard-agent   # группы читаются при старте службы
```

### Через POSIX ACL

ACL выдаёт чтение конкретному пользователю. Флаг `-d` задаёт ACL по умолчанию: он
применяется к файлам и каталогам, которые появятся позже (без него новые файлы снова
окажутся недоступными):

```bash
sudo setfacl -R -m u:sard-agent:rX /srv/data
sudo setfacl -R -d -m u:sard-agent:rX /srv/data
```

Каталогам по пути к `/srv/data` нужно право поиска (`x`) для `sard-agent`.

### Через `CAP_DAC_READ_SEARCH`

Возможность ядра позволяет читать любые файлы, минуя проверку прав. Выдайте её службе
дропином (`sudo systemctl edit sard-agent`):

```ini
[Service]
AmbientCapabilities=CAP_DAC_READ_SEARCH
CapabilityBoundingSet=CAP_DAC_READ_SEARCH
```

**Предупреждение.** `CAP_DAC_READ_SEARCH` даёт агенту чтение всех файлов хоста, в том
числе ключей и паролей других служб. Если агент будет скомпрометирован, всё это станет
доступным. Используйте её, только когда группа или ACL не подходят.

## Ограничения юнита systemd

Юнит `sard-agent.service` закрывает часть файловой системы, и это влияет на то, что
агент может прочитать:

- `PrivateTmp=true` — у службы собственный `/tmp`: файлы других процессов из `/tmp`
  хоста агент не увидит, а то, что видно ему в `/tmp`, — его собственное. Каталоги для
  бэкапа не держите в `/tmp`.
- `ProtectHome=read-only` — `/home` доступен для чтения, но не для записи; для
  бэкапа этого достаточно. `ProtectHome=true` скрыл бы `/home` совсем, и путь под
  ним получил бы ошибку «no such file or directory».
- `ProtectSystem=strict` — остальная система только для чтения; бэкапу запись не нужна.
