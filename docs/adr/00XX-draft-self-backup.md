# 00XX — Самобэкап Sard: системные источники встроенного агента

- Статус: черновик (F6, фазы 2–3; ответы владельца на вопросы 1–14 — 2026-10-09, на фазу 3 — 2026-10-12)
- Дата: 2026-10-09
- Номер ставится при слиянии; ADR агента-соседа (`00XX-draft-self-agent.md`) —
  перед ним.

## Контекст
F5 поставил рядом с сервером агента-соседа `sard-self`. Он читает базу ролью
только на чтение и каталог CA через том только на чтение. Источников у него
нет: без них установка сама себя не бэкапит. Ручная процедура
(`docs/operator/06-data-and-backup.md`) требует cron на хосте, и о сбое никто
не узнаёт. Главные риски — самобэкап, из которого нельзя восстановиться, и
самобэкап, который тихо сломан.

## Решение

### Что бэкапится
Два **системных источника** встроенного агента, отдельными запусками:
- **«Sard: database»** — плагин `postgresql`:
  - база сервера (хост, порт и имя — из его datasource);
  - роль `sard_self`, пароль — секрет `sard-db` соседа;
  - `tls_mode: disable` — сеть compose частная;
  - `include_globals: false`: роль `sard` создаёт инициализация образа
    postgres, `sard_self` — миграция, пароль ей задаёт сервер. Ответ 6.
- **«Sard: keys and configuration»** — плагин `files`:
  - каталог CA (`/var/lib/sard/pki`, том `sard-pki:ro`);
  - каталог установки (`/etc/sard/install`, bind-монтирование `./:ro`):
    `.env`, `docker-compose.yml`, override;
  - исключены `*.dump`, `*.tgz`, `*.tar`, `*.tar.gz`, `*.zst`: это ручные
    бэкапы и офлайн-архивы, которые лежат рядом.
  - `.env` хранится вместе с CA: без него восстановление неполное. Ответ 3.

Пути и параметры — `sard.self-backup.*` (`SARD_SELF_BACKUP_*`).

### Ключ CA и база — в одном репозитории (ответ 2)
Прежнее правило «бэкап CA храните отдельно от бэкапа базы» (`pki.md`)
самобэкап меняет: оба источника идут в один репозиторий restic.
- Репозиторий зашифрован.
- Пароль от него — только у соседа (ADR 0008). Копию пароля оператор держит
  вне ВМ.
- Кто получил хранилище без пароля, не получил ни CA, ни `.env`.
- Кто получил пароль и хранилище, получил корень доверия установки. Это тот же
  уровень доступа, что у самого соседа (принятый риск F5).
- Кому нужно разделение, ведёт ручной бэкап CA отдельно, по `pki.md`.
- Копия в два хранилища — этап 2.

### Привязка репозитория
`PUT /api/v1/self-backup/repository {repositoryName, confirmLocalStorage}`:
- Нужен живой встроенный агент тенанта (`agents.builtin`). Репозиторий
  должен быть в его последнем Register и иметь `repository_id`, то есть быть
  инициализирован.
- Локальный backend (D10) — только с `confirmLocalStorage: true`, иначе 422
  `local_storage_unconfirmed`. В состоянии остаётся признак `local` для
  постоянного предупреждения.
- Одна транзакция: источники, их расписания и строка `self_backups`
  (`bound_at`). Признак «локальное» не хранится: он выводится из backend в
  Register, а подтверждение — только ворота привязки.
  Расписание по умолчанию — `0 3 * * *` в поясе сервера, отдельно на каждый
  источник: F3a держит одно расписание на источник.
- Повторная привязка без изменений ничего не пишет.
- Привязка к другому репозиторию или новому встроенному агенту переводит те
  же источники (id, история, расписания сохраняются), `bound_at` — сейчас.
- Конфиг проверяется схемой плагина соседа. Без секрета `sard-db` — 422
  `invalid_config`.

### Системный источник
- `sources.system_role` (`self_database`, `self_keys`), не больше одного
  живого на роль и тенант.
- REST и консоль его помечают (`Source.systemRole`).
- `PUT` и `DELETE` → 409 `system_source`.
- Расписание и ручной запуск — через обычный API.
- Уникальность имени — только среди источников администратора: системное имя
  не отнимает имя у пользователя.

### «Запустить сейчас»
`POST /api/v1/self-backup/runs` — `Runs.start` для каждого источника, база
первой. Если у источника уже идёт запуск (D6), в ответе его id и
`started: false` — мастер просто следит за запусками. До привязки — 409
`self_backup_not_configured`.

### Учётные данные
Сервер знает только имя репозитория, backend и `repository_id` из Register
(ADR 0008). Пароль роли — по имени секрета. Ни один ключ, пароль или путь к
секрету не идёт через REST или журнал сервера.

## Последствия
- Восстановление (F7): агенты, зарегистрированные между последним бэкапом
  базы и аварией, после восстановления получат `CERT_UNKNOWN` и
  регистрируются заново.
- `.env` должен читаться группой 10001: `sudo chgrp 10001 .env && chmod 640
  .env` (`docs/operator/02-install.md`). Иначе источник ключей падает с
  понятной ошибкой файла.
- **Образ соседа — `sard-agent:<версия>-pg18`.** Это тот же
  `deploy/agent/Dockerfile` с `BASE_IMAGE=postgres:18`: pg_dump нужной версии
  на месте, openssh-client ставится как у обычного образа (ответ 1). Вариант
  годится и клиенту с контейнерным агентом. Новая major-версия — ещё одна
  строка в release.yml. compose, release.yml и офлайн-архив берут `-pg18`.
- **Репозиторий соседу — разовым контейнером:**
  `docker compose run --rm --no-deps -u 0 --cap-add CHOWN --cap-add
  DAC_OVERRIDE --cap-add FOWNER --cap-add SETUID --cap-add SETGID self-agent
  repo add …`, затем `docker compose restart self-agent` (ответ 5, проверено
  e2e). `exec -u 0` в работающего соседа не годится: у него `cap_drop: ALL`,
  и root в нём не войдёт в каталоги `0700` пользователя 10001. Пять
  capabilities нужны `repo add`, чтобы создать каталоги владельцу и запустить
  restic от его имени. Сосед после перезапуска снова работает без прав.
- **Состояние и предупреждения.** `GET /api/v1/self-backup` отдаёт `status`
  (худшее из `agent_replaced`, `overdue`, `failing`, `schedule_disabled`,
  иначе `ok`), `warnings` (те же плюс `local_storage`) и `overdueSince`. По
  каждому источнику — последний успех, последняя ошибка и последний запуск.
  Решает сервер, консоль показывает баннер на каждой странице и раз в минуту
  перечитывает состояние. «Давно не было успеха» — общая свежесть источников
  (ADR 00XX-draft-source-freshness), а не частный случай самобэкапа.

## Отклонённые варианты
- **Одно расписание на оба источника.** Требует расписания вне источника, а
  F3a держит 1:1.
- **Отдельная таблица привязки с агентом и репозиторием.** Это дубль того, что
  уже записано в источниках.
- **Монтировать `.env` отдельным файлом.** Редактор пересоздаёт файл, и
  bind-монтирование продолжает показывать старый.
- **`cap_add: DAC_READ_SEARCH` вместо группы.** Docker не даёт эффективных
  capabilities процессу не от root.
