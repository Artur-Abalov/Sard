# 0070 — Точки расширения server-core

- Статус: принято (CORE1 фаза 3, SARD-7; спецификация `docs/specs/server/server-core-extensions.feature`,
  решения владельца Р1–Р25 2026-10-30)
- Дата: 2026-10-30
- Дополняет [0013](0013-multitenancy-and-schema.md), [0021](0021-admin-password-login.md) и
  [0069](0069-database-roles.md)

## Контекст
Enterprise-сборка (первой — LIC1) — то же ядро плюс стартеры, собранная против опубликованного
`sard-server-core` той же версии. Ядру нужны швы, в которые она встаёт, и граница, по которой
видно, что в публичном API изменилось.

## Решения
1. **Публичное API — только `dev.sard.server.extension.**`.** Всё остальное внутреннее. ABI этих
   пакетов выгружается встроенной проверкой Kotlin Gradle plugin (`abiValidation`, фильтр по
   пакету) в `server/api/server.api`; `check` падает, если изменение не внесено в выгрузку
   (`./gradlew :server:updateLegacyAbi` — осознанное изменение, видимое в diff). Отдельной
   зависимости нет. ABI держится внутри одного `X.Y.Z` (все `X.Y.Z-*` совместимы между собой);
   расширения пересобираются под каждый `X.Y.Z`, совместимости между версиями нет. Публичны имена
   классов `*AutoConfiguration` (на них ссылается `before = …`), но не их методы `@Bean`: расширение
   их не вызывает. Так, `EditionAutoConfiguration.editionStartupCheck` убран до первого выпуска
   (заменён внутренним бином, пункт 2).
2. **Шов редакции и лицензии** (`EditionProvider`): реализация ядра — редакция `free`, лицензии нет.
   Ядро сообщает то, что дало расширение (`GET /api/v1/status`: только `edition`;
   `GET /api/v1/server`: `edition`, `extensions` по id, `licence`), не сверяет срок и не применяет
   лимиты. Редакция читается у шва один раз при старте и хранится (внутренний `ReportedEdition`):
   сбой `edition()` — отказ старта `Edition unavailable: …`, а не 500 на статус. Лицензия читается
   на каждый запрос `GET /api/v1/server` (может меняться); шов бросил исключение — состояние
   `unavailable` и одна строка WARN. Лицензия **никогда**
   не блокирует бэкап, восстановление и проверку: код запусков, отправки, проверки, планировщика и
   восстановления от шва не зависит (тест архитектуры).
3. **Шов политики доступа** (`AccessPolicy`, субъект `Subject`, операция `Operation` — метод и шаблон
   пути OpenAPI): реализация ядра разрешает администратору всё. Порядок проверок: Origin (403) →
   сессия (401) → политика (Р17). Политика спрашивается для всех операций под `/api/v1`, кроме
   публичных, шагов мастера и выхода; отказ — 403 `access_denied`; исключение политики — тоже отказ
   и одна строка WARN. Субъект — из сессии ядра или тот, которого расширение, заменившее фильтр
   сессии (SSO, Е3), положило в запрос под публичным `SUBJECT_REQUEST_ATTRIBUTE`. Операция, которую
   спрашивают, без субъекта — 401: заменённый фильтр не открывает API, пропустив субъекта (отказ
   закрыт). Спрашивает перехватчик
   MVC (`AccessPolicyInterceptor`), потому что шаблон пути известен только после выбора обработчика.
   Работа самого сервера (планировщик, цикл проверки) политике не подчинена.
4. **Замена шва** — `@AutoConfiguration(before = …)` и `@ConditionalOnMissingBean` у реализации
   ядра (порядок 0013/0021). Две реализации одного шва (`EditionProvider`, `AccessPolicy`,
   `TenantResolver`) от разных расширений — отказ старта с именами бинов и конфигураций
   (`BeanFactoryPostProcessor` по определениям бинов).
5. **События ядра — события приложения Spring** (`SardEvent`: запуск, вход и выход, окончание сессии,
   изменение настроек; Р18–Р25). Аудит — слушатели, отдельного механизма нет. Доставка синхронная,
   после фиксации, не более одного раза; слушатель, бросивший исключение, не меняет исход и не
   лишает события других: мультикастер приложения (`SardEventMulticaster`) ловит и логирует сбой
   слушателя события ядра, события самого Spring идут как прежде. События запуска публикуются из
   `RunEvents` по синхронизации транзакции Hibernate (только после коммита), по состоянию запуска
   в базе до и после изменения, а не по названному вызывающим статусу.
6. **Сроки сессии** — 1 час бездействия и 8 часов с входа (были 12 часов и 7 дней, Р23); окончание
   по сроку публикует `session.expired`, обход раз в минуту (`sard.session.sweep-interval`).
7. **Миграции расширений проверяются при старте** (`EXTENSION_MIGRATIONS_NOT_APPLIED`, после
   проверки ядра): уточнение пункта 5 ADR 0069. Проверка читает те же места
   (`SARD_MIGRATE_EXTENSION_LOCATIONS`) и ту же таблицу истории, что и `sard-server migrate`.
8. **REST расширения** — под `/api/v1`, под сессией ядра и в OpenAPI; контроллер расширения вне
   `/api/v1` — отказ старта (`ExtensionWebAutoConfiguration`).
9. **Публикация**: `maven-publish` для `sard-server-core`, `sard-proto-jvm`, `sard-server-console`
   (без удалённого репозитория — его добавит релизный workflow). `examples/extension-sample` —
   отдельная Gradle-сборка против опубликованного в локальный репозиторий ядра, строгая блокировка
   зависимостей как в корне; CI собирает и тестирует её.

## Последствия
- Изменение публичного API без отметки в `server/api/server.api` роняет `check`.
- Каждое место, где запуск меняет статус, обязано пройти через `RunEvents` (`movingStep`/`movingRun`:
  наблюдатель до, изменение, `settled` после); `RunEvents` внедряется туда явно, умолчания нет.
- Консоль показывает блок редакции и лицензии позже (нет спецификации консоли).
