# 0022 — Один активный запуск на источник (решение D6)

- Статус: принято (D6, записано в X2); реализация — миграция S6, REST — S8b
- Дата: 2026-09-29

## Контекст
S6 создаёт таблицы `sources`, `runs`, `run_steps` и отправляет агенту команды. Целевая схема ADR 0013 описывала `runs` как запуск workflow: `workflow_id` обязателен, `source_id` нет, статусы без `dispatched`. На этапе 1 workflow и расписаний нет, запуск только ручной — «сделать бэкап источника сейчас».

Контракт REST этапа 1 (ADR 0019, S8a) уже исходит из D6: у запуска есть `sourceId` (`server/src/main/kotlin/dev/sard/server/api/RunsController.kt:27`), статус `dispatched` активен наравне с `queued` и `running` (`ApiEnums.kt:39`), `POST /api/v1/sources/{id}/runs` и удаление источника отвечают 409 `run_active` со ссылкой на идущий запуск (`SourcesController.kt:165,177`, `Problems.kt:93-100`), имя репозитория задаётся в источнике (`SourcesController.kt:35`) и проверяется с ответом 422 `unknown_repository` (`SourcesController.kt:134`). Это решение записывает правило, его гарантию и правку схемы.

Два одновременных бэкапа одного источника ничего не добавляют: второй снимок почти не отличается от первого, оба ждут блокировку одного репозитория restic и вдвое нагружают хост. Если бэкап идёт дольше интервала расписания, запуски начинают накапливаться.

## Решение
- **Активный запуск** — статус `queued`, `dispatched` или `running`. `queued` включает запуск, который ждёт офлайн-агента: он будет отправлен при подключении (S6), и второй не создаётся.
- **Не больше одного активного запуска на источник.** Гарантия — частичный уникальный индекс `UNIQUE (tenant_id, source_id) WHERE status IN ('queued', 'dispatched', 'running')` на `runs`. Не проверка в коде: «прочитать, затем вставить» пропускает два одновременных запроса, индекс — нет. Код может проверить заранее, чтобы найти `activeRunId` для ответа, но корректность держит индекс; нарушение индекса при вставке тоже превращается в 409.
- **Ручной запуск при активном** — отказ 409 `run_active` (problem+json, ADR 0019) с `activeRunId`; новый запуск не создаётся.
- **Запуск по расписанию при активном** (этап 2) — видимый пропуск: запись о пропуске в истории источника, алерт при нескольких пропусках подряд. Запуск не ставится в очередь.
- **Запуск этапа 1 — запуск источника.** `runs.source_id` обязателен; `runs.workflow_id` допускает `NULL` только при `trigger = 'manual'`. Неявные workflow под каждый источник не создаются. *F3a (ADR 00XX-draft-scheduler):* расписание тоже запускает источник, поэтому `NULL` допустим и при `trigger IN ('schedule', 'catch_up')`; запуск `verification` по-прежнему требует workflow.
- **Workflow из нескольких источников** (после этапа 1): ограничение переходит на `run_steps.source_id` — тот же частичный индекс по активным шагам; форма `runs` для таких workflow решается вместе с ними.
- **Репозиторий задаётся в источнике**, `sources.repository_name`, а не при запуске: снимки одного источника живут в одном репозитории (дедупликация, `forget` и проверка восстановления идут по репозиторию). API при создании и замене источника проверяет имя по последнему `Register` агента (`agent_repositories`, S4a) и отвечает 422 `unknown_repository`. Снимок `Register` может устареть, поэтому агент при запуске всё равно может ответить `REJECTED` (S6). `run_steps.repository_name` хранит имя, отправленное агенту.

### Правка целевой схемы ADR 0013
Внесена в ADR 0013 этим же изменением; таблицы появляются в миграции S6.

```text
sources      + repository_name NOT NULL                    -- имя из снимка Register агента
runs         + source_id NOT NULL → sources
             workflow_id NULL → workflows
             CHECK (workflow_id IS NOT NULL OR trigger = 'manual')   -- F3a: OR trigger IN ('schedule', 'catch_up')
             status CHECK IN ('queued', 'dispatched', 'running', 'succeeded', 'failed', 'cancelled')
             definition JSONB NULL                          -- снимок workflow; NULL без workflow
             CHECK ((workflow_id IS NULL) = (definition IS NULL))
             UNIQUE (tenant_id, source_id) WHERE status IN ('queued', 'dispatched', 'running')   -- D6
             INDEX (tenant_id, source_id, queued_at DESC)
```

Ссылки — составные, как везде (ADR 0013, правило 2): `(tenant_id, source_id) → sources (tenant_id, id)`. Уникальный индекс D6 заодно служит индексом по `(tenant_id, source_id)` для поиска активного запуска.

## Отвергнуто
- **Очередь запусков на источник.** Если бэкап длится дольше интервала расписания, очередь растёт без предела, а каждый следующий запуск бэкапит почти то же, что предыдущий. Повторное нажатие кнопки тоже тихо удлиняет очередь.
- **Параллельные запуски одного источника.** Спор за блокировку репозитория restic, двойная нагрузка на хост, два почти одинаковых снимка и неясный ответ на вопрос «какой бэкап последний».
- **Неявный workflow на каждый источник.** Строки, которых пользователь не создавал, и две сущности, которые надо держать согласованными при каждом изменении источника; удаление и переименование источника тянут за собой скрытый workflow. Запуск источника с `workflow_id NULL` честнее.
- **Репозиторий при запуске.** Снимки одного источника расходились бы по репозиториям: `forget`, дедупликация и проверка восстановления перестали бы видеть историю источника целиком, а форма запуска требовала бы выбора, которого у пользователя нет.
- **Проверка в коде вместо индекса.** Два одновременных запроса проходят проверку оба; блокировка строки источника работала бы, но держится на дисциплине каждого пути записи, а индекс — на базе.

## Последствия
- Источник с офлайн-агентом нельзя запустить повторно, пока запуск ждёт подключения.
- Удаление источника при активном запуске отвечает 409 `run_active` (контракт S8a), история запусков источника остаётся (ADR 0013, правило 3).
- Одновременные запросы запуска — поведение S6: ровно один создаёт запуск, остальные получают 409 с тем же `activeRunId`.

## Отложено
- Пропуск запуска по расписанию и алерт при нескольких пропусках подряд — этап 2, вместе с планировщиком; форма записи о пропуске — там же.
- Перенос ограничения на `run_steps.source_id` — вместе с workflow из нескольких источников.
