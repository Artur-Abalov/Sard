# 00XX — Неполный бэкап: причина, хранение, полнота на хосте, метрика

- Статус: черновик (SARD-15 / PL7, часть 2; решения владельца 2026-10-28, `docs/specs/proto/partial-backup.feature`)
- Дата: 2026-10-29
- Основа: `docs/specs/proto/partial-backup.feature` (НБ1–НБ16, ВН1–ВН11), ADR 0008, черновик «Отпечаток источника» (V2), ADR 0024

## Контекст
Неполный бэкап — это запуск `FAILED`, у шага которого есть снимок (`partial`). До части 2
консоль знала только «часть данных не попала» и сырое сообщение агента; при этом
`partial` бывает и при полном основном снимке, когда упал связанный снимок (отпечаток,
глобальные объекты PostgreSQL). Нужно: причина, которую можно показать и посчитать;
место её хранения; признак на хосте без сервера; метрика, отличающая неполный бэкап от
полного провала.

## Решение

### (a) Причину решает сервер, по наличию поля proto3
`BackupOutput.unreadable_count` — `optional uint64` (поле 8); агент PL7-2 и новее шлёт его
в каждом выводе бэкапа (0, если нечитаемых нет), агент N−1 не шлёт. Наличие поля —
единственный признак «агент сообщил» (НБ6):

| partial | unreadable_count | причина |
|---|---|---|
| false | любое | нет |
| true | нет поля | `unknown` |
| true | 0 | `snapshot_set_incomplete` |
| true | > 0 | `unreadable_files` |

Правило — одна функция сервера (`IncompleteReason.of`); консоль причину не выводит, а
форматирует готовое значение. Альтернатива (ВН5): отдельное перечисление причины в
`BackupOutput`, которое пишет агент. Отвергнута: второй источник истины рядом с числом;
агент N−1 всё равно его не пришлёт, а граница между «0» и «не сказал» остаётся на
presence; новое значение причины потребовало бы менять proto и агента, а не сервер.

### (b) Где хранится причина
Две записи, один источник:
- `run_steps.output` (JSON) хранит число и первые десять путей (НБ4) — это данные
  карточки запуска. Причина запуска в REST **вычисляется** из этого вывода
  (`partial`, `unreadableCount`) той же функцией при каждом чтении.
- `snapshots.incomplete_reason` хранит причину, **вычисленную в момент записи снимка**
  (`StepResults`, `storedReason()`), для списка снимков и всего, что читает снимок без
  JOIN с выводом шага. Миграция `V202610281000` заполняет `unknown` для старых
  `partial`-снимков (агент числа не присылал) и добавляет два ограничения: значение из
  трёх и `partial = (incomplete_reason IS NOT NULL)`, чтобы признак и причина не
  расходились.

Авторитетна функция `IncompleteReason.of` над выводом шага: колонка — её сохранённый
результат, а не независимый факт. Альтернатива — вычислять причину снимка из
JSON вывода при каждом чтении: снимок пришлось бы связывать с шагом и разбирать JSON в
запросах списка; отвергнута, цена — колонка, которую поддерживает ограничение БД.

### (c) Полнота на хосте выводится из меток, без записи
`repo snapshots` и `repo restore` помечают снимок «полнота не подтверждена» (Р89–Р93),
ничего не дописывая в репозиторий (V2: ни агент, ни сервер не пишут меток после бэкапа).
Правило: у снимка есть `sard.run`, у него нет метки плагина (ключ с точкой, не `sard.`), и
в списке нет снимка с `files.part=fingerprint` и `files.main_snapshot=<полный id>`.
Правило ошибается только в сторону «не подтверждено»: так помечаются полные снимки,
у которых упал снимок отпечатка, снимки files до V2 и снимки сторонних плагинов без
меток. Ложного «подтверждено» оно дать не может: подтверждение — наличие снимка
отпечатка, который пишется после основного только при успехе.

Правило зависит от имён меток, которые пишет `pluginhost` для плагина `files`
(`files.part`, `files.main_snapshot`). Эта связь закреплена контрактным тестом
`agent/internal/pluginhost/completeness_contract_test.go`: настоящий бэкап files через
`pluginhost` даёт метки, которые `restore.List` читает как «подтверждён» для основного
снимка и «неприменимо» для снимка отпечатка. Переименование плагина или ключей
`withPluginTags` ломает тест.

Открытая идея: обобщить правило до `<p>.part=fingerprint` + `<p>.main_snapshot` для
любого плагина с `FingerprintCompleter`. Сейчас в agent зашит `files`; обобщение
имеет смысл, когда появится второй плагин с отпечатком, дописываемым отдельным снимком
(ВН3: метка `files.part=main` или общее правило).

### (d) Метрика — подмножество `failed`, а не новый статус или метка
`sard_run_partial_total{reason}` (Micrometer `sard.run.partial`): счётчик, растёт на 1,
когда запуск бэкапа завершается `failed`, а у его шага есть вывод с `partial`. Каждый
такой запуск учтён и в `sard_run_finished_total{status="failed"}`, поэтому «провал без
снимка» = `finished{failed}` − сумма `partial` по `reason`. Серии отдаются с нуля (МР13).
Альтернативы (ВН8): новый статус запуска — меняет enum, консоль, уведомления и серии
провалов (D7, ADR 0024); новая метка у `sard_run_finished_total` — меняет набор серий
существующей метрики, на которую опираются дашборды и правила.

## Последствия
- Старый агент даёт `unknown`; нейтральный текст (НБ8) верен и для него.
- Новая причина — правка `IncompleteReason.of`, enum REST, текстов консоли и CHECK в БД.
- Сумма `sard_run_partial_total` не больше `sard_run_finished_total{status="failed"}`;
  выражение в `docs/operator/14-monitoring.md`.
- Колонка и вывод шага могут расходиться только при ручной правке БД; ограничение
  `partial = (incomplete_reason IS NOT NULL)` ловит половину таких правок.
- Хост без сервера не видит «подтверждено» для снимков до V2 и сторонних плагинов:
  предупреждение, не отказ; `latest` не пропускает неподтверждённый снимок.

## Отвергнуто
- Перечисление причины в `BackupOutput` от агента (ВН5).
- Причина только в JSON вывода шага, без колонки (b).
- Новый статус запуска или метка `partial` у `sard_run_finished_total` (ВН8).
- Метка о полноте, дописанная к снимку после бэкапа (`restic tag` создаёт новый id; V2).
