# 00XX — Свежесть источников: эпизоды просрочки и уведомления не только о запусках

- Статус: черновик (F6, фаза 3; направление подтвердил владелец 2026-10-12)
- Дата: 2026-10-12

## Контекст
F3a сообщает о запусках по расписанию: о первой ошибке серии и о восстановлении.
Это вывод по каждому запуску (`Telling`), а очередь уведомлений
(`notification_deliveries`) знает только запуски (`run_id NOT NULL`).

Тихо сломанный бэкап при этом молчит. Агент офлайн — запуск висит в `queued`.
Слоты пропускаются как `skipped_active`. Расписание выключено. Ни одного
упавшего запуска нет, значит, нет и сообщения. То же нужно самобэкапу (F6):
«давно не было успеха». Делать это частным случаем самобэкапа владелец назвал
костылём.

## Решение

### Правило
Источник с включённым расписанием **просрочен**, если с последнего успеха
прошло полтора интервала расписания:
- отсчёт ведётся от последнего успешного запуска или от последнего изменения
  расписания, если оно позже;
- интервал — промежуток между первыми двумя срабатываниями cron после этого
  момента. Нерегулярный cron судится по тому промежутку, в котором он сейчас.

Для ежесуточного расписания это 36 часов: один пропущенный или упавший слот и
ещё полсуток. Правило — чистая функция `Freshness`, тесты на часах-фейке.

### Эпизод
Таблица `overdue_episodes`, одна строка на каждый период просрочки:
- `counted_from` — успех, от которого считали;
- `deadline` — момент, когда источник стал просроченным;
- `opened_at`, `closed_at`;
- `closed_by_run_id` — успех, который закрыл эпизод.

Открытым у источника может быть не больше одного эпизода (частичный
уникальный индекс). `FreshnessCheck` раз в `sard.freshness.interval`
(по умолчанию 60 с):
- сканирует источники в системной сессии только на чтение (ADR 0013, вызов 8);
- открывает эпизод, когда срок прошёл;
- закрывает его первым успехом, который новее `counted_from`;
- закрывает молча, без запуска, когда расписание выключено или источник удалён;
- пишет охраняемыми запросами в сессии тенанта. Второй сервер ничего не
  испортит.

### Уведомления о предметах
У доставки есть `subject`:
- `run` — запуск, как раньше;
- `overdue` — эпизод открылся;
- `overdue_over` — эпизод закрыт успехом.

Ключ эпизода — `(tenant, episode, subject, channel)`. Планирует
`OverdueDeliveries`, читает `Notices`, текст пишет `OverdueFormatter` (ru, en,
время в UTC).

**Одно сообщение на поворот событий.** Закрытие эпизода молчит, если
закрывший его запуск сообщает о себе сам: ручной результат или «восстановлен»
по расписанию. Тихий успех по расписанию после просрочки даёт «Бэкапы
возобновились». Эпизод, закрытый без успеха, не сообщается.

### Где видно
Самобэкап выводит из эпизодов своих источников предупреждение `overdue` и
`overdueSince` (ADR 00XX-draft-self-backup). Для обычных источников эпизоды
пока видны только в уведомлениях. Показ в консоли — отдельная задача.

## Последствия
- Недоставленная тревога о пропусках F3a (`schedule_fires.alert`) встанет на
  ту же очередь отдельным `subject` (F3b).
- Ещё один фоновый цикл. Пока гонка mutflow не устранена, он расширяет окно
  гонки фоновых потоков в тестах (журнал F6, фаза 2). В REST-тестах цикл
  выключен (`sard.freshness.interval=1h`).

## Отклонённые варианты
- **Просрочка как свойство только самобэкапа.** Это костыль: у обычных
  источников та же беда.
- **Считать просрочку на лету при чтении, без таблицы.** Тогда некому
  отправить уведомление ровно один раз, и нечего закрывать.
- **Синтетический упавший запуск при просрочке.** Ломает историю запусков
  (ADR 0013, правило 3) и D6.
- **`run_id` эпизода — последний висящий запуск.** Просрочка бывает и без
  запусков: при выключенном агенте их нет вовсе.
