# 0021 — Вход администратора по паролю (решение D2)

- Статус: принято; реализовано в W1b. **Пароль из окружения (`SARD_ADMIN_PASSWORD`) заменён ADR F4a** ([00XX-draft-f4a-first-start.md](00XX-draft-f4a-first-start.md)): пароль задаётся в мастере первого запуска и хранится в базе как хэш Argon2id, меняется из консоли; остальное решение (сессии в памяти, cookie, перебор, Origin) в силе.
- Дата: 2026-09-28

## Контекст
До этой фичи REST API сервера не был защищён: любой, кто достучится до порта
8080, видел и менял данные. Открытое ядро — один администратор на инсталляцию
(README, «Запуск»); полноценные роли, SSO/LDAP и хранение сессий в базе —
задачи enterprise-редакции (ADR 0008 — сервер остаётся управляющей плоскостью,
не хранилищем ключей; тот же принцип: минимум секретов, минимум состояния).
Контракт этапа 1 (ADR 0019) уже описывал операции `/api/v1/session` как
заглушки 501 — нужна была только их реализация.

## Решение
- **Один пароль из окружения.** `SARD_ADMIN_PASSWORD`, не короче 12 символов
  в кодовых точках Unicode (Р6); сервер не стартует без него и называет
  причину, но не сам пароль (`AdminPasswordAuthenticator`). Объекты Sard не
  хранят пароль как строку — только SHA-256 в `AdminPasswordAuthenticator.hash`;
  сравнение — `MessageDigest.isEqual` (JDK документирует его как постоянное
  по времени, сравнивающее оба массива целиком). Это не значит, что открытый
  пароль нигде не остаётся в процессе: переменная окружения и разрешённое из
  неё значение в Spring `Environment` живут в памяти JVM вне контроля Sard
  (Р6) — то же допущение, что и для любого секрета из окружения.
- **Сессия — только в памяти процесса, cookie `sard_session`.** Идентификатор
  — 256 случайных бит, `HttpOnly`, `SameSite=Strict`, `Path=/`, `Secure` при
  HTTPS, без `Max-Age`/`Expires` (Р7). 12 часов бездействия, 7 дней с входа,
  что раньше (Р1); активность — любой запрос с сессией под `/api/v1`
  (`SessionAuthFilter` трогает сессию по пути, до контроллера). Перезапуск
  сервера завершает все сессии (Р8) — это и есть решение D2 «без хранения
  сессий в БД» на этапе 1.
- **Перебор — по адресу клиента, тоже в памяти.** 5 неудач за 15 минут
  блокируют вход на 15 минут от пятой неудачи (Р2); адрес — соединение, не
  `X-Forwarded-For` (Р4, доверие к обратному прокси — отдельная задача).
  Проверка блокировки и её запись — одна критическая секция на адрес
  (`LoginAttemptTracker.withAddressLock`): иначе параллельные запросы могли
  бы все увидеть «не заблокировано» до того, как первый из них запишет
  неудачу, и порог перестал бы что-то ограничивать. Состояние на адрес не
  накапливается бесконечно: адрес без неудач в окне и без блокировки
  забывается на первой же следующей проверке этого же адреса
  (`LoginAttemptTracker.forgetIfInert`), так же `SessionStore.create` сметает
  истёкшие сессии при создании новой — обе карты ограничены количеством
  недавно активных адресов и живых сессий, а не растут вечно.
- **CSRF — проверка Origin, не токен** (К1, Р5). `OriginGuardFilter` сравнивает
  Origin со схемой, `Host` и портом запроса самого соединения (не
  `X-Forwarded-Proto`) для POST/PUT/PATCH/DELETE под `/api/v1`, до выбора
  обработчика Spring MVC. Отказ — 403 `origin_rejected`; значение добавлено в
  `ErrorCode`, ответ 403 — в OpenAPI каждой изменяющей операции
  (`describeOriginRejected`, springdoc `OpenApiCustomizer`, как уже работает
  `describeUnauthorized` для 401, ADR 0019).
- **Сессия — тенанта по умолчанию** (правило 9): `TenantResolver` уже пинует
  открытое ядро к нему (ADR 0013); своей резолюции для W1b не нужно.
- **Смена пароля — только переменная окружения и перезапуск** (правило 10):
  никакого API смены пароля на этапе 1.
- **Журнал** — вход, неудача, выход, блокировка (один раз при начале) с
  адресом клиента; ни пароль, ни идентификатор сессии в лог не попадают
  (правило 11, Р10).
- **Веб** — консоль без бизнес-логики (CLAUDE.md): пароль проверяет и сессию
  выдаёт сервер; консоль только формой, редиректом и разбором `redirect`
  (`docs/specs/web/admin-login.feature`, решения Р9).
- **Шов для enterprise-редакции.** `SessionApi` (`dev.sard.server.api`) не
  знает ни про HTTP, ни про пакет `auth`: только пароль, адрес клиента,
  предыдущий идентификатор сессии на входе и исход (`SignInResult` —
  `SignedIn`, `WrongPassword`, `Locked`). `AdminAuthAutoConfiguration`
  (`dev.sard.server.auth`) собирает пароль-реализацию по умолчанию и оба
  фильтра, каждый бин — `@ConditionalOnMissingBean`; свой `SessionApi`
  (SSO, LDAP) объявляется как `@AutoConfiguration(before =
  [AdminAuthAutoConfiguration::class])` — так же, как `TenancyAutoConfiguration`
  уступает enterprise-резолверу тенанта (ADR 0013). Заменивший `SessionApi`
  автоматически снимает и требование `SARD_ADMIN_PASSWORD`:
  `AdminPasswordAuthenticator` создаётся, только если своего `SessionApi` ещё
  нет.
  **Полный контракт замены — оба бина.** Замена одного только `SessionApi`
  не отключает проверку сессии: `SessionAuthFilter` (ядро) продолжает
  требовать валидную cookie на каждый защищённый путь и `SessionStore`
  ядра — единственное, что её признаёт, так что при своём `SessionApi`, но
  чужом фильтре все защищённые запросы становятся 401 (сознательно, отказ
  закрыт: фильтр не сделан условным по наличию `SessionApi`, чтобы стартер,
  забывший про фильтр, не открыл API без проверки вовсе). Стартер, который
  меняет вход целиком, обязан объявить оба бина: свой `SessionApi` и бин
  с именем `sessionAuthFilterRegistration` (тоже `@AutoConfiguration(before
  = [AdminAuthAutoConfiguration::class])`), регистрирующий свой фильтр под
  тем же путём и порядком — тогда `@ConditionalOnMissingBean(name =
  ["sessionAuthFilterRegistration"])` ядра его не создаёт.
  `AdminAuthAutoConfigurationTest` проверяет три случая: открытое ядро;
  стартер, заменивший только `SessionApi` (проверка сессии остаётся
  ядровой — отказ закрыт); стартер, заменивший оба бина (ядровой фильтр не
  создан вовсе).
  `SessionAuthFilter.SESSION_REQUEST_ATTRIBUTE` — имя атрибута запроса, под
  которым ядровой фильтр прикладывает найденную сессию; на этапе 1 его не
  читает ничего, кроме тестов. Он оставлен нарочно как будущий шов для
  enterprise-`TenantResolver`, чтобы тот мог взять субъекта (пользователя,
  роль) из уже проверенной сессии, не трогая сам фильтр или `SessionApi`.

## Отвергнуто
- **Работа без входа.** Рассматривалась для этапа 1 (как решение владельца 8
  в S8a), но не выдерживает даже локального `make up`: порт 8080 без пароля
  открыт всем, кто до него достучится.
- **Несколько пользователей на этапе 1.** Ролей, аудита по пользователю и
  управления учётками ещё нет — один пароль честнее подобия
  многопользовательской системы без них.
- **Spring Security.** Функциональность W1b — cookie, Origin-проверка,
  перебор — уместилась в два сервлет-фильтра и один сервис без новой
  зависимости (`docs/dependencies.md` требует нужности здесь и сейчас).
- **JWT или иной самоподписанный токен вместо серверной сессии.** Отозвать
  такой токен раньше срока нельзя без чёрного списка, который сам по себе
  и есть серверное состояние — не проще, чем сессия в памяти.

## Последствия
- **Перезапуск сервера обрывает все сессии администратора** — не только
  сессия сбрасывается, но и блокировки перебора: если это было решением
  DoS-атаки, злоумышленник получает новых 5 попыток. Приемлемо для одного
  администратора, если перезапуск сервера — редкая операция.
- **За TLS-терминирующим обратным прокси (или любым, что переписывает
  `Host`) вход и любой изменяющий запрос отвечают 403, консоль не
  работает.** Сервер видит схему и `Host` самого соединения от прокси —
  как правило, `http://<внутренний host:порт>` — а браузер отправляет
  `Origin: https://<внешний host>` (Р4: `X-Forwarded-Proto`/`Forwarded` не
  доверяются). `OriginGuardFilter` сравнивает их буквально и отклоняет
  такой `Origin` как чужой: `POST /api/v1/session` (вход) и любой
  изменяющий запрос под `/api/v1` получают 403 `origin_rejected`, пока
  прокси не пробрасывает `Host` без изменений и клиент не обращается по
  тому же имени и порту, что видит сервер. Отдельно и независимо от этого:
  cookie `sard_session` не получает атрибут `Secure`, хотя снаружи
  соединение зашифровано, — сервер судит о `Secure` по `request.isSecure`
  того же внутреннего соединения. Итого: этап 1 поддерживает только прямой
  доступ к порту 8080 (или проброс с сохранением `Host`/схемы 1:1); доверие
  к заголовкам обратного прокси — отдельная будущая задача (Р4).
  *Дополнено ADR 0046 (2026-10-06): `SARD_FORWARD_HEADERS=native` включает
  доверие к `X-Forwarded-Proto`/`X-Forwarded-For` от прокси с loopback или
  частного адреса; по умолчанию поведение прежнее.*
- Отложено на будущий этап: роли и авторизация по действиям, SSO/LDAP, смена
  пароля из консоли, хранение сессий в базе (переживает перезапуск,
  работает при нескольких экземплярах сервера) и, соответственно, высокая
  доступность сервера с несколькими репликами.
