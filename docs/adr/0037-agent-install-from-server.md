# 0037 — Установка агента с сервера: адрес раздачи и версии (U1b)

- Статус: принято (решения владельца В1–В9, 2026-10-05)
- Дата: 2026-10-05
- Связано: ADR 0008 (сервер — не хранитель ключей), ADR 0018 (упаковка агента), ADR 0041 (`0041-agent-release.md`) (раздача пакетов, подпись), `docs/specs/server/agent-install.feature`

## Контекст

Сервер раздаёт пакеты агента своей версии (U1a). Консоль должна показать
администратору путь от скачивания до запущенной службы и отметить устаревших
агентов, не вычисляя ничего сама: в вебе нет бизнес-логики (CLAUDE.md). Команды,
адреса, выбор пакета, порядок шагов и сравнение версий — на сервере, по REST
(`GET /api/v1/agent-install`, `GET /api/v1/agents/{id}/upgrade`, поле `outdated`).

## Решение

- **Адрес раздачи в командах (В1).** Агент ходит на gRPC-адрес (`AgentEndpoint`,
  host:port), а пакеты отдаёт HTTP-порт, возможно за обратным прокси с TLS, — адрес
  gRPC для скачивания не годится. Новая настройка `sard.agent-packages.downloads-url`
  (`SARD_AGENT_DOWNLOADS_URL`): абсолютный `http` или `https` без запроса и
  фрагмента; пусто — `http://<хост AgentEndpoint>:<SARD_HTTP_PORT>`. Сервер не
  стартует с другим значением (в сообщении — имя переменной); значение с кавычкой,
  пробелом, `$` и другими символами, ломающими команду оболочки, тоже отклоняется,
  потому что попадает в команды. Адрес из заголовков запроса не используется никогда
  (`Host` и `X-Forwarded-Host` не влияют на команды).
- **Версии (В4).** «Устарел» (`outdated`) — только если обе версии релизные
  `vX.Y.Z` и версия агента строго меньше раздаваемой по числовому сравнению
  semver. Агент новее, без Register, с версией из `git describe`, `dev` или
  предрелизной — не помечается; нерелизная сборка сервера не помечает никого. При
  выключенной раздаче сравнение идёт с версией сервера: пакеты сервера всегда его
  версии. Сравнение — `AgentVersions`, на сервере; консоль только показывает флаг.
- **Манифест.** Сервер читает из `manifest.json` ещё `restic_version`, `arch` и
  `format` пакетов; версия restic в ответе — из раздаваемого пакета, а не с хоста.
- **Ключ релизов (В5).** `deploy/release/sard-release.pub` входит в сборку сервера
  ресурсом (`release/sard-release.pub`); консоль показывает ID и строку ключа и
  требует сверить их с `README.md` репозитория. Ключ из `SHA256SUMS.minisig` не
  берётся; шаг проверки подписи передаёт ключ строкой (`minisign -P`), а не файлом
  с сервера. Раздача без подписи (образ без релиза) помечена `signed: false`, шага
  подписи нет.
- **Шаги (В2, В3, В6).** Порядок и состав — на сервере; команды используют только
  базовые утилиты (`sh`, `sha256sum`, `grep`, `curl` или `wget` по `fetch`, `tar`,
  `install`, `useradd`, `cp`, `sed`, `dpkg`, `systemctl`, `sudo`, сам `sard-agent`).
  Шаг `configure` создаёт `agent.yaml` из примера, только если файла нет, и
  подставляет адрес сервера; репозиторий оператор правит сам (ADR 0008). Архив даёт
  ту же раскладку, что deb; ссылка `/usr/bin/sard-agent` делается `cp -s`, чтобы не
  выходить за список утилит. Регистрация и создание репозитория — от
  пользователя `sard-agent`. В командах вместо токена — заполнитель `<TOKEN>`;
  строки токена в ответах нет никогда.
- **Форматы (вопрос 2).** Консоль предлагает deb и tar.gz; `format=rpm` — 422. RPM
  остаётся в релизе.
- **Пакет (В8).** `postinstall.sh` печатает следующий шаг только при первой
  установке; обновление о регистрации не пишет. Службу пакет по-прежнему не
  включает и не запускает до регистрации.

## Последствия

- Новая настройка, ключ релизов в ресурсах сервера (в Dockerfile сборки — `COPY
  deploy/release/sard-release.pub`), три новых поля контракта; `schema.d.ts` и
  `openapi.json` перегенерированы.
- Команда `enrollCommand` ответа создания токена (S2b) — без `sudo -u sard-agent`;
  диалог создания токена показывает её на месте шага регистрации без изменений
  (спецификация консоли), а пояснение шага говорит, что выполнять её нужно от
  имени пользователя службы. Если это неудобно — менять S2b (его тесты закрепляют
  строку), не консоль.
