# 0060 — Восстановление из консоли (R2a)

- Статус: принято (R2a); решения владельца ВВ1–ВВ13 — заголовки `docs/specs/*/console-restore.feature`
- Дата: 2026-10-14
- Дополняет: ADR 0008 (сервер не держит ключи), ADR 0059 (restic restore от пользователя службы, `--no-lock`)

## Контекст
Оператору нужно вернуть снимок на хост, не заходя на него. Сервер не держит
ключей и путей (ADR 0008), данные не идут через сервер.

## Решение
1. **Восстановление — это запуск** (`kind=restore`, триггер manual,
   `requestedBy`) с одним шагом `restore` на выбранном агенте. Шаг несёт имя
   репозитория агента, полный id снимка, конфиг из запроса и теги
   `sard.source`, `sard.run`, `sard.step`. D6 («один активный запуск на
   источник») считает только резервные копии; удаление источника блокирует
   любой активный запуск.
2. **Место решает хост.** `restore.dir` задаёт владелец хоста (в протоколе поля
   для него нет, агент сообщает его при регистрации); назначение — подкаталог.
3. **Всё или ничего.** restic пишет в `<restore.dir>/.sard-staging/<command_id>/root`
   от пользователя службы через удерживаемый дескриптор `<command_id>`
   (`--target /proc/self/fd/3/root`, как A8c). Перед переносом агент долговечно
   пишет в `<command_id>` метку (назначение и итог: временный файл, fsync,
   rename, fsync каталога), затем один `renameat` переносит только `root` на
   место. `<command_id>` с меткой удаляется только после того, как исполнитель
   записал результат в журнал (`executor.Options.Journaled`). Любой сбой
   откатывает всё. Сбой отката — `CLEANUP_FAILED (rollback)` и
   `RestoreOutput.leftover`.
   При старте, до приёма шагов, каждый `<command_id>` разбирается: есть `root`
   — удаляется, исход «nothing was restored»; есть метка, `root` нет — перенос
   состоялся, исход SUCCEEDED с итогом из метки и «agent restarted after the
   restore completed»; нет ни того ни другого — «nothing was restored».
   Каталог неизвестной журналу команды удаляется. Поправка владельца
   2026-10-15 (замечания architect F2, F5): без метки SIGKILL сразу после
   переноса давал полное назначение и ложное «nothing was restored».
4. **Порядок проверок (ВК33)**: снимок 404 → не восстанавливаемый 422 → agentId
   422 → отозванный 409 → репозиторий 409 `unknown_repository` → плагин 409
   `unknown_plugin` → конфиг и секреты 422 (недостающее обязательное свойство —
   `config/<prop>`).
5. **Потерянный шаг с поздним результатом** сохраняет результат и остаётся
   потерянным.
6. **Протокол**: только добавления (`restore_dir`, `restore_config_schema`,
   `RestoreOutput`); SDK получает необязательный интерфейс `Restorer`
   (Apache-2.0).
7. В R2a консоль восстанавливает только плагин `files`; postgresql не
   объявляется для восстановления.

## Последствия
Права на файлы не переносятся: оператор копирует результат сам (`cp -a`,
`rsync -a`, `restorecon`). Каталог с ограниченными правами внутри цели может
помешать откату — тогда остаток сообщается в `leftover`.
