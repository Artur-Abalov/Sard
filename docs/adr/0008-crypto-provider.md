# 0008 — Криптопровайдер: передача ключа в restic

- Статус: принято
- Дата: 2026-09-26

## Контекст
Хранение, дедупликацию и шифрование делает restic (AES-256 в режиме CTR + Poly1305-AES, алгоритм в restic фиксирован). В будущем нужен ГОСТ через ViPNet CSP.

## Решение
`crypto.Provider` в `agent/internal/crypto` отдаёт restic ключ репозитория, а не шифрует данные сам:

```go
type Provider interface {
    Name() string
    RepositoryKey(ctx context.Context, repository string) (Key, error)
}
type Key struct{ Env []string } // окружение процесса restic, напр. RESTIC_PASSWORD_FILE=...
```

Единственная реализация — `resticAES`: возвращает `RESTIC_PASSWORD_FILE=<путь из конфига>`, сам файл не читает. Остальной код агента (обёртка restic) получает `Provider` через конструктор.

## Причины
- Шифрование в стиле Encrypt/Decrypt поверх restic дало бы двойное шифрование и убило бы дедупликацию (шифротекст всегда разный).
- Передача пути к файлу пароля не кладёт секрет в память агента и в переменные окружения.

## Отвергнуто и отложено
- ГОСТ. Алгоритм restic заменить нельзя, поэтому ГОСТ потребует либо шифрования потока до restic (без дедупликации), либо собственного формата хранения. Владелец решил: restic — open source, при необходимости будет переписан; ГОСТ — отдельным ADR позже. Утверждение «без переделок» для ГОСТ этим интерфейсом **не** обеспечивается.
