# 0008 — Модель доверия: сервер — управляющая плоскость, ключи на хостах

- Статус: принято (пересмотрено 2026-09-27)
- Дата: 2026-09-26

## Контекст
Хранение, дедупликацию и шифрование делает restic (AES-256-CTR + Poly1305-AES, алгоритм в restic фиксирован). Сервер Sard управляет бэкапами многих тенантов. Если сервер хранит ключи репозиториев и учётные данные источников, его компрометация раскрывает все бэкапы всех клиентов.

## Решение
**Сервер — управляющая плоскость, а не держатель ключей.** Он решает, когда и какой шаг запустить, и ссылается на репозитории, секреты и скрипты **только по имени**. Их определения и значения живут на хосте агента (`/etc/sard/agent.yaml`):

- `repositories:` — URL restic, `password_file`, `env_file` с учётными данными бэкенда, `crypto_provider`;
- `secrets:` — имя → файл со значением; схемы плагинов содержат ссылки (`password_ref`, `key_ref`), а не значения;
- `scripts:` — allowlist исполняемых файлов для `ACTION_RUN`; сервер не может прислать текст скрипта.

В контракте (`proto/sard/agent/v1/agent.proto`): `RunStep.repository_name` вместо описания репозитория (поля `repository` и `secrets` зарезервированы); `Register` сообщает только имена и метаданные (`RepositoryInfo`, `secret_names`, `script_names`).

Скомпрометированный сервер может запускать и останавливать шаги и видеть метаданные, но не может прочитать бэкапы, узнать учётные данные, перенаправить данные в чужой репозиторий или выполнить произвольный код на хостах.

Исключение (F5, `docs/adr/00XX-draft-self-agent.md`): сервер генерирует и хранит пароль роли `sard_self` — роли только на чтение в его собственной базе — для агента-соседа `sard-self`. Новых прав это не даёт: в эту базу сервер и так ходит суперпользователем. Пароль не передаётся по gRPC; ключи репозиториев по-прежнему только на хостах.

Исключение (F4b, `docs/adr/00XX-draft-f4b-onboarding-self-backup.md`) — **принято владельцем 2026-10-13**: сервер хранит адрес хранилища самобэкапа (`self_backups.location`, без учётных данных: пароль в `user:password@`, токен в адресе http(s) и управляющие символы отклоняются при привязке, 422 `validation_failed` у поля `location`; для адресов, написанных вручную, проверка best-effort — не обнаруживаются неэкранированный `/` в пароле (`user:pa/ss@host`) и имя пользователя sftp, совпадающее со словом бэкенда (`sftp:rest:pw@host`); консоль такой адрес не отправляет, она шлёт адрес, собранный сервером из проверенных параметров) и сам составляет команду `docker compose run -u 0 --cap-add … self-agent repo add …`, которую владелец вставляет в оболочку root на машине самого сервера. Защита от скомпрометированного сервера — только в том, что владелец читает команду перед запуском; консоль показывает рядом с командой подсказку проверить её (Рк19). Проверка значений по наборам знаков (Р29) и одинарные кавычки защищают от ошибок ввода и от инъекции через пользовательский ввод, но не от скомпрометированного сервера: тот может составить любую команду. Идентификатор ключа S3 запрашивается в терминале, секретный ключ читает сам `repo add`, пароль репозитория печатает сам агент по `passwordRevealCommand`; через сервер и gRPC они не проходят. Новых прав это не даёт: сервер и так управляет своей установкой, а владелец исполняет команду своими руками.

`crypto.Provider` в `agent/internal/crypto` отдаёт restic ключ репозитория, не шифруя данные сам:

```go
type Provider interface {
    Name() string
    RepositoryKey(ctx context.Context, repository string) (Key, error) // repository — имя на хосте
}
type Key struct{ Env []string } // окружение процесса restic
```

Реализация `resticAES` строится из `repositories[].password_file` и возвращает `RESTIC_PASSWORD_FILE=<путь>`; файл не читает. Имя репозитория, не настроенного на хосте, — ошибка `ErrUnknownRepository`.

## Оборотная сторона и как продукт её ловит
Если `password_file` есть только на одном хосте и хост погиб, бэкапы этого репозитория **невосстановимы**. Продукт обязан это обнаруживать:

1. **Учёт хранителей ключа.** Агент сообщает в `Register` `RepositoryInfo.repository_id` — id из конфигурации restic-репозитория (не секрет). Сервер считает, сколько агентов могут открыть репозиторий с этим id.
2. **Предупреждение на дашборде**, если ключ есть только у одного агента: «ключ репозитория X существует на одном хосте — потеря хоста сделает бэкапы невосстановимыми».
3. **Проверка восстановления на другом хосте.** Политика по умолчанию — выполнять `ACTION_VERIFY` агентом, отличным от исходного, но с тем же `repository_id`. Успешная проверка доказывает не только целостность данных, но и то, что ключ существует вне исходной машины; для аудита это сильнее проверки на том же хосте. Если такого агента нет, проверка выполняется на исходном хосте, а отчёт помечает её как «ключ на одном хосте».

   **Поправка V1 (2026-10-12, `docs/adr/00XX-draft-agent-role.md`):** запасной вариант «проверка на исходном хосте» отменён. `ACTION_VERIFY` выполняет только агент с ролью `verifier`, источник в нём отказывает. Роль закреплена сертификатом. Признак «один хост» — `machine_id` из `Register`; что делать, если подходящего верификатора нет, решает V4.

Каркас: шов `restic.Repository.ID(ctx)` (заглушка), агент передаёт id в `Register`, если смог его получить; пустой id — «неизвестно». Подсчёт хранителей, предупреждение и выбор агента для проверки — этапы «первый бэкап» и «проверка восстановления».

## Отвергнуто
- **Ключи на сервере** (предыдущая версия контракта: `Repository.password`, `RunStep.secrets`): проще централизованное управление, но компрометация сервера раскрывает все бэкапы всех тенантов.
- **Шифрование в стиле Encrypt/Decrypt поверх restic**: двойное шифрование и потеря дедупликации.

## Отложено
- **ГОСТ.** Алгоритм restic заменить нельзя; ГОСТ потребует шифрования потока до restic (без дедупликации) или собственного формата. Поле `RepositoryInfo.crypto_provider` зарезервировано; отдельный ADR — позже.
- **Эскроу ключей** (резервная копия ключа у доверенного хранителя вне хостов) — возможное дополнение к п. 3, решение позже.
