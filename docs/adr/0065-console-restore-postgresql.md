# 0065 — Восстановление PostgreSQL из консоли (R2b)

- Статус: принято (R2b); решения владельца РВ1–РВ8 — шапка `docs/specs/agent/console-restore.feature`
- Дата: 2026-10-19
- Дополняет: ADR 0060 (восстановление из консоли, R2a), ADR 0008 (сервер не держит ключей), ADR 0027 (плагины), ADR 0051 (плагин postgresql)

## Контекст
R2a восстанавливает только `files`. R2b добавляет снимок базы PostgreSQL → новая база на
целевом агенте: все проверки до изменений, всё или ничего, пароль только в `PGPASSWORD`,
дамп не пишется на диск. Агент не имеет драйвера PostgreSQL (ADR 0051), плагин не вправе
импортировать `agent/internal` (ADR 0027).

## Решение
1. **Где что.** Плагин `postgresql` отвечает за схему (`restore_schema.json`) и разбор
   конфига: `PlanRestore` возвращает `sdk.RestorePlan{Postgres: &sdk.PostgresRestore{…}}`
   (аддитивное поле Apache-2.0 SDK; для плана базы `Destination` и `Paths` пусты). Выполняет
   восстановление движок `internal/consolerestore` (`Engine.RestoreDatabase`), потому что ему
   нужны restic, журнал, классификатор причин и отчёт шага, а плагину они недоступны.
   Выбор — по плану (`plan.Postgres != nil`) в `pluginhost`, без имени плагина в движке.
   Это принятый долг (около 1 900 строк `pg_*.go` в движке). Целевой дизайн: восстановление
   принадлежит плагину `postgresql`, а SDK даёт ему возможности хоста — поток снимка,
   долговечный журнал, секреты и отчёт шага; открытый вопрос OQ-235.
2. **Без драйвера.** Запросы — `psql` из стандартного ввода с переменными psql: имя базы и
   роли подставляет сам psql (`:'name'` — литерал, `:"name"` — идентификатор), SQL из имён
   не строится. Дамп идёт `restic dump` → канал → `pg_restore` (stdin); оглавление читается
   первым `restic dump`, который обрывается (SIGTERM группе) после `pg_restore -l`; для
   восстановления запускается второй. `restic.Repository` получает `Dump`. `conninfo` и среда
   программ (ПГ3, ПГ4) — один код в `agent/plugins/sdk/pgclient` (Apache-2.0, stdlib), им
   пользуются и плагин, и движок; тест следит, что `PGPASSWORD` задаёт только он.
3. **Режим pg_restore (РВ1, ВК28).** `N < restore.postgresql_lock_share × C` → одна
   транзакция; `C = max_locks_per_transaction × (max_connections + max_prepared_transactions)`;
   доля — 0…1, по умолчанию 0.5, вне диапазона агент не стартует (`config.LockShare`
   разбирает YAML и называет настройку). Всё или ничего держится на удалении базы, а не на
   транзакции `pg_restore`.
4. **Журнал отката (ВК27).** `executor.state_dir/pg-restore/<command_id>.json` (0600, запись
   через временный файл, fsync, rename, fsync каталога). Запись — по объектам: имя без OID —
   намерение, с OID — создано, `result` — завершено. Каждое состояние пишется до действия,
   которое оно объявляет. Объект без OID никогда не удаляется по имени (ВК16): при старте он
   попадает в `leftover` с `CLEANUP_FAILED` (РВ6). Исключение внутри одного шага: если psql
   ответил кодом 0 (транзакция глобальных объектов зафиксирована, `CREATE DATABASE`
   выполнен), шаг сам создал объект, и откат узнаёт его OID по имени (`resolveOIDs`) — отмена
   между созданием и чтением OID не оставляет мусора. Окно, которое остаётся: psql умирает
   после отправки COMMIT, но до ответа; роли тогда остаются и не удаляются по имени.
5. **Откат по OID.** Объект с записанным OID удаляется, только если по этому OID сейчас есть
   объект с записанным именем (`DROP DATABASE … WITH (FORCE)`, `DROP ROLE`); переименованный
   или подменённый не трогается и называется в `leftover` с OID; исчезнувший — не остаток.
   Неудавшееся остаётся в записи для следующего старта; запись «одни намерения» исчезает,
   когда результат шага записан в журнал исполнителя (`Engine.Abandon`), завершённая — после
   него же (`Engine.Settle`).
6. **Глобальные объекты (РВ7, ВК26).** Файл `.globals.sql` читается построчно, как пишет
   `pg_dumpall`: `CREATE ROLE`, `ALTER ROLE` начального суперпользователя целевого кластера
   (OID 10) пропускаются; `CREATE TABLESPACE` и существующая роль — отказ до изменений.
   psql исполняет команды с обратной косой чертой в любом месте строки вне кавычек
   (`ALTER ROLE a; \! id`, строка с отступом, `\gexec`), а `\!` исполняет оболочку на хосте
   агента. Правило безопасное по умолчанию: отказ для любой строки с обратной косой чертой,
   кроме точных строк `\restrict <ключ>` и `\unrestrict <ключ>` (ключ — буквы и цифры),
   которые `pg_dump` 2025 года пишет вокруг скрипта. Обратная косая черта в литерале тоже
   отказ, с понятным сообщением: разбирать кавычки psql сложнее и опаснее, чем отказать.
   Другой SQL файла исполняется суперпользователем целевого кластера: это решение хозяина
   восстановления (`restore_globals` и суперпользователь).
7. **Метка кластера (РВ8, ВК29).** Бэкап пишет снимку базы `postgresql.system_identifier`
   из `pg_control_system()`; на PostgreSQL 14, 16 и 18 `EXECUTE` на функцию выдан `PUBLIC`
   (проверено на кластерах), отдельный `GRANT` не нужен. Нет права — метки нет, бэкап идёт.
   Восстановление сравнивает метку с кластером цели и пишет WARN; не отказ.
8. **Сервер (ВК32a, ВК32b).** Реестр `RestorePlugins` — одна запись на плагин: конфиг по
   умолчанию (подключение из копии конфига шага бэкапа снимка, `<база>_restored_<ГГГГММДД>`
   до 63 байт по границе символа), цель, части, `restoreGlobals`, предупреждения
   (`pg_owners_not_restored` или `globals_change_cluster`, `pg_same_cluster` по агенту бэкапа
   и host/port без учёта регистра). Закрывает OQ-234. Секрет, которого нет на агенте, и
   пароль в запросе отклоняет схема агента (`format: sard-secret`, `additionalProperties`).
9. **Подсказка check (Ч28, РВ5)** добавлена и для `PG_CLIENT_MISSING`.

## Поправки (R2c-3, ADR 0066)
- **п. 1 — долг закрыт.** Восстановление базы выполняет плагин `postgresql` через необязательный
  интерфейс SDK `RestoreRunner`; `consolerestore/pg_*.go` и `pluginhost/handler_database.go`
  удалены (R2c-2), `sdk.PostgresRestore` и поле `RestorePlan.Postgres` — тоже (R2c-3). Выбор
  пути — по `RestoreRunner`, а не по `plan.Postgres`. `PlanRestore` плагина только читает
  конфиг; настройки восстановления (подключение, имя базы, глобальные объекты) плагин держит
  у себя. OQ-235 закрыт.
- **п. 2 — `conninfo` и среда программ** живут в пакете `agent/plugins/postgresql/pgclient`
  (AGPL-3.0, stdlib), а не в `agent/plugins/sdk/pgclient`: SDK не знает ни одной базы. Его
  импортирует только плагин; `PGPASSWORD` задаёт только он (тест
  `TestOnlyPgclientPutsThePasswordIntoTheEnvironment`).
- **п. 4 — журнал отката** лежит в `executor.state_dir/restore-journal/<command_id>.json` в
  конверте `{plugin, command_id, entry}` (ADR 0066 п. 3); запись плагина `postgresql` хранит
  те же поля, что запись `pg-restore/`. Прежний путь `pg-restore/` читается один выпуск и
  никогда не пишется.
- **п. 5 — `Engine.Settle`/`Abandon` заменены** удалением записи хостом после записи
  результата; запись с остатком, который ещё нужен, плагин помечает `Retain`
  (`sdk.RestoreError.Retain`, `sdk.Recovery.Retain`), и она остаётся до следующего старта.

## Последствия
- Агент ходит к PostgreSQL процессами `psql` и `pg_restore` от пользователя службы; пароль
  читается из секрета хоста (`PGPASSWORD`), в журнале отката лежит только имя секрета.
- Файл журнала — состояние, которое нужно сохранять вместе с `executor.state_dir`.
- Консоль не знает PostgreSQL: форма, предупреждения и цель приходят от сервера.
