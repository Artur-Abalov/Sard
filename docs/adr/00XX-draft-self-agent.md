# 00XX — Агент-сосед sard-self: образ, права, регистрация (черновик)

- Статус: черновик до слияния F5 (номер — при слиянии, как требует задача); решения владельца на контрольных точках F5 (2026-10-07, 2026-10-08)
- Дата: 2026-10-07
- Дополняет: ADR 0008 (модель доверия), ADR 0014 (локальный CA), ADR 0023
  (повторная регистрация), ADR 0043 (релиз агента), ADR 0045 (сборка один раз)

## Контекст
Sard должен уметь забэкапить сам себя: базу PostgreSQL и каталог CA (D14).
Делает это агент, как и любой другой бэкап. Этот агент живёт в той же
установке compose, что и сервер. Журнал исследования —
`docs/sessions/2026-10-07-f5-sidecar-agent.md`.

## Решение
- **Один образ агента** — `ghcr.io/<owner>/sard-agent`, тот же, что идёт в e2e
  (`deploy/agent/Dockerfile`, раньше `test/e2e/agent/Dockerfile`). Собирается
  из tar.gz `make package` каждой архитектуры. Сборка падает, если tar.gz не
  совпадает с `SHA256SUMS`. Ничего не компилирует (ADR 0045).
  Публикуется в job `image` release.yml рядом с `sard-server`: те же теги,
  amd64 и arm64, после повторной проверки `SHA256SUMS.minisig`. Подписи у
  самого образа нет — как у образа сервера (ADR 0043). Офлайн-архив несёт оба
  образа.
- **Клиента PostgreSQL в образе нет.** Дамп — дело плагина (F1).
- **Сосед работает под uid сервера (10001).** Каталог CA — 0700, файлы — 0600,
  с более широкими правами сервер не стартует (`pki/CaDirectory.kt`). Том
  `sard-pki` подключён к соседу `:ro`. Запись в него невозможна: проверено
  прогоном (touch, дописать, удалить — `Read-only file system`).
  Корневая ФС соседа — `read_only`, `cap_drop: ALL`, `no-new-privileges`.
  Отвергнуто: права группы на CA — меняет поведение сервера и проверку прав.
- **Риск принят: сосед держит ключ CA.** С ним можно выпустить сертификат
  любого агента. Бэкап CA без чтения ключа невозможен. В F6 это будет крупное
  предупреждение в консоли (решение владельца).
- **Роль `sard_self` создаёт миграция Flyway** `V202610071200__self_dump_role.sql`.
  - Права: `pg_read_all_data` (PostgreSQL 14+), никаких прав на запись,
    `CONNECTION LIMIT 4`, сессии по умолчанию только на чтение.
  - У `PUBLIC` отозваны `TEMPORARY` на базу, `CREATE` на `public` и
    `EXECUTE` на функции создания large objects. Это все способы записи,
    которые после `pg_read_all_data` оставались роли без привилегий.
  - Миграция выполняется, только если пользователь сервера — суперпользователь
    (так в compose). Иначе — `WARNING`, и оператор выполняет те же операторы
    вручную.
  - Пароль миграция не задаёт.
  - Проверка: `SelfDumpRoleIntegrationTest` — запись запрещена правами, даже
    если сессия выключила режим только для чтения; то же — psql на стенде.
  - Отвергнуто: скрипты `docker-entrypoint-initdb.d` (только пустой том, не
    обновление существующей установки с выпущенной беты); отдельный сервис psql (лишний сервис, решение
    владельца).
- **Имя `server` всегда в сертификате сервера** в compose: к
  `SARD_PKI_SERVER_NAMES` дописывается `,server`. Первое имя — адрес по
  умолчанию для внешних агентов — не меняется.
- **Конфиг соседа — в образе** (`/etc/sard/self/agent.yaml`), без репозиториев
  (D17). Том `sard-self-config` заполняется из образа при первом подключении.
  Обновление образа его не трогает. Состояние (сертификат, ключ, результаты,
  кэш restic) — в томе `sard-self-state`. Пересоздание контейнера даёт того же
  агента.
- **Канал** — том `sard-self-channel`. Сервер подключает его на запись
  (`SARD_SELF_DIR`), сосед — `:ro` в `/run/sard-self`. Больше его не подключает
  никто. Если `SARD_SELF_DIR` не задан, механизм выключен. Если задан, но
  каталог непригоден, сервер не стартует.
- **Встроенный токен** (`enrollment_tokens.builtin`). Сервер проверяет канал
  при старте и каждые `SARD_SELF_CHECK_INTERVAL` (по умолчанию 15 с).
  - Живого встроенного агента нет: сервер держит в `enroll-token` ровно один
    годный токен со сроком 1 час. Годный значит: активен, до истечения больше
    10 минут, файл есть и его хеш совпадает с базой. Иначе сервер отзывает
    прочие активные встроенные токены и пишет новый (0600, атомарно, без
    перевода строки).
  - Живой встроенный агент есть: сервер удаляет файл.
  - REST API встроенный токен не выпускает и не показывает: список, `GET`
    и отзыв по id отвечают 404.
- **Агент** запускается с `--enroll-token-file`.
  - Если в файле токен, которого нет в маркере `<tls.cert_file>.token-sha256`,
    агент регистрируется по нему в процессе. Существующая идентичность
    заменяется: это случай после отзыва.
  - Без файла и без идентичности агент ждёт.
  - Файл агент не удаляет — том подключён только на чтение. Файл удаляет
    сервер.
- **Встроенный агент** (`agents.builtin`) — не более одного живого на тенант,
  это держит уникальный частичный индекс.
  - Удалить его нельзя: удаления агентов нет вообще.
  - Отзыв — только с `confirm=sard-self`, иначе `409
    self_agent_confirmation_required`. Повторный отзыв отозванного отвечает
    200.
  - После отзыва сервер выпускает новый токен, и сосед регистрируется сам
    (решение владельца 7).
  - Пакет `selfagent` — лист: от него не зависит никто (`ArchitectureTest`).
- **Пароль роли `sard_self` генерирует и хранит сервер** (решение владельца
  2026-10-07, вариант а′). Файловые секреты Compose вне Swarm не применяют
  `uid`/`mode`: проверено прогоном, файл 0600 с хоста соседу под uid 10001 не
  читается.
  - При старте сервер создаёт `db-password` (64 hex, 0600), если файла нет или
    он испорчен.
  - При каждом старте сервер задаёт пароль роли через SCRAM на стороне клиента
    (`PGConnection.alterUserPassword`). Открытого пароля нет ни в SQL, ни в
    журнале PostgreSQL, ни в логах сервера.
  - Агент объявляет файл секретом `sard-db`. Проверка прав секрета проходит:
    у сервера и соседа один uid.

## Граница доверия (уточняет ADR 0008)

ADR 0008: сервер не держит ключей и учётных данных хостов. F5 вводит одно
исключение, и оно ничего не расширяет:

- **Один открытый секрет на сервере.** Это пароль роли `sard_self` — роли
  только на чтение в собственной базе сервера. В эту базу сервер и так
  ходит суперпользователем, так что, украв пароль, скомпрометированный
  сервер не получает ничего нового.
- **Пароль не идёт по gRPC** и не попадает в REST. Агент читает его как
  локальный файл секрета.
- **Ключи репозитория самобэкапа остаются на хосте соседа**, в его конфиге
  (D17, F6). Сервер их не видит.
- **Утечка тома канала** даёт одноразовый токен, годный не дольше часа и
  только пока встроенного агента нет. Ещё она даёт чтение базы. Ни записи в
  базу, ни ключа CA в канале нет.
- **Ключ CA читает сам сосед** через том `sard-pki:ro`, не через сервер. Это
  принятый риск (см. выше).
