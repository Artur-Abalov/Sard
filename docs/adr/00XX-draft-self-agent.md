# 00XX — Агент-сосед sard-self: образ, права, регистрация (черновик)

- Статус: черновик; решения владельца на контрольной точке 1 F5 (2026-10-07)
- Дата: 2026-10-07
- Дополняет: ADR 0008 (модель доверия), ADR 0014 (локальный CA), ADR 0023
  (повторная регистрация), ADR 0043 (релиз агента), ADR 0045 (сборка один раз)

## Контекст
Sard должен уметь забэкапить сам себя: базу PostgreSQL и каталог CA (D14).
Делает это агент, как и любой другой бэкап. Этот агент живёт в той же
установке compose, что и сервер. Журнал исследования —
`docs/sessions/2026-10-07-f5-sidecar-agent.md`.

## Решение
- **Один образ агента** — `ghcr.io/<owner>/sard-agent`, тот же, что идёт в e2e
  (`deploy/agent/Dockerfile`, раньше `test/e2e/agent/Dockerfile`). Собирается
  из tar.gz `make package` каждой архитектуры. Сборка падает, если tar.gz не
  совпадает с `SHA256SUMS`. Ничего не компилирует (ADR 0045).
  Публикуется в job `image` release.yml рядом с `sard-server`: те же теги,
  amd64 и arm64, после повторной проверки `SHA256SUMS.minisig`. Подписи у
  самого образа нет — как у образа сервера (ADR 0043). Офлайн-архив несёт оба
  образа.
- **Клиента PostgreSQL в образе нет.** Дамп — дело плагина (F1).
- **Сосед работает под uid сервера (10001).** Каталог CA — 0700, файлы — 0600,
  с более широкими правами сервер не стартует (`pki/CaDirectory.kt`). Том
  `sard-pki` подключён к соседу `:ro`. Запись в него невозможна: проверено
  прогоном (touch, дописать, удалить — `Read-only file system`).
  Корневая ФС соседа — `read_only`, `cap_drop: ALL`, `no-new-privileges`.
  Отвергнуто: права группы на CA — меняет поведение сервера и проверку прав.
- **Риск принят: сосед держит ключ CA.** С ним можно выпустить сертификат
  любого агента. Бэкап CA без чтения ключа невозможен. В F6 это будет крупное
  предупреждение в консоли (решение владельца).
- **Роль `sard_self` создаёт миграция Flyway** `V202610071200__self_dump_role.sql`.
  - Права: `pg_read_all_data` (PostgreSQL 14+), никаких прав на запись,
    `CONNECTION LIMIT 4`, сессии по умолчанию только на чтение.
  - У `PUBLIC` отозваны `TEMPORARY` на базу, `CREATE` на `public` и
    `EXECUTE` на функции создания large objects. Это все способы записи,
    которые после `pg_read_all_data` оставались роли без привилегий.
  - Миграция выполняется, только если пользователь сервера — суперпользователь
    (так в compose). Иначе — `WARNING`, и оператор выполняет те же операторы
    вручную.
  - Пароль миграция не задаёт.
  - Проверка: `SelfDumpRoleIntegrationTest` — запись запрещена правами, даже
    если сессия выключила режим только для чтения; то же — psql на стенде.
  - Отвергнуто: скрипты `docker-entrypoint-initdb.d` (только пустой том, не
    обновление с 0.0.1-rc1); отдельный сервис psql (лишний сервис, решение
    владельца).
- **Имя `server` всегда в сертификате сервера** в compose: к
  `SARD_PKI_SERVER_NAMES` дописывается `,server`. Первое имя — адрес по
  умолчанию для внешних агентов — не меняется.
- **Конфиг соседа — в образе** (`/etc/sard/self/agent.yaml`), без репозиториев
  (D17). Том `sard-self-config` заполняется из образа при первом подключении.
  Обновление образа его не трогает. Состояние (сертификат, ключ, результаты,
  кэш restic) — в томе `sard-self-state`. Пересоздание контейнера даёт того же
  агента.
- **Канал токена** (контрольная точка 1, фаза 3): общий том сервера и соседа.
  - Сервер, если у него нет живого встроенного агента, пишет в том одноразовый
    токен вида `self` с коротким сроком. Файл 0600, uid 10001.
  - Агент без сертификата ждёт этот файл, регистрируется по нему и удаляет его.
  - Через API такой токен не выпустить, в списке токенов его не видно.
  - После отзыва `sard-self` сервер сам выпускает новый токен, и сосед
    регистрируется заново.
- **Пароль роли** — открыт, см. журнал фазы 2. Файловые секреты Compose вне
  Swarm не применяют `uid`/`mode`: проверено прогоном, файл 0600 с хоста
  соседу под uid 10001 не читается.
