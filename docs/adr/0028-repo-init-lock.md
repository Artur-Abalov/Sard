# 0028 — Блокировка `sard-agent repo init` в `restic.cache_dir`

- Статус: предложено (решение владельца 2026-09-30; текст ждёт утверждения)
- Дата: 2026-09-30

## Контекст
A5b, решение владельца В8 (`docs/specs/agent/repo-init.feature`): один
репозиторий на хосте инициализирует одна команда; второй одновременный
`repo init` того же репозитория отказывает до обращения к бэкенду с причиной
`INIT_IN_PROGRESS` (код 6). Первая реализация
(`agent/internal/repoinit/lock.go`) кладёт файл блокировки
`.sard-init-<имя>.lock` рядом с файлом пароля, а неудачу его создания
относит к `PASSWORD_FILE_WRITE` (код 7).

Побочный эффект: `repo init` с уже существующим файлом пароля, который ничего
в каталог файла пароля не пишет, всё равно требует права записи в этот
каталог. Типичная раскладка — файл пароля пользователя службы в каталоге
`/etc/sard`, принадлежащем root, — даёт отказ `PASSWORD_FILE_WRITE`, хотя файл
пароля не создаётся; причина вводит оператора в заблуждение.

## Решение
- Файл блокировки — `<restic.cache_dir>/.sard-init-<имя>.lock`; имя
  репозитория экранировано как сегмент пути. `restic.cache_dir` по умолчанию —
  `/var/cache/sard/restic` (`restic.DefaultCacheDir`, ADR 0017). Механизм не
  меняется: неблокирующий `flock(2)`, файл удаляется при завершении команды;
  файл, оставшийся после аварийного завершения, повтору не мешает.
- Неудача создания файла блокировки — своя причина `LOCK_WRITE`. Сообщение
  называет ключ `restic.cache_dir`, путь и причину ОС.
- Класс `LOCK_WRITE` — «запись», код 7 (ADR 0025, раздел A2b). В A2b этот
  класс означает, что хост не даёт записать файл, нужный команде; `enroll`
  уже относит к нему неудачу создания своего файла блокировки
  (`agent/internal/enroll/lock.go`). Не «использование» — флаги и конфиг
  верны; не «временная» — повтор без действия оператора не поможет; не
  «ошибка агента» — агент исправен. Новых номеров кодов нет.
- `repo init` каталог `restic.cache_dir` не создаёт. Агент нигде не создаёт
  этот каталог: для пакета его создаёт systemd (`CacheDirectory=sard/restic`,
  ADR 0018), для другого пути — оператор (вместе с `ReadWritePaths=`). Так же
  `repo init` не создаёт каталог файла пароля (В1). Нет каталога, он
  недоступен на запись или это не каталог — `LOCK_WRITE`.
- Место проверки в порядке `repo init` не меняется: после проверки restic,
  до генерации пароля и до обращения к бэкенду. При `LOCK_WRITE` файл пароля
  не создаётся.
- `repo list` блокировку не берёт и от `restic.cache_dir` в этой части не
  зависит (Л2).
- Раздел A5b ADR 0025 (строка кода 7 таблицы `repo init`: «файл блокировки
  рядом с ним») уточняется этим ADR: код 7 — `PASSWORD_FILE_WRITE` или
  `LOCK_WRITE`.

## Оборотная сторона
- `repo init` требует существующего и доступного на запись
  `restic.cache_dir`. На хосте с пакетом каталог появляется при первом старте
  службы; до него `repo init` отказывает с `LOCK_WRITE`. Документация
  (`docs/operations/repo-init.md`) говорит об этом.
- Взаимное исключение действует между командами с одним `restic.cache_dir`:
  два конфига с разными `cache_dir` и одним именем репозитория друг друга не
  видят (раньше разделяющим был каталог файла пароля). Одновременный init
  одного адреса с разных хостов по-прежнему забота restic.
- Файл блокировки, оставшийся после `SIGKILL` команды, запущенной от root,
  принадлежит root; следующая команда от пользователя службы получит
  `LOCK_WRITE` с путём файла, и оператор удаляет его вручную.

## Отвергнуто
- **Рядом с файлом пароля** (первая реализация) — требует записи туда, где
  команда ничего не пишет; см. «Контекст».
- **`/tmp`, `/run/lock`** — общедоступные каталоги: чужой пользователь может
  заранее создать файл блокировки; у службы `PrivateTmp=true`, её `/tmp`
  отличается от `/tmp` оператора.
- **`executor.state_dir`** (`/var/lib/sard-agent/executor`) — хранилище
  результатов исполнителя со своей раскладкой; `repo init` к исполнителю не
  относится.
- **Создавать `restic.cache_dir`, если его нет** — агент этот каталог нигде
  не создаёт; созданный от имени оператора (часто root) каталог получил бы не
  того владельца, и служба потом не смогла бы писать в кэш.
