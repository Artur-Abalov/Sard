# 00XX — Роль агента в сертификате и идентификатор машины (черновик)

- Статус: черновик до слияния V1 (номер присваивается при слиянии); решения
  владельца на контрольных точках V1 (2026-10-12, 2026-10-14)
- Дата: 2026-10-14
- Дополняет: ADR 0008 (модель доверия, п. 3), ADR 0009 (перехватчик S3),
  ADR 0014 (локальный CA), ADR 0025 (таблица `Register`)

## Контекст
Проверка восстановления (M3) выполняется отдельным агентом-верификатором.
Верификатор не должен исполнять бэкапы и скрипты, а источник — проверки, даже
если сервер захвачен или агент подменил свои сообщения. Чтобы сервер не
проверял источник на том же хосте, ему нужен признак «одна машина», который
не раскрывает сам machine-id. Исследование, решения и ход работы —
`docs/sessions/2026-10-12-v1-agent-role.md`; спецификации —
`docs/specs/{server,agent,web}/agent-role.feature`.

## Решение

### Роль
- Ролей две: `source` выполняет `ACTION_BACKUP`, `ACTION_RESTORE` и
  `ACTION_RUN`, `verifier` — только `ACTION_VERIFY`.
- Роль задаёт **токен регистрации** (`enrollment_tokens.role`, REST
  `role`: по умолчанию и при `null` — `source`). Встроенный токен sard-self —
  всегда `source` (CHECK в БД у токенов и у агентов).
- Роль записывается в сертификат **вторым URI в subjectAltName**:
  `sard://roles/source` или `sard://roles/verifier`, рядом с URI личности
  `sard://tenants/<t>/agents/<a>` (ADR 0014). В тот же момент, в той же
  транзакции, она пишется в `agents.role`. Из CSR сервер по-прежнему берёт
  только ключ: SAN, расширения и subject CSR роль не задают.
- **Правило URI роли** одно для сервера и агента: URI роли — любой URI SAN со
  схемой `sard` и хостом `roles` (схема и хост без учёта регистра, RFC 3986).
  Нет URI роли — `CERT_ROLE_MISSING`. Значение не равно ровно одной из двух
  строк, или URI роли больше одного — `CERT_ROLE_INVALID`. Порядок имён в SAN
  не важен. Обе реализации (`server/.../pki/AgentRoleUri.kt`,
  `agent/internal/identity`) проверяются на одном файле векторов
  `test/vectors/agent-role-uri.tsv`.
- **Роль неизменна.** Ни в одном сообщении агента поля роли нет. Ни один вызов
  API её не меняет. Сменить роль можно только новой регистрацией: появится
  новый агент, старый останется как был.

### Где роль соблюдается
- **S3** (ADR 0009) сверяет роль сертификата с `agents.role`. Если они
  расходятся — `CERT_IDENTITY_MISMATCH`: роль — часть личности.
- **Сервер.** Источник привязывается только к агенту-источнику: REST POST и
  PUT источника — 422 `agent_role_mismatch` у поля `agentId`; запуск — 409;
  срабатывание расписания записывается как `refused` с той же причиной.
  `StepDispatcher` вдобавок не отправляет действие, которое роль не допускает:
  шаг завершается failed «agent role mismatch» (защита в глубину; без правки
  БД руками недостижимо).
- **Агент** читает роль из своего сертификата при старте. Без допустимой роли
  он не стартует (код 1, строка отказа с причиной, ключом `tls.cert_file`,
  путём и `sard-agent enroll --force`). Проверка роли — первая проверка
  принятого `RunStep`. Чужое действие получает `STEP_STATUS_REJECTED` и
  `StepResult.reject_reason = REJECT_REASON_ROLE_MISMATCH`, даже если его
  прислал подменённый сервер. Сервер `reject_reason` не читает: поле только
  поясняет отказ.
- `sard-agent status` — офлайн: печатает agent_id, tenant_id, роль и срок
  сертификата; читает только конфиг и сертификат.
- Консоль показывает роль токенов и агентов. В форме источника она не
  предлагает верификаторов и не показывает кнопку «Создать источник» на
  карточке верификатора. Это удобство (как с отозванными агентами, П6);
  решает сервер.

### Идентификатор машины
- Агент отправляет в каждом `Register` поле `machine_id` (proto, поле 10):
  `hex(HMAC-SHA256(ключ = "sard-machine-id/v1" ‖ tenant_id, данные = сырой id))`.
  Сырой machine-id никуда не уходит. Соль тенанта не даёт сопоставить машины
  между тенантами и установками.
- Источник сырого id по порядку: `/etc/machine-id`, `/var/lib/dbus/machine-id`.
  Если оба пусты или отсутствуют, агент один раз генерирует 32 случайных байта
  и хранит их в `<executor.state_dir>/machine-id` (0600, каталог 0700). Если
  источник есть, но не читается, или файл состояния испорчен — агент не
  стартует (код 1), значение заново не генерируется.
- Сервер требует ровно 64 строчных hex-символа (`FIELD_INVALID`,
  `field=machine_id`, ADR 0025; CHECK в БД), хранит значение в
  `agents.machine_id`, перезаписывает каждым `Register` и не логирует. В REST
  и консоли его нет. Агенты одной машины находятся через
  `fleet/MachineAgents.withMachineId`; признак «один хост» использует V4.
- `machine_id` сообщает сам агент, поэтому это сигнал, а не доказательство.
  Слепые зоны для V4: контейнеры без `/etc/machine-id` (sard-self, e2e)
  получают разные случайные id даже на одной физической машине;
  клонированные ВМ — одинаковые. Если `/etc/machine-id` появится позже, id
  сменится.

### Требование к C1 (продление сертификата)
- `RenewCertificate` выпускает сертификат с ролью из `agents.role`
  (`AgentPrincipal.role`), а не из CSR.
- Агент проверяет роль нового сертификата и не подменяет им текущий, если роль
  отличается от той, с которой он работает. Сейчас роль читается только при
  старте.

## Отвергнуто
- **Собственное расширение X.509 с OID `2.25.<UUID>`.** Первоначально
  утверждено, но `x509.ParseCertificate` в Go отвергает сертификат с дугой
  OID ≥ 2³¹ («x509: malformed extension OID field»), а в дуге `2.25` число
  128-битное. Проверено на сертификате openssl. Номер IANA PEN потребовал бы
  ждать регистрации.
- **Роль в CSR, `Register` или конфиге агента.** Агент выбирал бы роль сам.
- **Роль по умолчанию, если её нет в сертификате.** Релизов не было
  (решение владельца: без обратной совместимости). Сертификат без роли
  отклоняется, агенты до V1 регистрируются заново.
- **Сырой `/etc/machine-id`.** Он сопоставим между установками и раскрывает
  идентификатор хоста.
- **Фильтр `GET /agents?role=` сейчас.** Отложен до V2, где он нужен серверу;
  консоль фильтрует список сама.
