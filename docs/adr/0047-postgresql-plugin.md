# 0047 — Плагин postgresql (F1): решения на стороне агента

- Статус: принято (решения ПГ1–ПГ22 и ПГ17a–ПГ17j утверждены владельцем 2026-10-07)
- Дата: 2026-10-07
- Связано: ADR 0008 (сервер не хранит ключи и секреты), ADR 0017 (restic в составе агента), ADR 0027 (SDK плагинов), ADR 0029 (плагин files), ADR 0033 (маскирование логов), спецификация `docs/specs/agent/postgresql-plugin.feature`, документация `docs/plugins/postgresql.md`

## Контекст

F1 — первый плагин базы данных и первый плагин с секретом. Спецификация
фиксирует поведение; здесь записано то, что она оставляет реализации и что
меняет в общих частях агента и SDK.

## Решение

1. **Без драйвера PostgreSQL (ПГ1).** Правило 7 разрешает агенту только stdlib,
   gRPC, protobuf, YAML и валидатор схем. Подключение, пароль, версию сервера
   и роль плагин проверяет запуском `psql` с хоста, одним запросом
   (`server_version_num`, `rolsuper`, членство в `pg_read_all_data`, роль; роль
   последняя в строке, она может содержать `|`). `to_regrole` оставляет запрос
   верным на сервере без `pg_read_all_data`: версия проверяется до прав.
2. **Свой запуск процессов в плагине.** Встроенные плагины могут импортировать
   только SDK (`plugins/imports_test.go`), поэтому плагин не берёт
   `internal/restic.ProcessExecutor`, а содержит собственный `ProcessRunner`
   (группа процессов, SIGTERM, через 10 с SIGKILL, добивание группы после
   выхода) за интерфейсом `Runner`. Это копия ~40 строк; общий пакет,
   видимый плагинам, потребовал бы менять правило импортов, а оно защищает
   границу лицензий. Условие пересмотра: третий потребитель (плагин MySQL).
3. **Пароль — `PGPASSWORD` процесса (ПГ3), параметры — строка conninfo (ПГ4).**
   Окружение дочерних процессов — окружение агента без `PG*`, `LC_ALL` и
   `LC_MESSAGES`, плюс `LC_MESSAGES=C` и пароль; `HOME` и `PATH` остаются (libpq
   читает `~/.postgresql/root.crt`). Версия `--version` пароля не получает.
4. **`sdk.Dump.Tags` и `sdk.Dump.Extra` (ПГ11, ПГ17a).** Аддитивные поля
   Apache-2.0 SDK. Метки пишутся как `<плагин>.<ключ>=<значение>` после меток
   шага; совпадение с меткой шага — ошибка до restic. Дополнительные файлы
   сохраняются отдельными снимками `restic backup --stdin` после успешного
   основного; метки у них — метки шага, метки файла и
   `<плагин>.main_snapshot=<id>` (метки `Dump.Tags` основного снимка в них не
   входят). Итог — основной снимок и репозиторий, байты `TotalBytes`,
   `AddedBytes`, `AddedBytesRaw` — суммы. Сбой дополнительного файла после
   основного снимка возвращает итог основного (как снимок с нечитаемыми
   файлами в A6b) и ошибку, называющую файл. Прогресс дополнительных
   снимков не сообщается: счётчик байт загрузки не должен убывать.
5. **Сбой потока плагина не приписывается репозиторию.** `Source.Backup`
   запоминает ошибку `Plugin.Stream`; если restic вернул её же (restic
   оборачивает ошибку потока), ошибка не получает приставки
   `repository "R":` (как ошибка запроса в ADR 0029, п. 2). Сбой restic во
   время записи потока по-прежнему называет репозиторий.
6. **Передача результата Prepare в Dump.** `sdk.Plugin` не даёт состояния шага,
   а Dump должен знать версии из PREPARING (они идут в метки). Результат лежит
   в пакетной `sync.Map` по ключу `sdk.Host` (у каждого шага свой указатель) и
   забирается `LoadAndDelete` в Dump, который вызывается сразу после Prepare:
   запись не переживает шаг. Dump снимает запись раньше любой другой проверки. Это
   теперь контракт SDK (`Plugin`: один `Host` на шаг, Dump после каждого успешного
   Prepare), закреплённый тестами `TestOneStepHasOneHostAndTwoStepsTwo` и
   `TestDumpFollowsASuccessfulPrepareOfACancelledStep` в `pluginhost`. Пути инструментов Dump и Stream находят заново
   (только `stat`), версии заново не спрашивают.
7. **Проверка целостности (ПГ10).** `archive` держит первые 5 байт, пока не
   увидит `PGDMP`; в restic уходит только архив. Любое расхождение останавливает
   `pg_dump` (отмена контекста запуска) и возвращает ошибку из `Stream`, а
   механизм A6a останавливает restic до EOF. Ошибка записи в restic тоже
   останавливает `pg_dump`: иначе он завис бы на заполненной трубе.
8. **Глобальные объекты в памяти (ПГ17d).** `pg_dumpall` в `limited`
   до 64 МиБ; превышение отменяет запуск. Содержимое не пишется в лог.
9. **`include_globals` по умолчанию true, `globals_role_passwords` false
   (ПГ17b, ПГ17c).** `--no-role-passwords` по умолчанию; хэши — явный выбор
   администратора, для него нужен суперпользователь, иначе FAILED в PREPARING.
   Проверка делается только при включённых глобальных объектах: без них
   `globals_role_passwords` ничего не меняет.
10. **Правило «2–4 поля» снято.** `TestEveryConfigSchemaIsValidJSONSchema`
    требовал от схемы плагина 2–4 поля (наследие заглушек); у postgresql полей
    двенадцать по спецификации (ПГ6). Нижняя граница сохранена.
11. **Упаковка (ПГ21).** `deploy/agent/nfpm.yaml`: `Suggests: postgresql-client`
    у deb и `postgresql` у rpm через `overrides`; жёсткой зависимости нет.
    `scripts/package-agent.sh` проверяет метаданные deb (и rpm, если есть
    `rpm`).

## Оборотная сторона

- Сообщения libpq и `pg_dump` цитируются как есть: тесты и документация
  привязаны к их формулировкам (`LC_MESSAGES=C`). Файлы `testdata/` сняты с
  PostgreSQL 16.15; спецификация требует снимков с 14 и 18, их снять не
  удалось (в окружении сборки нет этих версий и Docker) — сценарии e2e на 14 и
  18 проверят формулировки на настоящих серверах.
- Окно, описанное в ADR 0027 («Оборотная сторона»): сбой потока после
  последнего байта, но до того, как restic прочитал EOF, не оставляет снимка
  только благодаря SIGTERM; принято.
- Глобальные объекты лежат во втором снимке, который сервер не знает (ПГ17j):
  удержание обязано удалять пару вместе, пока этого нет, `restic forget`
  по путям удерживает их по одной политике раздельно.
- Результат Prepare живёт в пакетной переменной по ключу `sdk.Host`: ключ
  обязан быть сравнимым значением (так и есть у `*host`); плагин, вызванный
  другим хостом с несравнимым ключом, вызвал бы панику.
- Копия запуска процессов (п. 2) расходится с `restic.ProcessExecutor` при
  правках одного из них.
- Таблицы без права `SELECT` обнаруживает сам `pg_dump`, уже в UPLOADING
  (ПГ2): отступление от буквы правила 6 принято владельцем.
