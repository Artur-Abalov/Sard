# 00XX — Сроки хранения и фоновая уборка сервера (H1, фаза 2)

- Статус: черновик (H1, фазы 2 и 3: метрики и страница оператора готовы); решения владельца 2026-10-21 — шапка `docs/specs/server/server-retention.feature`, ответы В1–В11
- Дата: 2026-10-21
- Дополняет: ADR 0013 (правило 3 отменено для `runs`, `run_steps`, `restore_verifications`; срок логов; 11-й вызов `system`), ADR 0041 (OQ-048 закрыт), ADR 0042 (OQ-071 закрыт: доставки удаляются)

## Контекст
База сервера росла без предела: у `runs`, `run_steps`, `restore_verifications`, журнала
срабатываний и `notification_deliveries` не было пути удаления, а удаление секций
`step_logs` было записано как «не сделано» (OQ-048). Правило 3 ADR 0013 объявляло историю
запусков доказательством для аудита и запрещало удаление. Внешние ключи в миграциях
без `ON DELETE` (`NO ACTION`), поэтому удалять можно только снизу вверх.

## Решение
1. **Правило 3 ADR 0013 отменено** для `runs`, `run_steps` и `restore_verifications`. Строки
   этих таблиц удаляются по сроку (пункт 3) и по правилам «никогда» (пункт 4). `snapshots`
   уборка не трогает никогда: ни строки, ни `forgotten_at`.
2. **Свойство логов переименовано и сокращено:** вместо `sard.logs.retention` (90 дней, ADR 0013,
   OQ-048) — `sard.retention.step-logs` = 30 дней. Фактический срок логов 30–61 день, потому что
   секция месячная и уходит целиком, когда её верхняя граница (первое число следующего месяца,
   00:00 UTC) не позже границы срока. Строки `step_logs` не удаляются `DELETE`. Строка лога
   может прийти позже `finished_at` шага: она ложится в секцию месяца получения.
3. **Сроки глобальные, свойства `sard.retention.*`:** `step-logs` 30d, `runs` 180d (запуски
   backup, restore, verify любого итога), `verifications` 180d (записи V4), `schedule-fires`
   180d, `notification-deliveries` 30d, `interval` 1h, `batch-size` 500. При старте все
   положительные, сроки доставок, запусков и срабатываний строго больше `sard.notify.ttl` (R1):
   удалённые уборкой доставка, запуск или срабатывание внутри окна `ttl` планировщик
   уведомлений создал бы заново. Соотношение сроков запусков и логов
   не проверяется. Отметка времени: `runs.finished_at`, `restore_verifications.verified_at`,
   `schedule_fires.recorded_at`, `notification_deliveries.created_at`; строка старше срока,
   если её отметка строго раньше `сейчас − срок`; доставка в `pending` не удаляется.
4. **Не удаляется никогда:** запуск, у шага которого есть строка в `snapshots` (любой статус,
   в том числе потерянный шаг с поздним результатом); последний успешный запуск источника
   каждого вида (backup, restore, verify; по `finished_at`, и для мягко удалённого источника);
   активный запуск; запуск, на который или на чей шаг ссылается строка, ещё не удалённая по
   своему правилу (`step_logs`, `restore_verifications.step_id`, `verification_jobs.run_id`,
   `schedule_fires.run_id`, `notification_deliveries.run_id`, `overdue_episodes.closed_by_run_id`);
   последняя успешная и последняя неуспешная (любой статус кроме `passed`) проверка источника;
   проверка с открытым заданием; открытый эпизод устаревания и закрытый эпизод, закрытый
   проверкой, которая хранится всегда. Правила считаются внутри тенанта.
5. **Порядок снизу вверх:** секции `step_logs` → доставки → срабатывания расписания (строки
   простоя с `catch_up_fire_id` раньше догоняющего срабатывания) → закрытые эпизоды устаревания,
   записи проверок и их задания → шаги и запуски. Запуск уходит в том же проходе, что и его
   последняя ссылка, если та ушла раньше по порядку, иначе в следующем.
6. **Цикл — свой `SmartLifecycle`** (`RetentionLoop`, образец `StepLogPartitions`): первый проход
   через `interval` после старта, один поток, ошибка не останавливает цикл. Часы внедряются.
   Проход удаляет всё подходящее пачками по `batch-size`, лимита на тик нет. Пачка — один
   оператор SQL: `DELETE … WHERE id IN (select … FOR UPDATE SKIP LOCKED LIMIT N)` либо
   `WITH picked AS (… FOR UPDATE … SKIP LOCKED) DELETE … ` для связанных таблиц: внешние ключи
   `NO ACTION` проверяются в конце оператора, поэтому родитель и ссылающиеся на него строки
   уходят вместе. Каждая пачка — транзакция тенанта (`inTenant`) с `tenant_id` в каждом
   запросе (правило 8 ADR 0013, `ArchitectureTest`). Консультативной блокировки нет: второй
   экземпляр пропускает строки, занятые первым.
7. **11-й вызов `TenantSessions.system`:** `RetentionPass.run` читает список тенантов
   (`select id from tenants`), как `VerificationLoop`. Удаление идёт в `inTenant` тенанта строки.
   Файл `retention/RetentionPass.kt` добавлен в список `ArchitectureTest` и в ADR 0013.
8. **Секции** удаляются `DROP TABLE` по одной в транзакции с `lock_timeout` = 2 с и
   `LOCK TABLE step_logs IN SHARE UPDATE EXCLUSIVE MODE` (два экземпляра не удаляют и не считают
   одну секцию дважды). `DROP` секции берёт `ACCESS EXCLUSIVE` и на родителя `step_logs`, поэтому
   запись логов может встать не более чем на `lock_timeout` = 2 с, пока `DROP` ждёт читателя
   секции (решение владельца F2, вариант b). Тест утверждает: запись завершается без ошибки не позже
   чем через `lock_timeout` + 1 с, создание запуска не ждёт, `DROP` падает с SQLSTATE 55P03
   (1994 мс — наблюдение одного прогона, не утверждение). Теоретически худший случай —
   ожидание на родителе плюс ожидание на секции, то есть до двух `lock_timeout`. Не получивший блокировку `DROP` падает, в журнал идёт `ERROR` с
   именем секции, классом исключения и `lock_timeout`, без текста сообщения (текст строк лога в
   журнал не попадает); остальные типы удаляются, секция уходит следующим проходом.
   `DROP` и `LOCK` секций `step_logs` — единственные запросы уборки к таблице тенанта без `tenant_id`: секции
   общие для всех тенантов (ADR 0013).
9. **Наблюдаемость:** одна строка `INFO` на проход (`Retention pass deleted step_log_partition=N
   notification_delivery=N schedule_fire=N restore_verification=N verification_job=N run_step=N
   run=N`), счётчик Micrometer с тегом `kind` (имя и значения в `RetentionKind.kt`). Ошибка прохода —
   `ERROR` с классом исключения; уже зафиксированные пачки остаются, следующий тик начинает заново.
   Метрика отдаётся слушателем Prometheus (`00XX-draft-metrics-prometheus.md`, имя
   `sard_retention_deleted_total{kind}`), страница оператора — `docs/operator/15-data-retention.md`.
10. **Чтение удалённого лога** не меняется: шаг без строк лога отдаёт 200, пустой `items`,
    `hasMore` false, `nextAfterSeq` равным `afterSeq`, прежний `truncated`; пометки об удалении
    по сроку нет (В2). Удалённый запуск — 404 `not_found`.

## Известные ограничения
- **В9.** Поздний результат успешного бэкапа для шага в `lost`, запуск которого уже удалён
  уборкой, получает ack без записи: снимок из репозитория не попадает в `snapshots`. Запуск
  со снимком от позднего результата, пришедшего до уборки, хранится вечно.
- **Закрытые эпизоды устаревания без `closed_by_id`** (эпизод закрыт потерей проверки или
  источника) и таблица `overdue_episodes` уборкой не охвачены: спецификация о них молчит.
- **R1.** `sard.retention.runs` и `sard.retention.schedule-fires` строго больше `sard.notify.ttl`
  (проверка при старте, как у доставок).
- **R2.** `run_steps` удаляются без `SKIP LOCKED`: шаг, строку которого держит транзакция
  позднего результата агента, заставляет пачку ждать её; уборка тенанта может отложиться на
  один проход.
- **R3.** Индексы миграции построены без `CONCURRENTLY`: на очень большой установке они
  блокируют запись в таблицы на время построения.
- `DROP` секции ждёт читателей не дольше `lock_timeout` = 2 с, и запись логов всех тенантов
  ждёт вместе с ним (пункт 8).

## Требование к L1
Пока строка `snapshots` жива, её запуск и шаги хранятся вечно. Когда L1 забывает снимок
(`forget`), он обязан сделать запуск этого снимка доступным уборке: удалить его или пометить
так, чтобы правило «запуск со снимком» на него больше не действовало. Без этого таблица
`runs` растёт на каждый бэкап. `snapshots.forgotten_at` сегодня не ставит никто.

## Отвергнуто
- **Вечное хранение записей проверок.** Таблица растёт на источник в сутки без предела;
  доказательством служат последняя успешная и последняя неуспешная проверка источника.
- **Обнуление `closed_by_id` вместо удаления эпизодов.** Эпизод остался бы с потерянной
  причиной закрытия; ХР10a удаляет закрытый эпизод вместе с проверкой, которая его закрыла.
- **Консультативная блокировка прохода.** Серьёзно ограничила бы одним экземпляром и не
  нужна: `SKIP LOCKED` делит работу между экземплярами без двойного удаления.
- **`DETACH PARTITION CONCURRENTLY` + `DROP`.** Не блокировал бы запись логов, но вне транзакции,
  с `FINALIZE` после обрыва и гонкой экземпляров — сложность не оправдана при ожидании до 2 с.
  Вернуться к нему, если ожидание записи логов начнёт вылезать на практике (жалобы, метрика
  задержки записи).
- **`DELETE` строк логов по сроку.** Вакуум и раздутие; секция уходит целиком.
- **Срок по тенантам.** Секции логов общие для всех тенантов (ADR 0013), владелец выбрал
  глобальные сроки.
- **Лимит строк на тик.** Проход удаляет всё подходящее: иначе после долгого простоя уборка
  не догоняла бы приток.

## Последствия
- Консоль и REST не меняются; запрос удалённого запуска и его лога — 404.
- Индексы под запросы уборки: миграция `V202610211200__retention_indexes.sql`.
- Для оператора: срок логов 30 вместо 90 дней, уход запусков без снимка через 180 дней,
  вечные снимки и последние успехи. Документация оператора — `docs/operator/15-data-retention.md`, проверяется
  `MonitoringDocsTest` (сроки и переменные совпадают с умолчаниями `RetentionProperties`).
