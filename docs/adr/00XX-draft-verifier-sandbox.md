# 00XX — Верификатор: конвейер проверки и песочница

- Статус: черновик (V5; решения владельца 2026-10-25, `docs/sessions/2026-10-25-v5-verifier.md`)
- Дата: 2026-10-26
- Основа: `docs/design/sard-restore-verification.md`, ADR 0008, 00XX-draft-verification-server, 00XX-draft-source-fingerprint

## Контекст
V4 научил сервер ставить и выдавать проверки, V2 — снимать отпечаток
источника. Агент с ролью `verifier` должен выполнить `ACTION_VERIFY` так,
чтобы «пройдено» значило «восстанавливается»: не верить серверу, не писать в
хранилище, не оставлять данных клиента, не сравнивать копию саму с собой.

## Решение

### Конвейер
`internal/verifier` выполняет стадии по порядку до первой непрошедшей, уборка —
всегда: `snapshot`, `fingerprint_tag`, `work_volume` (0), `restic_check` (1),
`sandbox` (0, только для плагинов с `sdk.Sandboxed`), `restore` (2), `start`
(3), `fingerprint` (4), `cleanup`. У каждого вида стадии свой срок
(`verify.stage_limits`), не дольше срока задания. Стадия, вышедшая за срок, —
вердикт «сбой инфраструктуры»; сервер считает его попыткой без вердикта и
повторяет (до трёх). Остальные исходы: провал — бэкап, «не можем проверить» —
окружение верификатора.

### Серверу не верим
- Отпечаток задания проверяется по хешу в теге снимка в репозитории
  (`sard.fp=<sha256>`), до чтения данных.
- Сервер передаёт `source_machine_ids`; верификатор отказывается от снимка
  своей машины.
- Копию измеряет код плагина на верификаторе, а не отчёт источника.

### Хранилище только на чтение
Все команды restic верификатора — с `--no-lock --no-cache` (`restic.WithReadOnly`),
в том числе `cat config` при регистрации: `check` без флага берёт
исключительную блокировку, а учётка только на чтение не дала бы агенту даже
зарегистрироваться. `restic check --read-data-subset=N%` (N = 10 по умолчанию):
без чтения данных повреждённый pack не виден. Ошибка `check` при изменившемся
списке снимков (параллельный prune) — одна повторная проверка, затем «не можем
проверить». Учётка, которой хранилище даёт блокировку, — предупреждение при
старте и в `repo check` (`repository.readonly`).

### Песочница — контейнер через CLI
Базы поднимаются в контейнере официального образа той же мажорной версии:
Docker или Podman через их CLI (`internal/sandbox`), без SDK рантайма —
агент остаётся на stdlib (ADR 0027). Podman пробуется первым и рекомендуется
без root: группа `docker` равна root.

Контейнер: `--network none`, `--user <uid агента>` (`--userns=keep-id` у
Podman), лимиты CPU, памяти и pids, каталог задания смонтирован в каталог
данных образа, метка `sard.verify.job=<задание>`. Пароль приложения случайный
на каждую проверку и передаётся через окружение CLI, а не аргументом. Плагин
работает с песочницей через `sdk.SandboxHost.Run` (`exec -i`): `psql` и
`pg_restore` — из образа, их версия совпадает с сервером копии.

Образ выбирается из списка релиза (`internal/sandbox/images.txt`: имя,
semver-версия, digest) и запускается только по digest. Список обновляется в
каждом релизе; `verify.images` заменяет его (свой реестр, зеркало). Образа нет
и `verify.pull: false` или загрузка не удалась — «не можем проверить».

Готовность сервера в песочнице — `SHOW listen_addresses` не пуст: образ
сначала поднимает временный сервер без TCP для инициализации. Расширение
источника, которого нет в `pg_available_extensions` образа, — `SandboxRefusal`,
«не можем проверить» до восстановления.

### Рабочий том и уборка
Копия лежит в `<work_dir>/<задание>`; том обязан быть `noexec` (проверка через
`statfs`, юнит пакета даёт `NoExecPaths=`), места — размер × 2 + 1 ГиБ
(настраивается). Демон рантайма монтирует каталог задания по тому же пути, что
видит агент. После каждой проверки удаляются контейнер с томами (`rm -f -v`)
и каталог; при старте агента — все контейнеры с меткой и все каталоги рабочего
тома.

### Статус верификатора
`VerifierStatus` в Register и Heartbeat: свободное место, рантайм, его версия
и образы списка, которые есть локально (`images`). Сервер обновляет статус
по heartbeat, а не только при регистрации.

## Последствия
- Контракт: `VerifyVerdict.INFRASTRUCTURE_FAILURE`, `VerifyTask.source_machine_ids`,
  `VerifierStatus.sandbox_version` и `images`, `SandboxImage` — добавления без
  поломки (buf breaking).
- SDK (Apache-2.0): `Sandboxed`, `SandboxSpec`, `SandboxHost`, `Process`,
  `SandboxRefusal`, `CopySizer`.
- Верификатору нужен рантайм контейнеров и место на две копии; e2e-стенд
  запускает песочницы через сокет демона стенда (`test/e2e/agent/Dockerfile.verifier`).
- Хвосты: свой реестр образов для закрытых контуров; сроки стадий на источник
  для больших баз.

## Отвергнуто
- **Docker SDK / API по сокету** — зависимость сверх ADR 0027 и только Docker.
- **psql и pg_restore верификатора на хосте** — версия клиента не совпадала бы
  с сервером копии, а хосту нужны были бы пакеты всех версий.
- **Тег по имени образа (`postgres:17`)** — образ меняется без ведома релиза;
  digest закрепляет то, что проверено.
- **Проверка без чтения данных** — пропускает повреждённые pack-файлы.
