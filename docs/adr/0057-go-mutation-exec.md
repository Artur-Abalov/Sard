# 0057 — Мутации Go: свой exec с `go test -overlay`, измеренный таймаут, шарды

- Статус: принято (решение владельца 2026-10-13 «делай все P0»; PR #65)
- Дата: 2026-10-13
- Дополняет: ADR 0006 (мутационное тестирование), ADR 0007 (шлюзы качества)

## Контекст
Замеры 2026-10-13 (CI run 38298083030 на `main`, локальный хост 4 ядра):

- Шаг `gate.sh agent` шёл 4 ч 27 мин из 4 ч 28 мин всего прогона; сервер — 27,5 мин, e2e — 35,5 мин.
- Встроенный исполнитель go-mutesting запускает `go test -timeout 10s <пакет>` на каждого из 4314
  мутантов агента, строго по одному, подменяя исходник **в рабочем дереве** (rename + copy,
  восстановление в `defer`). Прерванный прогон оставляет мутированный файл (OQ-030).
- Немутированный `cmd/sard-agent` идёт 19,4 с: `go test -count=1 -timeout 10s ./cmd/sard-agent/`
  падает с `panic: test timed out` и кодом 1, а код 1 go-mutesting считает убитым мутантом. Все 954
  мутанта пакета (22 %) засчитывались убитыми независимо от тестов; score 0.956 был недостоверен
  (OQ-130). `internal/enroll` под нагрузкой не укладывался в 10 с в 3 из 6 прогонов.
- Подсчёт go-mutesting: `(killed + errored + skipped) / total`, где skipped — мутант, который не
  компилируется.

## Решение
1. **`scripts/mutate-exec.sh`** — команда `--exec` для go-mutesting (защищён `guard-edit.sh`):
   - мутант передаётся компилятору через `go test -c -overlay`; рабочее дерево не пишется, поэтому
     несколько процессов go-mutesting работают в одном checkout, а прерванный прогон ничего не
     оставляет;
   - база: один раз на пакет и процесс собираются и запускаются немутированные тесты; если они
     падают или идут дольше 600 с — ошибка (код 3), а не «убит»;
   - таймаут мутанта — `max(3 × база, 10 с)` (до 2026-10-13 нижняя граница была 30 с; на 221 таймауте первого прогона она одна стоила ~70 мин шардов); мутант, вышедший за него, убит (бесконечный цикл —
     обнаруженный мутант) и печатается строкой `mutate-exec: TIMEOUT`;
   - выживший печатается с диффом; не скомпилировался — код 2 (как и раньше, засчитывается по
     формуле go-mutesting); тест-бинарь запускается без `go vet`.
   - тест-бинарь (база и мутант) запускается с `ulimit -v` 3072 МБ: мутант, который выделяет память
     без конца, падает с `out of memory` (убит), а не роняет раннер. Найдено в CI: мутант
     `internal/steplog/lines.go` `s.buf[i+1:]` → `s.buf[i+0:]` зацикливал отправку пустых строк,
     память росла ~100 МБ/с, раннеры шардов 4, 8 и 11 гибли с «runner has received a shutdown
     signal» (код 143). Без мутаций все пакеты agent, sdk, cli, tools проходят в этом лимите;
   - перед каждым мутантом печатается `mutate-exec: START <мс> <мутант>`, а в CI лог шарда идёт и в лог
     джобы (`MUTATION_STREAM=1`): потерянный раннер всё равно показывает последний мутант;
   - тест-бинарь запускается с `-test.failfast` (дополнение 2026-10-27): первый упавший тест убивает
     мутант, следующие тесты пакета для него не стартуют. Меняется время убийства, а не исход:
     выживший и так прогоняет все тесты, упавший тест не становится зелёным;
   - сначала покрывающие тесты (дополнение 2026-10-28): для пакета, чьи немутированные тесты идут
     ≥ 1 с (`SELECT_MIN_BASELINE_MS`), один раз на пакет и процесс каждый тест запускается отдельно
     с покрытием (`-cover -covermode=set`, `GOCOVERDIR`: в профиль попадает и код дочерних
     процессов, которые тест запускает через `os.Args[0]`) — карта «тест → покрытые блоки». Мутант
     сначала гоняется против тестов, чьи блоки содержат изменённые строки
     (`scripts/lib/covering-tests.awk`, тест — `scripts/test-covering-tests.sh`); упал хоть один —
     убит. Прошли все, или строк нет ни в одном блоке (переменные уровня пакета, таблицы флагов),
     или выбраны все тесты, или шаблон `-test.run` длиннее 64 КиБ — запускаются все тесты, как
     прежде. Выживший — всегда тот, кого пропустили все тесты. Тест, который падает или висит один,
     оставляет пакет без карты (строка `mutate-exec: NOMAP`): так ведут себя тесты `hostsetup`,
     считающие открытые дескрипторы, — рантайм покрытия держит свои. Карта `cmd/sard-agent`
     (1295 тестов) — ~35 с на хосте 4 ядра;
2. **Шарды.** Мутируются файлы `go-mutesting --list-files ./...` модуля, кроме файлов вложенного
   модуля (`agent/plugins/sdk` — свой модуль и свой гейт), в стабильном порядке; шард `i` из `n`
   получает файлы по весам: самый тяжёлый файл — в самый лёгкий шард (веса — секунды на файл в
   `scripts/mutation-weights/<модуль>.tsv`, считаются `scripts/mutation-weights.sh` по строкам
   `mutate-exec: START <мс>` логов шардов; файл без веса весит среднее, без файла весов все веса
   равны). Первые веса — из прогона 38397961703: шарды 11–40 мин по кругу, по весам ~23,7 мин
   каждый (оценка до снижения таймаута). `gate.sh <m>` (полный режим) запускает
   `MUTATION_JOBS` шардов параллельно (по умолчанию — число CPU). В CI `agent-mutation` — matrix из
   12 шардов на отдельных раннерах (`gate.sh agent mutation i/12`), `agent-mutation-total` суммирует
   логи (`gate.sh agent mutation-total <dir>`).
3. **Порог тот же и к тому же модулю:** `MUTATION_MIN` применяется к сумме всех шардов по формуле
   go-mutesting без ошибок: `(killed + did not compile) / (killed + survived + did not compile)`.
   Любая ошибка (немутированные тесты падают или висят) роняет гейт. Недостающий шард роняет гейт.
4. **Видимость.** Гейт печатает выживших с диффами, строки TIMEOUT/ERROR и сводку
   `mutants: N total, K killed (T of them by timeout), E survived, S did not compile, X errors,
   D duplicates skipped`; логи шардов — артефакты CI при любом исходе. У каждой джобы CI есть
   `timeout-minutes`.

## Проверено
- `tools`: свой exec и встроенный дают одинаковый score 0.981043 и тех же четырёх выживших (те же
  контрольные суммы); один мутант `crap.go` убит по таймауту при базе 46 мс — бесконечный цикл.
- `sdk` 1.000000 (39 мутантов), `cli` 1.000000 (12).
- Один мутант `cmd/sard-agent`: 19,6 с при честном таймауте против 15,7 с с ложным убийством —
  честный режим дороже, поэтому вводится вместе с шардами.
- `-test.failfast` (2026-10-27, хост 4 ядра, одни и те же срезы до и после): `tools` 373 мутанта,
  `sdk` 201, `cli` 12 — те же score и те же исходы по контрольным суммам; `agent` срез 2/24
  (`cmd/sard-agent/main.go`, 335 мутантов) — 2257 → 1531 с (−32 %), таймаутов 8 → 5, `sdk`
  146 → 112 с, `cli` 17 → 8 с, `tools` 201 → 216 с (тесты пакетов `tools` короче сборки, шум).
  Один мутант агента (`main.go`, `return err` после `executor.New` → `_ = err`) до был убит, после
  выжил; 10 повторных прогонов (5 с `-test.failfast`, 5 без) — выжил во всех: прежнее убийство —
  флейк теста под нагрузкой, а не эффект флага.
- Покрывающие тесты (2026-10-28, хост 4 ядра). Время между прогонами на хосте гуляет до ±50 %, поэтому
  итоговый замер — обе версии одновременно (A/B): срез агента 3/24 (`enroll_run.go`,
  `repo_password_run.go`, `config`, `restic`, `restore` и др., 330 мутантов) — 2051 → 1107 с
  (−46 %), `enroll_run.go` 1535 → 548 с, `repo_password_run.go` 210 → 141 с; `tools` (карт нет —
  пакеты быстрее порога) 368 → 325 с, тот же путь, шум. Отдельно: срез 2/24 (`main.go`) 1531 →
  1479 с (−3 %, главным образом таблицы и код, общий для всех тестов). Исходы по контрольным суммам
  совпали во всех сравнениях (`tools` 373, `sdk` 201, `cli` 12, агент 2/24 335 и 3/24 330), кроме
  одного мутанта `enroll_run.go` (`return code` → `_ = code`): в одном прогоне только с
  `-test.failfast` под двойной нагрузкой убит за 30,5 с без таймаута, в четырёх других прогонах обеих
  версий выжил — тот же флейк теста `cmd/sard-agent` под нагрузкой, что 2026-10-27. Прототип на
  92 мутантах `cmd/sard-agent`: исход выбора совпал с полным прогоном у всех, где тесты были выбраны.
  Без порога пакеты на десятки миллисекунд шли вдвое дольше.

## Отвергнуто
- Поднять `--exec-timeout` встроенного исполнителя: дерево по-прежнему пишется, параллелить нельзя,
  таймаут одинаков для пакета на 40 мс и на 19 с.
- `xargs -P` нескольких встроенных go-mutesting в одном дереве: они подменяют одни и те же файлы.
- Мутации только изменённых файлов на PR — сужает охват гейта; отдельное решение после того, как
  полный прогон станет быстрым.
- Не запускать тесты для мутанта в непокрытой строке (2026-10-27; покрывающие тесты 2026-10-28 этого
  тоже не делают — такой мутант идёт против всех тестов): в `cmd/sard-agent` (63 % времени
  мутаций агента по весам) нулевых блоков покрытия 52 из 2109 — выигрыш мал. Тесты `cmd/sard-agent`,
  `postgresql`, `restic`, `certpair` перезапускают тест-бинарь (`os.Args[0]`), профиль покрытия
  родителя не видит кода дочернего процесса — такие мутанты ложно попали бы в выжившие. Нужна была
  бы ещё компиляция ради «не скомпилировался».
- `-ldflags=-s -w` при сборке мутанта (2026-10-27): ~5,4 → ~4,9 с на сборку `cmd/sard-agent`
  (≈ 6 %), не стоит отличия бинаря мутанта от обычной сборки.
- Сэмплирование мутантов и отключение мутаторов — меняют саму метрику гейта, а не её стоимость;
  решение владельца, не исполнителя.

## Последствия
- Score агента после перехода может стать ниже 0.80: это честная цифра; чинится тестами, порог не
  меняется.
- Стоимость мутанта в `cmd/sard-agent` задаётся временем его тестов; их ускорение (часы в
  конструкторах, `t.Parallel`) — следующая задача.
- Мутанты `agent/plugins/sdk` проверяются только гейтом `sdk`.
