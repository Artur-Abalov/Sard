# 0060 — Роль sard_self приводится к виду миграции при каждом старте

- Статус: принято (F7, Р33, OQ-214; решения владельца 2026-10-14)
- Дата: 2026-10-14

## Контекст
Роль `sard_self` создаёт только миграция V202610071200, а самобэкап (F6) не
сохраняет глобальные объекты. В восстановленной базе роли нет, миграция
повторно не выполняется, и каждый самобэкап базы падает. Отзыв `TEMPORARY`
у PUBLIC на уровне базы `pg_dump` без `--create` тоже не сохраняет.

## Решение
- При каждом старте с включённым каналом (`SARD_SELF_DIR`) `SelfAgentSetup`
  вызывает `DumpRole.reconcile()` до установки пароля. Операторы SQL те же, что
  в миграции, но повторяемые: создать роль, если нет
  (`LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS
  CONNECTION LIMIT 4`), выдать `pg_read_all_data`,
  `default_transaction_read_only = on`, отзывы у PUBLIC.
- Пользователь сервера не суперпользователь — блок ничего не делает, пароль
  роли затем не устанавливается и сервер пишет прежнюю одну строку WARN
  (F5, правило B). Канал выключен — роль не трогается.
- Одновременный старт нескольких серверов на одной базе: всё действие
  (пароль канала, роль, пароль роли) выполняется под сеансовой консультативной
  блокировкой PostgreSQL (`pg_advisory_lock`) на отдельном соединении;
  состязания за создание роли и за файл пароля нет.
- Пароль идёт в сервер как проверочное значение SCRAM, как и раньше, и в SQL
  и логи не попадает.

## Последствия
- Миграция V202610071200 не меняется; два текста SQL (миграция и константа в
  `selfagent/DumpRole.kt`) нужно менять вместе, на это указывает комментарий.
- Сценарий F5 «роли нет» теперь относится к пользователю без прав
  суперпользователя.
