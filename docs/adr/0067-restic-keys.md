# 0067 — Ключи restic: назначение и метка в поле пользователя, признак ключа восстановления в Register, перезапуск службы, обратная проверка блокировки на верификаторе (V3)

- Статус: принято (срез 1 из 3: контракт и агент; сервер и консоль — следующие срезы); решения владельца — 2026-10-21 (`docs/specs/agent/restic-keys.feature`: В1–В10, ВС1, К1–К21)
- Дата: 2026-10-21
- Дополняет: ADR 0008 (сервер не держит ключи), ADR 0050 (права запуска), ADR 0059 (restic без блокировки), ADR 0063 (проверка хоста), `docs/adr/00XX-draft-agent-role.md` (роль в сертификате)

## Контекст
Оператор источника должен одной командой выпустить отдельный ключ restic для
верификатора и ключ восстановления, отозвать любой, не трогая остальные, и не
остаться с репозиторием, у которого один ключ на одном хосте. Ключи и пароли по
ADR 0008 на сервер не уходят: сервер должен узнавать только признак.

## Решение

### Назначение и метка хранятся в самом ключе (К1)
У ключа restic 0.19 нет полей «назначение» и «метка»: только имя пользователя
(`--user`), имя хоста (`--host`) и время. Назначение и метка пишутся в имя
пользователя: `sard:<назначение>` или `sard:<назначение>:<метка>`
(`internal/restickeys`). Ключ с другим именем (ключи до V3, созданные restic
вручную, `sard-agent` самого `restic init`) показывается с `-`. Так `repo key
list` на любом хосте видит, чей ключ, без какого-либо хранилища метаданных
(ни на сервере, ни в конфиге). Время создания restic печатает по-своему:
`2026-10-21 12:09:21`, местное время хоста без пояса (измерено на 0.19.1);
агент читает его в поясе хоста, а печатает RFC 3339 в UTC. Метка уникальна по
соглашению: два хоста, одновременно выпускающие одну метку, оба пройдут
проверку — restic такой гарантии не даёт.

### Пароль нового ключа не оставляет копий на хосте (К6–К9)
32 байта криптографического генератора, base64url без выравнивания, как у
сгенерированного пароля репозитория. Restic получает его через
стандартный ввод (`stdin`; для `key add` restic читает одну строку из `stdin`,
не являющегося терминалом), а не аргументом, окружением или временным файлом. Показ — один раз: в терминал или в
новый файл `--to-file` (владелец root, `0600`, временный файл в каталоге
назначения, права до содержимого, `fsync`, ссылка с отказом при существующем
имени, `fsync` каталога — тот же приём, что у файла пароля репозитория). Без
терминала и без файла ключ не выпускается: пароль, которого некуда показать,
потерян в момент создания.

### Признак ключа восстановления — перечисление в контракте (КП1)
`RepositoryInfo.recovery_key = 5` типа `RecoveryKeyState`
(`UNSPECIFIED`, `PRESENT`, `ABSENT`). Перечисление, а не `bool`: агент старше V3
и агент, не сумевший прочитать ключи, должны отличаться от «ключа нет», иначе
консоль покажет ложный баннер. Изменение добавочное, `buf breaking` зелёный.
Поле несёт только признак: ни id ключей, ни метки, ни число ключей (ADR 0008).
Агент считает его заново перед каждым Register (`restic key list --json
--no-lock` от пользователя службы, предел 30 секунд, как `--connect-timeout`),
не кэширует; сбой чтения — `UNSPECIFIED`, строка WARN с очищенной причиной
(`repoinit.Scrubber`), Register всё равно уходит.

### Перезапуск службы при смене ключа восстановления (К19)
Служба узнаёт признак только при Register. Поэтому `key add --for recovery` и
`key remove` ключа восстановления применяют изменение по Р8 (перезапуск по
журналу шагов, `--no-restart`, нет systemd, служба не активна), как команды,
меняющие конфиг, хотя конфиг они не меняют; ключи других назначений службу не
трогают. Обе команды держат блокировку конфига.

### Ключ восстановления нового репозитория (К15, К15а)
`repo add` и `repo init`, которые *создают* репозиторий, выпускают
`sard:recovery` сразу после `restic init`. Куда пойдёт пароль, решается до
создания (`--recovery-key-file`, иначе терминал, иначе `--no-recovery-key`;
ничего — `RECOVERY_KEY_OUTPUT_MISSING`, хост не изменён). Решение принимается в
тот момент, когда известно, что репозитория нет (`Connector.BeforeCreate`,
`repoinit.CreateGated`), чтобы Ansible мог повторять `repo add` существующего
репозитория без флагов. Неудача выпуска после `init` не откатывает
подключение: фрагмент и применение выполняются как обычно, код 1,
`RECOVERY_KEY_FAILED`.

### Верификатор только читает; проверка блокировки читается наоборот (К2, К17)
Роль берётся из сертификата (`identity.Read`); хост без сертификата, как и с
нечитаемым, ведёт себя как источник (В5). На верификаторе `repo init`, `repo key
add` и `repo key remove` — `VERIFIER_READ_ONLY` до обращения к хранилищу; `repo
add` не создаёт репозиторий (`REPOSITORY_NOT_INITIALIZED`). П29 (проверка доступа
командой, берущей блокировку) для верификатора трактуется наоборот: отказ
блокировки — ожидаемый, учётка только на чтение — то, что ему нужно; успех —
предупреждение о праве записи (утечка такой учётки позволила бы испортить
бэкапы). На источнике П29 не меняется; хост без сертификата получает подсказку
сначала зарегистрироваться токеном верификатора.

### Прочее
`repository.keys` — новая проверка `repo check` и `check` (после
`repository.id`, до `repository.locks`; `OK` / `WARN`). Удаление ключа не меняет
мастер-ключ репозитория: команда говорит это при каждом удалении, а полная смена
доступа — новый репозиторий (уточнение 4).

## Последствия
- Неинтерактивный `repo add` нового репозитория (e2e, плейбуки) должен получить
  `--recovery-key-file` или `--no-recovery-key`.
- Сгенерированный код (`proto/gen/go`, `:proto-jvm`) обновлён; сервер читает
  `recovery_key` в следующем срезе.
- Нет новых зависимостей.

## Поправка (2026-10-22): пароль нового ключа идёт через stdin, не через fd 3
Первая редакция отдавала пароль нового ключа унаследованным дескриптором
(`--new-password-file /proc/self/fd/3`). Это не работает, когда restic запущен
от пользователя службы: после смены uid процесс не «дампабелен», и
`/proc/self/fd/3` канала, созданного root, не открывается (restic завершается
с кодом 1, `BACKEND_REFUSED`). Локальные интеграционные тесты шли под одним uid и
этого не видели; поймал e2e (`HostRecoveryKeyTest`, `SelfRecoveryKeyTest`).
Теперь пароль нового ключа передаётся в `stdin` restic (`key add --user --host`,
без `--new-password-file`). Инвариант не изменился: пароль не попадает в
аргумент, переменную окружения или файл, копий на хосте не остаётся. Пароль
репозитория передаётся прежним способом и `stdin` не занимает.
