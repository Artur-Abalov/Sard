# 0031 — Проверка конфига источника на сервере: JSON Schema 2020-12

- Статус: принято
- Дата: 2026-10-01

## Контекст
`POST` и `PUT /api/v1/sources` принимают `config` плагина. Агент проверяет
его по `config_schema` до `Prepare` (ADR 0027), но сервер, не проверив,
отдал бы агенту заведомо неверный конфиг, а администратор узнал бы об
ошибке из отклонённого шага. Схему плагина агент присылает в Register
(S4a), сервер хранит её в `agent_plugins.config_schema`. Решение владельца
S8b, В15 (`docs/open-questions.md`, OQ-064): проверять на сервере, все
нарушения сразу, путь поля — JSON Pointer; нужен валидатор JSON Schema
2020-12 — новая зависимость сервера.

## Решение
- **Библиотека.** `com.networknt:json-schema-validator` 3.0.8, Apache-2.0.
  Полная поддержка 2020-12, построена на Jackson 3 (`tools.jackson`) — том
  же, что уже использует сервер; даёт все ошибки с путём значения и
  позволяет добавить свой формат. Транзитивно: `com.ethlo.time:itu`
  (Apache-2.0, разбор дат), `jackson-dataformat-yaml` и
  `org.snakeyaml:snakeyaml-engine` (Apache-2.0; YAML сервер не читает).
  Отвергнуты: `everit-org/json-schema` — draft-07 максимум;
  `erosb/json-sKema` — подходит, но у networknt нет второго JSON-парсера в
  classpath и есть возможность настраивать загрузку ссылок.
- **Что проверяется.** Конфиг — по схеме последнего Register агента.
  Поле с `"format": "sard-secret"` обязано быть именем секрета этого
  агента (`agents.secret_names`), как и на агенте (ADR 0027); сообщение
  называет имя, значения конфига в сообщения не попадают. Неизвестные
  ключевые слова (`x-sard-i18n`, ADR 0028) игнорируются. Форматы схемы
  проверяются как утверждения (формат — часть контракта плагина).
- **Чего не проверяется.** Того, что схема выразить не может (вложенные
  пути `files`): это по-прежнему отказ агента при запуске.
- **Схема приходит с хоста, который может быть скомпрометирован.**
  Валидатор не загружает ничего за пределами самой схемы: ни по сети, ни с
  файловой системы, ни из classpath; `$ref` работает внутри схемы.
  Схема, которую не удалось скомпилировать, — `422 invalid_config` с
  ошибкой у поля `config`.
- **Формат ошибок.** `errors[].field` = `config` + JSON Pointer значения
  (`config/paths/0`, объект целиком — `config`), по возрастанию поля.
  Размер `config` — не больше 64 КиБ (UTF-8 сериализованного JSON), иначе
  `422 validation_failed` у `config`.
- **Лог.** Значения конфига не попадают в журнал сервера и при DEBUG:
  `SourceInput`, `Source` и `CreatedEnrollmentToken` переопределяют
  `toString` (Spring пишет тела запросов и ответов в DEBUG), а категория
  Hibernate `org.hibernate.orm.core` (она печатает состояние сущностей при
  сбросе) удержана на INFO.

## Последствия
- Источник нельзя создать с конфигом, который агент заведомо отклонит по
  схеме; схему, ставшую несовместимой после замены Register, сервер
  обнаружит при следующем `PUT`, а при запуске — не проверяет (запуск
  отдаёт конфиг, снятый при создании, ADR 0022).
- Сборка сервера тянет ещё три библиотеки (см. `docs/dependencies.md`).
