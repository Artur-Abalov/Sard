# 0050 — Права запуска команд агента: sudo для изменений, пользователь службы — для чтения

- Статус: принято (A8a); решения владельца — 2026-10-07 (`docs/specs/agent/host-setup.feature`, Н1, Н2, Н9, Н11, Р5, Р6, Р9, Р24, Р25)
- Дата: 2026-10-07

## Контекст
Файлы агента (`/etc/sard/tls`, `secrets`, репозитории) принадлежат
пользователю службы `sard-agent`; проверка A1 отказывает в старте при другом
владельце. Оператор выполнял команды как `sudo -u sard-agent sard-agent …`,
после чего не мог ни положить файл в `/etc/sard` (`root:sard-agent`, `0750`),
ни создать каталог локального репозитория. Из-за этого процедуры состояли из
`install`, `chown`, `chmod`.

## Решение
- **Правило прав** проверяется сразу после разбора флагов, до чтения конфига
  и источника токена. euid 0 (`sudo`) — любая команда. euid пользователя
  службы — только чтение (`repo list`, `repo show`, `repo password --reveal`,
  `secret list`), плюс `repo init` и `enroll`, как раньше. Любой другой —
  `PRIVILEGES_REQUIRED` (класс «использование», код 2) с готовой командой
  `sudo sard-agent …`. Изменяющие команды от пользователя службы — тот же
  отказ: служба не меняет свою настройку.
- **Пользователь службы** — `sard-agent` или `service.user` основного конфига
  (только основной: во фрагменте это ошибка). Правило прав знает его раньше,
  чем читается конфиг, поэтому `service.user` вынимается отдельным чтением,
  которое не отказывает: файл, которого нет или который не разобрать, даёт
  имя по умолчанию, а ошибку конфига сообщает уже следующий шаг. uid и gid —
  `os/user` без cgo (`/etc/passwd`, `/etc/group`): пользователи LDAP и SSSD
  не видны (в документации оператора). Под root без пользователя службы —
  `SERVICE_USER_UNKNOWN`.
- **Созданное принадлежит пользователю службы** (каталог `secrets`, файлы
  значений и паролей, каталог локального репозитория, файлы `tls.*`);
  владелец и права выставляются временному файлу до переименования, так что ни
  в один момент целевой путь не принадлежит root.
- **restic под sudo запускается от пользователя службы**
  (`SysProcAttr.Credential`, стандартная библиотека; дополнительные группы
  сбрасываются): файлы репозитория, кэша `restic.cache_dir` и блокировок
  принадлежат тому, кто потом работает с ними как служба.
- **Терминал без эха** — `ioctl` `TCGETS`/`TCSETS` из `syscall` (Linux); новых
  зависимостей нет (ADR 0027, CLAUDE.md, правило 7).
- **Аудит** — одна строка в системный журнал (`log/syslog`, тег `sard-agent`,
  `journalctl -t sard-agent`; facility `LOG_AUTHPRIV`, поэтому на хостах с
  rsyslog строки попадают в `/var/log/secure` или `auth.log`, а
  `journalctl -t sard-agent` работает всегда) на каждое изменение и каждый `--reveal`: что
  сделано, вид, имя, кто (`SUDO_USER` и `SUDO_UID`, иначе пользователь
  процесса). Значений, адресов с учётными данными и содержимого файлов в
  строке нет. Недоступный syslog — предупреждение в stderr, изменение
  выполняется.
- **Применение** — перезапуск `sard-agent.service`, только если в журнале
  принятых команд (ADR 0044) нет записей; иначе команда печатает, как
  перезапустить. `--no-restart` не перезапускает никогда.
- **`enroll`** подчиняется тому же правилу и под root создаёт отсутствующий
  последний каталог файла `tls.*` (пользователь службы, `0700`); отсутствующий
  промежуточный — ошибка записи. Каталог, созданный неудачным запуском,
  удаляется. Команда консоли `sudo -u sard-agent …` продолжает работать
  (запуск от пользователя службы); её замена — задача server/web.

- **Локальный адрес без символьных ссылок (R2).** `repo add` работает от root
  и создаёт каталоги и меняет владельца в дереве, адрес которого задан путём;
  пользователь службы мог бы подменить ссылкой компонент, который он
  контролирует (`/var/lib/sard-agent/repos` → `/var`), и увести эту работу
  в `/var/backups`. Поэтому путь проходится от `/` по одному компоненту:
  `openat(O_DIRECTORY|O_NOFOLLOW)` относительно уже открытого каталога
  (`hostsetup.OpenDir`, только `syscall`); отсутствующие компоненты создаются
  `mkdirat` относительно удерживаемого родителя; ссылка в любом компоненте —
  `LOCAL_PATH_INVALID` («<компонент> is a symbolic link; give the resolved
  path»). Дерево затем обходится внутри `os.Root`, открытого по тому же пути,
  и его inode сверяется с удерживаемым дескриптором. Проверки владельца
  предков нет: она отказывала бы нормальным раскладкам. Предел: каталог,
  подменённый между последней проверкой и открытием `os.Root`, ловится
  сверкой inode, но не предотвращается; путь через ссылку оператору надо
  указать в разрешённом виде (`/run`, а не `/var/run`).

- **Файлы под root в каталогах пользователя службы (R3).** Каталоги
  `restic.cache_dir`, `secrets`, `tls` и репозитория принадлежат пользователю
  службы, он может подложить в них ссылку. Поэтому: файлы блокировок
  открываются с `O_NOFOLLOW` и отказывают при числе имён больше одного;
  временные файлы создаются `O_EXCL`, а владелец выставляется через
  дескриптор (`fchown`), не по пути; каталоги создаются `mkdirat` от
  удерживаемого родителя, владелец и права — через дескриптор; обход дерева
  репозитория не меняет владельца у файла с несколькими именами. Остаётся
  чтение по пути (`repo password --reveal`, `env_file`, журнал): оно не
  меняет файлы и печатает только оператору.

- **Файл ключей S3 (A8b-1, `repo add` для `s3:`).** `secrets/restic-<имя>.env`
  пишет root в каталог пользователя службы, значит, то же семейство атак (R3,
  R4). Файл записывается как пароль: временный `O_EXCL` в `secrets`,
  `fchown` и `fchmod` по дескриптору до записи содержимого, `fsync`,
  `rename` на месте (подложенная ссылка или жёсткая ссылка на конечном имени
  заменяется, запись через неё не идёт), затем `fsync` каталога; принятый
  кандидат становится `env`-файлом и файлом пароля вместе, первым `env`-файл —
  при сбое его записи файла пароля не остаётся. Существующий `env`-файл
  root читает только `secrets.ReadOwned` (без перехода по ссылке, владелец —
  пользователь службы, права A1, не больше 1 МиБ): подмена ссылкой, чужим
  владельцем или FIFO — `SECRET_FILE_REJECTED`, файл не меняется. restic
  читает тот же файл от имени пользователя службы через ту же проверку. Ключи
  попадают в restic окружением из файла, в аргументы, вывод, журнал и строку
  аудита — никогда.
- **Время на терминале не считается (A8b-1, Р33).** Таймер `--timeout` стоит,
  пока команда ждёт ответа оператора на терминале; `--connect-timeout`
  ограничивает только первое обращение к хранилищу и со времени ожидания
  оператора не пересекается.

## Альтернативы
- *Оставить `sudo -u sard-agent`.* Не даёт создавать файлы в `/etc/sard` и
  каталогах, которые принадлежат root; процедуры остаются ручными.
- *Дать пользователю службы право писать в `/etc/sard`.* Служба смогла бы
  менять собственную настройку и ключи доверия.
- *setuid-бинарник.* Расширяет поверхность атаки ради одной команды.

## Последствия
- Тесты подставляют euid, поиск пользователя, смену владельца, syslog,
  systemctl, терминал, запуск restic и часы через интерфейсы.
- Агент по-прежнему не принимает секреты аргументами: значения — терминал,
  `--stdin`, `--from-file` (`SECRET_SOURCE_MISSING`, если ничего нет и ввод не
  терминал).
