# 0058 — e2e в CI: три раннера, классы по измеренному времени

- Статус: принято (решение владельца 2026-10-14: «матрица из 3 раннеров»; PR #66)
- Дата: 2026-10-14
- Дополняет: ADR 0045 (собрать один раз), ADR 0057 (шарды мутаций)

## Контекст
Замер CI run 38455685808 (`6f45648`): `make e2e-test` — 35,3 мин, 32 класса подряд, сумма времени
классов 2099 с — всё время уходит на сами тесты. Дольше всех StreamBreakTest 352 с,
PostgresqlSourceTest 285, StorageOutageTest 284, PostgresqlRestoreTest 137, StepLossTest 125,
StorageFailureTest 117, StorageLockTest 115. e2e — самая длинная джоба прогона (мутации агента
~20 мин, сервер ~23).

Каждый класс поднимает свою установку (`SardEnvironment`: своя сеть, PostgreSQL, sard-server,
случайные порты), общего между классами нет — любое разбиение корректно.

## Решение
1. **`scripts/e2e-shard.sh`**: классы — `*Test.kt` исходников e2e; шард `i/n` раздаётся по LPT
   (самый тяжёлый класс — самому лёгкому шарду) по весам `scripts/e2e-weights.tsv` (секунды на
   класс из JUnit-отчётов прогона); класс без веса весит среднее. LPT — общий
   `scripts/lib/lpt.awk`, им же пользуются шарды мутаций `gate.sh` (разбиение агента не
   изменилось — проверено сравнением всех 12 шардов).
2. **`make e2e-test E2E_SHARD=i/n`** запускает классы шарда через `--tests`; без `E2E_SHARD` —
   все классы (локально и в `release.yml`). Пустой шард — ошибка, а не прогон всего набора.
3. **CI**: матрица `e2e-shard` из 3 раннеров (по весам 699/697/703 с), каждый со своими
   образами и CPU — запасы таймингов StreamBreak/StorageOutage не делятся с соседом. Джоба
   `e2e` (имя прежней проверки) собирает отчёты всех шардов, печатает время по классам и веса,
   падает, если у класса нет отчёта или шард не прошёл.
4. Веса обновляются вручную: `scripts/e2e-shard.sh times --tsv <отчёты>` (джоба `e2e` печатает
   их на каждом прогоне).

## Альтернативы
- `maxParallelForks = 2` на одном раннере: ~18–20 мин, но контейнеры двух классов делят 4 vCPU,
  тесты с таймингами рискуют стать нестабильными.
- Сократить ожидания в медленных классах (keepalive 30 + 10 с, простой хранилища 30 с): трогает
  параметры агента и сервера, выигрыш неизвестен до разбора.

## Последствия
- e2e ожидается ~12 мин тестов + ~2,5 мин подготовки на раннер вместо ~37 мин; подготовка
  (загрузка образов, сборка образов агента) теперь трижды.
- Новый класс без веса весит среднее (~66 с) до обновления весов; перекос виден в таблице джобы
  `e2e`.
- Проверка «каждый класс прогнан» ловит потерянный шард или класс, не попавший в фильтр.
