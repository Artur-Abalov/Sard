# 00XX — Привязка секретов к плагину и цели; защищённое подключение PostgreSQL

- Статус: черновик (S11; решения владельца на контрольной точке 1 2026-10-26,
  `docs/sessions/2026-10-26-s11-secret-binding.md`)
- Дата: 2026-10-26
- Дополняет: ADR 0008 (сервер — плоскость управления, а не хранитель ключей)

## Контекст
ADR 0008 держит значения секретов на хосте агента, а сервер ссылается на них по
имени. Цель подключения (host, port, database, tls_mode) при этом выбирает
сервер. Захваченный или ошибочно настроенный сервер мог создать источник
`host=evil.example, password_ref=пароль-боевой-базы`: агент шёл туда и
проходил аутентификацию. Пароль уходил на чужой хост. Есть ещё два канала:
слабая аутентификация (`password`, `md5`) отдаёт пароль или его эквивалент
серверу, а TLS без проверки сертификата отдаёт его посреднику.

## Решение

### Привязка — слово оператора хоста
- `sudo sard-agent secret set <имя> --plugin <плагин> --target <шаблон>…`
  пишет рядом со значением файл привязки `secret-bindings/<имя>.yaml` рядом с
  главным конфигом. Файл принадлежит root, группа — группа службы, права 0640,
  каталог 0750. Это не часть конфига: агент предыдущей версии запускается с
  ним (решение 2), а после отката просто не применяет привязку.
- Шаблон цели: `host[:port][/база]`, IPv6 в скобках, сокет —
  `/каталог[:порт[/база]]` (база у сокета — только после порта). Порт или база,
  опущенные или `*`, — любые. Групповых символов в хосте нет. Имя хоста
  сравнивается без учёта регистра, IP-адреса — по значению; имя и адрес —
  разные цели.
- Секретов без привязки нет (решение 9). `secret set` без `--plugin` и
  `--target` не пишет ничего (код 2). Секрет, объявленный в конфиге вручную,
  получает файл привязки вручную или из образа (sard-self).
- Решение принимает хост агента (решение 1). Новый метод SDK
  `Host.SecretFor(name, sdk.Target) (sdk.Secret, error)` заменяет
  `Host.Secret`. Имя плагина хост знает сам. Секрет, который привязка не
  разрешает, — `*sdk.BindingError`: файл значения не читается, в ошибке есть
  имя, цель и команда для оператора, но нет ни значения, ни пути. Механизм
  общий: следующий плагин с секретами называет свою цель.
- Файл привязки, который может менять кто-то кроме root и агента (права
  записи для группы или прочих, другой владелец), или файл не той формы — тоже
  отказ.

### Подключение PostgreSQL
Одна функция `target.secured` → `target.conninfo` для psql (проверка,
отпечаток V2), pg_dump, pg_dumpall, pg_restore и отката (R2, V5):
- `require_auth=scram-sha-256` по TCP — в строке подключения, а не в
  `PGREQUIREAUTH`. libpq ниже 16 отвергает неизвестный параметр строки до
  подключения, а неизвестную переменную пропустила бы молча. На сокете —
  только если привязка задаёт `--auth`: peer и trust на сокетах остаются
  рабочими.
- `--auth` привязки — точный список допустимых методов (`scram-sha-256`,
  `md5`, `password`, `none`).
- `channel_binding=require`, когда TLS включён и разрешён только SCRAM.
  Привязка может снять требование (`--allow-no-channel-binding`), например для
  пулера.
- tls_mode слабее verify-full к серверу в сети (не сокет, не `localhost`, не
  127.0.0.0/8, не ::1) — отказ до запуска программ, если привязка не
  разрешает `--allow-tls require|disable` (решение 6: ломать текущие установки
  можно).
- Без tls_mode сервер в сети получает `verify-full`, сервер на этом хосте —
  `require`, сокет — `disable`.
- CA: `--ca-file` привязки, иначе `tls_root_cert` источника, иначе
  `sslrootcert=system`.
- Подсказки к отказам libpq добавляются к сообщению шага: старый клиент,
  слабый метод, нет channel binding, нет CA.

### Видимость
- `RegisterRequest.secrets` (поле 13, `SecretInfo`): каждый секрет хоста с
  плагином, целями, разрешениями (`auth`, `allow_tls`,
  `allow_no_channel_binding`) и причиной, по которой его не отдают никому.
  Только имена и цели: без значения, без пути, без `ca_file`. Сервер хранит их в
  `agents.secret_bindings` (jsonb) и проверяет так же, как остальной снимок
  Register (количество, размер, NUL).
- Поле 8 `secret_names` остаётся заполненным. Владелец разрешил его удалить
  (N−1 нет), но гейт proto запрещает ломающие изменения против `main`
  (`buf breaking`, категория FILE). Удаление — отдельное решение владельца об
  исключении из гейта.
- Цель в схеме плагина помечает ключевое слово `x-sard-target`
  (`host`, `port`, `database`; умолчание порта — `default` поля),
  `sdk.TargetKeyword`. Сервер не знает плагинов: цель он берёт по этим
  пометкам, секрет — по `format: sard-secret`.
- Сервер сопоставляет цель источника с привязками по той же грамматике, что
  агент (`SecretTargets`). Это предупреждение, а не отказ: у `Source` в REST есть
  `secretWarnings` (их считает `SourceWarnings` для слоя API, а не сервис
  `Sources`), на странице источника показывается каждое — с командой
  для хоста. Решает агент; несовпадение реализаций даст неверное
  предупреждение, но пароль не выпустит.
- `sard-agent check`: строка `secret.bound` по каждому секрету.

## Оборотная сторона и как продукт её ловит
- Оператор должен знать цели заранее. Шаг с целью вне привязки падает с
  точной командой, а `secret list` показывает BOUND_TO.
- Привязка по имени хоста не защищает от подмены DNS. Защищает verify-full,
  и он теперь по умолчанию.
- Грамматика цели написана дважды, на Go (агент) и на Kotlin (консоль). Тесты
  сервера повторяют случаи из `secretbind/pattern_test.go`.
- Хосты с клиентом PostgreSQL ниже 16 теряют сетевые источники, пока не
  поставят клиент новее. Образ агента -pg18 его уже содержит.

## Отвергнуто
- Хранить привязку в `agent.d` или в `secrets:` конфига: конфиг читается с
  `KnownFields`, агент N−1 не запустился бы (решение 2).
- Проверять цель в плагине: каждый следующий плагин повторял бы проверку, а
  ошибся бы хоть один — пароль ушёл бы.

## Отложено
- Пути на хосте, которые задаёт сервер (`pg_dump_path`, `pg_restore_path`,
  `tls_root_cert`): OQ-262.
