# 0041 — Подписанные пакеты агента и их раздача сервером

- Статус: принято (U1a, решение D12); ответы владельца на контрольной точке 1 — 2026-10-04; номер присвоен в X2c
- Дата: 2026-10-04
- Связано: ADR 0008 (сервер — не хранитель ключей), ADR 0017 (restic в поставке агента), ADR 0018 (упаковка агента), ADR 0020 (e2e из пакета); OQ-024

## Контекст
К концу M2 администратор должен ставить и обновлять агента со своего сервера Sard.
`make package` (ADR 0018) уже собирает tar.gz, deb и rpm под amd64 и arm64 с
`SHA256SUMS`, но релизов нет: нет тегов, нет задачи CI для них, пакеты не
подписаны (OQ-024 — «позже этапа 2»). Модель доверия ADR 0008: взломанный
сервер не может выполнить код на хостах. Раздача пакетов сервером — новый путь,
по которому код приходит на хосты, поэтому подпись нужна сейчас, а не в этапе 2.

## Решение
- **Сервер раздаёт, но не подписывает.** Пакеты подписываются ключом релизов,
  которого на сервере нет. Сервер версии N несёт в образе пакеты агента
  версии N и раздаёт только их; скачивания у вендора во время работы нет —
  работает в закрытых контурах.
- **Схема подписи — minisign (Ed25519) над `SHA256SUMS` релиза.** В
  `SHA256SUMS` — каждый tar.gz, deb, rpm и `manifest.json`; подпись —
  `SHA256SUMS.minisig` с доверенным комментарием `sard-agent <версия>`, так что
  подпись одной версии не выдать за другую. Проверка — стандартными
  инструментами: `minisign -Vm SHA256SUMS -p sard-release.pub && sha256sum -c
  SHA256SUMS`; то же с проверкой полноты списка и версии —
  `scripts/release-verify.sh`.
- **Публичный ключ** — `deploy/release/sard-release.pub`, его ID и строка
  ключа — в `README.md` и `docs/release.md`, то есть в репозитории, а не только
  на сервере.
- **Ключ подписи — в секретах GitHub** (ответ В1/В3 владельца: подпись — в CI).
  Секреты `MINISIGN_SECRET_KEY` (зашифрованный файл ключа) и
  `MINISIGN_PASSWORD` (его пароль) — только у окружения `release`: им
  пользуются лишь теги `v*`, и запуск ждёт подтверждения владельца. Защита
  workflow от подмены — правила репозитория: в `main` и в теги `v*` пишет
  только владелец, без прямых пушей посторонних; PR из форков этот workflow не
  запускают, `pull_request_target` не используется. Каждое стороннее действие
  закреплено по коммиту. Ключ попадает на диск раннера только на время одного
  вызова minisign, во временный файл `0600`, который удаляется при выходе;
  в логи, артефакты и репозиторий он не попадает. Порядок настройки —
  `docs/release.md`.
- **Воспроизводимая сборка** (ответ В2: нужна сейчас). Все времена в
  архивах и пакетах — `SOURCE_DATE_EPOCH` (время коммита), gzip без имени и
  времени, у rpm постоянный build host. Релиз собирается дважды на разных
  машинах; подпись — только если `SHA256SUMS` совпали. Любой может пересобрать
  тег и сверить суммы с подписанными.
- **Подписывается только проверенное.** Порядок `release.yml`: две сборки →
  сверка и тесты подделок (одноразовым тестовым ключом) и установка deb на
  Debian 12, 13, Ubuntu 22.04, 24.04 с systemd (установка, `enroll`,
  `repo init`, служба, обновление N → N+1) → подпись → публикация в GitHub
  Release с повторной проверкой.
- **restic в релизе — только с проверенной подписью**: релизная сборка
  требует `REQUIRE_SIGNATURE=1` (отложенное в ADR 0017). Ключ restic берётся с
  keys.openpgp.org, принимается только с отпечатком, закреплённым в
  `restic-version`.
- **Манифест** `manifest.json`: схема, версия, версия пакета, коммит, версия
  restic, `protocol_version` агента (из `ProtocolVersion`), список артефактов с
  ОС, архитектурой, форматом, размером и SHA-256. Признака «подписан» в
  манифесте нет: манифест входит в подписанное, наличие подписи видно по файлу
  `SHA256SUMS.minisig`.
- **deb и rpm** (ответы В6–В8): RPM остаётся в релизе и подписывается, его
  установка в CI не проверяется (этап 2). Первая установка отдаёт `/etc/sard`
  группе `sard-agent` (`root:sard-agent 0750`) и создаёт `/etc/sard/tls` и
  `/etc/sard/secrets` (`sard-agent 0700`) — туда пишут `enroll` и
  `repo init --generate-password` от имени пользователя службы; пример
  конфига указывает туда. Обновление этих каталогов не трогает. Служба
  останавливается и выключается только при удалении пакета; обновление
  перезапускает её, только если она работала (`try-restart`).
- **Образ сервера несёт пакеты своей версии.** Стадия `agent-packages` в
  `deploy/server/Dockerfile` берёт результат `make package` (по умолчанию
  `dist/`), проверяет `SHA256SUMS` и что версия в манифесте равна
  `SARD_VERSION`, иначе сборка падает; в образ попадают только файлы из
  `SHA256SUMS` и подпись — `/usr/share/sard/agent-packages/`. Релизный образ
  (`ghcr.io/artur-abalov/sard-server:<версия>`) собирается из подписанных
  файлов после задачи `sign`; образы вне релиза (`make up`, CI, e2e) несут
  неподписанные пакеты (ответ В10).
- **Раздача** — `GET`/`HEAD /downloads/agent/<файл>`, вне `/api`, без сессии:
  пакеты нужны хостам, на которых ещё ничего нет. Только файлы релиза (из
  манифеста, плюс `manifest.json`, `SHA256SUMS`, `SHA256SUMS.minisig`),
  остальное — 404, списка каталога нет. Range, `ETag` (SHA-256 файла),
  `Last-Modified`; пакеты (версия в имени) — `Cache-Control: public,
  max-age=31536000, immutable`, манифест, суммы и подпись — `no-cache`.
  Настройки `sard.agent-packages.enabled` (`SARD_AGENT_DOWNLOADS`, по
  умолчанию `true`) и `.dir`; включённая раздача без каталога, без манифеста
  или `SHA256SUMS`, с пакетом другого размера или другой версии, с именем
  файла не из одного сегмента — сервер не стартует (ответ В9); выключенная —
  404. Код — `server/.../downloads`.
- **Агент подпись сейчас не проверяет**: проверяет человек (в будущем — apt).
  Код агента в U1a не меняется.

## Следующий шаг (этап 2)
Автообновление агента. Чтобы канал обновлений не стал исключением из ADR 0008,
обновлятор получает **вшитый в агента публичный ключ релизов** и **запрет
отката** на версию ниже установленной; пакет, не прошедший проверку подписи
этим ключом, не ставится, откуда бы он ни пришёл — в том числе с сервера Sard.
Агенты один раз обновляются вручную на первую версию с обновлятором. Там же —
APT/RPM-репозиторий с подписанными метаданными (GPG).

## Последствия
- Владелец, а не CI, отвечает за доступ к `main`, тегам `v*` и окружению
  `release`: кто может их менять, тот может изменить подписываемое.
- Утечка ключа требует его смены: новый ключ в `deploy/release/`, `README.md`,
  `docs/release.md`; до этапа 2 агенты ключ не знают, поэтому смена не
  ломает установленных агентов.
- `make up` и `make e2e` собирают пакеты агента перед образом сервера; локальный
  `bootRun` и тесты сервера работают с `SARD_AGENT_DOWNLOADS=false`.
- Релиз зависит от keys.openpgp.org (ключ restic) и Docker Hub (образы
  дистрибутивов в тестах установки).
- Обновление с пакетов до U1a: их `preremove` выключал службу при обновлении,
  но релизов до U1a не было.

## Отвергнуто
- **Подпись владельцем локально** (`make release-sign`, ключ вне CI).
  Отвергнуто владельцем: «подписывать надо в CI, это очень опасно без него».
- **GPG над `SHA256SUMS`.** Тяжелее в проверке и в хранении ключа; нужен для
  APT-метаданных — этап 2.
- **Подпись каждого файла отдельно.** Подпись `SHA256SUMS` покрывает все
  файлы и манифест одной проверкой.
- **Sigstore/cosign без ключа.** Привязывает доверие к идентичности GitHub и
  внешнему журналу прозрачности; в закрытом контуре проверка требует сети.
