# 00XX — Сервер проверки восстановления: очередь, цикл, выдача, записи

- Статус: черновик (V4; решения владельца 2026-10-19, `docs/sessions/2026-10-19-v4-verification-server.md`)
- Дата: 2026-10-19
- Основа: `docs/design/sard-restore-verification.md` (V-D1…V-D10), ADR 0008, 0013, 0022, 0038, 0041

## Контекст
Проверку восстановления выполняет отдельный агент-верификатор (V1: роль в
сертификате, идентификатор машины). Сервер должен каждый день ставить проверку
последнего снимка каждого источника, выдавать её подходящему верификатору,
вести её как запуск со стадиями и отличать «бэкап плохой» от «проверка не
состоялась». До V4 `lastVerifiedAt()` всегда был `null`. Исполнение проверки на
агенте, песочница и отпечаток — V5 и V2. Тексты и каналы уведомлений — V6.

## Решение

### Попытка — обычный запуск
Задание проверки (`verification_jobs`) выполняется попытками. Каждая попытка —
запуск `trigger = verification` с одним шагом VERIFY, назначенным верификатору
(`runs/VerificationRuns`). Доставку шага, прогресс, приём результата и потерю
шага делают S6a, S7a и FXs без изменений. Отдельного опроса `ClaimJob` и
сервиса `Verifier` из документа нет (V-D8). «Аренда» документа — это окно
потери шага FXs.

Проверка — не бэкап. Индекс D6 `runs_active_source_key` не считает запуски
`trigger = verification`: бэкап и проверка одного источника идут рядом, никто
никого не ждёт (ADR 0022 для бэкапов не меняется). Проверки исключены из
свежести (F6), уведомлений о запусках, здоровья самобэкапа, обзора и истории
запусков в REST.

### Шаг без секретов
`RunStep` проверки несёт `plugin`, локальное для верификатора имя репозитория
(найденное по `repository_id`), `snapshot_id`, `timeout` и `verify`
(`VerifyTask`: идентификатор задания, `repository_id`, отпечаток и его SHA-256,
срок). `config_json` — `{}`: у верификатора нет доступа к боевым системам,
конфигурация источника ему не нужна (решение владельца). Набор полей закреплён
тестом.

### Что сообщает верификатор
`RegisterRequest.verifier` (`VerifierStatus`: свободное место, песочница).
Ключи — `repositories[].repository_id`, плагины — `plugins[].actions` с VERIFY.
Агент без `verifier` (старше V4) верификатором не считается. До V5 агент шлёт
пустой статус: место и песочница неизвестны, неизвестное место не исключает
верификатор, а помечается предупреждением `space_unknown`. `Heartbeat.verifier`
в контракте есть, сервер его пока не читает.

### Выбор верификатора (`VerifierChoice`)
Подходит агент, который:
- онлайн, не отозван, роль verifier, прислал `verifier` и `machine_id`;
- сообщает `repository_id` задания и плагин задания с VERIFY;
- стоит не на машине агента источника и не на машине агента, сделавшего снимок
  (V-D7);
- имеет место ≥ `total_bytes` × `space-factor` + `space-headroom`
  (по умолчанию × 2 + 1 ГиБ; отпечатка V2 пока нет);
- не выполняет другую проверку.

Из подходящих — наименьшее число проверок за сутки, затем меньший id. Причины
отказа хранятся по каждому верификатору (`unsuitable`) для REST и V6.

### Цикл
Одно расписание на установку (`verification_schedule`, глобальная таблица; без
строки — `sard.verification.default-cron`, по умолчанию `30 4 * * *` в поясе
установки). Момент цикла вычисляется: последний момент cron ≤ сейчас, не раньше
изменения расписания. Источник с включённой проверкой и целым снимком получает
задание цикла, если с этого момента у него его не было; частичный уникальный
индекс держит одно открытое задание на источник (V-D9). Отдельной строки
состояния и блокировки у цикла нет: повторный такт и второй сервер второго
задания не создают. Тот же снимок проверяется снова, если новее нет.

Задание ждёт подходящего верификатора до следующего момента цикла, затем
записывается как `no_verifier` с причинами. В тенанте без единого верификатора
задания не создаются, и записей нет: «нет верификатора» там — состояние,
которое показывает REST (решение владельца 7, «без спама» по построению).

### Итог
Такт (`VerificationLoop`, раз в `sard.verification.interval`) в транзакции
тенанта: разбирает закончившиеся попытки, ведёт эпизоды «давно не проверялся»,
выдаёт задания (SKIP LOCKED), создаёт задания цикла и выдаёт их. Итог берётся
из шага, а не из события `RunFinished`, поэтому сервер, остановившийся между
ними, разберёт попытку на следующем такте.

- Вердикт агента (`VerifyOutput.verdict`): `passed`, `failed` (бэкап плохой),
  `cannot_verify` (окружение верификатора). `passed` засчитывается, только если
  шаг успешен и достигнут уровень ≥ 4; иначе — `cannot_verify`.
- Ответ без вердикта (агент старше V4) — `cannot_verify`.
- Попытка без вердикта (`lost`, `rejected`, `timed_out`, `cancelled`) — повтор
  на том же или другом верификаторе. Три подряд — `infrastructure_failure`.
- Уровень (V-D2): стадия несёт уровень 1–4 или 0 (подготовка, уборка).
  Достигнут наивысший L, для которого все стадии уровней ≤ L прошли или
  неприменимы. Уровень 5 — когда достигнут 4 и прислано время восстановления.
  Провал стадии уровня 0 даёт уровень 0.

### Записи и события
`restore_verifications` (ADR 0013) — неизменная история, по строке на
закрытое задание: верификатор, шаг, `key_holders`, статус, уровень, стадии с
уликами, расхождения, причины, время восстановления. События для V6:
- «проверка провалилась» — запись `status = failed`;
- «проверка снова прошла» — `recovered = true` (успех сразу после провала);
- «не проверялся успешно дольше N дней» — эпизод
  `verification_stale_episodes`: открывается один раз, закрывается следующим
  успехом. Отсчёт — от последнего успеха или от первого целого снимка.
  `sard.verification.stale-after`, по умолчанию 7 дней.

Планирование доставок (`notification_deliveries`) и тексты — V6.

### REST
- `GET` и `PUT /sources/{id}/verification`;
- `GET /sources/{id}/verifications` и `POST` («проверить сейчас»: 202, 409
  `verification_active`, 422 `snapshot_unusable`);
- `GET /verifications/{id}`;
- `GET` и `PUT /verification-schedule`;
- `GET /verifiers?sourceId=`.

`Source` получил `verificationEnabled`, `verificationStatus`, `lastVerifiedAt`,
`lastVerifiedLevel`. `GET /status.lastVerifiedRestoreAt` — самая старая из
последних успешных проверок по источникам с включённой проверкой и целым
снимком; `null`, пока у одного из них её нет (решение владельца 5).

## Последствия
- Источники самобэкапа (F6) проверяются тем же механизмом.
- Два сервера могут в одном такте выдать одному верификатору по заданию:
  занятость читается без блокировки. Окно — один такт; приемлемо для MVP.
- До V5 ни один встроенный плагин не объявляет VERIFY. В боевой установке
  каждое задание закончится `no_verifier` с причиной `no_plugin`. Это честное
  состояние, а эпизод «давно не проверялся» о нём скажет.
- Стадии по ходу (`StepProgress.stage`) в контракте есть, сервер хранит только
  итоговые стадии из `VerifyOutput`.
- Новый вызов `sessions.system`: `VerificationLoop.tick` читает список
  тенантов и расписание (ADR 0013, системные вызовы, п. 9).

## Отвергнуто
- **Отдельная таблица шагов проверки со своей выдачей и потерей** — копия
  S6a/S7a/FXs.
- **Строка цикла на тенант с `next_run_at`** — такт создавал бы её в каждом
  тенанте и мешал удалению тенантов; задача требует одно расписание на
  установку.
- **Запись `no_verifier` в каждом цикле для тенанта без верификаторов** —
  спам. Состояние выводится из отсутствия верификаторов.
- **Конфигурация источника в шаге проверки** — верификатору она не нужна и
  раскрывает адреса боевых систем.
