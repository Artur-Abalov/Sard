# 0046 — Консоль за обратным прокси: forward-headers Spring Boot

- Статус: принято; решение владельца — 2026-10-06 (развёртывание в OCI за Cloudflare Tunnel)
- Дата: 2026-10-06
- Дополняет: ADR 0021 (Р4 «заголовкам прокси не доверяем», «Последствия»)

## Контекст
`OriginGuardFilter` (ADR 0021, К1/Р5) сверяет `Origin` изменяющего запроса с
`<схема соединения>://<Host>`. Прокси, завершающий TLS (Cloudflare Tunnel,
nginx, Caddy), приходит к серверу по HTTP, а браузер присылает
`Origin: https://…`. Поэтому вход и любые изменения отвечали 403
`origin_rejected`, cookie `sard_session` не получал `Secure`, а блокировка
перебора считала всех клиентов одним адресом прокси (OQ-031, OQ-033,
OQ-142). Консоль должна работать на любом имени, которое выберет оператор.
Перечислять имена в конфиге сервера нельзя.

Проверено на развёртывании владельца (OCI, Cloudflare Tunnel, cloudflared
на хосте): вход работает со стандартной настройкой Spring Boot
`server.forward-headers-strategy=native`, без изменений кода.

## Решение
- **Используем штатный механизм, своего кода нет.** Это Tomcat
  `RemoteIpValve` через `server.forward-headers-strategy`. Переменная
  `SARD_FORWARD_HEADERS` проброшена в `application.yaml` и
  `deploy/docker-compose.yml`, по умолчанию `none`, как в ADR 0021.
  Значение `native` включает доверие:
  - `request.isSecure` и схема берутся из `X-Forwarded-Proto`, поэтому
    `OriginGuardFilter` и `Secure` у cookie работают без изменений;
  - `remoteAddr` — самый правый адрес из `X-Forwarded-For`, который не входит
    в доверенные. Клиент не может подставить чужой адрес: прокси дописывает
    настоящий в конец. Лог и `LoginAttemptTracker` видят клиента.
- **Кому верим.** Это умолчание Spring Boot 4.1 для `internal-proxies`:
  loopback, частные и link-local сети IPv4/IPv6 и `100.64.0.0/10`. Сузить до
  `127.0.0.1` нельзя: прокси на хосте приходит в контейнер с адреса шлюза
  Docker-сети. Проверено: соединение на порт, опубликованный на
  `127.0.0.1`, контейнер видит с `172.17.0.1`. Граница доверия — публикация
  порта 8080 только на loopback (`SARD_HTTP_PUBLISH`, умолчание compose).
  Это записано в `deploy/.env.example` и `docs/operator/04-tls-and-names.md`.
  Тонкая настройка возможна через `SERVER_TOMCAT_REMOTEIP_INTERNAL_PROXIES`
  в override-файле compose, но продуктом не поддерживается.
- **`Host` прокси обязан передавать без изменений.** Фильтр читает сам
  заголовок `Host`, а не `X-Forwarded-Host`. Для nginx это
  `proxy_set_header Host $host` (документация оператора).
- **Поддерживаются только `none` и `native`.** `framework` (Spring
  `ForwardedHeaderFilter`) верит заголовкам от любого адреса, поэтому в
  документации его нет.

## Отвергнуто
- **Свой фильтр с `SARD_TRUSTED_PROXIES` (CIDR).** Он повторяет
  `RemoteIpValve`, а это свой разбор `X-Forwarded-For` и свои ошибки. Выигрыш —
  только формат списка. Вернуться к нему стоит, если понадобится доверие к
  удалённому прокси с публичным адресом.
- **CSRF по `Sec-Fetch-Site` вместо сравнения с `Host`.** Это решает только
  `Origin`: `Secure` и адрес клиента по-прежнему требуют знать, что пришло от
  прокси. Как только сервер это знает, текущий фильтр работает и так.
- **Список разрешённых `Origin` или `SARD_CONSOLE_PUBLIC_URL` как эталон.**
  Каждое имя пришлось бы перечислять, а `public-url` по ADR — только ссылка в
  уведомлениях и из заголовков не выводится.
- **`native` по умолчанию.** Туннель заработал бы без настройки, но при
  `SARD_HTTP_PUBLISH=0.0.0.0:8080` любой хост частной сети подделал бы адрес
  клиента и обошёл блокировку перебора. Включение — явное, одной строкой в
  `.env`.

## Последствия
- Поведение по умолчанию не меняется. `ReverseProxyHeadersIgnoredByDefaultIntegrationTest`
  фиксирует, что без переменной заголовки прокси игнорируются.
- `ReverseProxyIntegrationTest` (реальный Tomcat, случайный порт) проверяет за
  прокси: вход с `Secure`, чужой `Origin` — 403, адрес клиента в логе из
  `X-Forwarded-For`, блокировка перебора по адресу клиента. Это закрывает
  OQ-033: `Secure` наконец проверен интеграционным тестом.
- Обновление Spring Boot может сменить умолчание `internal-proxies`. Тесты
  заметят только потерю доверия к loopback, а не расширение списка.
  Документация оператора называет версию.
