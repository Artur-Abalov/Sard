# 00XX — mutflow: порядок классов и отдельная JVM для Spring-тестов мутаций (черновик)

- Статус: черновик (номер — при слиянии); решение владельца по PR #61 «порядок + изоляция»
- Дата: 2026-10-12
- Дополняет: ADR 0006 (мутационное тестирование)

## Контекст
Мутационный шаг шлюза (`-Pmutflow.enabled=true :server:test --rerun`) выдавал недетерминированные
«MUTANT SURVIVED» в коде, не связанном с проверяемым тестом: на CI `StepDispatcher.kt`,
`AgentConnections.kt`, `AgentStreamSweeper.kt`, `SessionRevalidation.kt` под
`EnrollmentStatusTest` и `CaImportSourceTest`; локально — `Scheduler.kt`, `NotifyConfiguration.kt`,
`TenantSessions.kt` под `CaDirectoryTest`; в другом прогоне — ни одного.

Причина: `io.github.anschnapp.mutflow.MutationRegistry` 1.5.0 хранит сессию в глобальном
`private static volatile Session currentSession`, а не в `ThreadLocal` (проверено `javap`). Пока идёт
тест с `@MutFlowTest`, любой поток, исполняющий мутированный код, регистрирует точки в сессии этого
теста. Фоновые потоки кэшированных контекстов Spring (проверка потоков агентов, тики планировщика,
рассылка уведомлений, Hikari/JPA) попадают в посторонние юнит-тесты, и те «не убивают» чужих мутантов.

## Решение
1. **Порядок классов.** `SpringContextsLastOrderer` (`ClassOrderer`, включён в
   `server/src/test/resources/junit-platform.properties`) ставит классы с `@SpringBootTest`
   (прямо или через составную аннотацию) в конец, остальные идут первыми; внутри группы — по имени
   класса. Юнит-тесты выполняются, пока ни одного контекста ещё нет. Классы, которые сами поднимают
   сервер (`Installations`, `ApplicationContextRunner`), закрывают его в конце теста.
2. **Изоляция.** Классы, у которых есть и `@MutFlowTest`, и Spring-контекст, помечены
   `@Tag("mutflow-isolated")` и идут в отдельной задаче Gradle `isolatedTest`
   (`forkEvery = 1`: своя JVM на класс, чужих контекстов нет). Из `test` они исключены
   (`excludeTags`). Обе задачи настроены одинаково (`withType<Test>`: свойства, окружение, куча 1 ГиБ;
   плагин mutflow ставит мутированные классы первыми в classpath каждой задачи `Test`);
   `check` зависит от `isolatedTest`, JaCoCo-отчёт и проверка покрытия читают данные обеих задач.
   `scripts/gate.sh` запускает обе задачи с `--rerun`.
3. **Защита от гниения.** `MutationIsolationTest` обходит скомпилированные тестовые классы и падает,
   если класс с `@MutFlowTest` и Spring-контекстом не помечен тегом (или тег стоит на классе без того
   и другого). `SpringContextsLastOrdererTest` проверяет порядок.

## Отвергнуто
- **Ограничить кэш контекстов Spring.** Меняет только то, какие тесты видят фоновые мутанты;
  получались другие наборы выживших, причина оставалась.
- **Убивать выживших по одному.** Это симптом: набор меняется от прогона к прогону и не связан с
  тестом, который его «получил».
- Исключить фоновые классы из мутаций: нарушает запрет на подавление (ADR 0006).

## Последствия
- Новый Spring-тест с `@MutFlowTest` без тега ловит `MutationIsolationTest`.
- Остаточный риск: фоновый поток мутированного кода в JVM юнит-теста, не связанный с Spring
  (пул, таймер самого теста). Такие потоки должны закрываться тестом.
- Своя JVM не спасает от фоновых потоков собственного контекста. Код Sard не должен стоять
  на пути, по которому чужой поток проходит в случайный момент. Так было с фильтром метров
  `MeterFilter` (`MetricsConfiguration.kt:45`): он исполнялся при каждой первой регистрации метра,
  а метры регистрируют поток уведомлений GC (новая причина `jvm.gc.pause`) и исполнители gRPC
  (новый метод `grpc.server.*`). Выжившие в нём кочевали между `W2MutationTest`,
  `RestorePostgresMutationTest`, `BuiltinEnrollmentTokensIntegrationTest` и
  `SelfAgentWiringIntegrationTest` (24.10.2026, трассировка полного прогона: регистрации
  во время тестов). Отбор метров перенесён в scrape (`ExposedMeters`); первый тик метрик
  состояния тест дожидается целиком (`FreeMetricsPort`).
