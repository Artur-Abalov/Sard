# QA: расписания бэкапов (F3b)

Сценарии: `docs/specs/server/schedules.feature`,
`docs/specs/server/schedule-notifications.feature`,
`docs/specs/web/schedules.feature`. **Черновик, не утверждён владельцем:**
шаги с пометкой `(ОВ…)`, `(П…)`, `(Н…)`, `(ВП…)` проверяют предложения,
которые ещё ждут решения; если владелец решит иначе, шаг меняется вместе со
спецификацией.

Здесь вручную проходятся сценарии `@qa` и `@qa-only` и сквозной путь
«расписание в консоли → планировщик → агент → сообщение в Telegram» на
настоящих часах. Таблицы описаний, правила частоты, летнее время, гонки и
сбои базы проверяются тестами `@unit`, `@server`, `@vitest`, `@mocks` с теми же
названиями.

Ожидаемый результат указан после «→» в каждом шаге. Любое расхождение — дефект.
Время срабатываний в процедуре — «каждую минуту»: части 3–6 идут минутами,
а не сутками.

## Подготовка

1. Выполнить «Подготовку» из `docs/qa/run-notifications.md` (шаги 1–2:
   сервер, агент, репозиторий `qa`, бот, `SARD_CONSOLE_PUBLIC_URL`,
   `SARD_NOTIFY_LANGUAGE=ru`; функции `src`, `run`, `dlv`, `waitdlv`;
   переменные `API`, `PSQL`, `DC`, `QA`, `D`, `AGENT`, `AG`, `H`, `AGPID`).
2. Задать пояс сервера (П9) и вспомогательные функции:

```bash
sed -i '/^#\? *TZ=/d' deploy/.env; echo 'TZ=Europe/Moscow' >> deploy/.env
$DC up -d --wait server
J='Content-Type: application/json'
# prev <cron> [timezone] [lang] — предпросмотр
prev() { curl -sS -b $QA/jf -G $API/schedule-preview --data-urlencode "cron=$1" \
  ${2:+--data-urlencode "timezone=$2"} ${3:+--data-urlencode "lang=$3"}; }
# sch <source-id> — расписание; fires <source-id> — журнал, новые сверху
sch() { curl -sS -b $QA/jf $API/sources/$1/schedule; }
fires() { curl -sS -b $QA/jf "$API/sources/$1/schedule/fires?limit=20" | jq -c '.items[] | {kind, outcome, runId, reason, missedCount, missedCountCapped, skippedInRow, alert}'; }
# setsch <source-id> <cron> <enabled> — расписание в поясе Europe/Moscow
setsch() { curl -sS -b $QA/jf -X PUT $API/sources/$1/schedule -H "$J" \
  -d "{\"cron\":\"$2\",\"timezone\":\"Europe/Moscow\",\"enabled\":$3}"; }
```

   → сервер `healthy`.

## Часть 1. Предпросмотр (API)

3. `prev '0 2 * * *' Europe/Berlin ru | jq .`
   → `200`; `cron` = `"0 2 * * *"`; `timezone` = `"Europe/Berlin"`;
   `description` = `"Каждый день в 02:00"`; `nextFires` — три момента, каждый
   — 00:00Z (летом) или 01:00Z (зимой) трёх ближайших суток, строго позже
   текущего времени; `tooFrequent` = `false`.
4. `prev '0 2 * * *' | jq -r '.timezone, .description'`
   → `Europe/Moscow` (П9, пояс сервера) и `Every day at 02:00` (без `lang` — en, П7).
5. `prev '*/5 * * * *' UTC ru | jq -r '.description, .tooFrequent'` → `Каждые 5 минут`, `true` (ОВ1).
   `prev '*/15 * * * *' UTC | jq .tooFrequent` → `false`.
6. `prev '0 2 1-7 * 1' UTC ru | jq -r .description` → `Особое расписание: 0 2 1-7 * 1` (П4).
7. Ошибки — у каждой ответ `422`, `code` `validation_failed`, поле — в скобках:
   `prev '0 2 * *' UTC` (`cron`); `prev '@daily' UTC` (`cron`);
   `prev '0 0 30 2 *' UTC` (`cron`); `prev '0 2 * * *' '+03:00'` (`timezone`);
   `prev '0 2 * * *' UTC de` (`lang`);
   `prev "$(printf '0,%.0s' $(seq 1 100))0 2 * * *" UTC` — cron из 209 символов (`cron`, не `500`, G6).
   Проверка: `prev … | jq -r '.code, .errors[0].field'`.
8. `curl -sS -o /dev/null -w '%{http_code}' -G $API/schedule-preview --data-urlencode 'cron=0 2 * * *'` (без сессии) → `401`.
9. `$PSQL "select count(*) from schedules"` до и после шагов 3–7 → одинаково.

## Часть 2. Форма источника (консоль против сервера)

`cd web && npm run dev`, <http://localhost:5173>, язык RU. Открыть
инструменты разработчика, вкладку «Сеть».

10. «Создать источник»: агент, `files`, путь `$D`, репозиторий `qa`. В разделе
    «Расписание» по умолчанию «Без расписания». Выбрать «Каждый день», время `02:00`
    → запрос `GET /api/v1/schedule-preview` без `timezone`; выбор пояса
    показывает `Europe/Moscow`; под полем «Каждый день в 02:00» и три даты с
    `02:00` и названием `Europe/Moscow`; «Включено» отмечено (ВП1).
11. Выбрать пояс `Asia/Tokyo` → новый запрос с `timezone=Asia/Tokyo`; три даты —
    `02:00` `Asia/Tokyo`.
12. Переключить язык на EN → новый запрос с `lang=en`; описание `Every day at 02:00`;
    остальные надписи раздела — английские. Вернуть RU.
13. Переключить в режим «Cron» → поле содержит `0 2 * * *`. Быстро стереть и
    набрать `*/5 * * * *` → после паузы ввода один запрос предпросмотра, а не
    по одному на символ (ВП2); показано предупреждение о частоте (жёлтое, не
    красное); кнопка сохранения доступна (ВП4).
14. Набрать `0 2 * *` → у поля cron — локализованная ошибка; описания и дат нет.
15. Сохранить с `0 2 * *` → `POST /api/v1/sources` отправлен (ВП5), ответ `422`,
    ошибка у поля cron, все значения формы на месте;
    `$PSQL "select count(*) from sources"` не изменился (П1).
16. Набрать `* * * * *`, сохранить → один `POST /api/v1/sources`, в теле
    `schedule` с `cron` `* * * * *`, `timezone` `Asia/Tokyo`, `enabled` `true`;
    открыта карточка источника. Запомнить `S1=<id из адреса>`.
17. «Изменить» `S1` → открыт режим «Cron» с `* * * * *`, пояс `Asia/Tokyo`,
    варианта «Без расписания» нет (П3). Выбрать «По будням», `02:30`, сохранить →
    в теле `PUT` `schedule.cron` = `30 2 * * 1-5`; `sch $S1 | jq -r .cron` → `30 2 * * 1-5`.
18. «Изменить» `S1` → открыт вариант «По будням», `02:30`. Изменить только имя,
    сохранить → `PUT` содержит `schedule` с прежними значениями;
    `sch $S1 | jq -r .nextRunAt` — тот же, что до шага.
19. **Сеть.** Заполнить форму нового источника с «Раз в неделю», среда, `04:00`;
    `$DC stop server`; сохранить → сообщение о недоступности сервера; вариант,
    день, время и пояс на месте. `$DC start server`; сохранить снова → источник
    создан, `sch <id> | jq -r .cron` → `0 4 * * 3`.

## Часть 3. Пропуски, журнал и алерт (сквозной путь)

20. Остановить агента: `kill $AGPID`. Создать источник с расписанием каждую минуту:
    `S2=$(src "{\"paths\":[\"$D\"]}"); setsch $S2 '* * * * *' true >/dev/null`;
    запустить вручную: `R=$(curl -sS -b $QA/jf -X POST $API/sources/$S2/runs | jq -r .id)`
    (запуск в `queued` — агент офлайн, он активен).
21. Ждать 3 минуты 30 секунд. `fires $S2`
    → не меньше трёх строк `skipped_active` с `runId` = `$R`, `skippedInRow` 1, 2, 3…;
    у строки с `skippedInRow` 3 — `alert: true`, у остальных `false`.
22. В Telegram → **одно** сообщение (Н3, Н4):
    `⚠️ Бэкап по расписанию не выполняется: <имя S2>` (жирным);
    `Агент: <hostname>`; `Пропущено подряд: 3`;
    `Причина: предыдущий запуск всё ещё идёт`;
    `Пропущенное срабатывание: <ГГГГ-ММ-ДД ЧЧ:ММ> Europe/Moscow` — время третьей
    строки журнала в поясе Москвы; `Идущий запуск: $R`;
    `http://localhost:5173/runs/$R`. Ещё через 2 минуты новых алертов нет.
23. Консоль, карточка `S2` → раздел расписания: «Каждую минуту», пояс
    `Europe/Moscow`, следующий запуск — точное время в поясе Москвы и
    относительное; «пропущено подряд» с числом из `sch $S2 | jq .skippedInRow`;
    последнего запуска по расписанию ещё нет. Журнал: строки «пропущено —
    предыдущий запуск ещё идёт» со ссылкой; ссылка открывает карточку `$R`;
    у строки с `alert` — пометка об отправленном уведомлении.
24. Запустить агента (`"$AG" --config "$H/agent.yaml" >> $QA/agent.out 2>&1 & AGPID=$!`).
    Дождаться ближайшей минуты после завершения `$R`; `fires $S2 | head -1`
    → `run_created`, `skippedInRow` 0; на карточке — последний запуск по
    расписанию со статусом, триггером «по расписанию» и ссылкой; пока он
    активен, карточка обновляется сама (вкладка «Сеть» — запросы каждые 3 с).
25. Страница «Запуски» → колонка «Запущен»: у `$R` — «вручную», у новых — «по
    расписанию». На обзоре — то же.
26. В чате нет сообщений об успешных запусках по расписанию (правило 11); о
    ручном `$R` — обычное сообщение S9b без строки «По расписанию» (правило 13).

## Часть 4. Ошибка и восстановление

27. Сломать источник: в консоли «Изменить» `S2`, добавить путь `$QA/missing`,
    сохранить. Дождаться трёх срабатываний (3–4 минуты).
    → в Telegram **одно** сообщение: `❌ Бэкап завершился ошибкой: <имя S2>`,
    вторая строка `По расписанию` (Н1), далее `Агент`, `Длительность`,
    `Причина: …`, `Запуск: <id первого упавшего>`, ссылка. О втором и третьем
    упавших сообщений нет; `dlv <id второго>` → `skipped|0|`.
28. В консоли нажать «Запустить бэкап» у `S2` (вручную, путь всё ещё сломан)
    → сообщение S9b об ошибке без строки «По расписанию» (правило 13).
29. Починить: убрать `$QA/missing`, сохранить. Дождаться следующего срабатывания
    → **одно** сообщение: `✅ Бэкап снова работает: <имя S2>`, `По расписанию`,
    `Ошибок подряд перед этим: N`, где N — число запусков `failed` подряд перед
    ним, включая ручной шага 28 (сверить: `curl -sS -b $QA/jf "$API/runs?sourceId=$S2&limit=20" | jq -r '.items[].status'`) (Н2).
30. Ещё 2 минуты → новых сообщений об `S2` нет.
31. **Английский.** `sed -i 's/^SARD_NOTIFY_LANGUAGE=ru/SARD_NOTIFY_LANGUAGE=en/' deploy/.env; $DC up -d --wait server`;
    повторить шаги 27 и 29 → `❌ Backup failed: …` / `On schedule`;
    `✅ Backup is working again: …` / `Failures in a row before this: N`.
    Вернуть `ru`.

## Часть 5. Простой сервера и догоняющий запуск

32. `date -u; $DC stop server`; подождать 4 минуты; `date -u; $DC start server`;
    дождаться `healthy` и ещё 30 с.
    → `fires $S2 | head -3`: строка `skipped_downtime` с `missedCount` 3–4 и
    `missedCountCapped false`, затем `catch_up` / `run_created`;
    `curl -sS -b $QA/jf "$API/runs?sourceId=$S2&limit=5" | jq -c '.items[] | {trigger, catchUp}'`
    → у одного запуска `trigger` `catch_up` и `catchUp` с `missedFrom` и
    `missedUntil` — первое и последнее пропущенное срабатывание (целые минуты
    между остановкой и стартом), `missedCount` как в журнале,
    `timezone` `Europe/Moscow`; у остальных `catchUp` `null`.
33. Консоль: «Запуски» → у догоняющего — «догоняющий» и пометка «сервер не
    работал, пропущено N срабатываний с ЧЧ:ММ по ЧЧ:ММ» в поясе Москвы (П8);
    карточка этого запуска — тот же период. Журнал на карточке `S2` — строка
    простоя с тем же числом и периодом.
34. Алерта о пропусках за простой нет (простой не считается пропуском).

## Часть 6. Выключение

35. «Изменить» `S2`, снять «Включено», сохранить → карточка: «выключено»,
    описание есть, следующего запуска нет; `sch $S2 | jq '.enabled, .nextRunAt'`
    → `false`, `null`. Подождать 2 минуты → новых строк в `fires $S2` нет, новых
    запусков нет.
36. Источник без расписания (создан в части 2 без него или новый) → карточка
    говорит, что расписания нет и бэкап только вручную; ссылка ведёт в изменение;
    ошибок на странице нет (на `GET …/schedule` ответ `404` — ожидаемо).

## Часть 7. Уведомление об успехе (ОВ3)

Только если ОВ3 принят.

37. «Изменить» `S2`: включить расписание, отметить «Уведомлять об успешных
    бэкапах по расписанию», сохранить → в теле `notifyOnSuccess: true`; у
    переключателя пояснение, что об ошибках и восстановлении сообщения
    приходят всегда. Каждую минуту → сообщение `✅ Бэкап выполнен: …` со
    второй строкой `По расписанию`. Снять отметку → сообщения прекращаются.

## Часть 8. Консоль на моках

38. `cd web && VITE_API_MOCKS=1 npm run dev`. Повторить шаги 10–18 и 23, 25, 33
    по фикстурам моков (источники без расписания, с включённым, выключенным и
    с назначенным догоняющим; журнал со всеми исходами).
    → поведение консоли то же. **Отличия проходов:** мок не вычисляет cron —
    описание и даты верны только для готовых вариантов и `*/5 * * * *`, для
    любого другого cron мок отвечает «Особое расписание: …» и три даты с шагом
    в сутки; пояс сервера мока — `Europe/Moscow`; мок не срабатывает по
    расписанию, журнал и догоняющий запуск — из фикстур.

## Часть 9. Документация

39. `docs/operations/scheduler.md` → описывает задание расписания в консоли,
    предпросмотр (`/api/v1/schedule-preview`), порог частоты 15 минут, пояс по
    умолчанию и `TZ` (П9), что `catchUp` запуска называет период пропущенных
    срабатываний.
40. `docs/operations/notifications.md` → тексты «По расписанию», «Догоняющий
    запуск после простоя сервера», «снова работает» с числом ошибок, алерт о
    пропусках (оба языка), `notifyOnSuccess` (если ОВ3 принят); строки о
    «временном тексте» F3a нет.
41. `grep -n '^#\? *TZ=' deploy/.env.example` → строка есть, с пояснением.

## Завершение

42. `kill $AGPID`; `setsch $S2 '* * * * *' false`; убрать `TZ=` из `deploy/.env`;
    `chmod -R u+rwX $QA`; отозвать токен бота, если он создавался только для QA.
