### Черновик API
```go
package redact

const Marker = "[REDACTED]"

// New оборачивает dst. values — сырые значения; варианты кодирования
// строятся внутри. Пустые значения — ошибка (без текста значения).
func New(dst io.Writer, values [][]byte, opts ...Option) (*Writer, error)

func (w *Writer) Write(p []byte) (int, error) // n == len(p) при err == nil
func (w *Writer) Flush() error // выдаёт всё, что уже безопасно; хвост держит
func (w *Writer) Close() error // выдаёт хвост; дальше Write → ErrClosed
```
Не потокобезопасен: stdout и stderr — отдельные `Writer`.

### Черновик алгоритма
- Aho–Corasick по всем вариантам всех значений, байтовый алфавит,
  разреженные переходы + ссылки неудач (плотная таблица 256×узлы для
  десятков PEM-ключей в нескольких вариантах — сотни МБ).
- Инвариант границы: любое будущее вхождение начинается не раньше
  `pos − depth(state) + 1`, где `depth` — длина наибольшего суффикса,
  являющегося префиксом значения. Всё левее — либо выдано, либо внутри
  диапазона маскирования. Придерживаемый хвост ≤ `maxLen − 1` байт.
- Совпадения объединяются в диапазоны: новое совпадение, начинающееся не
  правее конца открытого диапазона (+0 — касание тоже сливается),
  продлевает его. Байты диапазона не буферизуются — хранится только его
  конец; маркер выдаётся один раз, когда диапазон закрыт.
- Итог зависит только от объединения диапазонов всех вхождений во всём
  тексте — поэтому не зависит от разбиения на порции. На этом и стоит
  тест свойства; эталон — наивный поиск `bytes.Index` по всем позициям.
- Время O(n + число совпадений) на поток, память O(суммарная длина
  вариантов).

## Фаза 3: бенчмарк, оптимизация

### Бенчмарк (`bench_test.go`, проверил запуском)
Поток — строки вида `restic --json`, каждая 50-я несёт секрет; 42 значения:
40 случайных по 12–48 байт и два PEM по ~1,7 КБ с символами `+/=@:% `,
т. е. со всеми вариантами кодирования. `TestBenchStreamIsMasked`
проверяет, что секреты бенчмарка действительно находятся. Машина
контейнера, 4 ядра, `-benchtime 10x -count 3`, медианы:

| Случай | до оптимизации | после |
|---|---|---|
| 8 МиБ, порции 4096 | 60 мс, 15,2 МБ/оп, 41 тыс. аллокаций | 58 мс (≈144 МБ/с), 6,15 МБ/оп, 37,5 тыс. |
| 8 МиБ, порции 17 | 96 мс, 18,9 МБ/оп, 524 тыс. | 78 мс (≈107 МБ/с), 6,15 МБ/оп, 37,5 тыс. |
| 1 МиБ, порции 4096 | 12,7 мс | 12,3 мс |
| `New` (42 значения) | 7,5 мс, 6,1 МБ, 37,5 тыс. | без изменений |
| a^k b, k = 1..40, поток из «a», 1 / 8 МиБ | — | 25,7 / 200 мс (≈41 МБ/с) |

- Линейность: без учёта `New` 8 МиБ обходятся в 8,4–8,8 раза дороже
  1 МиБ; на неудобном входе — ровно в 7,8 раза. Проверил.
- После оптимизации память и аллокации на операцию совпадают с `New`:
  `Write` в установившемся режиме не аллоцирует.

### Оптимизация
- `Write` больше не копирует порцию в `pend`: байты читаются из хвоста и
  из текущей порции (`appendStream`), в конце вызова в `pend` копируется
  только хвост (`holdTail`, два буфера по очереди). Порция после `Write`
  не удерживается (контракт `io.Writer`).
- Сдвиг `spans` — `slices.Delete` вместо `spans[1:]`, ёмкость не теряется.
- Тест свойства сразу поймал ошибку новой версии: диапазон, целиком лежащий
  в хвосте прошлой порции (`"\n\n" + "\na"` при значении `"\n\na"`) —
  выход за границу среза. Исправил, случай добавлен в таблицу
  (`TestSettledRangeInsideHeldTail`).
- Дальше не оптимизировал: вывод restic — килобайты в секунду, запас на
  порядки. `New` (7,5 мс) вызывается один раз на запуск. Возможные шаги,
  если понадобится: плотные переходы для неглубоких узлов, плоский массив
  рёбер вместо среза на узел.
