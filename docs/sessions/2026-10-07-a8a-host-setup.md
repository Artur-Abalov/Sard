# Сессия 2026-10-07: A8a — настройка хоста агента командами (coder)

Ветка `claude/gifted-rubin-b9ffcr`. Спецификация —
`docs/specs/agent/host-setup.feature` (утверждена владельцем 2026-10-07) и её
поправки в `repo-init.feature` (Р21, Р24, Л4а) и `agent-enroll.feature` (Р25,
Р25а, В12). Ручная проверка — `docs/qa/host-setup.md`,
`docs/qa/repo-init.md`, `docs/qa/agent-enroll.md`.

## Сделано

- **Конфиг.** `config.Load` читает `agent.d` рядом с основным файлом: только
  `repositories` и `secrets`, порядок файлов по именам, `DUPLICATE_NAME` с
  обоими файлами, ключ `service.user` (только в основном конфиге).
  `Repository.Fragment` и `Config.SecretSource` помнят, откуда пришло
  определение; сообщения A1 называют файл фрагмента. ADR 0048.
- **`internal/hostsetup`** (новый пакет): правило прав, источники секрета,
  атомарная запись с владельцем, блокировка конфига, политика перезапуска по
  журналу FXa, аудит, `systemctl`, терминал без эха через `ioctl` из
  `syscall` (новых зависимостей нет), drop-in systemd. Всё, что трогает хост,
  — за интерфейсами (`FS`, `Systemd`, `Auditor`, `Terminal`, `LookupFunc`). ADR 0049.
- **Команды.** `secret set|list|remove`; `repo add` (локальный путь,
  заглушка `BACKEND_NOT_SUPPORTED`), `repo show`, `repo remove`,
  `repo password --reveal`; `--json` у `repo list`, `repo show`, `secret list`;
  `repo init` и `repo list` под правилом прав; restic от пользователя службы
  (`restic.RunAs`, `SysProcAttr.Credential`).
- **`enroll`** под правилом прав: под root файлы `tls.*` принадлежат
  пользователю службы (владелец выставляется временному файлу до
  переименования), отсутствующий последний каталог создаётся и при неудаче
  удаляется (Р25, Р25а). `enroll.WriteIdentityAs`, `enroll.NewWriteError`.
- **Упаковка и документы.** `deploy/agent/postinstall.sh` и
  `scripts/test-postinstall.sh` без `sudo -u`; `docs/operations/agent-host-setup.md`
  (новая), правки `agent-enroll.md`, `agent-install.md`, `repo-init.md`,
  `docs/operator/05-agents.md`; ADR 0048 и 0049.

## Порядок работы

Тест перед кодом, красный запуск по существу и затем код — для конфига
(`agent.d`), A1 по фрагментам, правила прав, источников секрета, атомарной
записи, `secret set|list|remove`, `repo list --json`, справки и
`WriteIdentityAs`. Для `repo add`, `repo show`, `repo remove`,
`repo password`, `enroll` под `sudo`, каталога `tls.*` и сценариев `@start`
набор тестов писался целиком и реализация за ним, но красный запуск
по существу был не у каждого теста: часть тестов впервые запущена уже с
кодом (и прошла). Это отступление от цикла «один тест — один красный запуск»
записано здесь, чтобы cleaner и hardener знали, где искать слабые тесты:
мутационное тестирование (`gate.sh agent`, без `fast`) этим слоям нужнее
всего.

## Решения coder в рамках спецификации

- **Правило прав и `service.user`.** Р5 требует проверку до чтения конфига, а
  имя пользователя службы лежит в конфиге. `config.PeekServiceUser` вынимает
  только этот ключ и не отказывает: нет файла или он не разбирается — имя по
  умолчанию; ошибку конфига сообщает следующий шаг. На порядок отказов это
  влияет только так: постороннему пользователю с битым конфигом скажут
  `PRIVILEGES_REQUIRED`, а не ошибку конфига.
- **Терминал: два запроса всегда.** Р7 («дважды») применён и к паролю
  существующего репозитория у `repo add`.
- **Пароль из флагов `repo add` читается до блокировок и создания каталога**,
  а не после `restic cat config` (Р14): пустой или слишком большой ввод
  отказывает, пока на хосте ничего не создано. Меняется только то, какая из
  двух одновременных ошибок выигрывает.
- **`repo add`: проверка кандидата.** Пароль (данный, оставшийся файл или
  сгенерированный) пробуется на временном файле в `secrets`; репозиторий,
  который не открывается сгенерированным или оставшимся паролем, значит
  «существует» — тогда нужен пароль от оператора. Временный файл становится
  `restic-<имя>.pass` до `restic init` (Р16).
- **«Повтор»: `unchanged` только если репозиторий открывается.** Фрагмент
  есть, адрес тот же, `restic cat config` вернул id — `unchanged`; если
  репозитория нет, команда идёт обычным путём.
- **`secret list` и `repo password` под root не требуют пользователя
  службы** (ничего не отдаётся ему); остальные команды требуют
  (`SERVICE_USER_UNKNOWN`).
- **Имя секрета, начинающееся с `-`, задаётся после `--`**: `flag` читает
  `-db` как флаг. Сценарий «Недопустимое имя» проверяется так.
- **Syslog:** `LOG_NOTICE|LOG_AUTHPRIV`, тег `sard-agent`.
- **`repo remove` удаляет `env_file`,** только если он лежит в `secrets` и на
  него не ссылается другой ключ (Р19).

  подсказки.

## Конвейер после coder: cleaner → architect → hardener

- **Architect, шесть проверок.** Найдено и исправлено (тест первым, кроме
  отмеченного ниже):
  - F1 — `hostsetup` зависел от `repoinit`; словарь отказов и блокировка
    вынесены в лист `internal/refusal`, тесты импортов.
  - F2, R1, R2 — `repo add` под root мог отдать пользователю службы чужое
    дерево через ссылку (внутри дерева, в самом адресе, в родительском
    компоненте). Теперь адрес открывается обходом по дескрипторам с
    `O_NOFOLLOW`, смена владельца — внутри `os.Root`, файлы с несколькими
    именами не отдаются. Поправки П10, П11 к Р13 подтверждены владельцем.
  - F3 — файл пароля `repo init` под sudo: временный файл с владельцем,
    затем `link` без перезаписи.
  - F4 — экранирование drop-in systemd, отказ для управляющих символов.
  - R3 — файлы блокировок открываются с `O_NOFOLLOW` и проверкой числа
    ссылок; `EnsureDir` создаёт через удерживаемый родитель; `enroll` меняет
    владельца по дескриптору.
  - R4 — под root `env_file` и файл пароля читаются только через
    `secrets.ReadOwned` (правило A1 на дескрипторе).
  - Итог шестой проверки: APPROVED.
- **Отступление от «тест первым»:** в R2 тесты написаны после кода, в R4 —
  закоммичены вместе с кодом без отдельного красного прогона. Hardener
  проверил эти места мутациями.
- **Hardener:** выжившие в файлах среза 70 → 25, все 25 — эквивалентные,
  недостижимые или избыточный код (список в отчёте hardener). Полный гейт
  `./scripts/gate.sh agent` — PASSED, mutation score 0.950638, покрытие
  97.5%. `make license-check` — 862 файла OK.
- **Оставлено на A8b:** вынести логику подключения из
  `cmd/sard-agent/repo_add_connect.go` в internal-пакет до S3/SFTP; перевести
  сервер, веб и e2e-скрипты с `sudo -u` на `sudo sard-agent`.
- **Замечание о гейте:** параллельные прогоны `gate.sh`/`crap.sh` портят
  общий файл покрытия (видели 0% и 71.1%); запускать по одному.

## FXc: пример конфига без репозиториев и секретов

- `deploy/agent/agent.example.yaml`: `repositories`, `secrets` и `scripts`
  закомментированы как образец формата (решение О1); комментарий называет
  `sudo sard-agent repo add` / `secret set` и `docs/operations/agent-host-setup.md`,
  говорит, что S3 и SFTP пока пишутся в `repositories` вручную. Устаревший
  комментарий у `tls:` исправлен (`sudo sard-agent enroll` сам создаёт
  `/etc/sard/tls`).
- `scripts` тоже закомментированы: маскирование журналов читает файл каждого
  скрипта конфига как секрет (`agent/internal/secrets/secrets.go`), поэтому
  отсутствующий файл скрипта ломает каждый шаг так же, как секрета.
- Тест `agent/internal/config/example_test.go`: пример загружается и не
  определяет ни репозиториев, ни секретов, ни скриптов.
- `scripts/test-agent-install.sh`, e2e и тесты `InstallCommands` пример
  содержимым не используют (пишут свои конфиги / проверяют только команды
  копирования) — не менялись. `docs/demo.md`, шаг 5: ручная правка конфига
  убрана, репозиторий добавляет `sudo sard-agent repo add`.
- OQ-153 закрыт в `docs/open-questions.md`.
