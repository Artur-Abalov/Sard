## Фаза 1 — исследование и вопросы (до кода)

### Проверенные факты (file:line)
**Сервер (S5a, S6a)**
- Входящие маршрутизирует `AgentStreams.receive` (`server/.../agents/stream/AgentStreams.kt:273-300`): `extensions.progress|results|logs.handle(agent, msg)`. Интерфейсы `StepProgressHandler`, `StepResultHandler`, `LogChunkHandler` — не `suspend` (`AgentStreamExtensions.kt:145-166`). Их вызывают на корутине чтения потока (`Dispatchers.IO`, `AgentStreamConfiguration.kt:57-59`), по порядку, в gRPC Context агента. Исключение закрывает поток (`AgentStreamExtensions.kt:132-134`).
- Личность берётся только из сертификата: `ConnectedAgent(agentId, tenantId, serial)` (`AgentStreamExtensions.kt:122-130`). Заглушки — `LoggingInbound` (`:211-233`). Замена — единственным бином через `getIfUnique` (`AgentStreamConfiguration.kt:21-40`). Два бина одного типа молча возвращают заглушку: так было в S6a, и тестовый бин там помечен `@Primary` (`StreamIntegrationSupport.kt:106-109`).
- `AgentConnections.send(agentId, ConnectResponse): SendResult` — не `suspend` и не бросает. Возвращает `Queued | NotConnected | QueueFull`; `Queued` не значит «доставлено» (`AgentConnections.kt:22-25`, `SendResult.kt`). `ResultAck` сервер сейчас не строит нигде (grep пуст).
- `StepTransitions` (`server/.../runs/StepTransitions.kt`):
  - `accepted(tenant, step, phase)` — переход `dispatched → running` (`:132-133`);
  - `finished(tenant, step, StepOutcome)` — переход `dispatched|running →` финальный (`:136`);
  - `lost` — переход `running → lost` (`:137`);
  - каждый переход — один `inTenant`, в нём условный `UPDATE` шага и запуска (`move`, `:249-269`).
- `output`, `snapshot_id` (входной, `RunStep.snapshot_id`), `bytes_*` и смену `phase` после ACCEPTED никто не пишет. `RunStepRecord` не отображает `output` (`persistence/RunRecords.kt`).
- «Результат пришёл» — это статус шага в базе, отдельного интерфейса нет (`docs/adr/00XX-draft-run-dispatch.md:32`). `AGENT_LOST_STEP` в коде нет, есть статус `lost` с `message = 'agent lost the step'`.
- Решение владельца 6 в S6a: «Результат после `lost` — `lost` остаётся, ResultAck, запись в журнал (S7)» (`docs/sessions/2026-09-30-s6a-dispatch.md:36`).
- Транзакции — сессии Hibernate через `TenantSessions.inTenant`. Spring `@Transactional` и `TransactionTemplate` в `main` нет, поэтому `@TransactionalEventListener` не сработает. `ApplicationEventPublisher` нигде не используется.
- Нативный SQL обязан явно содержать `tenant_id = ?` (ADR 0013, правило 8). Правила `TenantSchemaRulesTest`:
  - FK `tenant_id → tenants`;
  - `UNIQUE (id, tenant_id)` для таблиц с `id`;
  - составные FK между тенантными таблицами.
  Партиционированную таблицу тест проверяет по родителю (relkind `p`, `TenantSchemaRulesTest.kt:14-26`).
- ADR 0013:
  - `step_logs` (`:166-171`): `PARTITION BY RANGE (received_at)`, PK `(step_id, seq, received_at)`, столбцы `time, level, text`. Секции месячные, «сервер создаёт их заранее». Срок хранения — `sard.logs.retention` (90 дней), истёкшие секции удаляются через `DROP`.
  - `snapshots` (`:173-178`): `UNIQUE (tenant_id, repository_id, snapshot_id)`, `UNIQUE (tenant_id, id, source_id)`.
  - Отложенный пункт о `repository_id` (`:214`) устарел.
- Метрики: `sard.<домен>...`, без тегов, адаптер `Micrometer*` за доменным интерфейсом (`DispatchConfiguration.kt:73-94`). Миграции: последняя — `V202609301200__runs.sql`. Список версий зашит в `SardServerIntegrationTest.kt:87`.
- `RunFinished` и S9a в репозитории нет. Упоминания — только в `docs/adr/0024-notification-policy.md:7,23`: S7 публикует событие; поля — триггер, итог, источник, агент, причина ошибки.

**Контракт и агент**
- `ResultAck` (`proto/sard/agent/v1/agent.proto:319-325`), дословно: «only after the result is durably recorded (its transaction committed), **and also for a command_id it does not know, so that the agent stops resending it**… the server must treat a repeated StepResult for a closed command as a no-op and ack it again».
- `StepResult` (`:225-248`) — только `message`, без кода причины; `oneof output`. `BackupOutput` (`:266-276`) — `snapshot_id, total_bytes, added_bytes, repository_id` (поле 4), **без `repository_name`**.
- OQ-018 закрыт: агент заполняет `repository_id` (`agent/internal/pluginhost/handler.go:103-111`, `docs/open-questions.md:59`). `BackupOutput` прикладывается, только если `SnapshotID != ""` (`handler.go:97-100`).
- Повтор результата — **только на новом потоке**, по таймеру в том же потоке агент не повторяет:
  - `outbox.sent` сбрасывается в `startStream` (`agent/internal/transport/outbox.go:103-112,130-137`);
  - переподключение — с backoff от 1 с до 1 мин (`transport.go:66-71`);
  - без ack результат лежит на диске агента бессрочно (`agent/internal/executor/store.go:66-80`).
- Порядок отправки на агенте: результаты → прогресс → логи (`outbox.go:126-146`). **`LogChunk` шага может прийти после его `StepResult`** (`executor.go:29-30`).
- `LogChunk` — `command_id` + `LogLine{time, level, text}`. seq и stdout/stderr нет. Не больше 64 строк в пакете (`outbox.go:14`), обратное давление без потерь. Длину строки агент не ограничивает (`restic/exec.go` `lineWriter`). stderr restic и редактор A7a к логам не подключены (`cmd/sard-agent/main.go:126-133`).
- Прогресс: ACCEPTED — при постановке в очередь (`command.go:84`). Дальше — не чаще 1 с на фазу, новая фаза проходит всегда (`executor/reporter.go:19-30`). Значит, OQ-006 частично закрыт исполнителем.
- «unknown plugin»:
  - `REJECTED`, `message = "unknown plugin \"absent\""`, без ACCEPTED, без `started_at` и `output` (`command.go:75-94`);
  - результат хранится и повторяется до ack.

### Расхождения постановки с контрактом и решениями — остановка
1. **Чужой `command_id`.** В постановке — «отклонить, без ResultAck». В proto — ack «also for a command_id it does not know» (`agent.proto:319-325`). Агент повторяет результат на каждом новом потоке (`outbox.go:103-112`), поэтому без ack чужой или неизвестный результат повторяется вечно — ровно тот риск, который постановка называет главным.
2. **Поздний результат после `lost`.** Постановка предлагает переход `lost →` фактический статус. Решение владельца 6 в S6a — `lost` остаётся (`s6a-dispatch.md:36`). Отмена требует нового решения.
3. **«Интерфейс результат пришёл», «AGENT_LOST_STEP».** Такого интерфейса и кода нет, есть статус `lost` (S6a, решения 1 и 7). Отметку ставит сам `finished`.
4. **«Шаг и запуск rejected» (тест 8).** Статуса `rejected` у запуска нет. Шаг `rejected` → запуск `failed` (`RunModel.kt:312-320`, ответ владельца 2 в S8a).
5. **«Успешный BACKUP без repository_id (агент без OQ-018)».** Такого агента в `main` нет. Ветка возможна только при ошибке или подделке агента, поэтому вопрос сводится к общему правилу «неверный результат».

### Проект (на ревью; детали зависят от ответов)
**Миграция `V202610011200__results.sql`**
- `step_logs`:
  - столбцы `tenant_id, step_id, seq BIGINT, received_at TIMESTAMPTZ, time TIMESTAMPTZ NULL, level TEXT CHECK IN ('debug','info','warn','error'), text TEXT`;
  - `PARTITION BY RANGE (received_at)`, PK `(tenant_id, step_id, seq, received_at)`;
  - FK `(tenant_id, step_id) → run_steps (tenant_id, id)`.
- `snapshots` — по ADR 0013:
  - FK `(tenant_id, source_id) → sources`, `(tenant_id, step_id) → run_steps`, `(tenant_id, agent_id) → agents`;
  - `repository_name` копируется из шага, потому что в proto его нет;
  - `created_at` — время сервера;
  - `UNIQUE (tenant_id, step_id)`.
- `run_steps`: добавить `log_lines BIGINT NOT NULL DEFAULT 0`, `log_bytes BIGINT NOT NULL DEFAULT 0`, `log_truncated BOOLEAN NOT NULL DEFAULT false`. seq выделяется условным `UPDATE … RETURNING`, одной строкой без гонок. Счётчики пишутся и после закрытия шага, потому что логи приходят после результата.

**Пакеты**
- `runs/`: домен без protobuf.
  - `StepResults.record(tenant, agent, stepId, StepReport)`, одна транзакция: `finished`, `output`, `snapshots`, запуск.
  - `StepLogs.append`, `StepProgressWrites`.
  - Событие `RunFinished` и `fun interface RunFinishedListener`.
- `agents/results/`: обработчики S5a, преобразование proto → домен, `ResultAck` через `AgentConnections.send`, метрики, журнал безопасности.
- `StepTransitions.finished` и `lost` возвращают сведения о завершённом запуске, чтобы `RunFinished` публиковался и из окна `lost` (запуск `failed` без результата).

**Порядок обработки StepResult**
1. Разобрать `command_id` как UUID; не UUID — «неизвестный».
2. В тенанте агента одной транзакцией:
   - прочитать шаг с `agent_id = агент` («не наш» = «неизвестный»);
   - `finished`;
   - при выигрыше — `output`, строка `snapshots` и запуск.
3. После фиксации:
   - `ResultAck`;
   - `RunFinished`, если запуск закрыт этим переходом;
   - счётчик.
4. Шаг уже закрыт (`finished = false`) — ничего не писать, отправить `ResultAck`.

**Метрики**: счётчик `sard.run.step.results` с тегом `status` (первый тег в проекте); `sard.run.step.results.rejected` (неизвестный/чужой, неверный); `sard.run.step.logs.truncated`; `sard.run.step.logs.dropped`.
