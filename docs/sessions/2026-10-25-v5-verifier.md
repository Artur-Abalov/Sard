### Проверено опытом на restic 0.19.1 (не через Sard, вручную)

Учётка только на чтение: локальный репозиторий, владелец root, команды от
nobody, ключ верификатора добавлен через `key add`.

| Команда | Итог |
|---|---|
| `check --read-data-subset=10%` | exit 1: «create **exclusive** lock … permission denied». check берёт эксклюзивную блокировку |
| `--no-lock check --read-data-subset=10%` | exit 0. Листинг репозитория до и после совпадает: ничего не записано |
| `snapshots` без `--no-lock` | exit 1 (блокировка). С `--no-lock` — exit 0, фильтр `--tag` работает |
| Повреждённый pack, `--no-lock check` без чтения данных | **exit 0**: структура цела, порчу содержимого не видно |
| Тот же pack, `--read-data-subset=100%` | exit 1, «repository contains errors» |
| `--read-data-subset=1/5` | exit 0: выбранная группа может не включать битый pack |
| Удалённый pack, `--no-lock check` | exit 1 |
| `--json check` | `summary.num_errors` и `exit_error.message`. Сообщение отличает «repository contains errors» от «unable to open repository». `num_errors=1` бывает и при ошибке открытия, поэтому ему верить нельзя |
| Неверный пароль / нет репозитория | exit 12 / exit 10 |

### Решения владельца (контрольная точка 1, 2026-10-25)

1. **restic check.** Всегда `--no-lock --json check --read-data-subset=N%`,
   N по умолчанию 10%, настраивается. Молча переходить на проверку с записью
   нельзя.
   - Код 1 разбирается по `exit_error.message`: «repository contains errors»
     — провал, остальное — «не можем проверить».
   - Если check нашёл ошибку, а список снимков за время проверки изменился
     или наш снимок пропал (параллельный prune) — «не можем проверить» и
     одна повторная проверка.
2. **psql и pg_restore выполняются внутри контейнера** через exec. SDK даёт
   плагину запуск процесса в песочнице. Путь R2 не меняется.
3. **Рабочий том.** Каталог проверок с noexec даёт systemd (`NoExecPaths=`,
   `ReadWritePaths=`); агент проверяет флаг через `statfs` (ST_NOEXEC). Без
   флага — «не можем проверить». Для хостов без systemd — строка fstab в
   документации оператора.
4. **Docker или Podman** — какой найдётся в PATH, через CLI, без SDK. В
   документации рекомендуется rootless Podman; там же сказано, что группа
   docker равна root.
5. **Новый вердикт `VERIFY_VERDICT_INFRASTRUCTURE_FAILURE`** (proto и
   сервер), повтор — по правилам V4. Ставится при превышении срока стадии,
   с именем стадии.
6. **Данные песочницы** лежат на bind mount каталога задания (uid агента,
   0700), контейнер запускается с `--user <uid агента>`. Жёстко
   ограничиваются CPU, память и pids; диск — предварительной проверкой
   места.
7. **Серверу не доверяем.** В `VerifyTask` добавляется
   `source_machine_ids`, сервер его заполняет, агент отказывает при
   совпадении со своей машиной.
8. **Образы.** Списки образов поставляются в каждом релизе: semver-версия
   образа и её digest (human-readable версия обязательна). Образ берётся
   только по digest. Нет образа локально и pull запрещён — «не можем
   проверить».
9. **Отчёт о машине.** В `VerifierStatus` добавляется поле
   `images` (proto и сохранение на сервере). Сервер начинает читать
   `Heartbeat.verifier`.
10. **Запас места** — ×2 + 1 ГиБ, настраивается. Размер берётся из
    отпечатка.
11. **Сроки стадий** — собственные лимиты агента в конфиге: подготовка
    10 мин, check 2 ч, восстановление 4 ч, отпечаток 1 ч. Каждый ограничен
    остатком `RunStep.timeout` и `deadline`.
12. **files** восстанавливается с `restic restore --verify` в
    `<рабочий том>/<job>/`, с `--no-lock` только в режиме чтения.
13. **Расширения.** До pg_restore их наличие в песочнице сверяется с
    отпечатком; логика — в плагине.
14. **Учётка с правом записи** даёт предупреждение при старте верификатора
    и в `check`. Проверка всё равно идёт.

- **Плагин postgresql.** Образ мажорной версии источника; готовность —
  непустой `listen_addresses` (временный сервер инициализации без TCP);

  `pg_restore` и `psql` внутри контейнера; `CopySize` из `database_size`.
- **Сервер.** Причина «сбоя инфраструктуры» называла последнюю стадию — это
  всегда `cleanup`. Теперь — первую непрошедшую.
- **Документация.** `docs/operator/17-verifier.md` (установка, ключ и
  учётка только на чтение, рабочий том `noexec`, образы, закрытый контур,
  настройки, исходы); ADR `docs/adr/00XX-draft-verifier-sandbox.md`.

### Найдено на стенде

- **`restic dump` на верификаторе не работал.** Флаги `--no-lock --no-cache`
  режима только чтения дописывались после `-- <снимок> <путь>`, restic
  принимал их за третий аргумент. Копия postgresql не восстанавливалась, и
  исход записывался как «провал», то есть как плохой бэкап. Unit-тесты
  `Dump` шли без режима только чтения. Исправлено: позиционные аргументы
  `dump`, `ls`, `restore` — в `tail`, после добавленных флагов; тест на
  порядок аргументов.
- **Образы e2e с устаревшим агентом.** BuildKit передаёт контекст сборки
  инкрементально и пропускает файлы с тем же размером и временем изменения.
  Пакет ставит файлам время коммита. Сборка из незакоммиченного дерева с тем
  же размером бинарника не доходит до образа — даже с `--no-cache`. В CI не
  проявляется (каждая сборка — новый коммит). Локально помог `touch` файлов
  контекста. Хвост: `agent_image_unpacked` мог бы делать это сам.
