# Сессия 2026-10-13: A8c-2 — `repo restore` каталога (coder)

Ветка `ccr-bb1484f1-25wm55`. Спецификация (утверждена владельцем 2026-10-12) —
`docs/specs/agent/repo-restore.feature`, правила и сценарии с пометкой `# A8c-2`
(Р58–Р61, Р63–Р71, Н26–Н28, Н30–Н31, Н36, Н38). Ручная проверка —
`docs/qa/repo-restore.md` части 2, 3, 5 (шаги без PostgreSQL), 6 (шаг 46 для
каталога), 7. A8c-3 (PostgreSQL, Р62) не тронут: снимок PostgreSQL
восстанавливается как обычный каталог, команды PostgreSQL не печатаются.

## Что сделано

- `internal/restore` (Р68): `CheckRef`/`Select` (id, префикс 8–63, `latest` с
  `--source` без снимков глобальных объектов, `SNAPSHOT_UNKNOWN`,
  `SNAPSHOT_AMBIGUOUS`), `CheckPaths`/`CheckTargetFlags` (флаги), `CheckTarget`
  (абсолютный путь, обход без ссылок, репозиторий и кэш, `lost+found`, `/`),
  `OpenTarget`/`Held` (создание `root:root 0700`, `flock`, уборка пустых
  созданных каталогов), `RequirePaths` (`PATH_NOT_IN_SNAPSHOT`), `Run` (вызов
  restic и классы отказов: `RESTORE_INCOMPLETE`, `TARGET_WRITE`, примечание о
  частичном результате), `SFTPCommand`. Зависит от интерфейсов `Lister`,
  `PathFinder`, `Restorer` (как `Lister` в A8c-1), `restic.Repository` не
  растёт.
- `internal/restic`: `CLI.RestoreTo` (`restore --json --no-cache --no-lock
  --target … --overwrite never|always [--include …] [-o sftp.command=…]`),
  `CLI.HasPath` (`ls --json --no-lock`), `RestoreError`, `ErrNoSpace`;
  `distinctPaths` общий с `PartialError`. Разбор ошибок файлов проверен на
  настоящем restic 0.19.1: `error`-строки идут в stderr, итог `summary` — в
  stdout, `exit_error` «There were N errors».
- `hostsetup.Dir`: `Names` и `Lock` (`flock`, `ErrBusy`).
- `refusal`: `SNAPSHOT_UNKNOWN`, `SNAPSHOT_AMBIGUOUS`, `TARGET_INVALID`,
  `TARGET_NOT_EMPTY`, `ROOT_TARGET_REFUSED`, `PATH_NOT_IN_SNAPSHOT` (2),
  `RESTORE_INCOMPLETE` (1), `TARGET_BUSY` (6), `TARGET_WRITE` (7).
- `package main`: `repo restore` (`repo_restore_run.go`), флаги `--target`,
  `--overwrite`, `--allow-root-target`, `--path` (повторяемый), `--timeout` без
  значения по умолчанию (`repoContext` с нулём не ограничивает), справка, строка
  «want a subcommand». `prepareRepository` общий с `repo snapshots`: порядок
  Р69 — флаги, права (без пользователя службы), конфиг, имя, цель без
  изменений, пользователь службы, restic, файлы пароля и ключей, список,
  выбор, `--path`, создание и блокировка цели, восстановление, аудит.
- restic для восстановления идёт без `RunAs` (от root), `env_file` читается с
  uid пользователя службы (`newResticReading`); список и `ls` — от пользователя
  службы. Цель описывается `repoconnect.TargetFor` (через общий `targetOf`).
- Документация: ADR 0056 (Н26, Н27 (а), Р59, Р62, Р63) и строка в ADR 0050,
  `docs/operations/agent-host-setup.md` (раздел «Снимки и восстановление на
  хосте», коды выхода), `docs/plugins/postgresql.md` («Восстановление руками» —
  `repo snapshots` и `repo restore` вместо `restic`; команды PostgreSQL печатает
  A8c-3), `docs/dependencies.md` и `deploy/agent/nfpm.yaml` (`util-linux` для
  rpm).

## Красный прогон

Тесты `repo restore` падали с кодом 2 («want a subcommand»), тест Dir — с
`undefined: Names`, restic — с `undefined: RestoreTo`; «Без общего таймаута» —
с кодом 6: нулевой `--timeout` создавал таймер на 0 и отменял команду сразу
(исправлено в `repoContext`). Конвейер `main` росло от сценария успеха наружу
(целиком по Р69), остальные сценарии написаны после него и проверены на
правильную причину отказа; мутационный прогон остаётся за `cleaner` и
`hardener`.

## Решения и отклонения

- **Механизм Н27 (а): `setpriv`.** Сценарий «ssh для SFTP запускается от
  пользователя службы» проверяется на границе фейка: `-o sftp.command` разобран
  и начинается с `setpriv --reuid=990 --regid=990 --clear-groups ssh …`, root не
  открывал файлы `~/.ssh` (смысл сценария тот же, ADR 0056). Реальный запуск
  `ssh` под `setpriv` в `@local` не проверяется — это `@stand`/`@vm` (QA часть
  5, шаг 44). Зависимость: `util-linux` (deb — обязательный пакет, rpm — в
  `nfpm.yaml`).
- Сценарий «Ключи S3 попадают в restic только окружением» и «в кэше и
  репозитории нет файлов root» проверены на границе фейка: ключ — в окружении
  и не в аргументах, `--no-cache --no-lock` в аргументах, кэш и каталог
  репозитория не изменились. Сами файлы root в `@local` не создаются
  (тесты идут не от root); `find -user root` — QA шаг 45.
- Фраза сценария «адрес в выводе — `s3:https://u:***@…`» для отказа restore не
  выполняется буквально: адрес с паролем в пользователе не проходит разбор
  `CheckS3Address`, сообщение общее («backend s3: …»), а текст restic с адресом
  проходит `Scrubber` (`[REDACTED]`). Так же ведёт себя `repo snapshots`
  (A8c-1); значения нигде не показаны.
- `--source` у `repo restore` с id (не `latest`) принимается и сужает поиск
  снимков этого источника; Р57 говорит об этом только для `latest`. Если
  specifier хотел отказ — это отдельный сценарий.
- `--overwrite never` без флага `--overwrite` команды (сценариев нет): файл,
  появившийся в цели после проверки, restic не заменит. Цель по пути
  открывает restic; подмена компонента ссылкой между проверкой и запуском
  restic не предотвращается для существующей цели (в ADR 0056 «Предел»).
- «Нет места» распознаётся по тексту `no space left on device` (в фатальном
  сообщении и в ошибках файлов); квоту и `read-only file system` команда
  отдельно не классифицирует: они дают `RESTORE_INCOMPLETE`.
- Строка аудита: путь цели с управляющими символами берётся в кавычки, как имя
  в `hostsetup.Audit`, чтобы перевод строки в пути не делал вторую строку.
- `docs/qa/repo-restore.md` шаг 50 требует, чтобы в документации не было
  `restic (snapshots|dump|restore)`: две фразы A8c-1 переписаны без этого сочетания.

## Не автоматизировано

Части 2–3, 5, 6 и 7 `docs/qa/repo-restore.md` (ВМ, стенд S3 и SFTP, SELinux,
`mkfs.ext4`/`mount`, реальное прерывание большого восстановления, владельцы
root/postgres/1001) — ручной QA. Тесты `@integration` — на настоящем restic в
`cmd/sard-agent/repo_restore_integration_test.go` (путь и права, несколько
`--path`, `PATH_NOT_IN_SNAPSHOT`, новый хост с паролем из копии).

## Для specifier

- См. выше: `--source` с id; `read-only file system` и квота; буквальное
  чтение фразы про адрес `***` в сообщении об отказе restore.
