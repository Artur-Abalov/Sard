### Откуда берётся schema.d.ts (проверено)

- Спецификация генерируется из кода сервера (springdoc):
  `server/build.gradle.kts:37`, `application.yaml:38-40`.
- `SardServerIntegrationTest.kt:110-120` запрашивает `/v3/api-docs` и пишет
  `server/build/openapi/openapi.json`.
- `Makefile:68-73` копирует этот файл в `web/src/api/openapi.json`, затем
  `web/scripts/gen-api.mjs` (openapi-typescript) пишет `schema.d.ts`.
- В CI два шага `git diff --exit-code`: для `openapi.json` в job server
  (`ci.yml:91-94`) и для `schema.d.ts` в job web (`ci.yml:107-111`).
- Следствие: если описать эндпоинт, которого нет в коде, job server
  упадёт. Значит, для контракта без реализации нужен другой источник
  истины.

### Что должно совпасть с proto и ADR 0013 (проверено)

- `StepPhase` (`agent.proto:192-202`): accepted, preparing, dumping,
  uploading, restoring, verifying.
- `StepStatus` (`agent.proto:251-264`): succeeded, failed, cancelled,
  timed_out, rejected.
- `run_steps.status` в ADR 0013 (строки 123-139) шире: к этим значениям
  добавлены queued, dispatched, running, lost.
- `Action` (`agent.proto:329-337`): backup, restore, verify, run.
- `LogLevel` (`agent.proto:217-223`): debug, info, warn, error.
- `runs.status` есть только в ADR 0013:116-121 (queued, running,
  succeeded, failed, cancelled); в proto его нет.
- `RegisterRequest` (`agent.proto:89-109`, `RepositoryInfo` 373-384) несёт
  репозитории, имена секретов и имена скриптов.
- Таблицы `enrollment_tokens`
  (`server/src/main/resources/db/migration/V202609271200__enrollment.sql`)
  нет колонки `revoked_at`, отзыв добавляет S2b.

## Решения по итогам ревью фазы 1 (пользователь, 2026-09-27)

Источник контекста — план этапа 1 от пользователя (`sard-stage1-plan.md`,
в репозиторий не закоммичен). Из него для S8a важны:
- D2: cookie `HttpOnly` + `SameSite=Strict`; все `/api/v1/*`, кроме входа и
  `/status`, требуют сессии;
- D6: активный запуск — `queued`, `dispatched` или `running`;
- `runs.workflow_id` может быть `NULL` при `trigger = 'manual'`;
- S8 — контракт; его поведение проверяется через сценарии W2.

Файлов `features/W1b-admin-login.md` и `features/S2b-enrollment.md` в
репозитории нет. Их заменяют текст задачи и этот план.

Решения:

1. Сессия. Детали cookie выбирает S8a: `sard_session`, `HttpOnly`,
   `SameSite=Strict`, `Path=/api`. CSRF-заголовка нет, защита держится на
   `SameSite=Strict`. W1b может уточнить.
2. Источник истины контракта — рукописный файл
   `web/src/api/openapi.yaml`, а не выгрузка springdoc. Сравнение
   `openapi.json` в job server (`ci.yml:91-94`) заменяется проверкой
   «каждый путь, который отдаёт springdoc, есть в спецификации». Решение
   записывается в ADR 0019.
3. У источника `agentId`, `plugin` и `repositoryName` не меняются после
   создания. `PATCH` меняет только `name` и `config`. `DELETE` при активном
   запуске отвечает 409 с `activeRunId`.
4. Действие запуска на этапе 1 — `backup` или `verify`. Отмены запуска в
   API этапа 1 нет: её не было в scope, пользователь не просил.
5. Проверка перечислений:
   - Сверяются с proto: фазы шага, действия, уровни логов, а также каждое
     значение `StepStatus` должно входить в API-перечисление статусов шага.
   - Значений, которых нет в proto (статусы запуска; статусы шага queued,
     dispatched, running, lost), с ADR 0013 не сверяем. Их сверка — в S8b,
     с CHECK-ограничениями миграций S6.
6. Моки. В dev (`VITE_API_MOCKS=1`) сессия по умолчанию открыта, чтобы W2
   работал до W1b. В Vitest тесты начинают без сессии.
7. Решения по умолчанию приняты без возражений:
   - `configSchema` — объект JSON;
   - `repositoryId` показывается;
   - у агента нет статуса `revoked`;
   - `trigger` запуска только для чтения, значения из ADR 0013;
   - адрес `--server` в команде `enroll` — строка, которую выдаёт сервер.

   после слияния #11.
