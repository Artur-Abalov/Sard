# 2026-10-08 — F3a: планировщик запусков

Ветка `ccr-bfde5281-j7cdly` (сессия привязана к ней вместо
`feat/f3a-scheduler`). Техническая задача, в обход `/ship-feature` (ответ
владельца 10). Черновик ADR — `docs/adr/00XX-draft-scheduler.md`.

## Вопросы и ответы владельца

1. Триггер: оставить `'schedule'`, добавить `'catch_up'` — да.
2. Ослабить `runs_workflow_check`, `runs.schedule_id`, расписание 1:1 с
   источником — да.
3. Уведомления «упал» и «восстановился» через очередь S9a, временный текст;
   об ошибке — только о первой в серии.
4. Алерт о пропусках подряд: в F3a — событие и метрика, доставка — F3b/S9;
   порог 3; сброс при создании запуска — да.
5. Летнее время: фиксированный час — один раз в момент перехода вперёд и в
   первом вхождении при переходе назад; час со `*` — по реальному времени.
6. Библиотека — Spring `CronExpression` с обвязкой.
7. Простой — одна строка журнала с количеством; один `catch_up`.
8. Растягивание — `catch_up_due_at` в базе, шаг настраивается.
9. Исходы и офлайн-агент — как предложено.
10. Процесс — в обход конвейера.

## Фаза 1 — модель, cron, время, догоняющий запуск

- `scheduler/CronSchedule.kt`: разбор 5 полей, отказы `InvalidSchedule`
  с полем (`CRON`, `TIMEZONE`), объединение дней, `*` дня недели как `0-7`,
  правила DST.
- `scheduler/Due.kt`: `NotYet` / `OnTime` / `Missed(first, count, next)`,
  лимит счёта 10 000.
- Проверено пробой Spring 7.0.9 (не полагаю, а видел вывод): без обвязки
  переход назад даёт два срабатывания `30 1 * * *`, переход вперёд — ни
  одного `30 2 * * *`, `13 * FRI` — пересечение, `*/2` в дне недели —
  пн/ср/пт/вс.
- Тесты: `CronScheduleTest` (14), `DueTest` (5) — зелёные.
- Mutflow (`-Pmutflow.enabled=true`, пакет `scheduler`): без выживших,
  `CronScheduleTest` 350 прогонов, `DueTest` 65. Первый прогон завис:
  мутант, инвертировавший сравнение в `nextOnWallClock`, давал бесконечный
  цикл. Корень — неограниченная последовательность; теперь она ограничена
  1 000 местных времён. Эквивалентный мутант `>` → `>=` убран: обход
  начинается с местного времени самого `after`, которое отсекается
  сравнением. `Due` зависит от интерфейса `Fires`, тест — на фейках.
- CRAP по `scheduler` (`.bin/crap`, JaCoCo по тестам пакета): максимум 4.6
  (`CronSchedule.nextInRealTime`), порог 6. `ArchitectureTest` и
  `make license-check` зелёные. Полный `make gate M=server` не запускался.
  Docker в контейнере сессии не запущен по умолчанию; `dockerd` стартует
  вручную — для Testcontainers фазы 2.

## Фаза 2 — миграция, цикл, пропуски, catch_up; тесты 1–7 (2026-10-09)

- Миграция `V202610091200__schedules.sql`: `schedules`, `schedule_fires`,
  `runs.schedule_id`, триггер `catch_up`, `runs_workflow_check` ослаблен.
  Первая попытка упала на имени: `schedule_fires_reason_check` совпало с
  автоматическим именем CHECK колонки `reason`; переименовано до первого
  применения.
- `Runs.startScheduled` — те же проверки и запись, что у `start`, в транзакции
  планировщика с исключительной блокировкой источника (вместо savepoint из
  черновика ADR; обоснование — в ADR).
- `Scheduler` (тик: системное чтение созревших → `FOR UPDATE SKIP LOCKED` в
  тенанте), `Firing` (одно расписание в транзакции), `Schedules` (установка и
  чтение), `SchedulerLoop`, настройки `sard.scheduler.*`.
- `RunTrigger.CATCH_UP` в REST, `make openapi`, подписи en/ru — иначе список
  запусков упал бы на `valueOf`.
- Тесты `SchedulerIntegrationTest` (16): 1–7 из промпта, плюс отказ
  (`unknown_plugin`), гонка ручного запуска с планировщиком, граница слота
  догоняющего, очередь слотов после уже назначенных, ожидание догоняющего при
  срабатывании cron. Перезапуск посреди срабатывания — триггер БД роняет
  вставку в журнал (транзакция откатывается целиком), новый экземпляр
  планировщика срабатывает ровно один раз. Два экземпляра — два `Scheduler`
  на одной базе в параллельных потоках, 12 расписаний × 4 минуты.
- Проверено: `:server:check` — 1513 тестов, 0 падений; покрытие 96,2 %
  инструкций; CRAP-гейт проходит (по `scheduler` максимум 6,0 —
  `SchedulerLoop.safeTick`, цикл в тестах не запускается, тики ручные);
  mutflow по пакету `scheduler` без выживших; web: tsc, линт, 430 тестов.
- Первый полный `:server:check` дал сотни ложных падений
  (`NoClassDefFoundError` в чужих пакетах): каталог классов перезаписывался
  во время прогона. Повтор без параллельной компиляции — чисто.
- mutflow: первый прогон интеграционного теста дал 28 выживших — почти все в
  транзитивно достигнутом коде (`CronSchedule`, `Due`, `AgentOffer`,
  `TenantSessions`). Цели сужены `includeTargets`. Проверка ослабленным тестом
  показала, что вложенный `private inner class Firing` в цели не попадал —
  вынесен в класс верхнего уровня; после этого выжили три мутанта сравнения
  слота, убиты новыми тестами границы.
- Полный mutflow сервера (`-Pmutflow.enabled=true :server:test --rerun`,
  как в `scripts/gate.sh`): после `:server:clean` — успех, выживших нет.
  Два прогона до этого падали не на мутантах: `NoClassDefFoundError` в
  `pki`/`notify` на прогоне без мутаций и `EOFException` в задаче тестов.
  Полагаю (не доказано), что причина — испорченное инкрементальное
  состояние сборки после чередования обычных и mutflow-прогонов; после
  чистой сборки не повторялось.
