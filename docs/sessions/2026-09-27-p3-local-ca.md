ADR 0008 касается ключей бэкапов. Ключ CA держит сервер; его компрометация
позволяет выдавать себя за агента или сервер, но не читать бэкапы. Это
не противоречит 0008, но в новом ADR это стоит записать явно.

gRPC-сервер:
- `server/src/main/resources/application.yaml:16-18` — только `spring.grpc.server.port`, TLS нет.
- Фабрику создаёт `NettyGrpcServerConfiguration.nettyGrpcServerFactory(...)` из `spring-boot-grpc-server-4.1.1` (`@ConditionalOnMissingBean`). TLS она берёт из `SslBundles` по `spring.grpc.server.ssl.bundle` и `ssl.client-auth` (`GrpcServerProperties$Ssl`: `enabled`, `clientAuth`, `bundle`, `secure`), затем вызывает `new NettyGrpcServerFactory(address, customizers, keyManagerFactory, trustManagerFactory, clientAuth)`.
- Автоконфигурация поднимает один сетевой сервер. Второй порт — это своя фабрика, свой `GrpcServerLifecycle` и `setServiceFilter` для разделения сервисов. Работать будет, но это самописная копия автоконфигурации.
- В `spring-boot-autoconfigure-4.1.1` есть `SslBundleRegistrar`: бандл можно зарегистрировать программно, без файлов PEM в настройках.
- Тесты gRPC: `SardServerIntegrationTest.kt:120` — `ManagedChannelBuilder...usePlaintext()`. После включения TLS клиенты этих тестов переходят на TLS с CA-бандлом. Проверки остаются прежними (`UNIMPLEMENTED`).
- Конфиг агента: `deploy/agent/agent.example.yaml:11-14` — `tls.ca_file`, `cert_file`, `key_file` с одним `server.address`.

Зависимости:
- В `server/build.gradle.kts` нет ни BouncyCastle, ни других криптобиблиотек. У JDK нет публичного API для разбора CSR и выпуска сертификатов: `sun.security.x509` закрыт модулями. Поэтому нужен BouncyCastle: `bcpkix-jdk18on` и транзитивно `bcprov-jdk18on`, `bcutil-jdk18on`. Лицензия Bouncy Castle эквивалентна MIT. Точную последнюю версию сверю по Maven Central в фазе 2; в кэше Gradle лежит 1.84. Больше новых зависимостей не нужно.

### Расхождения ADR 0009 с D4 и заданием — нужен выбор владельца

1. **Порты.** ADR 0009:21 требует разных портов или слушателей и `client-auth=require` для `AgentService`. Задание переносит проверку клиентского сертификата в перехватчик (S3), что подразумевает один порт с `client-auth=optional`.
2. **Идентичность в сертификате.** D4 говорит «SAN с agent_id». ADR 0009:14 требует определять и тенанта по сертификату, а ADR 0013:177 предлагает URI SAN с тенантом. Интерфейс «подпись CSR с заданным agent_id» тенанта не принимает.

### Предлагаемый дизайн

Пакет `dev.sard.server.pki`, по образцу `extension/` + `TenancyAutoConfiguration`.

```kotlin
/** Issues and anchors the certificates of the agent transport (ADR 0014). No algorithm or key store is implied. */
interface CertificateAuthority {
    /** PEM of the trust anchors agents and clients verify the server against. */
    fun caBundlePem(): String

    /** SHA-256 of the root's SubjectPublicKeyInfo; the agent checks it at Enroll. */
    fun fingerprint(): CaFingerprint

    /** Key material the gRPC TLS listener serves; the key may live in a file, Vault or an HSM. */
    fun serverKeyManager(): X509KeyManager

    /** Signs an agent CSR (DER); rejects a bad signature or an unsupported key. */
    fun issueAgentCertificate(csrDer: ByteArray, agent: AgentIdentity): IssuedCertificate
}

data class AgentIdentity(val tenantId: UUID, val agentId: UUID)
data class IssuedCertificate(val chainPem: String, val serial: BigInteger, val notAfter: Instant)
@JvmInline value class CaFingerprint(val sha256: ByteArray)  // строковое кодирование — в S2 вместе с форматом токена
```

- **Почему `X509KeyManager`, а не PEM ключа сервера.** Это тип JDK: за ним может стоять PKCS#11, Vault или провайдер ГОСТ, и ключ не покидает хранилище. Тот же тип позволит подставить сертификат из корпоративной PKI (D4.5) и обновлять сертификат без рестарта.
- **`serial` и `notAfter` в результате** — для строки `agent_certificates`, которую пишет S2.
- **`FileCertificateAuthority(dir: Path, serverNames: ServerNames, clock: Clock, random: SecureRandom)`.** Алгоритм — ECDSA P-256 и SHA256withECDSA, но это деталь реализации.
- **`PkiAutoConfiguration`** — `@ConditionalOnMissingBean(CertificateAuthority::class)`, настройки `sard.pki.*`. Enterprise-замена объявляет `before`, как в ADR 0013.
- **`GrpcTlsConfiguration`** — `SslBundleRegistrar` регистрирует бандл `sard-grpc`: `KeyManagerFactory` поверх `serverKeyManager()` и доверие к CA. `application.yaml` получает `spring.grpc.server.ssl.bundle: sard-grpc`. Своя фабрика gRPC не нужна.

Каталог ключей (`sard.pki.dir`):

```text
<dir>/            0700
  ca/             появляется атомарно (см. ниже)
    ca.crt        PEM
    ca.key        PKCS#8 PEM, 0600
```

- **Запись каталога `ca/`.** Файлы создаются во временном каталоге `<dir>/.tmp-<random>/`, сразу с правами 0600 (`PosixFilePermissions` при создании, без `chmod` после). Затем `fsync` и `Files.move(tmp, ca, ATOMIC_MOVE)`. Переименование каталога не перезаписывает существующий `ca/`, поэтому два одновременных первых старта не получат разные CA: проигравший загрузит CA победителя.
- **Проверки при загрузке.** Ключ соответствует сертификату (пробная подпись). Каталог 0700, ключ 0600. Функция проверки прав возвращает ошибку, сообщения оператору вне скоупа. На ФС без POSIX-атрибутов — ошибка.
- **CA-сертификат.** `BasicConstraints CA:true` без `pathLen`, чтобы допустить промежуточный CA (D4.5). `KeyUsage keyCertSign, cRLSign`, SKI.
- **Сертификат агента.**
  - EKU только `clientAuth`, `KeyUsage digitalSignature`, `CA:false`, AKI и SKI.
  - SAN: URI `sard://tenants/<tenant>/agents/<agent>` (вопрос 2), CN = `agent_id`. Subject и расширения из CSR игнорируются.
  - `notBefore` = сейчас, `notAfter` = сейчас + 365 дней.
  - Серийный номер — 128 случайных бит, положительный.
  - Принимаемые ключи: ECDSA P-256 и P-384 (вопрос 4). Подпись CSR проверяется (доказательство владения ключом).
- **Отпечаток — SHA-256 от DER `SubjectPublicKeyInfo` корня, а не сертификата целиком.**
  - Отпечаток не меняется, если CA-сертификат перевыпущен тем же ключом (продлён срок, изменены расширения), и не зависит от будущей цепочки с промежуточным CA.
  - Так же устроены пины в `curl --pinnedpubkey` и HPKP.
  - В Go это `sha256.Sum256(cert.RawSubjectPublicKeyInfo)`, без разбора.
  - Минус: пин по SPKI не фиксирует срок и имя CA. Но доверие агента всё равно строится по бандлу, а пин лишь подтверждает, что бандл тот самый.

### Порядок тестов (фазы 2–3)

1. **Go-фикстуры CSR.** Файл `server/src/test/resources/pki/gencsr.go` с `//go:build ignore` запускается `go run gencsr.go` и использует только stdlib; он вне всех Go-модулей и шлюзов. Он пишет `agent-p256.csr` (валидный), `agent-bad-signature.csr` (испорченный байт подписи), `agent-rsa.csr` и `agent-ed25519.csr` (неподдерживаемые ключи).
2. **Подпись CSR.** Проверки: цепочка до CA, EKU, SAN, срок, длина серийного номера, отказы.
3. **Перезапуск.** Второй `FileCertificateAuthority` на том же каталоге даёт тот же отпечаток, ключ 0600, каталог 0700. Одновременный первый старт (два экземпляра) приводит к одному CA.
4. **Отпечаток по эталону.** Фиксированный CA-сертификат сгенерирован `openssl` и лежит в фикстурах. Эталон посчитан `openssl x509 -pubkey -noout | openssl pkey -pubin -outform DER | sha256sum`; команда записана рядом.
5. **Сквозной TLS** (фаза 3): клиент с бандлом подключается, клиент без доверия к CA получает ошибку рукопожатия.

### Вопросы владельцу (самые трудные первыми)

1. **Порты.**
   - Рекомендую один порт с `client-auth=optional`, а обязательность сертификата для `AgentService` — в перехватчике S3 по списку разрешённых: без сертификата доступен только `EnrollmentService`.
   - Доводы: у агента один `server.address`, Spring Boot поднимает один сетевой gRPC-сервер, оператору нужно открыть один порт.

   - Согласны изменить ADR 0009:21?
2. **Тенант в сертификате.** Предлагаю URI SAN `sard://tenants/<tenant>/agents/<agent>` уже сейчас. Тогда S3 получает тенанта без запроса к базе (ADR 0009:14, 0013:177), а в сигнатуре подписи будет `AgentIdentity(tenantId, agentId)`. Или только `agent_id`, а тенант — из базы?
3. **Серверный сертификат.** Задание: «выпуск при старте, если нет или истекает». Предлагаю иначе:
   - ключ сервера только в памяти, сертификат выпускается при каждом старте на 90 дней;
   - раз в сутки фоновая проверка перевыпускает его за 30 дней до конца через тот же `X509KeyManager`, без рестарта;
   - на диске тогда один секрет (ключ CA) вместо двух, а сервер, работающий дольше срока сертификата, не упадёт. Агенты доверяют CA, а не сертификату сервера, поэтому смена сертификата им незаметна.
   - Принимаете, или хранить `server.crt` и `server.key` на диске?
4. **Какие ключи агента принимать.** ECDSA P-256 (агент генерирует его) и P-384. RSA и Ed25519 отклонять? RSA может понадобиться для TPM и HSM на хостах, но это этап 2.
5. **Срок CA-сертификата.** Предлагаю 10 лет. Перевыпуск тем же ключом не меняет отпечаток (SPKI), смена ключа означает повторную регистрацию всех агентов.
6. **Каталог по умолчанию.** Предлагаю `sard.pki.dir` = `${SARD_PKI_DIR:/var/lib/sard/pki}`. В `deploy/docker-compose.yml` для него отдельный том `sard-pki`, не том PostgreSQL. Для локального `./gradlew bootRun` — задавать переменную явно. Или другое значение по умолчанию?
7. **Имена серверного сертификата по умолчанию.** Предлагаю `sard.pki.server-names` = `localhost, 127.0.0.1, ::1`, прод задаёт свои. Добавлять ли hostname машины автоматически?
8. **TLS всегда включён?** Предлагаю без режима plaintext даже для разработки: одна конфигурация, и нет риска забыть включить TLS.
9. **Шифрование ключа CA на диске паролем из env** — вне P3 (пароль тоже надо где-то хранить); защита — права 0600 и отдельный том. Согласны?
10. **Номер ADR.** Предлагаю новый ADR 0014 «Локальный CA (D4)», а ADR 0009 дополнить отсылкой и исправленным п. 2 плана. Раздел про бэкап ключа CA — `docs/operations/pki.md`.

## Фаза 2 — CA, подпись CSR, отпечаток

### Решения
- Пакет `dev.sard.server.pki`:
  - `CertificateAuthority` — интерфейс; `AgentIdentity`, `IssuedCertificate`, `CaFingerprint`, `InvalidCsrException`.
  - `FileCertificateAuthority(dir, serverNames, clock, random)` — реализация.
  - `CaDirectory` — каталог ключей и `ownerOnlyViolation(path): String?` (механизм проверки прав: возвращает описание нарушения).
  - `CaKeyPair` — сверка ключа с сертификатом при загрузке.
  - `Certificates` — профили X.509.
  - `AgentCsr` — проверка CSR.
  - `ServerKeyManager` — `X509ExtendedKeyManager`; замена ключа без рестарта, предыдущий ключ остаётся доступен по алиасу для рукопожатия, начатого до замены.
- BouncyCastle используется только для ASN.1, CSR и сборки сертификатов. Ключи, подписи и разбор сертификатов — JCA JDK, провайдер BC не регистрируется.
- Профили:
  - CA — `CN=Sard CA`, `CA:true` без `pathLen`, `keyCertSign|cRLSign`, срок `now-1h … now+3650d`.
  - Агент — `CN=<agent_id>`, URI SAN, EKU только `clientAuth`, KU `digitalSignature`, `CA:false`, срок `now … now+365d`.
  - Сервер — SAN из настроек (IP-литералы как `iPAddress`, остальное как `dNSName`), EKU `serverAuth`, срок `now-1h … now+90d`.
  - Серийный номер — ровно 128 случайных бит, положительный.
  - Сдвиг `notBefore` на час назад терпит отстающие часы агентов, которые проверяют CA и сертификат сервера. Сертификат агента проверяет сам сервер по своим же часам, поэтому ему сдвиг не нужен и срок ровно 365 дней.
- Отпечаток — SHA-256 от DER `SubjectPublicKeyInfo`, взятого из сертификата (`JcaX509CertificateHolder`), а не от `PublicKey.getEncoded()`: JDK может перекодировать SPKI, а Go хэширует исходные байты (`RawSubjectPublicKeyInfo`).
- `IssuedCertificate.chainPem` — только лист: корень агент получает отдельно (`EnrollResponse.ca_bundle_pem`), промежуточных CA пока нет.
- Go-фикстуры: `server/src/test/resources/pki/gencsr.go` (`//go:build ignore`, только stdlib; `go run gencsr.go`) пишет CSR P-256, P-384, P-521, RSA, Ed25519 и P-256 с испорченной подписью. `golden-ca.crt` сделан `openssl`, эталонный отпечаток посчитан `openssl … | sha256sum` (команда — в `CaFingerprintTest`).
- Единственная пометка `// mutflow:falsePositive` — на `syncDirectory()` (fsync каталога после rename). Удаление fsync не меняет ничего, что можно наблюдать без сбоя ОС; это эквивалентный для тестов мутант. Запись файлов тоже делает `force(true)` — это тоже не проверяется тестами, по той же причине.

### Как mutflow считает мутанты (вывод из прогонов)
Мутант, достигнутый внутри `MutFlow.underTest` в тестовом классе, должен быть
убит этим же классом. Отсюда правило для тестов:
- в `underTest` оборачивать то, что проверяет класс;
- исходные данные (пары ключей CA для `CaDirectoryTest`) готовить снаружи.

Первые прогоны нашли реальные пробелы, их закрыли:
- не было CSR с ключом EC на неподдержанной кривой (P-521);
- серийный номер проверялся как «≥ 64 бит», а не «ровно 128»;
- в `CaDirectoryTest` не было отказов по правам и по несовпадающему ключу;
- серверный сертификат проверялся вне `underTest`.

## Фаза 3 — TLS на gRPC-порту, перевыпуск, документация

### Решения
- **`CertificateAuthority.renewServerCertificate(): Boolean`** добавлен в интерфейс: жизненный цикл сертификата сервера — дело CA. Vault-реализация перевыпускает свой, корпоративная PKI возвращает false. Файловая реализация перевыпускает, когда до конца осталось 30 дней или меньше (граница включительно).
- **`PkiAutoConfiguration`** (в `AutoConfiguration.imports`):
  - `PkiProperties` (`sard.pki.dir`, `server-names`, `renewal-check-interval` = 1 день);
  - `FileCertificateAuthority` (`@ConditionalOnMissingBean`);
  - `SslBundleRegistrar` с бандлом `sard-grpc`;
  - `ServerCertificateRenewal` (`SmartLifecycle`, демон-поток планировщика).
- **`KeyManagerFactory`** — обёртка над `serverKeyManager()` без копирования ключа: перевыпуск действует на новые рукопожатия без рестарта.
- **`spring.grpc.server.ssl.secure: true` обязателен.** При `false` Spring gRPC передаёт фабрике не доверие из бандла, а свой TrustManager (видно по байткоду `ServerCredentials.get`). Контрольный прогон с `SPRING_GRPC_SERVER_SSL_SECURE=false` роняет тест «сертификат чужого CA отвергается» (`expected UNAVAILABLE but was UNIMPLEMENTED`) — тест охраняет эту настройку.
- **Каталог CA в тестах** — `server/build/test-pki` через `systemProperty` в `tasks.test`: `/var/lib/sard/pki` в CI недоступен на запись, а тесты S1 так не пришлось менять. `SardServerIntegrationTest` ходит в gRPC по TLS с CA-бандлом; проверки прежние.
