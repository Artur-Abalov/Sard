## Суть решения

Проверку восстановления делает отдельный агент-верификатор на другой машине: он
достаёт снапшот из репозитория, восстанавливает его в изолированной песочнице и
сравнивает с отпечатком источника. В MVP это работает для PostgreSQL (только
pg_dump) и для файлов: файлы нужны первому пилоту.

Три решения, на которых всё держится:

1. Проверка — отдельное задание, а не шаг бэкапа. Задание ссылается на ID
   снапшота restic, поэтому один снапшот можно проверить позже и глубже.
2. Уровни — конвейер стадий с остановкой на первой ошибке. Итог задания —
   максимальный достигнутый уровень.
3. Плагин отдаёт отпечаток, сравнивает ядро. Один и тот же код снимает отпечаток
   с источника и с восстановленной копии.

Что уже есть: агенты-источники делают бэкапы и шифрованно отправляют их в
репозиторий restic.

Данные идут от источника в хранилище и оттуда к верификатору, минуя сервер.
Через сервер проходят только отпечаток, ID снапшота, задания и отчёты.

## Уровни проверки

Каждый следующий уровень доказывает больше и стоит дороже. В MVP все пять
выполняются одним полным циклом раз в сутки для последнего снапшота каждого
источника.

| Уровень | Что делаем | Что доказывает |
|---|---|---|
| 1. Целостность хранилища | restic check с чтением части данных | Блобы не побились |
| 2. Извлечение | restic dump снапшота ключом верификатора | Данные достаются без исходного хоста |
| 3. Запуск приложения | pg_restore в контейнер нужной версии PostgreSQL | Дамп пригоден для СУБД |
| 4. Смысл данных | Сравнение отпечатка копии с отпечатком источника | Восстановились те же данные, а не пустая база |
| 5. Время восстановления | Сумма длительностей стадий | Фактический RTO |

Уровни 2 и 3 идут одним потоком: restic dump | pg_restore, без промежуточного
файла на диске.

Таблица описывает PostgreSQL. Для файлов уровня 3 нет, остальные устроены
иначе: см. раздел «Проверка файлов».

## Безопасность

Сервер не хранит и не передаёт пароли репозиториев и учётные данные хранилищ: он
видит только метаданные — ID снапшотов, статусы, отпечатки.

- Отдельный ключ restic у верификатора. restic поддерживает несколько ключей на
  репозиторий. У источника ключ A, у верификатора ключ B, отзыв — restic key
  remove.
- Ключ заводит админ вручную. restic key add, пароль в локальный файл на
  верификаторе, так же как на источнике.
- Хранилище только на чтение. Любой ключ restic открывает весь репозиторий,
  поэтому верификатор ограничен учёткой хранилища без права записи и работает с
  --no-lock.
- Ключ восстановления. При создании репозитория продукт требует выпустить
  третий, офлайновый ключ: потеря хоста иначе означает потерю пароля.
- Верификатор не исполняет скрипты с сервера. Только встроенные шаги плагина.

Модель угроз MVP: защищаемся от утечки базы сервера, но не от его полного
захвата. Захваченный сервер по-прежнему может отправить агенту-источнику
сценарий с произвольным bash; это закрывает подпись сценариев, она отложена.

## Отпечаток источника

Отпечаток — это небольшой набор фактов о базе в момент дампа, с которым
сравнивается восстановленная копия. Он закрывает главную ловушку: пустой дамп
тоже восстанавливается «успешно».

Что собираем для PostgreSQL:

- версию PostgreSQL и список расширений;
- число таблиц и размер базы;
- точный count(*) по небольшому списку ключевых таблиц, который задаёт админ.

Как добиваемся точного совпадения. Агент-источник открывает транзакцию, берёт
pg_export_snapshot(), снимает отпечаток и запускает pg_dump --snapshot на том
же снимке. Источник живой, но отпечаток и дамп видят одно состояние, поэтому
допуск расхождения равен нулю.

Где хранится. Отпечаток уходит на сервер вместе с результатом задания бэкапа, а
его хеш пишется в тег снапшота restic. Верификатор сверяет хеш из тега с тем, что
прислал сервер.

Интерфейс плагина. Вместо одного verify три метода: Fingerprint(conn),
RestoreInto(sandbox) и снова Fingerprint(conn) по копии. Сравнение делает ядро,
поэтому новый плагин не пишет свою логику проверки.

## Чем верификатор отличается от агента-источника

Это тот же бинарник и тот же транспорт (gRPC с mTLS, агент подключается сам), но
роль задаётся токеном регистрации и навсегда фиксируется в сертификате агента.
Предложение ниже ещё не согласовано.

| | Агент-источник | Верификатор |
|---|---|---|
| Роль в сертификате mTLS | source | verifier |
| Принимает задания | Только бэкап | Только проверка |
| Скрипты с сервера | Да, шаги сценария | Нет, только встроенные шаги |
| Ключ restic | Свой (A) | Свой (B), заведён вручную |
| Доступ к хранилищу | Запись | Только чтение |
| Доступ к боевым системам | Да, к своему источнику | Нет |
| Что нужно на хосте | Клиент СУБД | Docker или Podman, диск под полный объём базы или каталога |

Роль приходит из токена регистрации. Админ создаёт на сервере одноразовый токен
с коротким сроком жизни и ролью verifier. Агент предъявляет токен при первом
подключении, и сервер выпускает ему сертификат mTLS с ролью внутри. В локальном
конфиге роли нет, поэтому подменить её на хосте агента нельзя.

Сервер авторизует по сертификату. Каждый вызов ClaimJob несёт роль в
сертификате, и сервер отдаёт верификатору только задания проверки. Взломанный
агент-источник не может назваться верификатором.

Роль неизменна. Сменить её можно только новой регистрацией с новым токеном, то
есть действием админа на самом хосте. Агент читает роль из своего сертификата и
отклоняет задания другого типа, а при продлении сертификата не принимает другую
роль. Это страховка на случай захвата сервера: он выпускает сертификаты, но не
может молча превратить верификатор в исполнителя сценариев.

Возможности вместо секретов. При подключении и в каждом heartbeat верификатор
сообщает серверу:

- ID репозиториев, к которым у него есть ключ (без паролей);
- поддерживаемые плагины, в MVP файлы и postgresql;
- свободное место на диске и наличие Docker или Podman.

Правило разделения. Верификатор не может проверять репозиторий источника,
который работает на том же хосте: иначе проверка не доказывает восстановление
без исходной машины.

## Как верификатор получает задания

Верификатор сам забирает задания из очереди на сервере: сервер никогда не
подключается к агенту, входящие порты не нужны. Это тоже предложение, числа
ниже — стартовые значения.

Откуда берутся задания. Планировщик раз в сутки создаёт задание для последнего
успешного снапшота каждого источника, у которого включена проверка. На один
источник — не больше одного открытого задания.

Очередь. Таблица verify_jobs в PostgreSQL сервера. Отдельный брокер в MVP не
нужен: выдача делается через SELECT … FOR UPDATE SKIP LOCKED.

Выдача. Верификатор раз в 30 секунд вызывает ClaimJob. Сервер отдаёт задание,
только если выполнены все условия:

- у верификатора есть ключ к этому репозиторию и нужный плагин;
- он работает не на хосте источника;
- свободного диска хватает: размер базы из отпечатка с запасом.

Что в задании. ID задания, ID репозитория, ID снапшота, плагин, отпечаток и его
хеш, срок. Секретов нет.

Аренда. Выданное задание закрепляется за верификатором на 10 минут и
продлевается каждым heartbeat. Если верификатор пропал, аренда истекает и
задание возвращается в очередь. После трёх неудачных попыток оно получает статус
«сбой инфраструктуры».

Проверки на стороне верификатора перед стартом: тип задания соответствует роли,
снапшот существует в репозитории, хеш отпечатка в теге снапшота совпадает с
присланным.

Отчёт. После каждой стадии — ReportStage, в конце — Complete. Вызовы
идемпотентны по ID задания. Один верификатор выполняет одно задание за раз.

```proto
service Verifier {
  rpc ClaimJob(ClaimRequest) returns (ClaimResponse);
  rpc Heartbeat(HeartbeatRequest) returns (HeartbeatResponse);
  rpc ReportStage(StageReport) returns (Ack);
  rpc Complete(FinalReport) returns (Ack);
}
```

## Итоговые статусы

Главное различие — между «бэкап плохой» и «проверка не состоялась»: это разные
тревоги для разных людей.

| Статус | Что значит | Кто виноват |
|---|---|---|
| Пройдено | Все стадии успешны, отпечатки совпали | — |
| Провал | Стадия упала или отпечатки разошлись | Бэкап |
| Не можем проверить | Нет нужного расширения в образе, не хватает диска | Окружение верификатора |
| Сбой инфраструктуры | Три попытки исчерпаны, верификатор пропадал | Верификатор |
| Нет верификатора | Ни один верификатор не подходит под условия выдачи | Конфигурация |

## Конвейер проверки PostgreSQL

Верификатор выполняет шаги по порядку и останавливается на первой ошибке. После
каждого шага на сервер уходят статус, длительность и улики: вывод команды, код
возврата, digest образа.

1. Сверить хеш отпечатка из тега снапшота с присланным сервером.
2. Запустить restic check с чтением части данных.
3. Поднять контейнер postgres:<версия из отпечатка> без сети, с лимитами CPU,
   памяти и диска.
4. Выполнить restic dump | pg_restore в этот контейнер.
5. Снять отпечаток с копии тем же кодом, что и на источнике.
6. Сравнить отпечатки; любое расхождение — провал с перечнем различий.
7. Удалить контейнер и том, отправить итоговый отчёт.

Уборка. Контейнеры и тома помечаются метками задания. При старте агент удаляет
всё, что осталось от упавших проверок.

Расширения. Если в отпечатке есть расширение, которого нет в стандартном образе,
статус — «не можем проверить», а не «провал».

## Проверка файлов

Для файлов верификатор полностью восстанавливает снапшот во временный каталог и
сверяет его с отпечатком; контейнер и СУБД не нужны. Раздел — предложение, ещё
не согласован.

Отпечаток файлового источника состоит из трёх частей:

- Итоги restic. Число файлов и суммарный размер из сводки restic backup --json.
  После восстановления сравнение точное.
- Контрольные пути. Список файлов и каталогов от админа, которые обязаны
  существовать и быть непустыми. Это ловит главный файловый сбой:
  отмонтированный диск или пустой каталог бэкапится «успешно».
- Выборка хешей. Агент-источник до бэкапа считает SHA-256 примерно для 100
  случайных файлов. Это единственная проверка, не зависящая от самого restic.

Конвейер:

1. Сверить хеш отпечатка из тега снапшота с присланным сервером.
2. Запустить restic check с чтением части данных.
3. Выполнить restic restore --verify во временный каталог на отдельном томе.
4. Посчитать файлы и размер, сравнить с итогами restic.
5. Проверить контрольные пути.
6. Сравнить хеши выборки.
7. Удалить каталог, отправить отчёт с временем восстановления.

Чем это отличается от PostgreSQL:

- Нет общего снимка. Файлы меняются во время бэкапа, поэтому после бэкапа
  агент-источник выбрасывает из выборки файлы, у которых изменились размер или
  время правки.
- Ничего не исполняется. Том для восстановления смонтирован с noexec,
  восстановленные файлы только читаются.
- Предупреждение о резком падении. Если число файлов или объём упали больше чем
  на 30% относительно прошлого снапшота, проверка получает статус «пройдено» с
  предупреждением в уведомлении.

Что нужно узнать у пилота: объём данных и число файлов. ОС известна: у пилота
Ubuntu, Windows в MVP не поддерживается ни на источниках, ни на верификаторе.

## Отчёт, дашборд и уведомления

Главная метрика дашборда — «последнее проверенное восстановление N часов назад»
по каждому источнику, с достигнутым уровнем.

Запись о проверке на сервере: снапшот, верификатор, статус и длительность каждой
стадии, достигнутый уровень, расхождения отпечатков, digest образа, итоговое
время восстановления.

Уведомления в Telegram:

- проверка провалилась — с указанием стадии и расхождений;
- источник не проверялся дольше N дней.

Второе важнее первого: молчащий или сломанный верификатор не должен выглядеть
как успех.

## Что откладываем после MVP

- Автоматическая доставка ключей верификатору с подтверждением отпечатка ключа
  на источнике.
- Подпись сценариев ключом админа, которого нет на сервере: защита от захвата
  сервера.
- Физические копии и WAL (pg_basebackup): общего снимка нет, сравнение придётся
  вести по границам «до и после».
- Свои образы для баз с расширениями (PostGIS, Timescale).
- Ярусы для больших баз: ежедневно целостность, полное восстановление реже и с
  ротацией.
- MikroTik и Eltex: пока только restic check и пробное извлечение.
- Неизменяемые отчёты для аудита.
- Постоянный поток вместо опроса ClaimJob.
