# PostgreSQL сервера Sard

Документ описывает базу, на которой работает `sard-server`. В нём собраны
решения D25 (параметры инициализации) и D29 (внешний кластер — после 0.1.0).
Эксплуатация — в [разделе 16 руководства оператора](operator/16-postgresql.md),
обоснование — в [ADR 00XX-draft-embedded-postgresql](adr/00XX-draft-embedded-postgresql.md).

## Что хранится в базе

В базе только управляющие данные: агенты, источники, расписания, история
запусков, журналы шагов, результаты проверок восстановления. Данные бэкапов
в неё не попадают никогда: агент отправляет их в хранилище через restic.
Ключей и паролей хранилищ в базе тоже нет (ADR 0008). Поэтому база маленькая:
сразу после установки около 50 МБ, растёт она в основном за счёт журналов
шагов (`step_logs`, секции по месяцам) и истории запусков, которые чистит
уборка ([раздел 15](operator/15-data-retention.md)).

Схема — миграции Flyway в `server/src/main/resources/db/migration`. Сервер
применяет их сам при старте. Версия миграции — время `VГГГГММДДЧЧММ`.
Две миграции с одной версией Flyway не принимает, поэтому
`ArchitectureTest` проверяет, что версии не повторяются.

## Версия

| Что | Значение |
|---|---|
| Встроенный сервер (compose) | PostgreSQL 18.6, `postgres:18.6-alpine`, закреплён по digest |
| Основа образа агента `-pg18` | `postgres:18.6-trixie`, закреплён по digest: `pg_dump` той же версии, что сервер |
| Внешний сервер | 16, 17, 18 |
| Отказ стартовать | PostgreSQL 15 и старше |
| Предупреждение | PostgreSQL 19 и новее: не проверялся |

Обе ссылки на образы записаны в одном файле, `deploy/postgres.env`. Его копии
есть в `deploy/docker-compose.yml` и `deploy/.env.example`: релиз раздаёт эти
файлы отдельно от репозитория. `DeployPostgresTest` падает, если копия
расходится с файлом или если скрипт, workflow, тест или страница документации
называет другой образ.

Минорная версия меняется так: оба образа сразу, одной правкой
`deploy/postgres.env` и копий. Клиентские утилиты в образе агента
(`pg_dump` самобэкапа) не бывают старше сервера: тест проверяет, что у обоих
образов одна минорная версия.

### Офлайн-установка и digest

Digest образа даёт только реестр. После `docker load` у образа нет
digest реестра, поэтому ссылку `postgres:18.6-alpine@sha256:…` без сети
найти нельзя (проверено на хранилище образов containerd и на классическом
overlay2). Офлайн-архив несёт PostgreSQL под тегом `postgres:18.6-alpine`:
скрипт скачивает образ по digest и сохраняет под тегом. В `.env` офлайн-установки
пишется `SARD_POSTGRES_IMAGE=postgres:18.6-alpine`
([раздел 11](operator/11-offline.md)). Содержимое архива то же, что по digest:
архив собирается из образа, скачанного по digest.

## Параметры инициализации (D25)

`initdb` выполняется один раз, на пустом томе. Его параметры потом не меняются:
другая локаль или контрольные суммы — это новый кластер и перенос данных.
Поэтому они заданы до раздачи `0.1.0-beta.1` наружу, а у установки, созданной
раньше, остаются прежними.

Аргументы — `POSTGRES_INITDB_ARGS` в compose-файле:

```text
--data-checksums --encoding=UTF8 --locale-provider=builtin --builtin-locale=C.UTF-8 --locale=C.UTF-8
```

| Параметр | Значение | Почему |
|---|---|---|
| Контрольные суммы страниц | включены | повреждённая страница на диске даёт ошибку при чтении, а не неверные данные в бэкапе и в отчёте |
| Кодировка | `UTF8` | имена источников и тексты журналов — в любом алфавите |
| Локаль | встроенный провайдер, `C.UTF-8` | сравнение строк по кодам символов, свойства символов Unicode; не зависит от libc образа (musl в alpine, glibc в Debian): индексы не ломаются при смене образа или обновлении libc |
| Часовой пояс | `UTC` | все столбцы времени — `timestamptz`, секции `step_logs` по месяцам UTC; `psql` оператора показывает время в UTC |

Без этих аргументов образ создаёт базу с libc-локалью `en_US.utf8` (проверено
на `postgres:18.6-alpine`). Контрольные суммы и UTC у такой базы уже есть:
в PostgreSQL 18 `initdb` включает суммы сам, часовой пояс образа — UTC.

### Сортировка имён и ICU

С локалью `C.UTF-8` строки упорядочены по кодам символов:

```text
C.UTF-8:  Banana < apple < zeta < Ёлка < Арбуз < Яблоко < ёж
ICU und:  apple < Banana < zeta < Арбуз < ёж < Ёлка < Яблоко
```

Для списков, которые читает человек, нужен второй порядок. Правило такое:
запрос, который сортирует имена, введённые людьми, пишет
`ORDER BY name COLLATE "und-x-icu"`. Коллация столбца при этом остаётся `C.UTF-8`.

Почему так, а не коллация ICU у столбцов:

- уникальные индексы (`sources`, `workflows`, `tenants` по имени) и
  проверки `CHECK (name ~ '^[A-Za-z0-9]…')` остаются побайтовыми и не
  зависят от версии ICU;
- обновление ICU меняет порядок, а с ним — индексы по столбцу с ICU-коллацией;
  сортировка в запросе индекса не требует;
- на 24 октября 2026 база не сортирует ни одного списка имён, введённых людьми:
  сортируются только имена плагинов и репозиториев (ASCII по `CHECK`), имена
  хостов сортирует Kotlin, консоль показывает порядок сервера. Миграция была бы
  без потребителя.

ICU-коллации есть в официальных образах PostgreSQL. Внешний сервер, собранный
без ICU, такой запрос не выполнит, поэтому первый запрос с `und-x-icu`
добавляет к проверке при старте наличие этой коллации.

## Профиль small

Настройки — файл `/etc/postgresql/postgresql.conf` в контейнере. Его
содержимое задано в compose-файле (`configs:`), PostgreSQL запускается
с `-c config_file=…`. Файл `postgresql.conf`, который `initdb` записал в том,
не читается. Значение меняется перезапуском сервиса `postgres`, без пересборки
образа. Поэтому профиль действует и на базах, созданных до DB1.

Профиль рассчитан на машину из [требований](operator/01-requirements.md):
2 ГБ памяти на сервер Sard и PostgreSQL вместе, до нескольких сотен источников.

| Параметр | Значение | Зачем |
|---|---|---|
| `max_connections` | 50 | пул сервера (10), роль самобэкапа `sard_self` (4), запас на `psql` и обслуживание |
| `shared_buffers` | 256MB | вся рабочая часть базы в памяти |
| `effective_cache_size` | 768MB | оценка кэша ОС для планировщика |
| `work_mem` | 4MB | сортировки и хеши одного узла плана |
| `maintenance_work_mem` | 64MB | `VACUUM`, создание индексов в миграциях |
| `wal_level` | `replica` | допускает `pg_basebackup` и реплику без перезапуска |
| `max_wal_size` | 1GB | реже контрольные точки при всплеске записи журналов |
| `log_min_duration_statement` | 1s | медленные запросы в журнале |
| `log_lock_waits` | on | ожидания блокировок дольше `deadlock_timeout` |
| `log_autovacuum_min_duration` | 10s | долгие проходы автоочистки |
| `track_io_timing` | on | время ввода-вывода в `pg_stat_*` и `EXPLAIN (BUFFERS)` |
| `timezone`, `log_timezone` | `UTC` | как у `initdb` |
| `listen_addresses` | `*` | сервер подключается по сети compose |

Значения не проверялись под нагрузкой: это расчёт по памяти, а не замер.
Профиль medium — после 0.1.0.

## Проверка при старте сервера

До миграций сервер читает параметры базы. Он только читает: `current_setting`,
строку текущей базы из `pg_database`. Права суперпользователя не нужны,
расширения не нужны.

| Что | Новая установка | Если иначе |
|---|---|---|
| Версия | 16–18 | 15 и старше — отказ `DATABASE_VERSION_UNSUPPORTED`; 19 и новее — предупреждение |
| `data_checksums` | `on` | предупреждение |
| Кодировка | `UTF8` | предупреждение |
| Локаль | builtin `C.UTF-8` или libc `C.UTF-8` | предупреждение |
| `log_timezone` | `UTC` или `Etc/UTC` | предупреждение |

Часовой пояс читается из `log_timezone`. JDBC-драйвер ставит `TimeZone`
сессии по часовому поясу JVM сервера, поэтому `SHOW TimeZone` из сервера
показал бы `TZ` контейнера сервера, а не настройку базы.

Отличие — не отказ: внешнюю базу заказчика могли настроить иначе намеренно.
Сервер пишет одну строку `WARN` со всеми отличиями и ссылкой на
[раздел 16](operator/16-postgresql.md) и ставит
`sard_database_settings_mismatch{reason}` в `1` для каждого отличия
(`data_checksums`, `encoding`, `locale`, `timezone`, `version`).

## Внешний кластер (D29)

После 0.1.0. Ничего в DB1 не предполагает, что база встроенная: сервер
подключается по `SARD_DB_URL`, проверка при старте работает на любом
PostgreSQL 16–18 и под ролью без прав суперпользователя. Роли и `bootstrap.sql` —
DB2, таймауты, пулы и `application_name` — DB3.

## Переход базы, созданной до DB1

База, созданная раньше, работает дальше: сервер стартует, данные на месте,
в журнале и метрике — отличие локали. Чтобы получить параметры новой
установки, базу переносят в новый том: самобэкап (F6) → новый том →
восстановление по процедуре F7 ([раздел 12](operator/12-server-recovery.md)) →
проверка. Шаги — в [разделе 16](operator/16-postgresql.md). Процедура F7
подходит без изменений: дамп `pg_dump --format=custom` без `--create`
не несёт параметров кластера, и `pg_restore` заливает его в пустую базу `sard`,
которую `initdb` нового тома создаёт уже с новыми параметрами.
Автоматический помощник — после 0.1.0.
