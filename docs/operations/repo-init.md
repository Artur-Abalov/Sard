# Репозитории агента: `sard-agent repo init` и `sard-agent repo list`

Команды A5b создают репозиторий restic по имени из конфига агента и
показывают, какие репозитории конфига уже инициализированы. Сценарии и
решения владельца — `docs/specs/agent/repo-init.feature`; ручная проверка —
`docs/qa/repo-init.md`; коды выхода закреплены в ADR 0025 (раздел A5b) и
продублированы ниже. Модель доверия — ADR 0008: адрес репозитория, файл
пароля и файл окружения берутся только из конфига, флагами пароль и ключи
не принимаются.

## От чьего имени запускать

Команды неинтерактивны, не читают стандартный ввод, не меняют конфиг и не
обращаются к серверу Sard, поэтому работают и до `enroll`. Запускайте их через
`sudo` (поправка A8a, `docs/adr/0049-agent-privilege-model.md`): созданный
`--generate-password` файл пароля тогда принадлежит пользователю службы
(`sard-agent`, или `service.user` основного конфига; права `0600`), а `restic`
запускается от его имени — иначе файл пароля или кэш принадлежали бы root, и
служба отказалась бы стартовать (проверка A1: секретные файлы не должны быть
доступны никому, кроме владельца, и должны ему принадлежать). Запуск от
самого пользователя службы работает как раньше; любой другой пользователь
получает `PRIVILEGES_REQUIRED` (код 2) с подсказкой `sudo` — это относится и к
`repo list`:

```bash
sudo sard-agent repo list
sudo sard-agent repo init --generate-password main
sudo systemctl restart sard-agent
```

Новый репозиторий на этом хосте проще добавить командой `sudo sard-agent repo
add` (`docs/operations/agent-host-setup.md`): она создаёт каталог, пароль,
разрешение записи для службы и фрагмент `agent.d`, не меняя `agent.yaml`.
`repo init` остаётся для репозиториев, описанных в `agent.yaml` (в том числе в
облачном хранилище). Репозитории из фрагментов `agent.d` видят `repo init`,
`repo list`, `repo show` и агент при старте.

`--config` по умолчанию — `/etc/sard/agent.yaml`. Каталог файла пароля
команда не создаёт. Пакеты deb и rpm при первой установке создают для этого
`/etc/sard/secrets` (владелец `sard-agent`, права `0700`) — туда указывают
`password_file` и `env_file` в примере конфига. При установке из tar.gz или
другом каталоге создайте его сами и отдайте пользователю службы
(`sudo install -d -o sard-agent -g sard-agent -m 0700 /etc/sard/secrets`; `secret
set` и `repo add` создают его сами). Если файл пароля уже есть, `repo init` ничего
не пишет в его каталог и права записи в него не требует.

### Каталог кэша restic и блокировка

На время работы `repo init` берёт блокировку — файл
`<restic.cache_dir>/.sard-init-<имя>.lock` (по умолчанию
`/var/cache/sard/restic`); при любом нормальном завершении файл удаляется,
оставшийся после аварии никем не удерживаемый файл повтору не мешает.
`restic.cache_dir` **должен существовать и быть доступен на запись**
пользователю, который запускает команду; команда его не создаёт. Иначе —
код 7, `LOCK_WRITE`, в сообщении ключ `restic.cache_dir`, путь и причина ОС;
файл пароля при этом не создаётся, к бэкенду команда не обращается.

- Пакеты deb и rpm создают `/var/cache/sard/restic` при установке
  (владелец и группа `sard-agent`, права `0700`), так что `repo init`
  работает сразу после установки, до первого старта службы. Повторная
  установка и обновление сохраняют содержимое и возвращают владельца и права;
  удаление пакета каталог оставляет. Unit задаёт `CacheDirectoryMode=0700`,
  поэтому старт службы права не меняет.
- Архив tar.gz каталог не создаёт: создайте его сами, например
  `install -d -o sard-agent -g sard-agent -m 0700 /var/cache/sard/restic`.
- Если в конфиге задан другой `restic.cache_dir`, создайте и его так же
  (и добавьте в `ReadWritePaths` службы, см. unit).
- Локальный репозиторий (`url` — путь на этом хосте) служба под
  `ProtectSystem=strict` видит только на чтение, а restic берёт в нём
  блокировку даже для чтения конфига и ждёт её бесконечно: агент при старте
  зависает. Добавьте каталог репозитория в `ReadWritePaths`
  (`sudo systemctl edit sard-agent`); `repo add` делает это сам:

  ```ini
  [Service]
  ReadWritePaths=/srv/sard-repo
  ```

- `repo list` блокировку не берёт и работает без каталога кэша.
- Под `sudo` блокировку берёт root: файл создаётся и удаляется им, каталог
  кэша остаётся пользователя службы.

## `repo init [--config C] [--generate-password] [--timeout 2m] <имя>`

Порядок проверок (первая сработавшая определяет код выхода): флаги →
конфиг → имя → `crypto_provider` → `password_file` → `env_file` → restic →
блокировка → генерация пароля → `restic cat config` → `restic init`.

- **Файл пароля.** Должен существовать, быть непустым и доступным только
  владельцу. Нет файла — команда откажет, если не указан
  `--generate-password`: с флагом она создаст файл (32 случайных байта в
  base64url, 43 символа и перевод строки, права `0600`, владелец — пользователь службы) и
  инициализирует репозиторий. Существующий файл с флагом используется как
  есть и никогда не перезаписывается. Если инициализация не удалась,
  созданный файл остаётся и будет использован при повторе — прерванный
  `restic init` мог успеть записать ключ этим паролем.
- **Ключ есть только на этом хосте.** Итог успеха всегда напоминает: сохраните
  копию файла пароля вне хоста — без неё при потере хоста бэкапы
  невосстановимы. Сервер не хранит ключей (ADR 0008).
- **Перезапуск.** После успеха перезапустите службу агента: `repository_id`
  попадает на сервер в `Register`, а работающий агент конфиг не перечитывает.
- **Репозиторий уже есть.** Команда сначала выполняет `restic cat config`;
  найденный репозиторий никогда не инициализируется повторно (код 4, в
  сообщении его `repository_id`). Если пароль из файла его не открывает —
  код 2, `WRONG_PASSWORD`.
- **Таймаут.** `--timeout` (по умолчанию 2 минуты) ограничивает всю команду.
  restic сам повторяет запросы к недоступному сетевому бэкенду с нарастающей
  паузой около 15 минут (проверено на закреплённом restic 0.19.1), поэтому
  недоступный по сети бэкенд обычно даёт `TIMEOUT` по истечении `--timeout`
  (код 6), а не мгновенный `BACKEND_UNAVAILABLE`; повторить команду можно.
  Истечение таймаута и SIGINT останавливают restic (SIGTERM) и
  дожидаются его завершения; репозиторий мог быть создан частично — повторите
  команду, она увидит его как существующий или доведёт создание.

### Коды выхода `repo init`

| код | класс             | когда |
|---|---|---|
| 0 | успех             | репозиторий создан; также `--help` |
| 1 | ошибка агента     | restic не найден, старый или непригоден; несетевой отказ бэкенда (`BACKEND_REFUSED`: учётные данные, права, TLS бэкенда); непредусмотренный вывод restic |
| 2 | использование     | флаги, `PRIVILEGES_REQUIRED`, `SERVICE_USER_UNKNOWN`, конфиг, неизвестное имя, `crypto_provider`, `password_file`, `env_file`, `WRONG_PASSWORD` |
| 4 | идентичность есть | репозиторий уже инициализирован (`REPOSITORY_EXISTS`) |
| 6 | временная         | бэкенд недоступен по сети, `TIMEOUT`, `INTERRUPTED`, идёт другой init (`INIT_IN_PROGRESS`) |
| 7 | запись            | файл пароля не создать (`PASSWORD_FILE_WRITE`); файл блокировки в `restic.cache_dir` не создать (`LOCK_WRITE`) |

Каждый отказ содержит строку причины (`REPOSITORY_UNKNOWN`,
`CRYPTO_PROVIDER_UNSUPPORTED`, `PASSWORD_FILE_MISSING`, `PASSWORD_FILE_EMPTY`,
`ENV_FILE_MISSING`, `ENV_FILE_INVALID`, `RESTIC_NOT_FOUND`, `RESTIC_TOO_OLD`,
`RESTIC_UNUSABLE`, `REPOSITORY_EXISTS`, `WRONG_PASSWORD`, `BACKEND_UNAVAILABLE`,
`BACKEND_REFUSED`, `INTERRUPTED`, `TIMEOUT`, `INIT_IN_PROGRESS`,
`PASSWORD_FILE_WRITE`, `LOCK_WRITE`), кроме нарушения прав или владельца секретного файла:
его команда печатает текстом A1, как при старте агента. Пароль, значения из
`env_file` и пароль из адреса репозитория в вывод не попадают.

## `repo list [--config C] [--timeout 2m] [--json]`

Только чтение: ничего не создаёт и не инициализирует. Таблица со столбцами
`NAME BACKEND STATUS REPOSITORY_ID`, по строке на репозиторий в порядке конфига;
`STATUS` — `initialized`, `not-initialized` или причина, по которой строку
проверить не удалось (`WRONG_PASSWORD`, `SECRET_FILE_REJECTED`,
`BACKEND_UNAVAILABLE`, `TIMEOUT` …); адрес репозитория не печатается.
Проблема одной строки не прерывает список: сообщение по ней — в stderr, с
именем репозитория в начале. С `--json` (поправка Л4а) в stdout — один объект
`{"repositories":[{"name","backend","status","repository_id","defined_in"}]}`
(`repository_id` — `null`, если не известен); сообщения и коды выхода те же.

| код | когда |
|---|---|
| 0 | состояние каждого репозитория известно (неинициализированный — не ошибка); конфиг без репозиториев; `--help` |
| 1 | restic не найден, старый или непригоден; либо первая постоянная проблема строки — класса 1 |
| 2 | флаги, `PRIVILEGES_REQUIRED` или конфиг; либо первая постоянная проблема строки — класса 2 |
| 6 | все проблемы строк временные; прерывание (таблица не печатается) |

Код один на запуск: код класса первой в порядке конфига проблемной строки,
класс которой не «временная»; если все проблемы временные — 6.

## restic при старте агента

Агент (и `repo init`, `repo list`) проверяет restic до обращения к сети:
`restic.path` из конфига, а если он не задан — `restic` рядом с настоящим
файлом `sard-agent` (символьные ссылки разворачиваются). Не найден, не
запускается, не отвечает на `version` строкой `restic X.Y.Z` или старше
минимальной версии (`min_version` в `agent/internal/restic/restic-version`) —
агент не стартует, код 1, сообщение называет путь, причину и версии
(`RESTIC_NOT_FOUND`, `RESTIC_UNUSABLE`, `RESTIC_TOO_OLD`). Версия новее
закреплённой принимается без предупреждения. `enroll` и `--version` restic не
требуют.
