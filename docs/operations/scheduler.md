# Планировщик запусков

Сервер сам запускает бэкап источника по расписанию: стандартный cron из пяти
полей в часовом поясе IANA. Запуск по расписанию создаётся тем же путём, что и
ручной, и подчиняется тому же правилу: не больше одного активного запуска на
источник (ADR 0022). Решения — `docs/adr/00XX-draft-scheduler.md`.

## Расписание источника

```bash
# Каждую ночь в 02:30 по Берлину
curl -X PUT .../api/v1/sources/<id>/schedule \
  -H 'Content-Type: application/json' \
  -d '{"cron":"30 2 * * *","timezone":"Europe/Berlin","enabled":true}'

# Выключить: cron и пояс сохраняются, срабатываний нет
curl -X PUT .../api/v1/sources/<id>/schedule -d '{"cron":"30 2 * * *","timezone":"Europe/Berlin","enabled":false}'

# Журнал срабатываний, новые сверху
curl .../api/v1/sources/<id>/schedule/fires
```

- Cron — ровно пять полей; имена месяцев и дней (`JAN`, `MON-FRI`) можно.
  `?`, `L`, `W`, `#`, `@daily` и шестое поле — 422 `validation_failed` с полем
  `cron`. Если заданы и день месяца, и день недели, срабатывает любой из них,
  как в стандартном cron.
- Летнее время: расписание с фиксированным часом (`30 2 * * *`) в ночь перевода
  вперёд срабатывает один раз в момент перевода, в ночь перевода назад — один
  раз, в первом прохождении часа. Расписание со `*` в поле часа идёт по
  реальному времени.
- Изменение cron, пояса или включение пересчитывает следующее срабатывание от
  текущего момента; повторная отправка того же расписания его не сдвигает.

## Что пишет журнал

| `outcome` | Что случилось |
|---|---|
| `run_created` | Запуск создан (`kind=schedule`) или догоняющий (`kind=catch_up`) |
| `skipped_active` | У источника идёт запуск (`runId` — он); срабатывание пропущено, не в очередь |
| `skipped_gone` | Агент отозван (`reason=agent_revoked`) или источник удалён в момент срабатывания |
| `refused` | Агент больше не предлагает плагин или репозиторий (`unknown_plugin`, `unknown_repository`) |
| `skipped_downtime` | Сервер был остановлен: `missedCount` срабатываний с `scheduledFor` по `missedUntil` |

Пропуски `skipped_*` и `refused` считаются подряд (`skippedInRow`); на третьем
подряд (`sard.scheduler.skip-alert-threshold`) у строки `alert=true`. Созданный
запуск обнуляет счётчик.

## Простой сервера

Если сервер стоял и пропустил несколько срабатываний, после старта источник
получает **один** догоняющий запуск (`trigger=catch_up`), а пропущенные — одну
строку `skipped_downtime`. Догоняющие запуски разных источников идут с шагом
`sard.scheduler.catch-up-spacing` (10 с), а не все в одну секунду. Одно
пропущенное срабатывание, у которого следующее ещё впереди, — обычный запуск,
просто поздний.

## Настройки

| Свойство | По умолчанию | |
|---|---|---|
| `sard.scheduler.interval` | 10s | Как часто сервер проверяет расписания; держать меньше минуты |
| `sard.scheduler.catch-up-spacing` | 10s | Шаг между догоняющими запусками после простоя |
| `sard.scheduler.skip-alert-threshold` | 3 | Какой пропуск подряд помечается алертом |
| `sard.scheduler.batch` | 500 | Сколько расписаний за одну проверку |

## Уведомления

Запуск по расписанию уведомляет только о первой ошибке в серии и о первом
успехе после ошибок (ADR 0024); ручной — всегда. См. `notifications.md`.

## Наблюдать

- `sard.scheduler.fires` (теги `kind`, `outcome`) — срабатывания после коммита.
- `sard.scheduler.lag.seconds` — насколько самое старое созревшее срабатывание
  отставало от «сейчас» в начале последней проверки. Растёт — планировщик не
  успевает или стоит.
- Несколько экземпляров сервера на одной базе безопасны: каждое срабатывание
  берётся одним из них (`FOR UPDATE SKIP LOCKED`).
