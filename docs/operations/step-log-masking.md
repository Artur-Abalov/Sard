# Маскирование секретов в логах шагов

Агент заменяет значения секретов маркером `[REDACTED]` в логах шага, в
сообщении результата шага и в `detail` проверок **до** того, как они попадут
на диск или уйдут на сервер. Сценарии и решения владельца —
`docs/specs/agent/step-log-masking.feature`, ADR 0033; ручная проверка —
`docs/qa/step-log-masking.md`. Модель доверия — ADR 0008: сервер секретов агента
не знает, поэтому маскирует только агент.

## Что маскируется

Значения берутся из конфига агента и читаются заново на каждом шаге:

| Источник | Что маскируется |
|---|---|
| `secrets:` | значения **всех** секретов агента (все секреты агента, а не только те, на которые ссылается шаг: плагин или скрипт может прочитать и чужой) |
| `env_file` | правая часть каждой строки `KEY=VALUE` файла окружения **всех репозиториев** конфига |
| `tls.key_file` | закрытый ключ агента (PEM целиком) |
| адрес репозитория шага | пароль из `user:пароль@` в адресе, например `rest:http://u:пароль@host/repo` |

Значение — содержимое файла без завершающих `\r\n`. Пробелы и табуляции по
краям остаются частью значения (как у `$(cat файл)` в shell): скрипт, напечатавший
значение без пробела на конце, замаскирован не будет — пробел в значении
секрета лучше не использовать. Пустое значение пропускается и не отключает
остальные.

**Виды значения.** Каждое значение ищется в каждом из видов:

- как есть;
- в строке JSON: с экранированием и без экранирования HTML (так пишет
  `restic --json`);
- с экранированием URL: для запроса (пробел как `+`), для сегмента пути и как
  пароль в userinfo; шестнадцатеричные цифры `%XX` в верхнем и нижнем регистре;
- base64 стандартный и base64url (RFC 4648, разделы 4 и 5), с выравниванием `=`
  и без него. Маркер поглощает знаки `=`;
- base64 значения внутри более длинного base64-текста, при любом из трёх
  сдвигов: заголовок `Authorization: Basic …` (`user:значение`), `echo значение
  | base64` с переводом строки на конце. Маскируются знаки, которые целиком
  определяются значением; два-три знака на краю, зависящие от соседнего текста,
  остаются.

Многострочное значение (ключ PEM) заменяется **одним маркером** и в одной
строке лога, где бы оно ни стояло: в выводе restic, в одной строке плагина, в
JSON-строке или в base64. Значение, разорванное между порциями вывода restic,
тоже находится.

Маркер всегда `[REDACTED]`: **имя секрета в журнале не раскрывается**. Соседние
и перекрывающиеся вхождения дают один маркер. Строки без секретов маскирование
не меняет и их порядок внутри одного источника сохраняет; остальное изменение
строк (удаление `\r`, замена невалидного UTF-8, разрез по 8 КиБ, правила
сервера) остаётся как раньше.

В журнал самого агента значения тоже не попадают: например, значение паники
плагина проходит через то же маскирование, что и лог шага.

## Предупреждение о коротких значениях

Значение короче 4 знаков (кодовых точек Unicode; для невалидного UTF-8 — байт)
маскируется так же, как остальные, но заменит такой же текст **везде** в логах
шага, и логи станут менее читаемыми. Это же касается несекретных значений в
`env_file`, например `AWS_DEFAULT_REGION=eu`: агент не отличает секретное от
несекретного и маскирует все значения.

При старте агент читает файлы секретов и `env_file` и пишет по одной строке
уровня `WARN` на каждое короткое значение. Строка называет секрет, для
`env_file` репозиторий и переменную, и не содержит ни значения, ни его длины. На
каждом шаге предупреждение не повторяется; значение, которое стало коротким
после старта (файл заменили), предупреждается один раз, на первом шаге, который
его увидел. Нечитаемый при старте файл старт не отменяет. Нечитаемый файл `secrets:`
(даже если шаг на него не ссылается) и нечитаемый или неверный `env_file`
репозитория самого шага валят шаг: он падает с FAILED и сообщением вроде
`log redaction: cannot read secret "<имя>": <причина ОС>` (без пути к файлу).

## Что не маскируется

Маскируется только то, что агент знает, и только в перечисленных видах.
**Секрет, напечатанный в другом виде, маскирован не будет:**

- зашифрованный или хешированный (`openssl enc`, SHA-256 значения);
- по частям: части значения, напечатанные отдельными строками или вызовами;
  отдельная строка ключа PEM без остального ключа; многострочный секрет, который
  плагин пишет по строке на вызов `Host.Log` (многострочный текст пишите одним
  вызовом `Host.Log`; значение, разорванное между двумя вызовами, не находится);
- base64 с переносами строк (MIME, 76 знаков в строке; PEM, 64): перенос
  разрывает последовательность знаков;
- целиком в hex (`xxd -p`): шестнадцатеричная запись всего значения не ищется
  (hex-цифры `%XX` в URL-видах ищутся);
- с другими переводами строк, например CRLF вместо LF внутри многострочного
  значения;
- с другими пробелами по краям, чем в файле секрета (см. выше);
- значения нечитаемого `env_file` другого репозитория (не репозитория шага)
  и нечитаемого `tls.key_file`: шаг от них не зависит и не падает, но их
  значения не маскируются, пока файл не прочитается (то же для неверного
  `env_file` другого репозитория). Агент пишет одно предупреждение в журнал агента
  (уровень `WARN`; называет репозиторий и `env_file` или `tls.key_file`, причину
  ОС, но не путь и не значения), на следующих и параллельных шагах оно не
  повторяется. Когда файл снова читается, значения маскируются со следующего
  шага без сообщений; если он сломается снова, предупреждение будет новым;
- значения, которых агент не знает: секреты, заданные не в конфиге агента.

Кроме того:

- **Пароль репозитория из `password_file` агент не читает и не маскирует**:
  он передаёт файл restic по пути (ADR 0008), restic пароль не печатает.
- **Сервер логи повторно не маскирует**: секретов агента он не знает. Он только
  нормализует строки (удаляет NUL, обрезает длинную строку, держит бюджет шага).
- **Новое значение секрета маскируется со следующего шага.** Набор значений
  читается в начале шага; внутри шага `Host.Secret` отдаёт плагину то же
  значение, что известно маскировщику, поэтому заменённый во время шага файл не
  раскрывает новое значение в этом шаге.
- Гарантия на порядок строк действует внутри одного источника (вывод
  инструмента; строки плагина), между источниками её нет: строка вывода restic держит хвост,
  который может оказаться началом значения, и может прийти позже более поздней
  строки плагина. Порядок строк между источниками по `time` не восстанавливается.

## Проверить самому

```bash
# значение секрета tok печатает плагин или скрипт: в логе шага стоит [REDACTED]
# короткое значение: при старте в журнале агента одна строка WARN с именем секрета
journalctl -u sard-agent | grep 'less readable'
```
