# Настройка хоста агента: `sard-agent secret` и `sard-agent repo`

Секреты и репозитории, по ADR 0008, живут на хосте агента, а сервер знает
только их имена. Команды этой страницы (A8a) делают всю работу с файлами за
оператора: создают файлы с владельцем и правами, которых требует проверка A1,
пишут отдельные файлы рядом с основным конфигом, не трогая его, и применяют
изменение, не обрывая идущий шаг. Ручные `sudo -u`, `install`, `chown` и
`chmod` не нужны. Сценарии и решения владельца —
`docs/specs/agent/host-setup.feature`; ADR 0049 (каталог `agent.d`) и 0050
(права запуска); ручная проверка — `docs/qa/host-setup.md`.

`repo add` подключает **локальный путь**, **S3** (срез A8b-1, раздел «Репозиторий
S3» ниже) и **SFTP** (срез A8b-2, раздел «Репозиторий SFTP»). Адреса остальных
видов (`rest:`, `b2:`, `azure:`, `gs:`, `swift:`, `rclone:`) отказывают с
`BACKEND_NOT_SUPPORTED`; такие репозитории описывают в `agent.yaml` руками
(`docs/operator/05a-storage.md`, `docs/operations/repo-init.md`).

## Кто запускает

Все команды выполняются через `sudo` — от имени root:

```bash
sudo sard-agent secret set pg-prod --stdin < /root/pg-prod.pass
sudo sard-agent repo add main /srv/sard/main
```

| кто запускает | что может |
|---|---|
| root (`sudo`) | всё, в том числе `repo restore`, которое пишет файлы хоста и доступно только root |
| пользователь службы (`sard-agent`, или `service.user` основного конфига) | только чтение: `secret list`, `repo list`, `repo show`, `repo snapshots`, `repo password --reveal`; а также `repo init` и `enroll`, как раньше |
| любой другой | ничего: `PRIVILEGES_REQUIRED`, код 2, в сообщении готовая команда с `sudo` |

Проверка идёт сразу после разбора флагов, до чтения конфига. Изменяющая
команда от пользователя службы тоже отказывает: служба не меняет свою
настройку. Под `sudo` файлы, которые создала команда, принадлежат пользователю
службы, а `restic` запускается от его имени, так что файлы репозитория, кэша и
блокировок принадлежат тому, кто потом работает с ними как служба.

Пользователь службы — `sard-agent`; другой задаётся в **основном** конфиге:

```yaml
service:
  user: backup
```

Во фрагменте `agent.d` ключ `service` — ошибка конфига. Пользователя команда
ищет по `/etc/passwd` и `/etc/group` (без cgo): пользователи LDAP и SSSD ей не
видны; если служба работает от такого пользователя, заведите локальную запись
с теми же uid и gid. Нет такого пользователя — `SERVICE_USER_UNKNOWN`.

## Где что лежит

Рядом с основным конфигом (`/etc/sard/agent.yaml`):

| путь | что | владелец, права |
|---|---|---|
| `/etc/sard/agent.d/` | фрагменты | `root:sard-agent`, `0750` |
| `/etc/sard/agent.d/repo-<имя>.yaml` | репозиторий | `root:sard-agent`, `0640` |
| `/etc/sard/agent.d/secret-<имя>.yaml` | секрет | `root:sard-agent`, `0640` |
| `/etc/sard/secrets/<имя>` | значение секрета | `sard-agent`, `0600` |
| `/etc/sard/secrets/restic-<имя>.pass` | пароль репозитория | `sard-agent`, `0600` |
| `/etc/sard/secrets/restic-<имя>.env` | ключи репозитория S3 (A8b) | `sard-agent`, `0600` |
| `<домашний каталог>/.ssh/id_ed25519`, `.pub` | ключ пользователя службы для SFTP (A8b-2) | `sard-agent`, `0600`, `0644` |
| `<домашний каталог>/.ssh/known_hosts`, `config` | ключ хоста SFTP и блок на хост (A8b-2) | `sard-agent`, `0600` |
| `/etc/systemd/system/sard-agent.service.d/sard-repo-<имя>.conf` | `ReadWritePaths` каталога репозитория | `root`, `0644` |

Агент читает основной файл, затем фрагменты `agent.d/*.yaml` в порядке имён
(остальные файлы — `.имя.tmp-*`, `*.rpmsave`, `README` — пропускаются). Во
фрагменте допустимы только `repositories` и `secrets`. Одно имя в двух местах
— ошибка `DUPLICATE_NAME` с обоими файлами: агент с ней не стартует, `repo
list` и `secret list` тоже отказывают. Команды **никогда не меняют основной
конфиг**: имя, определённое в нём, отказывает с `DEFINED_IN_CONFIG`, а файл,
на который ссылается другой ключ (`password_file`, `env_file`, `secrets.*`,
`scripts.*`, `tls.key_file`), — с `PATH_IN_USE`.

Имя репозитория и секрета, которое принимают изменяющие команды, — 1–64
символа из `A–Z a–z 0–9 - _`, первый — буква или цифра (`NAME_INVALID`).
Имя, начинающееся с `-`, команда читает как флаг: чтобы получить
`NAME_INVALID`, а не ошибку флага, поставьте его после `--`
(`sudo sard-agent secret set --stdin -- -db`).

## Секреты

```bash
sudo sard-agent secret set <имя> [--stdin | --from-file <путь>] [--no-restart]
sudo sard-agent secret list [--json]
sudo sard-agent secret remove <имя> [--no-restart]
```

Значение **никогда не передаётся аргументом**: оно попало бы в историю
терминала и в список процессов. Источник — ровно один:

- терминал: без флагов, если стандартный ввод — терминал; ввод без эха, дважды
  (`SECRET_MISMATCH`, если разные); значение хранится как введено, без перевода
  строки;
- `--stdin` — весь стандартный ввод до конца, байт в байт;
- `--from-file <путь>` — содержимое файла, байт в байт; сам файл не меняется.

Без флага и без терминала команда ничего не читает и сразу отказывает с
`SECRET_SOURCE_MISSING`. Пустое значение — `SECRET_EMPTY`, больше 65536 байт —
`SECRET_TOO_LARGE`. `--stdin` хранит и перевод строки: передавайте значение
через `printf '%s' "$VALUE" | sudo sard-agent secret set db --stdin`, а не
`echo`.

Повтор с тем же значением ничего не меняет (`unchanged`, без перезапуска и
строки аудита). Новое значение существующего секрета заменяет старое атомарно и
применяется перезапуском: маскирование значений в логах шагов строится при
старте агента. `secret list` показывает только имена (`NAME DEFINED_IN`) и не
открывает файлы значений. `secret remove` удаляет фрагмент и файл значения;
несуществующего секрета нет — `nothing to remove`, код 0.

## Локальный репозиторий

```bash
sudo sard-agent repo add <имя> <абсолютный путь> [--password-stdin | --password-from-file <путь>] [--no-restart] [--timeout 2m] [--connect-timeout 30s]
sudo sard-agent repo list [--json]
sudo sard-agent repo show <имя> [--json]
sudo sard-agent repo password <имя> --reveal
sudo sard-agent repo remove <имя> [--no-restart]
```

`repo add` за одну команду:

1. создаёт отсутствующие родительские каталоги (root, `0755`) и каталог
   репозитория (пользователь службы, `0700`); существующий каталог получает
   владельца пользователя службы рекурсивно, права файлов не меняются;
2. если репозитория нет — создаёт его с **сгенерированным паролем**
   (`restic-<имя>.pass`, 43 символа base64url); для пустого хранилища
   терминал пароль не спрашивает, а `--password-stdin` или
   `--password-from-file` задают свой;
3. если репозиторий уже есть — подключает его; нужен его пароль:
   `--password-stdin`, `--password-from-file` или терминал (дважды, без эха).
   Пароль проверяется до записи: неверный — `WRONG_PASSWORD`, и не остаётся ни
   файла пароля, ни фрагмента, ни временных файлов;
4. на хосте с systemd создаёт drop-in `sard-repo-<имя>.conf` с
   `ReadWritePaths=<путь>` и выполняет `systemctl daemon-reload`: без него
   служба под `ProtectSystem=strict` зависает на блокировке restic
   (`docs/operations/repo-init.md`);
5. пишет фрагмент `agent.d/repo-<имя>.yaml` последним, записывает строку
   аудита и применяет изменение.

Адрес не должен проходить через символьную ссылку ни в одном компоненте и
должен быть задан в разрешённом виде (`/run`, а не `/var/run`): команда
работает от root и создаёт каталоги и меняет владельца, а пользователь службы
мог бы подменить ссылкой каталог, которым он владеет, и увести эту работу в
другое место. Со ссылкой в пути — `LOCAL_PATH_INVALID` («… is a symbolic link;
give the resolved path»); найдите настоящий путь `readlink -f`.

Итог всегда напоминает два факта. **Ключ репозитория есть только на этом
хосте**: сохраните копию пароля вне хоста — `sudo sard-agent repo password
<имя> --reveal` печатает его в stdout (на stderr — предупреждение; строка
аудита пишется всегда), без копии потеря хоста — потеря бэкапов. **Локальный
бэкап погибнет вместе с хостом**: добавьте ещё и репозиторий на другом хосте
или в облаке.

Если `restic init` отказал, сгенерированный файл пароля остаётся (прерванный
init мог записать ключ этим паролем), фрагмент не пишется; повтор с тем же
адресом использует этот файл — пароль заново не генерируется и не
спрашивается. Тот же адрес повторно — `unchanged`; то же имя с другим
адресом — `REPOSITORY_CONFLICT` (код 4): сначала `repo remove`.

`repo remove` убирает фрагмент, `env_file` репозитория (если он лежит в
`secrets` и на него ничего не ссылается) и drop-in (с `daemon-reload`). Он не
вызывает restic, не трогает данные в хранилище и **не удаляет файл пароля**:
итог называет его путь, и повторный `repo add` того же адреса подключит
репозиторий с ним. Источники на сервере, которые ссылаются на это имя, начнут
получать отказ.

`repo show` описывает один репозиторий (`name`, `backend`, `address` — с `***`
вместо пароля в адресе, `status`, `repository_id`, `password_file`,
`env_file`, `defined_in`), `repo list` — все репозитории таблицей `NAME
BACKEND STATUS REPOSITORY_ID` (в `--json` ещё и `defined_in`). `--json` у `repo list`, `repo show` и `secret list` печатает один
объект JSON в stdout; ошибки по-прежнему текстом в stderr, коды выхода те же.

## Репозиторий S3

```bash
sudo sard-agent repo add <имя> s3:https://<хост>[:<порт>]/<бакет>[/<путь>] \
  --access-key-id <id> [--region <регион>] \
  [--secret-key-stdin | --secret-key-from-file <путь>] \
  [--password-stdin | --password-from-file <путь>] [--no-restart] [--timeout 2m] [--connect-timeout 30s]
```

Адрес — формат restic (с `https`, с `http` и предупреждением о передаче без TLS,
или без схемы); учётных данных в нём нет (`ADDRESS_INVALID`: нет хоста или
бакета, другая схема, `user:pass@`, управляющий символ, хост с `-` в начале).

- **Предустановка провайдера.** `--provider aws|b2|yandex|vk|selectel` с адресом
  `s3:<бакет>[/<путь>]` (без схемы и хоста) строит адрес: `aws` —
  `s3:https://s3.<регион>.amazonaws.com/<бакет>[/<путь>]`, `b2` —
  `s3:https://s3.<регион>.backblazeb2.com/<бакет>[/<путь>]`, `yandex` —
  `s3:https://storage.yandexcloud.net/…` (регион `ru-central1`), `vk` —
  `s3:https://hb.ru-msk.vkcloud-storage.ru/…` (регион `ru-msk`), `selectel` —
  `s3:https://s3.<регион>.storage.selcloud.ru/…` (по умолчанию `ru-1`, `--region`
  выбирает пул). У `aws` и `b2` `--region` обязателен, у остальных подставляется;
  `yandex` и `vk` принимают только свой регион. Во фрагмент пишется полный
  адрес, в `env`-файл — `AWS_DEFAULT_REGION=<регион>` (и подставленный).
  Схема или хост в адресе, неизвестный провайдер (в сообщении все пять), нет
  `--region` у `aws`/`b2`, чужой регион у `yandex`/`vk`, плохой формат региона,
  нет бакета — ошибка использования.
  Списка регионов нет: несуществующий регион — `BACKEND_UNAVAILABLE`.
  `--provider` с адресом другого вида — ошибка использования, называющая флаг.
  Пример: `sudo sard-agent repo add main s3:<бакет>/<путь> --provider aws
  --region eu-central-1 --access-key-id <id> --secret-key-from-file <путь>`.
- **Ключи.** `--access-key-id` обязателен (1–128 печатных символов ASCII без
  пробелов). Секретный ключ — один источник из трёх: `--secret-key-stdin`,
  `--secret-key-from-file` или терминал (дважды, без эха); значением флага или
  аргументом он не передаётся. Один перевод строки в конце отбрасывается (`\n`
  или `\r\n`), любой другой управляющий символ — `SECRET_INVALID`; пусто —
  `SECRET_EMPTY`, больше 65536 байт — `SECRET_TOO_LARGE`. `--secret-key-stdin`
  вместе с `--password-stdin` — `SECRET_SOURCE_CONFLICT`. `--region`:
  `a–z 0–9 -`, до 64 символов.
- **`env`-файл.** `secrets/restic-<имя>.env`, владелец и группа — пользователь
  службы, `0600`: `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, с `--region` —
  `AWS_DEFAULT_REGION`. Он пишется временным файлом (владелец и права выставляются
  до записи содержимого) и становится `env`-файлом в тот же момент, что и файл
  пароля, после того как restic принял ключи. Существующий `env`-файл под root
  читается только через проверку владельца и прав (`SECRET_FILE_REJECTED`,
  если файл не принадлежит пользователю службы, открыт другим, это ссылка или
  не обычный файл; такой файл не меняется). Файл, на который ссылается другой
  ключ конфига, — `PATH_IN_USE`.
- **Проверка.** `restic cat config` от имени пользователя службы с ключами
  кандидата. Репозитория нет (код 10 restic) — `restic init`, со
  сгенерированным паролем, как для локального пути; репозиторий есть — нужен
  его пароль, как выше. Отказ хранилища относится к классу
  (`S3_KEY_REJECTED`, `STORAGE_ACCESS_DENIED`, `BUCKET_NOT_FOUND`,
  `BACKEND_UNAVAILABLE`, `WRONG_PASSWORD`, `BACKEND_REFUSED`); сообщение
  называет причину, адрес (пароль скрыт), очищенную строку restic и что делать.
  Таблица причин — `docs/operator/05a-storage.md`.
- **`--connect-timeout`** (по умолчанию `30s`; для любого вида адреса,
  в том числе локального пути) ограничивает каждое сетевое обращение проверки
  (первое обращение restic; для SFTP ещё получение ключа хоста и проверку
  входа по ssh): программа получает SIGTERM, а через 10 секунд SIGKILL; код 6,
  `BACKEND_UNAVAILABLE`, в сообщении последняя причина повтора, которую restic
  успел напечатать. `restic init` и проверку пароля после первого ответа он не
  ограничивает, их ограничивает `--timeout`; он объемлет всё. Время, которое
  команда ждёт ответа оператора на терминале, не входит ни в тот, ни в другой.
- **Следов нет**, пока кандидат не принят: ни `env`-файла, ни файла пароля, ни
  фрагмента, ни временных файлов, `systemctl` не вызывается, строки аудита нет.
  После принятия ключей и отказа `restic init` `env`-файл и файл пароля остаются
  и используются повтором без вопросов.
- **Повтор.** Тот же адрес, тот же `--access-key-id`, тот же `--region` и
  либо ни одного источника секретного ключа (терминал не спрашивается), либо
  тот же ключ — `unchanged`: ничего не записано, нет строки аудита и перезапуска.
  Другие ключи или регион подключённого имени проверяются так же, как новые;
  проверка идёт с файлом пароля, который уже лежит на месте: пароль не
  спрашивается и не заменяется (`--password-stdin` и `--password-from-file`
  с этим — ошибка использования), неверный пароль — `WRONG_PASSWORD`, а ключи,
  которые не видят репозитория, — `REPOSITORY_CONFLICT` (репозиторий заново не
  создаётся); принятые заменяют `env`-файл атомарно (`credentials updated`, строка аудита
  `repository <имя> credentials updated`, службу не перезапускают: `env`-файл
  читается на каждом шаге); отклонённые оставляют `env`-файл как был. Другой
  адрес для того же имени — `REPOSITORY_CONFLICT`.
- **Итог** называет имя, `backend: s3`, адрес (пароль скрыт), `repository_id`,
  `env`-файл и файл пароля, «created» или «attached» и напоминает о копии
  пароля (`repo password <имя> --reveal`); предупреждения о бэкапе на этом же
  хосте нет. Drop-in systemd для S3 не пишется. `repo remove` удаляет
  фрагмент и `env`-файл, файл пароля оставляет.
- **Аудит.** `repository <имя> added` или `repository <имя> credentials
  updated`; ключей, паролей и адресов с учётными данными в строке нет. Секретный
  ключ и пароль нигде не появляются: ни в выводе, ни в аргументах процессов, ни
  в журналах; ключи получает только restic, окружением из `env`-файла.
- **Бакет.** Если бакета нет, `restic init` создаёт его сам, когда ключ вправе
  создавать бакеты (Н19). Агент бакеты не создаёт и не проверяет заранее.

## Репозиторий SFTP

```bash
sudo sard-agent repo add <имя> sftp:[<пользователь>@]<хост>:<путь> \
  [--host-key-fingerprint SHA256:<отпечаток>] [--replace-host-key] \
  [--password-stdin | --password-from-file <путь>] [--no-restart] [--timeout 2m] [--connect-timeout 30s]
```

Адрес — формат restic: `sftp:[пользователь@]хост:путь` или
`sftp://[пользователь@]хост[:порт]/путь` (IPv6 в квадратных скобках).
`ADDRESS_INVALID`: нет хоста или пути, пароль в адресе (`ssh` работает по
ключу), порт вне 1–65535, управляющий символ, хост или пользователь с `-` в
начале. Флаги S3 (`--provider`, `--access-key-id`, `--region`, `--secret-key-*`) с адресом
`sftp:` и флаги SFTP с другими адресами — ошибка использования, называющая флаг.

- **Клиент OpenSSH.** До блокировок и любых изменений проверяется, что `ssh`,
  `sftp`, `ssh-keygen` и `ssh-keyscan` есть в `PATH`, который получает restic;
  иначе `SSH_CLIENT_MISSING` (код 1) называет программу и команды установки
  (`sudo apt-get install openssh-client`, `sudo dnf install openssh-clients`;
  `dpkg -i` и `rpm -U` зависимостей не ставят). Для S3 и локального пути клиент
  не нужен.
- **Каталог `.ssh`.** Домашний каталог пользователя службы — из passwd (у пакета
  `/var/lib/sard-agent`, ADR 0047), путь проходится от `/` без перехода по
  ссылкам (`SSH_HOME_INVALID`: не абсолютный, `/`, ссылка в любом компоненте).
  Нет домашнего каталога — создаётся последний компонент (`0700`, пользователь
  службы), нет родителя — `CONFIG_WRITE`, ничего не создано. Каталог `.ssh`
  открывается относительно удерживаемого домашнего каталога; нет — создаётся
  (`0700`). Существующие каталоги владельца и прав не меняют.
- **Запись под root.** Каждое создание, смена владельца и прав, переименование
  и чтение идут относительно удерживаемого дескриптора `.ssh` (`openat`,
  `fchown`, `fchmod`, `renameat`), ни одного вызова по полному пути. Новый файл —
  временный (`O_EXCL|O_NOFOLLOW`), владелец и права выставляются до записи
  содержимого, `fsync`, `renameat` в том же каталоге, `fsync` каталога. Файл,
  который читается (`known_hosts`, `config`, `id_ed25519.pub`), открывается с
  `O_NOFOLLOW|O_NONBLOCK` и должен быть обычным файлом с одним именем, владелец —
  пользователь службы или root, не больше 1 МиБ: иначе `SSH_FILE_REJECTED`
  с путём и причиной, файл не читается дальше `fstat` и не меняется. Закрытый
  ключ root не открывает никогда. Результат: `config` и `known_hosts`
  принадлежат пользователю службы, `0600`. ADR 0054.
- **Ключ хоста.** Сканирование — `ssh-keyscan` от имени пользователя службы с
  портом адреса. Известный ключ (обычная или хешированная запись, `хост` или
  `[хост]:порт`) — ничего не спрашивается и не пишется. Неизвестный:
  `--host-key-fingerprint SHA256:…` (43 символа base64 без `=`; MD5 и другое —
  ошибка использования) принимает ключ любого типа с этим отпечатком, иначе
  `HOST_KEY_MISMATCH` (код 5); без флага на терминале показывается один ключ
  (ed25519, ecdsa, rsa) и принимается ответ ровно `yes` (иначе
  `HOST_KEY_REJECTED`, код 5); без флага и без терминала — `HOST_KEY_UNCONFIRMED`
  (код 2), ввод не читается. Записи хоста, ни одна из которых не совпала, —
  `HOST_KEY_CHANGED` (код 5; файл и номера строк); `--replace-host-key`
  заменяет их ключом, подтверждённым тем же способом. Принятый ключ дописывается
  одной строкой без хеширования, остальное содержимое — байт в байт.
- **Ключ пользователя службы.** Нет `~/.ssh/id_ed25519` — `ssh-keygen` от имени
  пользователя службы создаёт ed25519 без пароля с комментарием
  `sard-agent@<имя хоста>`; ни один файл ключа не пишет root. Только после
  принятия ключа хоста; ключ не удаляется ни при каком отказе. Открытая часть
  всегда печатается в stdout: при успехе и при `SSH_KEY_NOT_AUTHORIZED`. Есть
  закрытый ключ без `.pub` — открытая часть берётся `ssh-keygen -y` от имени
  пользователя службы, файл не пишется.
- **Блок `~/.ssh/config`.** В начале файла блок на хост (`StrictHostKeyChecking
  yes`, `BatchMode yes`, `IdentityFile`, `IdentitiesOnly yes`,
  `ServerAliveInterval 15`, `ServerAliveCountMax 4`, `ConnectTimeout 30`) между
  строками `# sard-agent begin <хост>` и `# sard-agent end <хост>`. Тот же блок —
  файл не переписывается, иной блок того же хоста заменяется на месте, прочее
  содержимое — байт в байт. Те же `StrictHostKeyChecking` и `BatchMode` команда
  передаёт и в командной строке каждой программы `ssh` и `sftp`.
- **Проверка входа.** `sftp -b /dev/null` от имени пользователя службы с
  `--connect-timeout`; причина берётся из его stderr, а не из строки restic:
  `SSH_KEY_NOT_AUTHORIZED` (код 2; открытая часть ключа печатается), `HOST_KEY_MISMATCH`
  (код 5), `BACKEND_UNAVAILABLE` (код 6), прочее — `BACKEND_REFUSED` (код 1).
  Затем `restic cat config`; `permission denied` в каталоге —
  `STORAGE_ACCESS_DENIED` с каталогом из адреса.
- **Процессы.** `restic`, `ssh`, `sftp`, `ssh-keygen` и `ssh-keyscan` запускаются
  от uid и gid пользователя службы, с окружением `PATH` (restic), `HOME`
  (из passwd) и `LC_ALL=C`: ни пароль, ни `AWS_*`, ни переменные оператора в них
  не попадают, пароль не бывает аргументом.
- **Порядок.** Флаги, права, имя, вид и адрес, флаги вида, источники секретов,
  конфиг, конфликт имени, пользователь службы, restic, клиент OpenSSH, блокировка
  конфига, блокировка `init`, `.ssh` и его файлы, ключ хоста, ключ SSH,
  `known_hosts`, `config`, проверка входа, первое обращение restic, пароль,
  файл пароля, `init` или проверка пароля, фрагмент, аудит, применение. Drop-in
  systemd не пишется.
- **Файлы `ssh` — настройка, а не отказ.** Записанные до проверки входа ключ,
  запись `known_hosts` и блок `config` остаются при любом отказе дальше
  (`SSH_KEY_NOT_AUTHORIZED`, `STORAGE_ACCESS_DENIED`, `BACKEND_UNAVAILABLE`);
  повтор их использует и ничего не спрашивает. Фрагмент, файл пароля и временные
  файлы при отказе до `init` не остаются; после отказа `init` остаётся файл
  пароля, как у S3. Изменение только файлов `ssh` службу не перезапускает.
- **Повтор.** Ключ хоста известен, ключ SSH есть, блок тот же и репозиторий
  открывается файлом пароля — `unchanged`: без записи, вопросов, строки аудита
  и перезапуска.
- **Итог** называет имя, `backend: sftp`, адрес, `repository_id`, файл пароля,
  хост с отпечатком принятого ключа, открытую часть ключа и напоминает о копии
  пароля; предупреждения о бэкапе на этом же хосте нет. `repo remove` удаляет
  фрагмент, `~/.ssh` не трогает и называет файл ключа и хост, которые остаются.
- **Аудит.** Своя строка на каждое изменение, в порядке изменений:
  `ssh key of service user <польз> created`, `ssh host key of <хост>[:<порт>]
  trusted <тип> <отпечаток>` (при замене `replaced`), `repository <имя> added`.
  Строки ключа и ключа хоста пишутся и тогда, когда команда потом отказала.
  Значений, ключей и паролей в строках нет.

## Снимки репозитория: `repo snapshots`

```bash
sudo sard-agent repo snapshots <имя> [--source <источник>] [--json] [--timeout 2m] [--connect-timeout 30s]
```

Показывает снимки репозитория (A8c-1, `docs/specs/agent/repo-restore.feature`,
Р53–Р57) без сервера Sard и без регистрации агента: нужны только конфиг и
файлы пароля и ключей репозитория. Один вызов restic со списком снимков
(`--json --no-lock`: ключ только на чтение подходит, файлов блокировки нет) от имени
пользователя службы; пароль restic получает только файлом, ключи S3 — из
`env`-файла. Команда только читает и в журнал не пишет. Запускать её можно через
`sudo` или от пользователя службы, остальные получают `PRIVILEGES_REQUIRED`.

Снимки показаны **все**, в том числе сделанные другими хостами: на новом хосте
после потери старого их видно сразу после `repo add`. Порядок — по времени
по возрастанию, при равном времени по id:

```
ID TIME HOST SOURCE RUN PATHS
dddd1111 2026-10-09T12:00:00Z old-host - - /etc
aaaa1111 2026-10-10T03:00:00Z db1 s1 r1 /srv/data
```

- `ID` — короткий id (8 символов); `TIME` — UTC, RFC 3339 до секунд с `Z`;
- `SOURCE` и `RUN` — значения тегов `sard.source` и `sard.run`, `-`, если тега
  нет или он пуст (снимок, сделанный вручную); `PATHS` — пути через запятую;
- нет снимков — одна строка `no snapshots in repository <имя>` (с `--source` —
  `no snapshots of source <id> in repository <имя>`), код 0;
- `--source <id>` (1–128 печатных символов ASCII без пробела и запятой) — только
  снимки этого источника; иначе ошибка использования, называющая `--source`;
- `--json` — один объект `{"repository":"<имя>","snapshots":[{"id","short_id",
  "time","hostname","paths","source","run","step","tags"}]}`: `id` полный (64
  символа), `source`, `run`, `step` — строка или `null`, `tags` — все теги;
  ошибки остаются текстом в stderr.

Отказы: `REPOSITORY_UNKNOWN` (называет подключённые имена),
`REPOSITORY_NOT_INITIALIZED`, `WRONG_PASSWORD`, `PASSWORD_FILE_MISSING`,
`SECRET_FILE_REJECTED`, `STORAGE_ACCESS_DENIED` — код 2; `BACKEND_UNAVAILABLE`
(в том числе молчащее хранилище дольше `--connect-timeout`), `TIMEOUT` — код 6;
restic не найден — код 1. Восстановление снимка — `repo restore`, ниже.

## Снимки и восстановление на хосте: `repo restore`

```bash
sudo sard-agent repo restore <имя> <снимок> --target <каталог> [--path <путь>]...
sudo sard-agent repo restore <имя> latest --source <источник> --target <каталог>
```

Восстанавливает снимок на этом хосте (A8c-2, `docs/specs/agent/repo-restore.feature`,
Р58–Р79; решения — ADR 0056) **без сервера Sard и без регистрации агента**:
команда не соединяется с сервером, не читает `tls.*`, не требует работающей
службы и не меняет настройку хоста (конфиг, `agent.d`, `secrets`, drop-in,
`~/.ssh`; `systemctl` не вызывается). Нужны только конфиг и файлы пароля и
ключей репозитория. Запускать её можно только через `sudo`: она пишет файлы с
владельцами из снимка. Пользователь службы и посторонний получают
`PRIVILEGES_REQUIRED` с готовой командой `sudo sard-agent repo restore …`.

**Восстанавливать можно только в пустой или новый каталог.** Флаг `--overwrite`
(слияние в непустой каталог, в том числе в `/`) пока недоступен: он распознаётся
и отказывает сразу, ошибка использования (код 2) «`--overwrite is not available
yet: restore into an empty or new directory`». Слияние появится в отдельном
срезе (A8c-2b, OQ-201).

### После потери хоста

1. Установите пакет агента (`deb` или `rpm`, он приносит restic, `ssh` и
   `setpriv`). Служба и регистрация **не нужны**.
2. Подключите репозиторий с паролем из копии (копия лежит вне потерянного хоста):

   ```bash
   sudo sard-agent repo add main s3:https://s3.example.com/bucket/main \
       --access-key-id AKIA... --secret-key-from-file /root/s3.secret \
       --password-from-file /root/main.password.copy --no-restart
   ```

   Для SFTP и локального пути — те же флаги пароля, см. разделы выше.
3. Найдите снимок: `sudo sard-agent repo snapshots main` (видны снимки всех
   хостов, в том числе потерянного).
4. Восстановите в пустой каталог:

   ```bash
   sudo sard-agent repo restore main latest --source <id источника> --target /srv/restore
   ```

### Снимок

Второй аргумент — полный id (64 символа), префикс id из 8–63 строчных
шестнадцатеричных символов или `latest`. `latest` берёт самый новый снимок
источника и **требует `--source`** (в одном репозитории снимки многих
источников); снимки глобальных объектов PostgreSQL он пропускает. Команда
находит снимок в списке сама и передаёт restic полный id. Нет такого —
`SNAPSHOT_UNKNOWN` (называет `repo snapshots <имя>`); префикс подходит
нескольким — `SNAPSHOT_AMBIGUOUS` (называет полные id, время и источник
каждого). `--source` с id сужает поиск снимками этого источника.

### Раскладка и цель

Файлы снимка ложатся **под исходными абсолютными путями внутри цели**: снимок
`/srv/data`, цель `/r` — `/r/srv/data/…`, с владельцем, группой, правами и
временем изменения из снимка. В `/` восстановить пока нельзя (до A8c-2b).

- `--target` обязателен, путь абсолютный (`/srv/r/` и `/srv/./r` — `/srv/r`).
  Путь проходится от `/` без перехода по ссылкам: ссылка или файл в любом
  компоненте — `TARGET_INVALID` с компонентом. Цель не может совпадать с
  каталогом локального репозитория или `restic.cache_dir` и лежать внутри них.
- Отсутствующая цель и её родители создаются: `root:root`, `0700` при любой
  umask. При отказе созданные этим запуском пустые каталоги удаляются.
- Непустая цель — `TARGET_NOT_EMPTY`, ничего не записано. Каталог только с
  пустым `lost+found` (свежий том ext4) считается пустым. Если прежнее
  восстановление убили (`SIGKILL`), в цели остаётся каталог `.sard-restore-…`:
  сообщение называет его как остаток прерванного восстановления; удалите его
  вручную (с `sudo`) и повторите.
- `/` без `--allow-root-target` — `ROOT_TARGET_REFUSED`; с ним — `TARGET_NOT_EMPTY`
  (`/` не бывает пустым, до A8c-2b).
- `--path <путь>` (повторяемый) восстанавливает только этот файл или
  поддерево: абсолютный путь внутри снимка, **буквально** (символы `* ? [ \` и
  компонент `..` — ошибка использования). Пути, которого нет в снимке, —
  `PATH_NOT_IN_SNAPSHOT` до записи в цель.
- На время восстановления цель удерживается блокировкой (существующая — уже
  при обходе, до проверки пустоты); вторая команда в ту же цель —
  `TARGET_BUSY` (код 6), restic второй команды не запускается.
- `--source` вместе с id или префиксом сужает поиск снимками источника: id
  снимка другого источника — `SNAPSHOT_UNKNOWN`.

Итог (stdout): имя репозитория, полный id снимка, время (UTC), источник,
запуск, цель, число восстановленных файлов и байт и слово `restored`; затем
строка, что файлы лежат в цели под исходными путями. До A8c-3 снимок PostgreSQL
восстанавливается как обычный каталог (`<цель>/<база>.dump`), команды
PostgreSQL не печатаются; см. «Восстановление руками» в
`docs/plugins/postgresql.md`.

### Время и прерывание

`--connect-timeout` (30 с) ограничивает первое обращение к хранилищу.
**Общего таймаута по умолчанию нет** (восстановление бывает долгим);
`--timeout` — положительная длительность, истёк — `TIMEOUT`. `SIGINT` или
`SIGTERM` команде: restic получает `SIGTERM` своей группе и `SIGKILL` через
10 с, код `INTERRUPTED`. Отказ после начала записи (`TIMEOUT`, `INTERRUPTED`,
`BACKEND_UNAVAILABLE`, `TARGET_WRITE`) говорит, что в цели могут остаться
частично восстановленные файлы. `RESTORE_INCOMPLETE` (код 1) — restic не
восстановил отдельные файлы: число и первые 10 путей, восстановленное остаётся.
`TARGET_WRITE` (код 7) — не создана цель, нет места или квоты, файловая
система только для чтения, имя появилось в цели за время восстановления.

### Как это устроено

- Чтение списка и проверка `--path` — вызовы restic со списком снимков и
  списком файлов снимка, оба с `--no-lock`, от имени пользователя службы.
- Восстановление — вызов restic с `--no-cache --no-lock` от root, чтобы
  владельцы и группы вернулись из снимка. После команды в `restic.cache_dir`,
  каталоге локального репозитория и `~/.ssh` нет файлов root.
- **Временный каталог.** restic пишет не в цель, а в каталог
  `.sard-restore-<случайное>/root` внутри неё (владелец root, `0700`; restic
  получает его унаследованным дескриптором, в аргументах пути цели нет), и по
  окончании агент переносит записи верхнего уровня в цель без копирования и без
  замены (`renameat2`); владельцы, права, время, жёсткие ссылки и FIFO
  сохраняются. Так пользователь службы, если ему доступен каталог внутри цели,
  не может подменить его ссылкой и увести запись root. Если имя появилось в цели
  за время восстановления, оно не заменяется (`TARGET_WRITE`, уже перенесённое
  остаётся, остальное удалено); точка монтирования в цели —
  `TARGET_INVALID` («mount point inside the target»). После отказа restic
  частичный результат удаляется вместе с временным каталогом; исключение —
  `RESTORE_INCOMPLETE`: восстановленное переносится в цель.
- Для SFTP restic получает `-o sftp.command`: `ssh` запускается от пользователя
  службы через `setpriv` (пакет `util-linux`) и читает его `~/.ssh`; root
  закрытый ключ не открывает. Нет `setpriv` — `SETPRIV_MISSING` (код 1),
  остальным видам хранилища он не нужен.
- Ключи S3 restic получает только окружением из `env`-файла, пароль — каналом
  (`--password-file /proc/self/fd/N`): агент читает файл пароля сам, с той же
  проверкой, что и все секреты (`SECRET_FILE_REJECTED`, `PASSWORD_FILE_MISSING`),
  и FIFO или подменённый файл команду не повесят. В аргументах процессов,
  выводе, журнале и строке аудита значений нет.
- Из `env`-файла root-процессу restic доходят только переменные своего вида
  хранилища: для S3 — `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`,
  `AWS_SESSION_TOKEN`, `AWS_DEFAULT_REGION`; для `local`, `sftp`, `rest` —
  никакие. Любая другая переменная — `ENV_FILE_INVALID` (файл, строка, имя
  переменной; значения нет) до запуска restic; `rclone`, `azure`, `b2`, `gs`,
  `swift` — `BACKEND_NOT_SUPPORTED`. `repo snapshots` под пользователем службы
  принимает прочие переменные, как раньше.
- `--no-lock`: `restic prune`, запущенный вручную во время восстановления, может
  удалить нужные данные; restic откажет с ошибкой (тихой порчи нет). Sard
  `forget` и `prune` не выполняет.

### Журнал и SELinux

Если запись в цель началась, команда пишет одну строку аудита после исхода:
`repository <имя> snapshot <короткий id> restored to <цель>` или `… restore to
<цель> failed: <ПРИЧИНА>`; отказ до записи строки не оставляет.

На хосте с SELinux enforcing метки файлов, восстановленных в системные каталоги
(`/etc`, `/var`, `/srv`), могут не совпасть с политикой этого хоста: restic
возвращает расширенные атрибуты снимка, а снимок мог быть сделан на другом
хосте. После восстановления в системный каталог выполните
`sudo restorecon -R <каталог>`; `sudo restorecon -nv -R <каталог>` после этого
ничего не меняет, а в журнале аудита нет отказов AVC для `sard-agent` и
`restic`.

## Применение изменения и перезапуск

После изменения, в этом порядке:

1. `--no-restart` — не перезапускать, напечатать `sudo systemctl restart
   sard-agent`;
2. нет systemd (`/run/systemd/system` или `systemctl`) — перезапустите агента
   самостоятельно;
3. служба не активна — команда её не запускает, изменение вступит при старте;
4. в `<executor.state_dir>/journal` есть записи принятых команд — идущие шаги:
   команда не перезапускает службу, называет их число и печатает команду
   перезапуска; журнал нельзя прочитать — то же, с причиной;
5. иначе `systemctl restart sard-agent.service` и «restarted». Неудача — код 1,
   `SERVICE_RESTART_FAILED`; изменение сохранено, см. `journalctl -u
   sard-agent`.

Команда, которая ничего не изменила, службу не трогает. Окно между проверкой
журнала и перезапуском не закрывается: шаг, принятый в это окно, провалится по
D13 (`docs/adr/0044-agent-command-journal.md`): «interrupted: agent restarted
before the step finished». Для хоста с длинными шагами используйте
`--no-restart` и перезапускайте в паузе между запусками.

## Журнал изменений

Каждое изменение и каждый `--reveal` — одна строка в системный журнал, тег
`sard-agent`:

```bash
sudo journalctl -t sard-agent --since today
# secret db added by alice (uid 1000)
# repository main password revealed by alice (uid 1000)
```

Строки идут с facility `LOG_AUTHPRIV`: на хостах с rsyslog они лежат в
`/var/log/secure` (RHEL) или `/var/log/auth.log` (Debian), а
`journalctl -t sard-agent` показывает их всегда. В строке — действие, вид, имя и кто (`SUDO_USER` и `SUDO_UID`, иначе
пользователь процесса); значений, адресов с учётными данными и содержимого
файлов нет. Если syslog недоступен, изменение выполняется, а stderr
предупреждает.

## Параллельные команды

Изменяющая команда держит блокировку `agent.d/.sard-config.lock` от чтения
конфига до записи фрагмента; вторая сразу отказывает с `CONFIG_LOCKED` (код 6) —
повторите. Оставшийся без держателя файл блокировки не мешает. `repo add` и
`repo init` одного имени одновременно не идут (`INIT_IN_PROGRESS`, код 6).

## Коды выхода

| код | класс | когда |
|---|---|---|
| 0 | успех | изменение применено или не требовалось; чтение; `--help` |
| 1 | ошибка агента | restic не найден, старый, непригоден; `BACKEND_REFUSED`; `SSH_CLIENT_MISSING`, `SSH_CLIENT_FAILED`; `SERVICE_RESTART_FAILED`; `RESTORE_INCOMPLETE`; `SETPRIV_MISSING` |
| 2 | использование | флаги, `PRIVILEGES_REQUIRED`, `SERVICE_USER_UNKNOWN`, `NAME_INVALID`, конфиг и `DUPLICATE_NAME`, `DEFINED_IN_CONFIG`, `PATH_IN_USE`, `SECRET_SOURCE_MISSING`, `SECRET_SOURCE_CONFLICT`, `SECRET_EMPTY`, `SECRET_TOO_LARGE`, `SECRET_MISMATCH`, `SECRET_INVALID`, `SECRET_FILE_REJECTED`, `BACKEND_NOT_SUPPORTED`, `ENV_FILE_INVALID`, `ADDRESS_INVALID`, `LOCAL_PATH_INVALID`, `WRONG_PASSWORD`, `S3_KEY_REJECTED`, `STORAGE_ACCESS_DENIED`, `BUCKET_NOT_FOUND`, `SSH_HOME_INVALID`, `SSH_FILE_REJECTED`, `SSH_KEY_NOT_AUTHORIZED`, `HOST_KEY_UNCONFIRMED`, `REPOSITORY_UNKNOWN`, `REPOSITORY_NOT_INITIALIZED`, `REVEAL_REQUIRED`, `PASSWORD_FILE_MISSING`, `SNAPSHOT_UNKNOWN`, `SNAPSHOT_AMBIGUOUS`, `TARGET_INVALID`, `TARGET_NOT_EMPTY`, `ROOT_TARGET_REFUSED`, `PATH_NOT_IN_SNAPSHOT` |
| 4 | идентичность есть | `REPOSITORY_CONFLICT`: имя уже подключено к другому адресу |
| 5 | доверие | `HOST_KEY_MISMATCH`, `HOST_KEY_REJECTED`, `HOST_KEY_CHANGED`: ключ хоста SFTP не подтверждён, не совпал или сменился |
| 6 | временная | `BACKEND_UNAVAILABLE` (в том числе `--connect-timeout`), `TIMEOUT`, `INTERRUPTED`, `CONFIG_LOCKED`, `INIT_IN_PROGRESS`, `TARGET_BUSY` |
| 7 | запись | `CONFIG_WRITE` (каталог или файл `agent.d`, `secrets`, drop-in, каталог репозитория, домашний каталог, `~/.ssh` и его файлы, смена владельца), `LOCK_WRITE`, `TARGET_WRITE` (создание цели или запись файла у `repo restore`, нет места или квоты, только чтение, имя занято при переносе) |

Таблица каждой команды — в её `--help`.

## SELinux

На хосте с SELinux enforcing файлы, созданные командами, получают метки от
типа каталога; после первой настройки проверьте, что
`sudo restorecon -nv -R /etc/sard` ничего не меняет и в журнале аудита нет
отказов AVC для `sard-agent` (`docs/qa/host-setup.md`, часть 5).
