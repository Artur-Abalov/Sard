# Агент-сосед sard-self

В установке Docker Compose (`deploy/docker-compose.yml`) рядом с сервером
работает ещё один контейнер — `self-agent`. Это обычный агент Sard: он
регистрируется сам и виден в консоли как встроенный агент `sard-self`. Его
задача — бэкап самой установки: базы PostgreSQL, каталога CA и конфигурации
(F6, `docs/operator/06-data-and-backup.md`). Образ — `sard-agent:<версия>-pg18`:
тот же агент на `postgres:18`, с `pg_dump` нужной версии. Репозиториев в его
конфиге нет: репозиторий добавляется отдельно (D17), разовым контейнером
`docker compose run --rm --no-deps -u 0 --cap-add … self-agent repo add …`
(`docs/operator/06-data-and-backup.md`). `exec` в работающего соседа не годится:
у него нет capabilities, и root в нём не войдёт в его каталоги.

Спецификации — `docs/specs/server/self-agent.feature`,
`docs/specs/agent/self-agent.feature`, `docs/specs/web/self-agent.feature`.
Решения — `docs/adr/00XX-draft-self-agent.md`.

## Что ему можно

| Что | Как |
|---|---|
| Читать базу целиком | роль PostgreSQL `sard_backup`, член `pg_read_all_data`; по сети compose до `postgres:5432`; пароль — файл тома `sard-db-backup`, подключённый в `/run/sard-self/db-password`. Секрет `sard-db` привязан к плагину `postgresql` и цели `postgres:5432/sard` без TLS (файл `secret-bindings/sard-db.yaml` образа, S11): серверу ничего не стоит прислать другой хост, но пароль туда не уйдёт |
| Читать каталог CA, ключ CA тоже | том `sard-pki` подключён `:ro` в `/var/lib/sard/pki` |
| Читать конфигурацию установки | каталог compose (`./`) подключён `:ro` в `/etc/sard/install`; `.env` — группа 10001, 0640 |
| Звонить серверу | `server:9090`, mTLS, как любой агент. Имя `server` всегда есть в сертификате сервера |
| Писать своё состояние | том `sard-self-state` (`/var/lib/sard-self`): ключ, сертификат, результаты шагов, кэш restic |
| Читать канал от сервера | том `sard-self-channel` подключён `:ro` в `/run/sard-self`: файл `enroll-token` (поверх пустого `db-password` канала лежит пароль `sard_backup` из своего тома) |

## Чего ему нельзя

- **Писать в базу.** У `sard_backup` нет прав на таблицы и последовательности.
  Нет прав на временные таблицы, на создание объектов в `public` и на
  создание large objects. Права задаёт `bootstrap.sql` (его выполняет
  `db-init`). Сессии роли по умолчанию только на чтение, но роль может это
  переключить — держится запрет на правах, не на этом флаге.
- **Писать в каталог CA и в канал.** Оба тома подключены `:ro`.
- **Писать в собственную корневую ФС.** `read_only: true`, `cap_drop: ALL`,
  `no-new-privileges`. Контейнер работает под uid 10001 — это uid сервера:
  каталог CA доступен только ему (0700/0600).
- **Получить ключи и пароли других агентов.** Их нет ни в базе, ни на
  сервере (ADR 0008).

**Ключ CA у соседа — принятый риск.** С ключом CA можно выпустить сертификат
любого агента. Без чтения ключа бэкап CA невозможен. Тот, кто получил
контейнер `self-agent`, получил корень доверия установки. Самобэкап кладёт ключ
CA в зашифрованный репозиторий рядом с базой; пароль репозитория храните вне
машины (`docs/operator/06-data-and-backup.md`).

## Как он регистрируется

1. Сервер с `SARD_SELF_DIR` (в compose — `/var/lib/sard/self`, том
   `sard-self-channel`) при старте проверяет каталог. Если каталога нет, это
   не каталог или в него нельзя писать, сервер не стартует.
2. Роль базы и её пароль сервер не трогает: роль `sard_backup` и пароль
   (64 hex-символа, файл `password` тома `sard-db-backup`) создаёт `db-init`
   ([раздел 16](../operator/16-postgresql.md#роли)); сервер этот пароль не видит.
3. Каждые `SARD_SELF_CHECK_INTERVAL` (по умолчанию 15 с) сервер проверяет,
   есть ли живой (не отозванный) встроенный агент.
   - **Нет:** сервер держит в `enroll-token` один годный одноразовый
     встроенный токен со сроком 1 час. Токен заменяется за 10 минут до
     истечения, а также если файл пропал или не совпадает с базой.
   - **Есть:** сервер удаляет файл.
   Встроенный токен не выпустить и не увидеть через REST API, и его строки
   нет в логах.
4. Агент запущен с `--enroll-token-file /run/sard-self/enroll-token`. Без
   сертификата и без файла он ждёт файл. Получив файл, регистрируется и
   записывает рядом с сертификатом хеш использованного токена. Дальше он
   работает как любой агент.

Пересоздание контейнера (`docker compose up -d --force-recreate self-agent`)
даёт того же агента: сертификат лежит в томе `sard-self-state`. Нового токена
при этом нет. Удаление тома `sard-self-state` даёт нового агента. Старый
останется офлайн, а новый токен сервер выпустит, только когда старого
отзовут.

## Отзыв

Удалить агента в Sard нельзя — ни встроенного, ни обычного. Встроенный агент
отзывается только с подтверждением: в консоли нужно ввести `sard-self`, в REST —
`POST /api/v1/agents/{id}/revoke?confirm=sard-self`. Без подтверждения
ответ — `409 self_agent_confirmation_required`. После отзыва сервер в течение
одного интервала проверки выпускает новый встроенный токен. Сосед, которому
сервер отказал, перезапускается, регистрируется заново и становится новым
встроенным агентом. Старый остаётся в списке отозванным.

## Без compose и с внешним PostgreSQL

- Без `SARD_SELF_DIR` механизм выключен: ни токенов, ни пароля, сервер
  ведёт себя как раньше.
- Роль `sard_backup` создаёт `bootstrap.sql`: `db-init` в compose, DBA внешнего
  кластера вручную ([раздел 16](../operator/16-postgresql.md#внешний-кластер)).
  Пароль ей задаёт тот, кто выполнил скрипт; сервер роль и пароль не меняет.

Если база не `postgres:5432/sard` (`SARD_SELF_BACKUP_DATABASE_HOST`, `…_PORT`, `…_NAME`),
поправьте привязку пароля в томе конфигурации sard-self: агент отдаёт его только туда, куда
она разрешает ([привязка секрета](../plugins/postgresql.md#привязка-секрета)). Секрет
объявлен в `agent.yaml` образа, поэтому `secret set` его не меняет: правьте файл.

```bash
docker compose exec -u 0 self-agent sh -c 'cat > /etc/sard/self/secret-bindings/sard-db.yaml' <<'YAML'
plugin: postgresql
targets:
  - db.internal:5432/sard
allow_tls: require    # или уберите строку, если сервер с проверяемым сертификатом
YAML
docker compose restart self-agent
```

## Обновление

Обновление со сборок до DB2 (схема `public`, пользователь сервера — суперпользователь) не
поддерживается: установок нет, выпусков для обновления нет, миграции переписаны
так, чтобы схема `sard` и владение были верны с первой версии (ADR 0069). Такую
установку переустанавливают с новыми томами (`docker compose down -v`,
`docs/operator/07-upgrade.md`). Обновление с первого выпуска, где это уже так,
сохраняет данные, агентов, встроенный агент `sard-self` и пройденный мастер:
после `docker compose up -d` с новым файлом и версией `db-init` и `migrate`
идут до сервера, новый встроенный токен не выпускается.

Том `sard_sard-self-config` получает файлы образа только при создании, поэтому
привязку пароля `secret-bindings/sard-db.yaml` (S11) в существующий том при
обновлении дописывают один раз — команда в
[разделе 7](../operator/07-upgrade.md#обновление-до-версии-с-привязкой-секретов-s11).
