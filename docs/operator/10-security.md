# 10. Безопасность

## Что открыто наружу

| Что | По умолчанию | Защита |
|---|---|---|
| 9090/tcp, порт агентов | открыт | взаимный TLS: без сертификата от CA сервера доступна только регистрация, и та — по одноразовому токену с ограниченным сроком |
| 8080/tcp, консоль и REST | только `127.0.0.1` | пароль администратора; без TLS — поэтому не наружу ([раздел 4](04-tls-and-names.md)) |
| порт метрик (8081 внутри контейнера) | только loopback внутри контейнера, не опубликован | токен bearer (не короче 32 символов), обязателен вне loopback; HTTP без TLS — открывать только в своей сети ([раздел 14](14-monitoring.md)) |
| `/downloads/agent/` на 8080 | включена, без сессии | раздаются только файлы релиза своей версии; подлинность проверяется на хосте по `SHA256SUMS` и подписи minisign |

Сервер — плоскость управления, а не хранилище ключей (ADR 0008): адреса
хранилищ, пароли репозиториев и ключи доступа остаются на хостах агентов и на
сервер не передаются. Компрометация сервера не раскрывает бэкапы, но позволяет
запускать шаги на агентах.

## Пароль администратора

- Задаётся при первом запуске в мастере консоли, по коду настройки из лога
  сервера ([раздел 2](02-install.md)); от 12 до 1024 символов. Генерируйте менеджером
  паролей. В `.env` его нет, переменной окружения для него нет.
- Хранится в базе как хэш Argon2id: пароль нельзя прочитать ни из базы, ни из
  бэкапа базы, но бэкап базы позволяет подобрать его офлайн — храните дампы как
  секрет. Хэш читается из базы при каждой проверке.
- Смена — на странице «Настройки» консоли: нужен текущий пароль; после смены все
  остальные сессии заканчиваются, а эта продолжается. Неверный текущий пароль
  считается неудачной попыткой входа.
- Неверные попытки входа, ввода кода настройки и смены пароля ограничиваются: пять
  за 15 минут блокируют адрес на 15 минут; блокировка сбрасывается перезапуском
  сервера.
- Код настройки печатается в лог только пока нет администратора. Он открывает
  мастер тому, кто читает лог (то есть у кого есть доступ к хосту); логи сервера
  поэтому храните так же строго, как `.env`.

## Восстановление доступа

Пароль потерян, а сессии нет. Доступ возвращает только тот, у кого есть хост
сервера и право запускать на нём `docker compose`:

```bash
cd ~/sard
docker compose run --rm server admin-reset      # удаляет хэш пароля; сервер не стартует, порты не открываются
docker compose restart server                   # новый старт печатает новый код настройки
docker compose logs server | grep "SARD SETUP CODE"
```

Затем откройте консоль: мастер сразу просит пароль (шаг CA остаётся выполненным,
данные, агенты и источники не затронуты). Пока сервер не перезапущен, он отвечает на
вход `setup_required`; после перезапуска прежние сессии не действуют. Команда без
администратора ничего не меняет. Сброс виден аудиту: команда оставляет в базе метку, и
первый старт сервера после неё публикует одно событие `settings.changed` с настройкой
`admin_password` (без субъекта); второй перезапуск события не даёт. Подробнее — в [разделе 9](09-troubleshooting.md).

## Ключ CA

- `ca/ca.key` в томе `sard_sard-pki`, права `0600`, владелец — uid сервера
  (10001). С ним можно выпустить сертификат любого агента.
- Бэкап — отдельно от базы, в хранилище секретов ([раздел 6](06-data-and-backup.md)).
- Срок CA — 10 лет; сертификат сервера (90 дней) перевыпускается сам, ключ
  сервера живёт только в памяти.

## Раздача пакетов агента

Пакеты агента раздаются без сессии, потому что хосту нечем аутентифицироваться
до установки. Отдаются только файлы релиза той же версии, что и сервер; ничего
не загружается извне.

- Проверка на хосте: шаг «Проверьте контрольную сумму» и необязательный шаг
  «Проверьте подпись» в консоли. Ключ релизов сверяйте с `README.md`
  репозитория, а не с сервером ([релизы и подпись](../release.md)).
- Выключить: `SARD_AGENT_DOWNLOADS=false` — путь отвечает 404, консоль
  предлагает ручную установку.

## Проверка релиза

Каждый релиз подписан двумя ключами владельца; закрытые ключи есть только в
защищённом окружении `release` на GitHub, публичные — в репозитории
(`deploy/release/`) и в [README](../../README.md#verifying-releases).
Берите их из репозитория по тегу релиза, а не с сервера, с которого скачали
пакет, и сверяйте с README; храните копию у себя.

| Что | Чем подписано | Публичный ключ |
|---|---|---|
| пакеты агента (tar.gz, deb, rpm), их SBOM, `manifest.json` — через `SHA256SUMS` | minisign | `deploy/release/sard-release.pub` |
| офлайн-архивы, `docker-compose.yml`, `sard.env.example`, `images.json`, SBOM образов — через `SHA256SUMS.server` | minisign | `deploy/release/sard-release.pub` |
| образы `sard-server`, `sard-agent` в GHCR и их SBOM (аттестации CycloneDX) | cosign | `deploy/release/cosign.pub` |

Подписи с ключом проверяются без доступа к внешним сервисам: нужны только
файлы и публичный ключ. Подпись cosign дополнительно записана в журнал
прозрачности Rekor; он нужен только тем, кто хочет сверить и его.

### Пакеты агента

```bash
minisign -Vm SHA256SUMS -p sard-release.pub && sha256sum -c --ignore-missing SHA256SUMS
```

`minisign` печатает `Trusted comment: sard-agent <версия>` — это версия, для
которой сделана подпись; она должна совпасть с той, что вы ставите.

### Образы

Нужен [cosign](https://docs.sigstore.dev/cosign/system_config/installation/)
2.x или 3.x.

<!-- verify-image:begin -->
```bash
SARD_TAG=<vX.Y.Z>
curl -fsSLO "https://raw.githubusercontent.com/Artur-Abalov/Sard/$SARD_TAG/deploy/release/cosign.pub"
for image in "sard-server:${SARD_TAG#v}" "sard-agent:${SARD_TAG#v}" "sard-agent:${SARD_TAG#v}-pg18"; do
  cosign verify --key cosign.pub "ghcr.io/artur-abalov/$image" >/dev/null
  cosign verify-attestation --key cosign.pub --type cyclonedx "ghcr.io/artur-abalov/$image" >/dev/null
  echo "ok: $image is signed by the Sard release key, its SBOM too"
done
```
<!-- verify-image:end -->

Чтобы запускать ровно проверенное, закрепите образ по digest: он есть в
`images.json` релиза (подписан через `SHA256SUMS.server`) и в выводе
`cosign verify`.

### SBOM

Состав каждого релиза в формате CycloneDX JSON:

- пакеты агента: `sard-agent_<версия>_linux_<arch>.cdx.json` в файлах релиза
  (что входит в tar.gz, deb и rpm этой архитектуры: `sard-agent`, `restic`);
- образы: `sard-server_linux_<arch>.cdx.json`,
  `sard-agent-image_linux_<arch>.cdx.json`,
  `sard-agent-pg18-image_linux_<arch>.cdx.json` в файлах релиза и те же
  документы в аттестациях образов (`cosign verify-attestation` выше,
  `cosign download attestation`).

### Происхождение сборки

Дополнительно, не взамен подписей: у файлов релиза и образов есть
аттестация происхождения GitHub (SLSA provenance) — из какого коммита и
каким workflow собрано. Проверка требует доступа к GitHub и Sigstore:

```bash
gh attestation verify sard-agent_<версия>_linux_amd64.tar.gz --repo Artur-Abalov/Sard
gh attestation verify oci://ghcr.io/artur-abalov/sard-server:<версия> --repo Artur-Abalov/Sard
```

Без сети — подписи ключом выше; офлайн-установка — [раздел 11](11-offline.md).

## Образ

- Процесс — пользователь `sard` (uid 10001), не root.
- Секретов в образе нет; всё — переменными окружения из `.env`.
- Пакеты агента в образе подписаны в релизе ключом владельца; сервер их не
  подписывает.
