# 5a. Хранилища репозиториев: S3 и SFTP

Репозиторий restic агента может лежать на диске хоста, в S3-совместимом
хранилище или на SFTP-сервере. Данные бэкапа идут от агента прямо в
хранилище, через сервер Sard они не проходят. Адрес, пароль и ключи доступа
лежат только на хосте агента, в `/etc/sard/agent.yaml` и файлах рядом с ним.
Сервер знает только имя репозитория (ADR 0008).

Этот раздел описывает, как подключить хранилище. И **S3**, и **SFTP**
подключает одна команда `sudo sard-agent repo add` (ниже): файлы и ключи руками
на хосте агента не создаются. Общий порядок
подключения агента — в [разделе 5](05-agents.md); команды `repo add`, `repo init`
и `repo list`, их коды выхода и права файлов — на страницах
[«Настройка хоста агента»](../operations/agent-host-setup.md) и
[«Репозиторий агента»](../operations/repo-init.md).

Всё ниже проверено сквозными тестами на Garage (S3) и OpenSSH (SFTP): классы
`StorageChainTest`, `StorageFailureTest`, `StorageOutageTest` и
`StorageLockTest` в [`test/e2e`](../../test/e2e/README.md), ADR 0047.

## S3

### Подключение одной командой

```bash
sudo sard-agent repo add main s3:https://<s3.example.com>/<бакет>/<путь> \
  --access-key-id <идентификатор ключа> --region <регион> --secret-key-from-file /root/s3.secret
```

Адрес — формат restic: `s3:<схема>://<хост>[:<порт>]/<бакет>[/<путь>]` со
схемой `https` или `http`, либо `s3:<хост>[:<порт>]/<бакет>[/<путь>]` без
схемы (restic возьмёт `https`). `<путь>` — каталог репозитория внутри бакета;
в одном бакете можно держать несколько репозиториев с разными путями. Учётных
данных в адресе быть не должно (`ADDRESS_INVALID`). Адрес по `http` команда
принимает с предупреждением: запросы идут без TLS, данные restic зашифрованы, но
имена объектов и подписи запросов видны в сети.

### Предустановки провайдеров: `--provider aws|b2`

Для AWS S3 и Backblaze B2 адрес строится из региона:

```bash
sudo sard-agent repo add main s3:<бакет>[/<путь>] --provider aws --region eu-central-1 \
  --access-key-id <идентификатор ключа> --secret-key-from-file /root/s3.secret
sudo sard-agent repo add archive s3:<бакет>[/<путь>] --provider b2 --region us-west-004 \
  --access-key-id <идентификатор ключа> --secret-key-from-file /root/b2.secret
```

| `--provider` | адрес в `agent.d/repo-<имя>.yaml` |
|---|---|
| `aws` | `s3:https://s3.<регион>.amazonaws.com/<бакет>[/<путь>]` |
| `b2` | `s3:https://s3.<регион>.backblazeb2.com/<бакет>[/<путь>]` |

С `--provider` адрес пишется как `s3:<бакет>[/<путь>]` — без схемы и хоста
(иначе ошибка использования); `--region` обязателен и проверяется как обычно
(`a–z`, `0–9`, `-`); в `env`-файл попадает и `AWS_DEFAULT_REGION=<регион>`.
Списка регионов у агента нет: несуществующий регион даёт отказ хранилища —
`BACKEND_UNAVAILABLE` (имя хоста не разрешается). Неизвестный провайдер — ошибка
использования со списком `aws`, `b2`. Повтор с теми же флагами — `unchanged`.

Секретный ключ **никогда не передаётся значением флага**: в истории терминала
и в списке процессов он стал бы виден всем. Источник — один из трёх:

- `--secret-key-from-file <путь>` — содержимое файла;
- `--secret-key-stdin` — стандартный ввод (`printf '%s' "$KEY" | sudo sard-agent
  repo add … --secret-key-stdin`);
- терминал: без этих флагов, если стандартный ввод — терминал; ввод без эха,
  дважды.

Один перевод строки в конце ключа (`\n` или `\r\n`) отбрасывается; любой другой
управляющий символ — `SECRET_INVALID`. Идентификатор ключа не секрет и
передаётся флагом `--access-key-id` (1–128 печатных символов ASCII без
пробелов); `--region` (необязательный) — `a–z`, `0–9`, `-`, до 64 символов.
Хранилищам, которые отвечают только в своём регионе (например, Garage с
заданным `s3_region`), регион нужен.

Что делает команда:

1. проверяет адрес и флаги, не обращаясь к хранилищу;
2. пишет ключи в `/etc/sard/secrets/restic-<имя>.env` (владелец — пользователь
   службы, права `0600`): `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` и, с
   `--region`, `AWS_DEFAULT_REGION`. Ключи попадают в restic только окружением из
   этого файла, не аргументами;
3. спрашивает хранилище командой `restic cat config` от имени пользователя
   службы. Если бакета нет, `restic init` создаст его сам, когда ключ вправе
   создавать бакеты; если не вправе — `BUCKET_NOT_FOUND`;
4. пустое хранилище получает репозиторий со **сгенерированным паролем**
   (`restic-<имя>.pass`); если репозиторий уже есть, нужен его пароль —
   `--password-stdin`, `--password-from-file` или терминал (одновременно со
   стандартным вводом для ключа и пароля читать нельзя:
   `SECRET_SOURCE_CONFLICT`);
5. пишет фрагмент `/etc/sard/agent.d/repo-<имя>.yaml` (с `env_file`) и применяет
   изменение, как для локального репозитория
   ([«Настройка хоста агента»](../operations/agent-host-setup.md)).

Если на этапе 3 или 4 хранилище отказало, не остаётся ни `env`-файла, ни
файла пароля, ни фрагмента. Если отказал сам `restic init` (после того как
ключи приняты), `env`-файл и файл пароля остаются и используются при повторе
без вопросов. Сохраните копию пароля вне хоста: `sudo sard-agent repo password
<имя> --reveal`.

Повтор команды с тем же адресом и теми же `--access-key-id`, `--region` ничего
не меняет (`unchanged`); секретный ключ при этом не спрашивается. Другие ключи
для подключённого имени команда проверяет тем же способом и заменяет `env`-файл
(`credentials updated`, строка аудита, перезапуск не нужен: `env`-файл читается
на каждом шаге); отклонённые ключи `env`-файл не меняют.

Ключу нужны права на чтение, запись и удаление объектов в бакете. Удаление
restic использует для своих блокировок (`locks/`) и для `forget --prune`.
Ключ только на чтение отказывает уже при подключении: restic берёт
блокировку даже для `cat config`.

### Ограничение ожидания: `--connect-timeout`

Каждое сетевое обращение проверки ограничено `--connect-timeout` (по
умолчанию `30s`): первое обращение restic к хранилищу, получение ключа хоста
SFTP-сервера и проверка входа по ssh. Программа останавливается (SIGTERM,
через 10 секунд SIGKILL), команда заканчивается ошибкой `BACKEND_UNAVAILABLE`
(код 6); для restic в сообщении стоит последняя причина повтора, которую он
успел напечатать. Создание репозитория и проверку пароля этот предел не
ограничивает, их ограничивает `--timeout` (по умолчанию `2m`); время, которое
команда ждёт ответа оператора на терминале, не входит ни в тот, ни в другой.

### Руками (для хранилищ, которые команда не подключает)

Конфиг и `env_file` можно написать самому; формат тот же, что делает команда:

```yaml
repositories:
  - name: main
    url: s3:https://<s3.example.com>/<бакет>/<путь>
    password_file: /etc/sard/secrets/restic-main.pass
    env_file: /etc/sard/secrets/restic-main.env
```

`env_file` — строки `ИМЯ=значение` без кавычек и `export`. Владелец файла —
`sard-agent`, права `0600`; иначе агент файл не примет (проверка A1).
Переменные `RESTIC_*`, `PATH`, `HOME`, `TMPDIR`, `LD_*`, `XDG_*`,
`SSH_AUTH_SOCK` и `GO*` в нём запрещены: агент называет строку и переменную,
значение не печатает. Агент читает `env_file` заново на каждом шаге.

## SFTP

### Что нужно на хосте

restic подключается к SFTP-серверу через системный `ssh`. Пакет `sard-agent`
зависит от `openssh-client`, а для rpm — от `openssh-clients`.

- `apt-get install ./sard-agent_<версия>_<арх>.deb` поставит зависимость сам.
- `dpkg -i` и `rpm -U` зависимостей не ставят. Если клиента на хосте нет,
  сначала выполните `sudo apt-get install openssh-client` (Debian, Ubuntu)
  или `sudo dnf install openssh-clients` (семейство RHEL). Без клиента `repo
  add` отказывает до любых изменений: `SSH_CLIENT_MISSING` называет
  программу, которой нет.
- Для установки из tar.gz клиент OpenSSH ставится отдельно.

Программы клиента ищутся в том `PATH`, который получает restic.

### Подключение одной командой

```bash
sudo sard-agent repo add main sftp:<пользователь>@<sftp.example.com>:/<каталог>/main \
  --host-key-fingerprint SHA256:<отпечаток>
```

Формы адреса те же, что у restic: `sftp:[пользователь@]хост:путь` и
`sftp://[пользователь@]хост[:порт]/путь` (абсолютный путь — после второго `/`:
`sftp://u@host:2222//srv/main`). Пароль в адресе не принимается: `ssh`
работает по ключу (`ADDRESS_INVALID`).

**Ключ хоста.** Команда сама получает ключ сервера, но не принимает его
молча. Отпечаток сообщает администратор сервера:

```bash
# на SFTP-сервере (или у его администратора)
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

- С `--host-key-fingerprint SHA256:…` ключ принимается без вопроса, если его
  отпечаток совпал с отпечатком любого ключа сервера. Не совпал ни с одним —
  `HOST_KEY_MISMATCH` (код 5): сообщение называет данный отпечаток и
  отпечатки, которые предъявил сервер. Другой формат (в том числе MD5) —
  ошибка использования.
- Без флага и с терминалом команда показывает хост, порт, тип и отпечаток
  одного ключа (порядок ed25519, ecdsa, rsa); ключ принимается только на
  ответ ровно `yes`. Любой другой ответ или конец ввода —
  `HOST_KEY_REJECTED` (код 5).
- Без флага и без терминала — `HOST_KEY_UNCONFIRMED` (код 2) сразу, ввод не
  читается; сообщение называет отпечатки всех ключей сервера.

Принятый ключ дописывается в `known_hosts` пользователя службы одной строкой
(`хост` для порта 22, `[хост]:порт` для другого), остальное содержимое файла
не меняется. Ключ уже известен (обычная или хешированная запись) — ничего не
спрашивается и не пишется.

**Ключ пользователя службы.** Нет ключа — команда создаёт ed25519 без
пароля программой ssh-keygen от имени пользователя службы и **печатает его
открытую часть** с указанием, куда её добавить. Ключ создаётся только после
того, как ключ хоста принят, и не удаляется никогда: администратор мог уже
получить открытую часть. Первый запуск обычно заканчивается так:

```
sard-agent repo add: SSH_KEY_NOT_AUTHORIZED: the server … did not accept the key …
Public key of the service user sard-agent: add it to authorized_keys of backup on <sftp.example.com>, then repeat the same command:
  ssh-ed25519 AAAA… sard-agent@<имя хоста>
```

Администратор добавляет строку в `authorized_keys` пользователя хранилища
(лучше выделить для бэкапов отдельного пользователя только с SFTP,
`ForceCommand internal-sftp`, и своим каталогом). Затем **та же команда**
повторяется: ключ и ключ хоста уже на месте, ничего не спрашивается, ключ
заново не создаётся, репозиторий подключается.

**Куда команда пишет.** `ssh` берёт домашний каталог пользователя из passwd
(у пользователя службы это `/var/lib/sard-agent`; переменная `HOME`, которую
агент передаёт restic, на `ssh` не влияет). Все файлы лежат в
`<домашний каталог>/.ssh/` и принадлежат пользователю службы:

| Файл | Права | Что в нём |
|---|---|---|
| `id_ed25519`, `id_ed25519.pub` | `0600`, `0644` | ключ пользователя службы; закрытую часть root не открывает |
| `known_hosts` | `0600` | ключ хоста, принятый командой |
| `config` | `0600` | блок на хост, ниже |

Нет домашнего каталога — команда создаёт его последний компонент, если есть
родитель (`0700`, владелец — пользователь службы); нет родителя —
`CONFIG_WRITE` с первым отсутствующим каталогом. Существующие домашний
каталог и `.ssh` владельца и прав не меняют.

**Блок `config`.** В начале `~/.ssh/config` команда ставит блок, который
`ssh` применяет раньше любого `Host *` ниже:

```text
# sard-agent begin <sftp.example.com>
Host <sftp.example.com>
    StrictHostKeyChecking yes
    BatchMode yes
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes
    ServerAliveInterval 15
    ServerAliveCountMax 4
    ConnectTimeout 30
# sard-agent end <sftp.example.com>
```

`StrictHostKeyChecking` и `BatchMode` значат, что `ssh` службы не спрашивает
ни пароль, ни «continue connecting» и сам `known_hosts` не пополняет.
`ServerAlive*` разрывают связь через минуту молчания: без них сервер,
пропавший из сети молча, держит шаг бэкапа, пока сеть не вернётся (OQ-154);
с ними шаг становится FAILED. Тот же блок файл не переписывает, иной блок
того же хоста заменяется на месте, остальное содержимое сохраняется байт в
байт, блоки разных хостов живут рядом.

**Сменившийся ключ хоста.** В `known_hosts` есть запись хоста, но сервер
предъявляет другие ключи: `HOST_KEY_CHANGED` (код 5), сообщение называет файл
и номера строк. Это может быть подмена сервера или его переустановка. Если
сервер действительно переустановлен, повторите команду с
`--replace-host-key` и отпечатком нового ключа (или ответом `yes` на
терминале): старые записи этого хоста и порта заменяются, записи других
хостов не меняются. Флаг подтверждения не отменяет.

**Что видно после.** Итог называет имя, `sftp`, адрес, `repository_id`, файл
пароля, хост с отпечатком принятого ключа и открытую часть ключа. Пароль
репозитория — как у S3: сгенерированный лежит только на этом хосте,
сохраните копию (`sudo sard-agent repo password main --reveal`). Повтор той
же команды при готовых ключе, ключе хоста и блоке — `unchanged`, без
вопросов, записей и перезапуска. Изменения только файлов `ssh` службу не
перезапускают: `ssh` читает их при каждом соединении. В журнал (`journalctl
-t sard-agent`) идёт отдельная строка на каждое изменение: ключ пользователя
службы создан, ключ хоста принят (или заменён), репозиторий добавлен.

**Отказ после записи файлов `ssh`.** Ключ, запись `known_hosts` и блок
`config` — настройка, а не отказ: при отказе проверки входа или restic они
остаются, повтор их использует. Пароль репозитория и фрагмент при этом не
остаются (если отказал `init`, пароль остаётся, как у S3, и команда это
говорит).

**Защита от подмены.** Каталог `~/.ssh` принадлежит пользователю службы, и он
может подложить ссылку, жёсткую ссылку, FIFO или подменить сам каталог.
Поэтому root пишет в него только через удерживаемый дескриптор каталога, без
перехода по ссылкам, а файл, который не обычный, имеет больше одного имени,
принадлежит не пользователю службы и не root или больше 1 МиБ, команда не
читает и не меняет: `SSH_FILE_REJECTED` с путём и причиной. Ссылка на пути к
домашнему каталогу — `SSH_HOME_INVALID`. Подробнее — ADR 0054.

`sudo sard-agent repo remove main` ключ, `known_hosts` и блок `config` не
трогает: ими могут пользоваться другие репозитории. Итог называет файл
ключа и хост и говорит, что они остаются.

### Причины отказа `repo add` для SFTP

| Причина | Код | Что случилось | Что делать |
|---|---|---|---|
| `ADDRESS_INVALID` | 2 | нет хоста или пути, пароль в адресе, порт не 1–65535, управляющий символ, `-` в начале хоста или пользователя | исправить адрес |
| `SSH_CLIENT_MISSING` | 1 | нет `ssh`, `sftp` или одной из утилит ключей в `PATH` restic | поставить `openssh-client` / `openssh-clients` |
| `SSH_CLIENT_FAILED` | 1 | непредвиденный отказ утилиты клиента, со строкой её stderr | по строке |
| `SSH_HOME_INVALID` | 2 | домашний каталог из passwd пуст, не абсолютный, `/`, или на пути к нему ссылка | исправить passwd пользователя службы; ссылку заменить путём |
| `SSH_FILE_REJECTED` | 2 | файл или каталог `~/.ssh` — ссылка, не обычный файл, несколько имён, чужой владелец, больше 1 МиБ | разобраться, кто его подложил; убрать |
| `HOST_KEY_UNCONFIRMED` | 2 | ключ хоста неизвестен, флага нет, терминала нет | `--host-key-fingerprint` или запуск на терминале |
| `HOST_KEY_MISMATCH` | 5 | отпечаток флага не совпал ни с одним ключом сервера, или `ssh` отказал: ключ другой | сверить отпечаток у администратора |
| `HOST_KEY_REJECTED` | 5 | ответ на терминале не `yes` | повторить, сверив отпечаток |
| `HOST_KEY_CHANGED` | 5 | `known_hosts` держит другой ключ этого хоста | выяснить причину; при переустановке — `--replace-host-key` |
| `SSH_KEY_NOT_AUTHORIZED` | 2 | сервер не принял ключ (`Permission denied (publickey)`) | добавить напечатанную открытую часть в `authorized_keys`, повторить |
| `STORAGE_ACCESS_DENIED` | 2 | `permission denied` в каталоге репозитория | права пользователя хранилища на каталог из адреса |
| `BACKEND_UNAVAILABLE` | 6 | имя не разрешается, порт закрыт, нет маршрута, `--connect-timeout` | вернуть сервер, повторить |
| `CONFIG_WRITE` | 7 | нельзя записать файл `ssh`, домашний каталог или `.ssh` | по сообщению |
| `WRONG_PASSWORD` | 2 | репозиторий есть, пароль не подходит | `--password-from-file` с верным паролем |

Класс отказа входа определяет сама команда проверкой входа по ssh от имени
пользователя службы, а не строка restic (restic не всегда передаёт причину
`ssh`, OQ-155).

## Отказы: что видно в консоли

Шаг бэкапа показывает сообщение и журнал. Журнал — это строки restic, которые
агент передал серверу; секреты в нём замаскированы. В таблице — что тесты
видят сейчас, за сколько и что делать. Строки с пометкой «проба restic»
измерены запуском restic 0.19.1 напрямую (`docs/sessions/2026-10-07-f2-s3-sftp.md`),
остальные — сквозными тестами через агента.

| Что случилось | Шаг | Где причина | Что делать |
|---|---|---|---|
| S3: неверный секрет ключа | FAILED, < 1 с | сообщение: `Stat: Access Denied.`; `repo add` — `STORAGE_ACCESS_DENIED` | исправить `env_file` / ключи `repo add` |
| S3: у ключа нет прав на запись | FAILED, < 1 с | только журнал: `Forbidden: Operation is not allowed for this key`; сообщение — `restic cat: exit code 1` | дать ключу запись в бакет |
| S3: бакета нет | FAILED, < 1 с | сообщение: `repository does not exist` | создать бакет, `repo init` |
| S3: хранилище недоступно до шага (имя не разрешается, порт закрыт) | FAILED через **13–15 мин**: restic повторяет запросы (проба restic, не e2e) | сообщение: `connection refused` / `no such host` | вернуть хранилище; следующий запуск успешен |
| S3: хранилище пропало посреди бэкапа и вернулось | restic ждёт, бэкап **успешен** (проверено на 30 с) | — | — |
| S3: хранилище пропало посреди бэкапа и не вернулось | `running` **дольше 20 мин** (проба restic, OQ-154) | — | вернуть хранилище; предел — таймаут шага |
| SFTP: ключ не принят сервером | FAILED, < 1 с | сообщение: `unable to start the sftp session`; журнал: `Permission denied (publickey)` — не всегда (OQ-155) | `sudo sard-agent repo add …` напечатает открытую часть; добавить её в `authorized_keys` на сервере |
| SFTP: ключ хоста неизвестен или сменился | FAILED, < 1 с | сообщение: `unable to start the sftp session`; журнал: `Host key verification failed` | `repo add` с `--host-key-fingerprint` (новый хост) или `--replace-host-key` (сменился) |
| SFTP: каталог только на чтение | FAILED, < 2 с | только журнал: `permission denied`; сообщение — `restic cat: exit code 1` | права пользователя хранилища на каталог репозитория |
| SFTP: каталога нет | FAILED, < 1 с | сообщение: `repository does not exist` | проверить путь, `repo init` |
| SFTP: сервер выключен (имя не разрешается; порт закрыт — проба restic) | FAILED, < 1 с | сообщение: `unable to start the sftp session`; журнал: `Could not resolve hostname` / `Connection refused` | вернуть сервер |
| SFTP: сервер остановлен посреди бэкапа | FAILED, когда кончатся данные источника | сообщение: `ssh command exited: exit status 255` | вернуть сервер; следующий запуск успешен |
| SFTP: сервер пропал из сети молча | с `ServerAliveInterval` — FAILED (`ssh command exited`); без него — `running`, пока сеть не вернётся (OQ-154) | — | `repo add` ставит `ServerAlive*` в `~/.ssh/config` сам; для репозитория, подключённого раньше, повторите команду |

Предел для любого зависания — таймаут шага. Сервер его пока не задаёт, а
максимум агента — 24 часа (OQ-154). Сообщения без причины перечислены в
OQ-155: причину ищите в журнале шага.

### Причины отказа `repo add` для S3

| Причина | Код | Что случилось | Что делать |
|---|---|---|---|
| `ADDRESS_INVALID` | 2 | нет хоста или бакета, схема не `https`/`http`, учётные данные в адресе, управляющий символ | исправить адрес |
| `S3_KEY_REJECTED` | 2 | хранилище не знает идентификатор ключа или подпись не сошлась | проверить `--access-key-id`, секретный ключ, `--region` |
| `STORAGE_ACCESS_DENIED` | 2 | `Access Denied` / `Forbidden`: неверный секрет (Garage отвечает на него так же) или у ключа нет права читать, писать, удалять в бакете | проверить ключи; дать права в бакете |
| `BUCKET_NOT_FOUND` | 2 | бакета нет, а ключ не может его создать | создать бакет или дать ключу право создавать бакеты |
| `BACKEND_UNAVAILABLE` | 6 | имя не разрешается, порт закрыт, нет маршрута, `--connect-timeout` | вернуть хранилище, повторить |
| `WRONG_PASSWORD` | 2 | репозиторий есть, пароль не подходит | `--password-from-file` с верным паролем |
| `BACKEND_REFUSED` | 1 | прочее, со строкой restic | по строке |

Сообщение называет причину, адрес (пароль в нём скрыт), очищенную строку
restic и что делать.

## Блокировки restic в удалённом репозитории

restic берёт в репозитории блокировку (`locks/`). Процесс, убитый посреди
работы (сбой агента, `kill -9`, перезагрузка хоста), оставляет её в
хранилище.

- **Блокировка прерванного бэкапа** — общая. Следующий бэкап через неё
  проходит, шаг успешен. Но `restic check` и `restic prune` берут
  исключительную блокировку и откажут, пока старая лежит:
  `repository is already locked by PID … on <хост>`.
- **Исключительная блокировка прерванной команды оператора** (`check`,
  `prune`) останавливает бэкапы. Шаг сразу FAILED:
  `restic cat: repository is locked by another process`. Ожидание до 5 минут
  (`--retry-lock 5m`, ADR 0029) сейчас не срабатывает: проверка `restic cat`
  перед бэкапом ждать не умеет (OQ-156).

Снять оставшиеся блокировки — от имени службы, когда ни один restic с этим
репозиторием точно не работает (ни на этом хосте, ни на других):

```bash
sudo -u sard-agent sh -c 'set -a; . /etc/sard/secrets/restic-main.env; exec /usr/libexec/sard/restic \
  --repo <url> --password-file /etc/sard/secrets/restic-main.pass unlock --remove-all'
```

Ключи берутся из `env_file` и не попадают в список процессов. Для SFTP строка
`set -a; . …;` не нужна. Обычный `unlock` без `--remove-all` удаляет
только устаревшие блокировки: старше 30 минут или оставленные процессом этого
же хоста, которого уже нет.
