# 7. Обновление и откат

## Откуда можно обновляться

- **С 0.1.0-beta.N, где работает `db-init`** (DB2: схема `sard`, роли и
  владение верны с первой версии, [раздел 16](16-postgresql.md)) и новее — по
  порядку ниже. Обновление сохраняет данные, пароль администратора и пройденный
  мастер первого запуска: после него мастер не открывается, сервер не печатает
  код настройки, вход — прежним паролем.
- **Со сборок до DB2 (схема `public`, сервер — суперпользователь) — не
  обновляется:** установок нет и пути обновления не делали. Такую установку
  переустанавливают с новыми томами, как `0.0.1-rc1` ниже.
- **С 0.0.1-rc1 — не обновляется.** В той версии пароль администратора был в
  `.env` (отдельная переменная окружения), у базы не было записей о первом запуске и
  происхождении CA. Установку **переустанавливают с новыми томами**: сохраните
  нужное (ключ CA, дамп базы — [раздел 6](06-data-and-backup.md)), затем
  `docker compose down -v`, свежие `docker-compose.yml` и `.env` нужной версии
  ([раздел 2](02-install.md)) и мастер первого запуска. Агенты регистрируются
  заново: CA нового сервера другой, если вы не импортируете прежний
  ([раздел 8](08-migrate-and-remove.md)).

### Обновление до версии с самобэкапом в мастере (F4b)

Версия с шагами самобэкапа и копии ключей при первом старте смотрит в базу:
если в ней уже есть живой обычный агент или источник администратора, установка
помечается «обновлённой» (ограничение `new_agents`). Пока вы не пройдёте шаги
самобэкапа и копии ключей (консоль показывает баннер «Настройте самобэкап» со
ссылкой на `/setup`), сервер не выпускает токены регистрации
(`POST /api/v1/enrollment-tokens` отвечает `409 onboarding_incomplete`) и не
регистрирует новых агентов по уже выпущенным (Enroll возвращает
`FAILED_PRECONDITION`, причина `ONBOARDING_INCOMPLETE`, токен остаётся
неиспользованным). Всё остальное работает как прежде: агенты работают, источники
и расписания меняются. Установка без агентов и источников такой пометки не
получает: для неё до конца мастера закрыты все изменения, кроме самобэкапа.
Пометка не снимается удалением агентов и источников; завершённый онбординг
снимает ограничение.

### Обновление до версии с привязкой секретов (S11)

Агент отдаёт пароль плагину только по привязке секрета. Образ соседа несёт привязку
пароля самобэкапа `secret-bindings/sard-db.yaml`, но в существующий том
`sard_sard-self-config` Docker копирует файлы образа только при создании тома. После
`docker compose up -d` (шаг 3) допишите её один раз, иначе шаг самобэкапа базы
завершится с ошибкой `SECRET_NOT_ALLOWED`:

```bash
docker compose exec -u 0 self-agent sh -c 'mkdir -p /etc/sard/self/secret-bindings && cat > /etc/sard/self/secret-bindings/sard-db.yaml' <<'YAML'
plugin: postgresql
targets:
  - postgres:5432/sard
allow_tls: disable
YAML
docker compose restart self-agent
```

С внешней базой (`SARD_SELF_BACKUP_DATABASE_HOST`) цель и `allow_tls` — её
([самоагент](../operations/self-agent.md#без-compose-и-с-внешним-postgresql)).

## Порядок

Сначала сервер, потом агенты. Образ сервера версии N несёт и раздаёт
пакеты агента той же версии N, а консоль помечает отставшие агенты
«Доступно обновление».

1. **Бэкап базы и ключа CA** — [раздел 6](06-data-and-backup.md). Без свежего
   дампа отката нет: миграции базы идут только вперёд.
2. **Новая версия в `.env`** и, если в релизе изменился, новый
   `docker-compose.yml` (сверьте с текущим: свои правки секции `environment`
   перенесите):

   ```bash
   cd ~/sard
   NEW_TAG=<vX.Y.Z>
   curl -fsSL -o docker-compose.new.yml "https://github.com/Artur-Abalov/Sard/releases/download/$NEW_TAG/docker-compose.yml"
   diff docker-compose.yml docker-compose.new.yml    # пусто — файл не менялся
   mv docker-compose.new.yml docker-compose.yml
   sed -i "s/^SARD_VERSION=.*/SARD_VERSION=${NEW_TAG#v}/" .env
   sudo chgrp 10001 .env && chmod 640 .env
   ```

   `sed -i` пишет файл заново, и группа 10001 у него теряется. Без неё сосед не
   прочитает `.env`, и самобэкап ключей упадёт ([раздел 6](06-data-and-backup.md)).
   При обновлении с версии без самобэкапа эту строку нужно выполнить один раз.

3. **Запуск:**

   ```bash
   docker compose pull
   docker compose up -d --wait
   curl -fsS http://localhost:8080/api/v1/status     # новая версия
   ```

   `db-init` и `migrate` идут до сервера: они возвращают роли и права на месте,
   применяют миграции новой версии и не меняют пароли ролей; сам сервер
   миграций не применяет и без них не стартует
   (`MIGRATIONS_NOT_APPLIED`, [раздел 16](16-postgresql.md)). Агенты переподключаются сами
   (с паузой, нарастающей от 1 с); сессии консоли сбрасываются — войдите снова
   прежним паролем администратора (он в базе, а не в `.env`).
4. **Агенты.** В «Агентах» отставшие помечены; в карточке агента — команды
   обновления пакетом с сервера. Обновляйте агента, когда у него нет активных
   запусков: перезапуск службы их прерывает. deb ставится поверх и не трогает
   `/etc/sard`, ключи и пароль репозитория ([установка агента](../operations/agent-install.md),
   «Обновление»).

## Совместимость версий агентов

Политика: сервер версии N работает с агентами N и N−1, поэтому сервер
обновляют первым, а агенты — после, без спешки. Автоматической проверки этой
политики пока нет (OQ-152): перед обновлением, которое меняет контракт
агента, сверяйтесь с примечаниями к релизу.

## Откат

Миграции только вперёд: прежний сервер на базе после миграций не гарантирован.
Откат — это восстановление базы из дампа, снятого перед обновлением, и прежний
тег:

```bash
cd ~/sard
sed -i "s/^SARD_VERSION=.*/SARD_VERSION=<прежняя версия без v>/" .env
```

и затем [восстановление](06-data-and-backup.md#восстановление) с дампом,
снятым на шаге 1 (ключ CA при обновлении не меняется, его восстанавливать не
нужно, но процедура не вредит). Всё, что сервер записал после обновления
(запуски, снимки в истории), из базы уходит; сами снимки остаются в
репозиториях restic.

Агенты, уже обновлённые до N, после отката сервера до N−1 — это сочетание
«агент новее сервера», которое не поддерживается: откатите и их тем же
пакетом прежней версии (из GitHub Releases).
