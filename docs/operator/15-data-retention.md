# 15. Хранение данных сервера

База сервера не растёт без предела: фоновая уборка удаляет то, что старше срока,
и никогда не трогает то, что нужно для восстановления и доказательства. Решения и
причины — ADR [00XX-draft-server-retention](../adr/00XX-draft-server-retention.md).
Уборка касается только базы сервера; снимки в репозиториях бэкапов она не удаляет.

## Сроки

Сроки общие для всей установки, не по тенантам. Задаются свойствами `sard.retention.*`;
переменная окружения — имя свойства в верхнем регистре, точки заменены
подчёркиванием, дефисы убраны (правила Spring Boot). Compose их не пробрасывает: добавьте
строку в секцию `environment` сервера в `docker-compose.yml`
([раздел 3](03-configuration.md)).

| Свойство | Переменная | Что хранится | По умолчанию |
|---|---|---|---|
| `sard.retention.step-logs` | `SARD_RETENTION_STEPLOGS` | строки журналов шагов | `30d` |
| `sard.retention.runs` | `SARD_RETENTION_RUNS` | запуски и их шаги (backup, restore, verify, любой итог) | `180d` |
| `sard.retention.verifications` | `SARD_RETENTION_VERIFICATIONS` | улики записей проверок восстановления (`stages`, `mismatches`; не меньше 180 дней); сами записи хранятся всегда | `180d` |
| `sard.retention.schedule-fires` | `SARD_RETENTION_SCHEDULEFIRES` | журнал срабатываний расписаний | `180d` |
| `sard.retention.notification-deliveries` | `SARD_RETENTION_NOTIFICATIONDELIVERIES` | доставки уведомлений | `30d` |
| `sard.retention.interval` | `SARD_RETENTION_INTERVAL` | как часто идёт проход уборки; первый — через интервал после старта | `1h` |
| `sard.retention.batch-size` | `SARD_RETENTION_BATCHSIZE` | сколько строк удаляется одной пачкой | `500` |

Значения — длительности (`30d`, `12h`). Сервер не стартует, если срок или интервал не
положителен, срок улик (sard.retention.verifications) меньше 180 дней (нижний предел записан в
базе и меняется только миграцией) или `batch-size` меньше 1, а сроки запусков, срабатываний и доставок не
больше `sard.notify.ttl` (иначе планировщик уведомлений создал бы удалённое заново);
сообщение называет свойство. Журналы шагов уходят целыми месячными секциями, поэтому
реальный срок журнала 30–61 день.

## Что не удаляется никогда

- **Снимки** (`snapshots`): это доказательство того, что бэкап был. Уборка не трогает
  ни строку, ни пометку `forgotten_at`.
- **Запуск, у шага которого есть снимок**, вместе с шагами: на него ссылается снимок.
- **Последний успешный запуск** источника каждого вида (backup, restore, verify):
  по нему считается свежесть источника.
- **Активные запуски** (`queued`, `dispatched`, `running`).
- **Записи проверок восстановления.** Они хранятся всегда, и сервер не может
  изменить или удалить такую запись ([раздел 16](16-postgresql.md#роли)). Старше срока
  база очищает только улики (`stages`, `mismatches`); статус, уровень, время и число
  держателей ключа остаются. Поэтому не удаляются и закрытые задания проверок, их
  запуски и шаги.
- **Последние проверки источника**: улики последней успешной и последней неуспешной
  проверки не очищаются никогда.
- **Всё, на что ссылается строка, которая ещё хранится**: журнал, срабатывание
  расписания, доставка, эпизод просрочки.

Правила считаются внутри каждого тенанта.

## Известные ограничения

- **R2.** Шаги удаляются без пропуска занятых строк: поздний результат шага может
  задержать уборку этого тенанта на один проход.
- **R3.** Индексы, которые добавила миграция уборки, построены без `CONCURRENTLY`:
  на очень большой установке при обновлении запись в таблицы ждёт построения индексов.
- **В9.** Поздний результат успешного бэкапа для шага, который сервер уже считал
  потерянным, а запуск удалила уборка, подтверждается агенту, но снимок в базу не
  записывается. Сам снимок в репозитории цел.
- Закрытые эпизоды устаревания проверок и таблица просрочек уборкой не охвачены.
- Удаление секции журнала ждёт читателей до 2 секунд, и запись журналов всех
  тенантов ждёт вместе с ним.

### Что требуется от L1

Пока снимок хранится, его запуск хранится вечно, и таблица запусков растёт на каждый
бэкап. Когда будет реализовано забывание снимков (L1, `forget`), запуск удаляется или
помечается, когда L1 забыл его снимок: требование к L1 — сделать запуск
этого снимка доступным уборке. Сегодня `snapshots.forgotten_at` не ставит никто.

## Как читать результат

После каждого прохода в журнале сервера одна строка уровня `INFO`:

```bash
cd ~/sard
docker compose logs server | grep "Retention pass deleted"
```

```text
Retention pass deleted step_log_partition=0 notification_delivery=12 schedule_fire=40 verification_evidence=3 run_step=210 run=210
```

Те же числа — счётчик Prometheus `sard_retention_deleted_total{kind}` с теми же
значениями `kind` ([раздел 14](14-monitoring.md)); он обнуляется при перезапуске, и
все шесть серий видны нулями сразу. Ошибка прохода пишется строкой `ERROR` с классом
исключения; уже удалённые пачки остаются, следующий проход начинает заново. Запрос
удалённого запуска или его журнала через REST и консоль отвечает `404`.
